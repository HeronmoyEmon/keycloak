The capstone: Northwind Apps, built end to end

Every other unit in this course either teaches one concept or runs one isolated lab. The capstone is different, per the curriculum's own description: "own project, not a chapter page" — a real, running, multi-app Keycloak-secured system, assembled from pieces this course already proved independently, with no narrated transcript standing in for an actual run. It's built around Northwind Apps specifically, because that's the org with the most accumulated, real infrastructure across the labs: the northwind-apps realm (chapter 20), its roles and groups (chapter 23), identity brokering (chapter 31), the billing-api Spring Boot resource server (chapter 34), UMA 2.0 authorization (chapter 37), and the TenantIdProtocolMapper custom SPI (chapter 39). This page is both the walkthrough and the exact, reproducible command sequence — every file below is the real one this capstone's own stack ran, with a copy button, not a pointer to a repository you'd need to clone.

Key idea

The capstone's job is integration, not invention: every piece below was already independently verified in its own chapter. What's new here is wiring them together into one stack that actually runs, plus one genuinely new endpoint (a UMA-gated "premium invoice report") that didn't exist until this unit — and the real, live-verified bugs that only showed up once these pieces had to work together, not in isolation.

How to run it

Everything below is the real, complete set of files and commands this capstone's own stack actually ran — nothing paraphrased and nothing left in a repository you'd need to clone. Five steps: start the stack, seed the realm, build/run billing-api, build/run the dashboard SPA, then run the M2M job.

Files you'll need for the capstone

Infra:

  • docker-compose.yml — the capstone's own isolated Keycloak 26.8.2 + PostgreSQL 17 stack (project capstonekc, host port 18200)
  • seed-realm.sh — reconstructs the full northwind-apps realm: roles, groups, users, clients, the tenant-context client scope, and the UMA resource/scope/policy/permission
  • m2m-billing-job.sh — a real client-credentials job calling the running billing-api, standing in for chapter 36's nightly reconciliation job

billing-api (adapted from chapter 34's lab):

  • pom.xml — the Maven build file
  • BillingApiApplication.java — the Spring Boot entry point
  • BillingController.java — the four endpoints, including the new UMA-gated /api/invoices/premium-report
  • KeycloakRealmRoleConverter.java — translates Keycloak's realm_access.roles claim into Spring authorities
  • SecurityConfig.java — the resource-server security wiring
  • UmaPermissionService.java — new for the capstone: a real server-side UMA 2.0 Policy Enforcement Point against Keycloak's Protection API
  • application.properties — issuer-uri and the UMA client credentials/resource id (filled in from step 2's output)

Dashboard SPA (northwind-spa, adapted from chapter 35's lab):

  • package.json — the only file npm install actually needs; everything else below is the app's own source
  • vite.config.js — the dev server/build config
  • eslint.config.js — lint config (not required to run the app, included for completeness)
  • index.html — the app's HTML entry point
  • src/main.jsx — the React root render, wrapping the app in react-oidc-context's AuthProvider
  • src/App.jsx — the real authorization-code + PKCE login flow and the two billing-api buttons

  • src/oidcConfig.js — the OIDC client configuration pointing at northwind-apps/northwind-spa

Step 1 — start the stack

Make a new, empty folder for the capstone and move into it. This stack also needs the custom SPI jar chapter 39's lab built (its TenantIdProtocolMapper is what actually stamps the tenant_id claim) — if you haven't already, follow that chapter now and build it in a folder named custom-spis-lab (chapter 39's own instructions use exactly this name). Create this capstone's folder as a sibling of custom-spis-lab, not nested inside it, so the compose file below's relative path lines up:

mkdir capstone-lab
cd capstone-lab

Create docker-compose.yml with this exact content:

# The capstone's own, isolated Keycloak + PostgreSQL stack -- same pattern as chapter 39's and
# chapter 37's own isolated stacks, NOT an override of the shared stack chapter 20 gives you
# (used by chapters 20-30+) and NOT sharing a project name/port with any other lab stack.
#
#   mvn -q -f ../custom-spis-lab/pom.xml clean package   # rebuild the custom SPI jar fresh
#   docker compose -p capstonekc up -d
#
# Keycloak is published on host port 18200 (http://localhost:18200), per this course's convention
# of giving each isolated lab/capstone stack its own project name + port.
services:
  postgres:
    image: postgres:17-alpine
    environment:
      POSTGRES_DB: keycloak
      POSTGRES_USER: keycloak
      POSTGRES_PASSWORD: keycloak_lab_password
    volumes:
      - capstone_pg_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U keycloak"]
      interval: 5s
      timeout: 5s
      retries: 10

  keycloak:
    image: quay.io/keycloak/keycloak:26.8.2
    command: start-dev
    environment:
      KC_DB: postgres
      KC_DB_URL: jdbc:postgresql://postgres:5432/keycloak
      KC_DB_USERNAME: keycloak
      KC_DB_PASSWORD: keycloak_lab_password
      KC_BOOTSTRAP_ADMIN_USERNAME: admin
      KC_BOOTSTRAP_ADMIN_PASSWORD: admin_lab_password
      KC_HEALTH_ENABLED: "true"
    ports:
      - "18200:8080"
    volumes:
      # The already-built custom SPI jar from chapter 39's lab, mounted read-only. Only its
      # TenantIdProtocolMapper is actually wired into this realm; the other two providers in the
      # jar (chapter 39's own event listener and authenticator) are simply unused here, not
      # disabled -- Keycloak registers every provider it finds but nothing references them unless
      # a client scope/flow actually uses them. This path assumes you built chapter 39's lab in a
      # sibling folder named custom-spis-lab (chapter 39's own instructions use exactly this name)
      # -- adjust the path if you used a different folder name or location.
      - ../custom-spis-lab/target/custom-spis-1.0.0.jar:/opt/keycloak/providers/custom-spis-1.0.0.jar:ro
    depends_on:
      postgres:
        condition: service_healthy

volumes:
  capstone_pg_data:

Bring it up:

docker compose -p capstonekc up -d

Wait for Keycloak to be ready:

for i in $(seq 1 40); do
  code=$(curl -s -o /dev/null -w "%{http_code}" http://localhost:18200/realms/master/.well-known/openid-configuration)
  echo "attempt $i: $code"
  if [ "$code" = "200" ]; then break; fi

done

Step 2 — seed the realm

Create seed-realm.sh (same folder, capstone-lab) with this exact content, then make it executable:

#!/usr/bin/env bash
# Reconstructs the full northwind-apps realm for the capstone's own isolated stack (project
# capstonekc, port 18200), as established across chapters 20-39 plus the UMA-protected resource
# this capstone adds on top. This is exactly what was actually run, in order, against a real
# running Keycloak -- including the fixes for two real bugs hit live (see capstone.html's "Real
# bugs found while building this" section for the full write-up of both). Idempotent-ish:
# re-running against an already-seeded realm will hit
# "already exists" errors on the create steps; tear down and re-up the stack for a clean reseed.
set -euo pipefail

KC="docker compose -p capstonekc exec keycloak /opt/keycloak/bin/kcadm.sh"
BASE_URL="http://localhost:18200"

$KC config credentials --server http://localhost:8080 --realm master --user admin --password admin_lab_password

echo "== realm =="
$KC create realms -r northwind-apps 2>/dev/null || true
$KC create realms -s realm=northwind-apps -s enabled=true \
  -s ssoSessionIdleTimeout=3600 -s ssoSessionMaxLifespan=28800

echo "== roles (chapters 23, 34) =="
$KC create roles -r northwind-apps -s name=tenant-admin -s 'description=Full admin access within one customer tenant'
$KC create roles -r northwind-apps -s name=support-agent -s 'description=Support tooling and tenant-facing queues'
$KC create roles -r northwind-apps -s name=platform-engineer -s 'description=Platform engineering tooling and infrastructure'
$KC create roles -r northwind-apps -s name=billing-reader -s 'description=Can view invoice data'
$KC create roles -r northwind-apps -s name=billing-admin -s 'description=Can create/modify invoice data'

echo "== groups (chapter 23) =="
$KC create groups -r northwind-apps -s name=Engineering
$KC create groups -r northwind-apps -s name=Support

echo "== BUG FOUND LIVE: declare tenant_id in the User Profile schema BEFORE setting it on any user =="
# Keycloak 26's declarative User Profile silently drops any user attribute that isn't part of
# its schema (no error, no warning -- the attribute just never appears on GET or in a token).
# tenant_id has to be declared here first, or every later 'attributes.tenant_id=[...]' call
# below is a no-op.
curl -s "$BASE_URL/admin/realms/northwind-apps/users/profile" \
  -H "Authorization: Bearer $($KC config credentials --server http://localhost:8080 --realm master --user admin --password admin_lab_password >/dev/null; true)" >/dev/null || true
ADMIN_TOKEN=$(curl -s -X POST "$BASE_URL/realms/master/protocol/openid-connect/token" \
  --data-urlencode "grant_type=password" --data-urlencode "client_id=admin-cli" \
  --data-urlencode "username=admin" --data-urlencode "password=admin_lab_password" \
  | python3 -c "import sys,json;print(json.load(sys.stdin)['access_token'])")
curl -s "$BASE_URL/admin/realms/northwind-apps/users/profile" -H "Authorization: Bearer $ADMIN_TOKEN" > /tmp/northwind-user-profile.json
python3 - "$ADMIN_TOKEN" <<'PYEOF'
import json, sys
with open("/tmp/northwind-user-profile.json") as f:
    profile = json.load(f)
if not any(a["name"] == "tenant_id" for a in profile["attributes"]):
    profile["attributes"].append({
        "name": "tenant_id",
        "displayName": "Tenant ID",
        "permissions": {"view": ["admin"], "edit": ["admin"]},
        "multivalued": False,
    })
with open("/tmp/northwind-user-profile-updated.json", "w") as f:
    json.dump(profile, f)
PYEOF
curl -s -X PUT "$BASE_URL/admin/realms/northwind-apps/users/profile" \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H "Content-Type: application/json" \
  -d @/tmp/northwind-user-profile-updated.json > /dev/null

echo "== users (chapters 22, 23, 34) -- email is required: an unverified/emailless user hits VERIFY_PROFILE at login (second real bug found live) =="
for spec in "jane.doe:Jane:Doe:acme-corp" "priya.patel:Priya:Patel:acme-corp" "amara.reader:Amara:Reader:acme-corp" "devon.admin:Devon:Admin:acme-corp" "priya.sales:Priya:Sales:contoso"; do
  IFS=: read -r u f l t <<< "$spec"
  $KC create users -r northwind-apps -s username="$u" -s enabled=true -s firstName="$f" -s lastName="$l" \
    -s email="${u}@northwindapps.example" -s emailVerified=true
  $KC set-password -r northwind-apps --username "$u" --new-password 'CapstoneLab1!' --temporary=false
  USER_ID=$($KC get users -r northwind-apps -q username="$u" --fields id --format csv --noquotes)
  $KC update "users/$USER_ID" -r northwind-apps -s "attributes={\"tenant_id\":[\"$t\"]}"
done

echo "== role/group grants =="
$KC add-roles -r northwind-apps --uusername jane.doe --rolename tenant-admin
$KC add-roles -r northwind-apps --uusername priya.patel --rolename platform-engineer
PRIYA_ID=$($KC get users -r northwind-apps -q username=priya.patel --fields id --format csv --noquotes)
ENGINEERING_GID=$($KC get groups -r northwind-apps --fields id,name --format csv --noquotes | awk -F, '$2=="Engineering"{print $1}')
$KC update "users/$PRIYA_ID/groups/$ENGINEERING_GID" -r northwind-apps -b '{}'
$KC add-roles -r northwind-apps --uusername amara.reader --rolename billing-reader
$KC add-roles -r northwind-apps --uusername devon.admin --rolename billing-admin
# priya.sales deliberately gets no billing role and no tenant-side role.

echo "== clients =="
$KC create clients -r northwind-apps \
  -s clientId=northwind-dashboard -s protocol=openid-connect \
  -s publicClient=false -s standardFlowEnabled=true -s directAccessGrantsEnabled=false \
  -s serviceAccountsEnabled=false -s 'redirectUris=["http://localhost:8081/*"]'

$KC create clients -r northwind-apps \
  -s clientId=northwind-spa -s protocol=openid-connect \
  -s publicClient=true -s standardFlowEnabled=true -s directAccessGrantsEnabled=false \
  -s 'redirectUris=["http://localhost:5173/*"]' -s 'webOrigins=["http://localhost:5173"]' \
  -s 'attributes."pkce.code.challenge.method"=S256'

$KC create clients -r northwind-apps \
  -s clientId=billing-service-account -s protocol=openid-connect \
  -s publicClient=false -s standardFlowEnabled=false -s directAccessGrantsEnabled=false \
  -s serviceAccountsEnabled=true

$KC create clients -r northwind-apps \
  -s clientId=billing-direct-grant -s protocol=openid-connect \
  -s publicClient=false -s standardFlowEnabled=false -s directAccessGrantsEnabled=true \
  -s serviceAccountsEnabled=false

$KC create clients -r northwind-apps \
  -s clientId=billing-api -s protocol=openid-connect \
  -s publicClient=false -s standardFlowEnabled=false -s directAccessGrantsEnabled=false \
  -s serviceAccountsEnabled=true -s authorizationServicesEnabled=true

$KC add-roles -r northwind-apps --uusername service-account-billing-service-account --rolename billing-admin
$KC add-roles -r northwind-apps --uusername service-account-billing-api --rolename billing-admin

echo "== tenant-context client scope (chapter 39's TenantIdProtocolMapper) =="
$KC create client-scopes -r northwind-apps -s name=tenant-context -s protocol=openid-connect
TCS_ID=$($KC get client-scopes -r northwind-apps --fields id,name --format csv --noquotes | awk -F, '$2=="tenant-context"{print $1}')
$KC create "client-scopes/$TCS_ID/protocol-mappers/models" -r northwind-apps \
  -s name=tenant_id -s protocol=openid-connect -s protocolMapper=northwind-tenant-id-mapper \
  -s 'config."claim.name"=tenant_id' -s 'config."access.token.claim"=true' \
  -s 'config."id.token.claim"=true' -s 'config."userinfo.token.claim"=true'

DASH_ID=$($KC get clients -r northwind-apps -q clientId=northwind-dashboard --fields id --format csv --noquotes)
SPA_ID=$($KC get clients -r northwind-apps -q clientId=northwind-spa --fields id --format csv --noquotes)
$KC update "clients/$DASH_ID/default-client-scopes/$TCS_ID" -r northwind-apps -b '{}'
$KC update "clients/$SPA_ID/default-client-scopes/$TCS_ID" -r northwind-apps -b '{}'

echo "== billing-api: UMA resource/scope/policy/permission (mirrors chapter 37's proven pattern) =="
CID=$($KC get clients -r northwind-apps -q clientId=billing-api --fields id --format csv --noquotes)

# BUG FOUND LIVE: a resource URI with a path-segment wildcard ("/api/invoices/*/premium-report")
# is rejected -- wildcard is only accepted as a trailing "/*" or a "/*.ext" suffix. Use a fixed
# path instead (billing-api's actual endpoint is a fixed GET /api/invoices/premium-report, not
# parameterized per invoice id).
$KC create "clients/$CID/authz/resource-server/resource" -r northwind-apps \
  -s name="premium-invoice-report" -s displayName="Premium invoice analytics report" \
  -s 'uris=["/api/invoices/premium-report"]' -s type=urn:northwind:invoice-report
RID=$($KC get "clients/$CID/authz/resource-server/resource" -r northwind-apps --fields _id,name --format csv --noquotes | grep premium-invoice-report | cut -d, -f1)

$KC create "clients/$CID/authz/resource-server/scope" -r northwind-apps -s name=view
SID=$($KC get "clients/$CID/authz/resource-server/scope" -r northwind-apps --fields id,name --format csv --noquotes | grep ',view$' | cut -d, -f1)

# GOTCHA (also confirmed by chapter 37): a permission can't reference this resource+scope pair
# until the resource itself lists the scope.
$KC update "clients/$CID/authz/resource-server/resource/$RID" -r northwind-apps \
  -s name="premium-invoice-report" -s type=urn:northwind:invoice-report \
  -s 'uris=["/api/invoices/premium-report"]' -s "scopes=[{\"id\":\"$SID\"}]"

$KC create "clients/$CID/authz/resource-server/policy/role" -r northwind-apps \
  -s name="billing-admin-policy" -s 'roles=[{"id":"billing-admin"}]' -s logic=POSITIVE
PID=$($KC get "clients/$CID/authz/resource-server/policy" -r northwind-apps --fields id,name --format csv --noquotes | grep billing-admin-policy | cut -d, -f1)

$KC create "clients/$CID/authz/resource-server/permission/scope" -r northwind-apps \
  -s name="view-premium-invoice-report" -s "resources=[\"$RID\"]" -s "scopes=[\"$SID\"]" \
  -s "policies=[\"$PID\"]" -s decisionStrategy=UNANIMOUS

echo "== secrets (for the app config in the next steps -- these are fresh per seed run, never commit them) =="
for cid in billing-service-account billing-direct-grant billing-api northwind-dashboard; do
  ID=$($KC get clients -r northwind-apps -q clientId=$cid --fields id --format csv --noquotes)
  SECRET=$($KC get "clients/$ID/client-secret" -r northwind-apps --fields value --format csv --noquotes)
  echo "$cid: $SECRET"
done
echo "premium-invoice-report resource id: $RID"

echo "Seed complete."
chmod +x seed-realm.sh
./seed-realm.sh

This prints each client's secret and the premium-invoice-report resource id at the end — copy them, you need them for steps 3 and 5. These are fresh per run; never commit real values from your own run anywhere.

package com.northwindapps.billing;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

/**
 * Northwind Apps billing/invoicing API -- the chapter 34 lab's Spring Boot OAuth2 Resource
 * Server. See {@link SecurityConfig} for the JWT validation and authorization wiring, and
 * {@link BillingController} for the three endpoints this chapter curls at three different
 * protection levels.
 */
@SpringBootApplication
public class BillingApiApplication {

    public static void main(String[] args) {
        SpringApplication.run(BillingApiApplication.class, args);
    }
}
package com.northwindapps.billing;

import java.time.Instant;
import java.util.List;
import java.util.Map;
import java.util.concurrent.atomic.AtomicLong;

import org.springframework.http.HttpHeaders;
import org.springframework.http.ResponseEntity;
import org.springframework.security.access.prepost.PreAuthorize;
import org.springframework.security.oauth2.jwt.Jwt;
import org.springframework.security.oauth2.server.resource.authentication.JwtAuthenticationToken;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

/**
 * Four endpoints at four different protection levels -- the first three exactly as chapter 34's
 * brief asked for, the fourth new for the capstone:
 *
 * <ul>
 *   <li>{@code GET /api/public/health} -- no token required at all.</li>
 *   <li>{@code GET /api/invoices} -- any caller holding the realm role {@code billing-reader}
 *       or {@code billing-admin} (enforced in {@link SecurityConfig}'s filter chain, before this
 *       method body ever runs).</li>
 *   <li>{@code POST /api/invoices} -- only a caller holding {@code billing-admin}, enforced here
 *       with method-level {@code @PreAuthorize} instead of the filter chain, to show both
 *       enforcement styles for real in the same small app.</li>
 *   <li>{@code GET /api/invoices/premium-report} -- gated not by a Spring role check but by a
 *       real server-side UMA 2.0 decision from Keycloak itself ({@link UmaPermissionService}),
 *       demonstrating resource-level authorization a static role check can't express as cleanly:
 *       this app asks Keycloak, per request, "is this specific caller allowed this specific
 *       scope on this specific resource" rather than baking the rule into its own code.</li>
 * </ul>
 *
 * <p>Invoice data is an in-memory stand-in (no database) -- this app's subject is the
 * security boundary in front of the API, not the billing domain behind it.
 */
@RestController
@RequestMapping("/api")
public class BillingController {

    private final List<Map<String, Object>> invoices = new java.util.concurrent.CopyOnWriteArrayList<>(List.of(
            Map.of("id", 1001, "customer", "Acme Robotics", "amountUsd", 4200.00, "status", "paid"),
            Map.of("id", 1002, "customer", "Blue Harbor Logistics", "amountUsd", 980.50, "status", "overdue")
    ));
    private final AtomicLong nextId = new AtomicLong(1003);
    private final UmaPermissionService umaPermissionService;

    public BillingController(UmaPermissionService umaPermissionService) {
        this.umaPermissionService = umaPermissionService;
    }

    @GetMapping("/public/health")
    public ResponseEntity<Map<String, Object>> health() {
        return ResponseEntity.ok(Map.of(
                "status", "up",
                "service", "northwind-apps-billing-api",
                "time", Instant.now().toString()
        ));
    }

    @GetMapping("/invoices")
    public ResponseEntity<Map<String, Object>> listInvoices(JwtAuthenticationToken auth) {
        Jwt jwt = (Jwt) auth.getCredentials();
        return ResponseEntity.ok(Map.of(
                "invoices", invoices,
                "requestedBy", jwt.getClaimAsString("preferred_username") != null
                        ? jwt.getClaimAsString("preferred_username")
                        : jwt.getSubject(),
                "callerAuthorities", auth.getAuthorities().stream().map(Object::toString).toList()
        ));
    }

    @PostMapping("/invoices")
    @PreAuthorize("hasRole('billing-admin')")
    public ResponseEntity<Map<String, Object>> createInvoice(@RequestBody Map<String, Object> body) {
        long id = nextId.getAndIncrement();
        Map<String, Object> invoice = Map.of(
                "id", id,
                "customer", body.getOrDefault("customer", "Unknown"),
                "amountUsd", body.getOrDefault("amountUsd", 0.0),
                "status", "draft"
        );
        invoices.add(invoice);
        return ResponseEntity.status(201).body(invoice);
    }

    @GetMapping("/invoices/{id}")
    public ResponseEntity<Map<String, Object>> getInvoice(@PathVariable long id) {
        return invoices.stream()
                .filter(inv -> ((Number) inv.get("id")).longValue() == id)
                .findFirst()
                .<ResponseEntity<Map<String, Object>>>map(ResponseEntity::ok)
                .orElse(ResponseEntity.notFound().build());
    }

    /**
     * Any authenticated caller reaches this method (the filter chain only requires a valid
     * token, see {@link SecurityConfig}) -- the real access decision happens inside
     * {@link UmaPermissionService}, against Keycloak's own UMA 2.0 resource/scope/policy/
     * permission model (the {@code premium-invoice-report} resource, {@code view} scope,
     * {@code billing-admin-policy}), not against anything hardcoded in this method.
     */
    @GetMapping("/invoices/premium-report")
    public ResponseEntity<Map<String, Object>> premiumReport(
            @org.springframework.web.bind.annotation.RequestHeader(HttpHeaders.AUTHORIZATION) String authorizationHeader) {
        String callerToken = authorizationHeader.replaceFirst("(?i)^Bearer ", "");
        boolean permitted = umaPermissionService.callerMayViewPremiumReport(callerToken);
        if (!permitted) {
            return ResponseEntity.status(403).body(Map.of(
                    "error", "access_denied",
                    "detail", "Keycloak's UMA policy for the premium-invoice-report resource denied this caller."
            ));
        }
        double total = invoices.stream().mapToDouble(inv -> ((Number) inv.get("amountUsd")).doubleValue()).sum();
        return ResponseEntity.ok(Map.of(
                "report", "premium-invoice-analytics",
                "totalOutstandingAndPaidUsd", total,
                "invoiceCount", invoices.size(),
                "grantedVia", "UMA 2.0 RPT from Keycloak Authorization Services"
        ));
    }

package com.northwindapps.billing;

import java.util.Collection;
import java.util.List;
import java.util.Map;
import java.util.stream.Collectors;

import org.springframework.core.convert.converter.Converter;
import org.springframework.security.core.GrantedAuthority;
import org.springframework.security.core.authority.SimpleGrantedAuthority;
import org.springframework.security.oauth2.jwt.Jwt;

/**
 * Converts a Keycloak-issued JWT's {@code realm_access.roles} claim into Spring Security
 * {@link GrantedAuthority} instances, each prefixed {@code ROLE_} so {@code hasRole(...)} and
 * {@code @PreAuthorize("hasRole(...)")} work the way Spring Security expects.
 *
 * <p>This class exists because of a real, well-documented gap -- confirmed the hard way while
 * building this chapter's lab, not assumed up front: Spring Security's own default JWT-to-
 * authorities converter ({@code JwtGrantedAuthoritiesConverter}) looks for a {@code scope} or
 * {@code scp} claim (space-separated OAuth2 scopes), which is the shape a generic OAuth2
 * authorization server's access token carries. Keycloak's access tokens carry roles in a
 * differently-shaped, Keycloak-specific claim instead:
 *
 * <pre>
 * "realm_access": { "roles": ["billing-reader", "offline_access", "uma_authorization"] }
 * </pre>
 *
 * Without this converter, every endpoint protected with {@code hasRole("billing-reader")} or
 * similar returns 403 for every caller, no matter how correctly that caller's token was issued
 * and signed -- the token is valid and authenticated, but Spring Security never extracts any
 * authority named {@code ROLE_billing-reader} from it, because it was never looking at
 * {@code realm_access} in the first place. This chapter's "common mistakes" section covers the
 * exact 403 this produces and how it was diagnosed.
 */
public class KeycloakRealmRoleConverter implements Converter<Jwt, Collection<GrantedAuthority>> {

    private static final String REALM_ACCESS_CLAIM = "realm_access";
    private static final String ROLES_CLAIM = "roles";
    private static final String ROLE_AUTHORITY_PREFIX = "ROLE_";

    @Override
    public Collection<GrantedAuthority> convert(Jwt jwt) {
        Map<String, Object> realmAccess = jwt.getClaim(REALM_ACCESS_CLAIM);
        if (realmAccess == null || !(realmAccess.get(ROLES_CLAIM) instanceof List<?> roles)) {
            return List.of();
        }
        return roles.stream()
                .map(Object::toString)
                .map(role -> new SimpleGrantedAuthority(ROLE_AUTHORITY_PREFIX + role))
                .collect(Collectors.toList());
    }
}

import org.springframework.security.web.SecurityFilterChain;

/**
 * Wires this app up as an OAuth2 Resource Server: every request is authenticated (or rejected)
 * based solely on a bearer JWT's validity against the realm named in
 * {@code spring.security.oauth2.resourceserver.jwt.issuer-uri} -- no session, no cookie, no
 * login form of its own. This is "What concept is this?" territory recalled concretely: chapter
 * 8 named the bearer-token model and chapter 16 named signature verification against a JWKS;
 * this class is where Spring Security actually performs both, automatically, once
 * {@code spring-boot-starter-oauth2-resource-server} is on the classpath and an issuer-uri is
 * configured -- fetching {@code <issuer-uri>/.well-known/openid-configuration} to learn the
 * token issuer and jwks_uri, then verifying every incoming token's signature, issuer, and
 * expiry against that JWKS automatically on every request (see this chapter's validation-flow
 * diagram).
 *
 * <p>The one piece Spring Security does <em>not</em> do automatically, correctly, out of the
 * box against a Keycloak-issued token is turn that token's roles into Spring Security
 * authorities -- see {@link KeycloakRealmRoleConverter}'s javadoc for the real gotcha this
 * chapter's lab hit and how {@code jwtAuthenticationConverter()} below fixes it.
 */
@Configuration
@EnableMethodSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            // This API is a pure resource server: every caller presents a fresh bearer token on
            // every request, so there is no server-side session to create or maintain.
            .sessionManagement(session -> session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            // A resource server validating only bearer tokens (never a browser form submission)
            // has no CSRF-vulnerable session-cookie-based state to protect -- CSRF protection is
            // a defense for cookie-authenticated, browser-based requests, which this API never
            // accepts (chapter 18 covers CSRF defenses for flows that genuinely need them).
            .csrf(AbstractHttpConfigurer::disable)
            .authorizeHttpRequests(authorize -> authorize
                .requestMatchers("/api/public/**").permitAll()
                .requestMatchers("/api/invoices/**").hasAnyRole("billing-reader", "billing-admin")
                .anyRequest().authenticated()
            )
            .oauth2ResourceServer(oauth2 -> oauth2
                .jwt(jwt -> jwt.jwtAuthenticationConverter(jwtAuthenticationConverter()))
            );
        return http.build();
    }

    /**
     * Combines Spring Security's default JWT claim extraction ({@code sub} as the principal
     * name) with {@link KeycloakRealmRoleConverter}'s realm-role-to-authority mapping, instead
     * of the default {@code JwtGrantedAuthoritiesConverter} that looks for a {@code scope}/
     * {@code scp} claim Keycloak's access tokens don't carry in that shape.
     */
    private JwtAuthenticationConverter jwtAuthenticationConverter() {
        JwtAuthenticationConverter converter = new JwtAuthenticationConverter();
        converter.setJwtGrantedAuthoritiesConverter(new KeycloakRealmRoleConverter());
        return converter;
    }
}
package com.northwindapps.billing;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Service;
import org.springframework.web.client.RestClient;
import org.springframework.web.client.HttpClientErrorException;

import java.util.List;
import java.util.Map;

/**
 * Makes this app a real UMA 2.0 Policy Enforcement Point against Keycloak's own Protection API
 * and token endpoint -- the exact wire-level round trip chapter 37's lab already proved out with
 * raw curl, now driven by the resource server itself instead of staying a standalone transcript.
 *
 * <p>Two calls, in order, for every protected request:
 * <ol>
 *   <li>Using this app's own client-credentials token, ask the Protection API for a permission
 *       ticket naming the resource + scope the caller is trying to reach.</li>
 *   <li>Exchange that ticket for a Requesting Party Token (RPT) at the normal token endpoint,
 *       using {@code grant_type=urn:ietf:params:oauth:grant-type:uma-ticket} and forwarding the
 *       caller's own bearer token in the {@code Authorization} header -- that header is how
 *       Keycloak learns who is actually asking (confirmed live in chapter 37's lab).</li>
 * </ol>
 * A 200 here means Keycloak's policies (the {@code billing-admin-policy} role policy, in this
 * app's case) permitted the request; any other status means denied, and this service treats
 * every non-200 response as a denial rather than trying to distinguish error shapes, since
 * chapter 37's lab found the denial error body has no documented stable contract.
 */
@Service
public class UmaPermissionService {

    private final RestClient restClient = RestClient.create();

    @Value("${northwind.uma.token-endpoint}")
    private String tokenEndpoint;

    @Value("${northwind.uma.protection-endpoint}")
    private String protectionEndpoint;

    @Value("${northwind.uma.client-id}")
    private String clientId;

    @Value("${northwind.uma.client-secret}")
    private String clientSecret;

    @Value("${northwind.uma.premium-report-resource-id}")
    private String premiumReportResourceId;

    public boolean callerMayViewPremiumReport(String callerBearerToken) {
        String rsToken = fetchResourceServerToken();
        String ticket = requestPermissionTicket(rsToken, premiumReportResourceId, "view");
        return exchangeTicketForRpt(callerBearerToken, ticket);
    }

    private String fetchResourceServerToken() {
        Map<String, Object> body = restClient.post()
                .uri(tokenEndpoint)
                .header("Content-Type", "application/x-www-form-urlencoded")
                .body("grant_type=client_credentials&client_id=" + clientId + "&client_secret=" + clientSecret)
                .retrieve()
                .body(Map.class);
        return (String) body.get("access_token");
    }

    private String requestPermissionTicket(String rsToken, String resourceId, String scope) {
        Map<String, Object> body = restClient.post()
                .uri(protectionEndpoint)
                .header("Authorization", "Bearer " + rsToken)
                .header("Content-Type", "application/json")
                .body(List.of(Map.of("resource_id", resourceId, "resource_scopes", List.of(scope))))
                .retrieve()
                .body(Map.class);
        return (String) body.get("ticket");
    }

    private boolean exchangeTicketForRpt(String callerBearerToken, String ticket) {
        try {
            restClient.post()
                    .uri(tokenEndpoint)
                    .header("Authorization", "Bearer " + callerBearerToken)
                    .header("Content-Type", "application/x-www-form-urlencoded")
                    .body("grant_type=urn:ietf:params:oauth:grant-type:uma-ticket"
                            + "&ticket=" + ticket
                            + "&client_id=" + clientId
                            + "&client_secret=" + clientSecret)
                    .retrieve()
                    .toBodilessEntity();
            return true;
        } catch (HttpClientErrorException e) {
            // Keycloak returns 403 access_denied for a denied UMA exchange (chapter 37's finding,
            // reconfirmed here) -- any 4xx here is a real denial, not an application error.
            return false;
        }
    }
}

Real bugs found while building this

1. A UMA resource URI with a path-segment wildcard (/api/invoices/*/premium-report) is rejected outright — Keycloak only accepts a trailing /* or a /*.ext suffix. Fixed by making the endpoint a fixed path instead of a per-invoice one.

2. Keycloak 26's declarative User Profile silently drops any user attribute not declared in its schema — no error, no warning, the attribute just never appears, and a protocol mapper reading it never fires. tenant_id had to be added to the realm's User Profile schema before it would actually persist and ride in a token — the exact fix is the "declare tenant_id in the User Profile schema" step inlined in seed-realm.sh below, under "How to run it."

How to defend this in an interview

  • Why one realm, not two or three? A realm is Keycloak's unit of complete isolation — themes, password policy, session lifetimes, brute-force protection all apply realm- wide. Northwind's actual separation need (per-tenant data isolation) is an authorization-time concern, not an authentication-time one, so it's enforced with roles, the tenant_id claim, and UMA policies inside one realm instead of paying for N realms' operational overhead.
  • Why UMA instead of just a role check on the premium endpoint? A role check is static and compiled into the app; the UMA resource/scope/policy/permission model lives in Keycloak and can be changed by an administrator — add a second policy, change the decision strategy, scope it to a specific resource instance — without touching or redeploying the app. It also demonstrates the general shape fine-grained, resource-level authorization takes, which a hardcoded @PreAuthorize can't express as the resource count grows.
  • What does the tenant_id mapper actually buy? Every downstream application gets the authenticated user's tenant on every token, for free, with no separate lookup call and no risk of that lookup silently drifting out of sync with the user's real assignment.
  • What would change at real scale? The in-memory invoice list becomes a real, tenant-partitioned database with the tenant_id claim enforced in every query, not just read for display; the single-node Keycloak instance becomes a clustered deployment (Part IX); and the UMA policy set would likely grow from one role policy to a small policy set per resource type as the number of distinct resources grows past what hand-authored policies comfortably cover.
  • What's honestly out of scope here? Identity brokering (a second realm standing in for Acme Corp's own IdP, demonstrating JIT provisioning) was deliberately cut from this build to keep scope manageable — chapter 31 already proves the mechanism works; this capstone's job was integrating the pieces that hadn't been wired together yet, not re-proving ones that already were.
