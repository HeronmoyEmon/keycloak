Essay section — 5 questions

Write out a real answer before clicking to reveal the model answer. These are the kind of questions an interviewer asks to see if you actually understand the mechanism, not just whether you memorized a menu path.

  1. A protocol mapper on northwind-dashboard is configured correctly — right mapper type, right token claim name — but the claim never shows up in any issued token. Walk an interviewer through your diagnosis, in order.

    Model answerChapter 24's own "if you see this" pitfall is exactly this scenario, and the mapper configuration is the last thing to check, not the first. First: is the source attribute actually populated on the user or client you tested with — a mapper reading a user attribute that was never set has nothing to map. Second: is the client scope carrying this mapper actually attached to the client as a default (or at minimum requested-and-granted optional) scope — a mapper sitting in an unattached scope never runs for that client at all. Third: is the token type you're inspecting one the mapper is actually configured to populate (access token vs. ID token vs. userinfo — these are independent checkboxes on the same mapper). Only after all three come back clean does the mapper's own configuration (claim name spelling, JSON type) become the suspect.

  2. Why does chapter 23 deliberately keep tenant-admin, support-agent, and platform-engineer as three independent, non-composite roles instead of nesting them under one composite role for convenience?

    Model answerA composite role grants everything underneath it in one assignment, which is convenient right up until someone moves teams. If platform-engineer quietly included support-agent as an associated role, moving Priya from Support to platform engineering by granting platform-engineer would leave her holding support-agent's access forever, nested invisibly inside the new role — nobody would ever see it on her direct role list to think to remove it. Keeping the three roles independent means a mover's access is exactly the union of roles explicitly, visibly assigned to them at any moment, which is what makes a clean offboard-the-old-role step on a role change actually work.

  3. An admin adds a "Condition - user role" REQUIRED execution (role: tenant-admin) next to an existing "Condition - user configured OTP" REQUIRED execution in the browser flow, expecting this to mean "every tenant-admin must do OTP." It doesn't work as expected. Explain the actual resulting behavior and why.

    Model answerTwo REQUIRED conditions inside the same conditional subflow both have to pass for anything inside that subflow to even be considered, and "user has OTP configured" is itself one of those conditions. So the actual behavior is "OTP only for tenant-admins who have already enrolled OTP" — which silently excludes every tenant-admin who hasn't enrolled yet, the exact opposite of forcing enrollment. Getting "require OTP for every tenant-admin, enrolling them on the spot if they haven't yet" requires a different structure: the role condition alone gating entry into a subflow that then requires OTP Form regardless of prior enrollment status (which triggers Keycloak's OTP-enrollment required action for anyone without a credential yet), not stacking the enrollment-status condition on top of the role condition.

  4. Chapter 21 sets Access Token Lifespan to a short value and SSO Session Max to a much longer one on northwind-apps. Explain to an interviewer why shortening one of these without touching the other doesn't actually bound the risk you might think it does.

    Model answerAccess Token Lifespan only bounds how long one individual bearer token is valid before it has to be refreshed — it says nothing about how many times refresh can happen. SSO Session Max is the separate, absolute ceiling on the underlying session that silent refreshes ride on top of. A user can refresh a 10-minute access token every 10 minutes, unattended, for the entire 8 hours SSO Session Max allows, with every individual token perfectly valid the whole time. Shortening only the access token lifespan without also bounding the session max makes stolen-token replay windows shorter but does nothing to bound how long a session (and therefore the refresh privilege that session carries) can be abused for — the two settings answer genuinely different risk questions and neither substitutes for the other.

  5. Keycloak's Quarkus distribution splits configuration into build-time and runtime. Why does this matter operationally, and what's the concrete failure mode of treating start-dev as a production-ready mode because it "already works"?

    Model answerBuild- time options (like which features are compiled in) get baked into an optimized server image via kc build, which lets Quarkus pre-compile far more aggressively than a server that has to stay flexible about what might be enabled later — but it means changing a build- time option requires rebuilding, not just restarting. start-dev is explicitly a development convenience: it auto-enables an in-memory H2 database and relaxes settings that a real deployment should never run with. The concrete failure mode chapter 19 names directly: running start-dev in production because it was the fastest way to get a demo working, then forgetting to switch to a real database vendor and proper production mode before real traffic arrives — silently losing all realm data on restart, since the default dev database never persisted anything durable in the first place.
