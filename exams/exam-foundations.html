Essay section — defend your answer to an interviewer

Five harder, synthesis-heavy questions. Click to reveal a model answer, but write your own answer out first — an interviewer won't show you theirs before you give one.

  1. An interviewer says: "Our last vendor called their product an 'authentication system,' but it also handled account lockout policies and logged every access attempt. Was their terminology accurate?" How do you answer, precisely, using chapter 3's model?

    Model answerNot fully — what they built is better described as an AAA system, not just authentication. Account lockout policy enforcement is still part of authentication (deciding whether a login attempt succeeds), but logging every access attempt is accounting, a third, independent pillar: the real-time recording of what happened, separate from both proving identity (authentication) and deciding permissions (authorization). Calling the whole thing "authentication" undersells what it does and risks someone assuming it has no audit trail at all, when accounting is explicitly what produces one.

  2. Riverside Health's clinician directory stores each doctor's department as an attribute. A new hospital policy says "only doctors in the Cardiology department may view cardiology patient records." Using chapters 4 and 6 together, explain what kind of authorization model this actually requires, and why a directory attribute alone doesn't automatically give you that model for free.

    Model answerThis is an ABAC (attribute-based access control) requirement: the access decision depends on comparing an attribute of the subject (the doctor's department) against an attribute of the resource (the record's associated department) at request time. A directory (chapter 4) is just where that attribute lives and how it's queried — storing "department: Cardiology" on a directory entry doesn't itself enforce anything. A separate authorization layer has to actually read that attribute and evaluate the rule on every access request; the directory is a data source for the policy, not the policy engine itself.

  3. Meridian Trust's security team reports a spike in failed logins against retail customer accounts, almost all using previously-breached password lists found on the open web, not passwords generated specifically for Meridian. Using chapter 9's vocabulary, name the attack precisely, and explain in one sentence why "make customers choose stronger passwords" is the wrong primary fix.

    Model answerThis is credential stuffing, not brute-forcing — the attacker already has real, previously valid username/password pairs leaked from some other, unrelated breach, and is testing whether the same person reused that password at Meridian. Stronger password rules don't help, because the problem isn't a weak password — the passwords being tried are often perfectly strong; the fix has to target reused-password detection and risk-based or multi-factor authentication, not password complexity policy.

  4. Explain, in terms an engineer who has never heard the words "bearer token" would understand, why a stolen access token is dangerous even if the thief never learns the user's password — and why this matters specifically for Northwind Apps, a company whose customers embed its API inside their own browser-based applications.

    Model answerA bearer token's defining property, per chapter 8, is that whoever holds it can use it — there's no second check tying it back to the original owner, the way a password-plus-device combination might be. If a thief steals the token itself (say, by exploiting a bug in one customer's browser-based integration — exactly the realistic path for Northwind, whose customers run their own frontend code against Northwind's API), the thief can act as that user for as long as the token stays valid, without ever needing the password at all. The password was never the thing protecting that session once the token existed; the token itself became the credential that mattered.

  5. A colleague argues: "Zero Trust means we don't trust our own employees." Using chapter 6, correct this misconception precisely, and illustrate with a one-sentence example involving Meridian Trust's internal banking staff.

    Model answerZero Trust isn't about distrusting people personally — it's the principle that no request should be implicitly trusted just because of where it came from (inside the corporate network, from an already-authenticated session, from a previously-verified device), and that every access decision should be re-evaluated against current context and least-privilege scope instead. For Meridian's staff, that means a teller who successfully logged into the corporate network this morning still has every subsequent action — viewing one specific customer's account, approving one specific transfer — checked on its own terms, not waved through just because the login earlier in the day succeeded.
