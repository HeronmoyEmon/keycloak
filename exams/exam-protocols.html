Graded section — 20 questions

Essay section — defend your answer to an interviewer

These have no scoring. Write (or at least say out loud) a real answer before revealing the model answer — the point is to catch a gap between "I recognize this" and "I can explain this cold, under question, to someone evaluating me."

  1. An interviewer asks you to defend, in under a minute, why PKCE matters even for a confidential client that already has a client secret. What do you say?

    Model answerA client secret protects one specific step: proving to the authorization server, at the token endpoint, that the caller really is the registered client. It does nothing to protect the authorization code itself on its way to that exchange — a code can leak through a referrer header, a misconfigured proxy or log aggregator, or a malicious app on a shared device registering the same redirect scheme a native confidential client uses. PKCE closes exactly that separate gap: whoever intercepts the code still can't redeem it without the original code_verifier, which never left the legitimate client. That's why RFC 9700 §2.1.1 recommends PKCE for confidential clients too, not just mandates it for public ones.

  2. Walk through exactly why an authorization server enforcing only a "starts with" or same-domain redirect_uri check is dangerous, using the specific live finding this course turned up as your example.

    Model answerRFC 6749 §3.1.2.3 requires exact, byte-for-byte string comparison against a registered redirect URI, not a prefix or domain check — and chapter 13's own live testing against a public demo OAuth server found exactly this gap in practice: a request with redirect_uri=https://evil.example.com/ callback, never registered for that client, still got a valid authorization code delivered to it. A loose check lets an attacker register or simply supply a look-alike URI — a different path on the same domain, a subdomain they control, anything that passes a weaker comparison — and receive the authorization code meant for the real application. Whoever receives that code can exchange it for tokens issued on behalf of whatever user just authenticated, which is a full login hijack, not a theoretical edge case.

  3. An interviewer asks: "If the token is already signed, why do you also need a client secret?" What's the difference between a client proving who it is, and a token proving who issued it?

    Model answerThese are two separate trust relationships, not redundant layers of the same one. A client secret (or equivalent client authentication) proves, to the authorization server, that the application calling the token endpoint really is the registered client it claims to be — a one-time check at issuance time. A token's signature proves something different, to a different party, later: that the token a resource server just received genuinely came from the authorization server that issued it and hasn't been altered since, independent of who happens to be presenting it. Losing either check creates a different failure: a stolen client secret lets an attacker request new tokens; a broken signature check lets an attacker forge or tamper with tokens that already exist.

  4. Defend the decision to use an opaque reference token instead of a self-contained JWT for a session where immediate server-side revocation really matters — for example, Meridian Trust's online banking session after a customer reports a stolen device.

    Model answerA self-contained JWT carries its own claims and signature with no server-side record behind it — revoking it can mark it revoked in a list somewhere, but a verifier that only checks signature and exp (as chapter 14's own lab found happening against a real demo server) will keep accepting it until it naturally expires. A reference token is the opposite: it's an opaque string the server looks up in its own store on every introspection call, so deleting that record on revocation means the very next check reports active: false immediately — there's an actual record to delete. For a stolen-device response, where the whole point is an immediate cutoff rather than "eventually, once it expires," that server-side lookup is the feature, not overhead to avoid.

  5. An interviewer who knows SAML well but has never used OIDC asks you to explain OIDC's split between the ID token and the UserInfo endpoint using only SAML terms they already know — and why OIDC bothers splitting it into two pieces at all.

    Model answerThe ID token is the closest thing to a SAML assertion: a signed statement, delivered directly to the client at the same moment the token exchange happens, saying who just authenticated. The UserInfo endpoint has no direct SAML equivalent — it's a separate, callable API, reachable later and independently of the original token issuance, that returns additional profile claims when presented with a valid access token. OIDC splits these because it treats "who authenticated" (small, time-sensitive, needed immediately) as a different concern from "what do we know about this person's profile" (potentially larger, refreshable, not always needed on every request) — SAML's single assertion has to carry everything at once because it has no equivalent of a separate, re-callable profile endpoint built into the core protocol.
