    33. Custom User Storage SPI

    Chapter 32 federated Keycloak against LDAP using a provider Keycloak already ships — no Java, no JAR, just configuration. This chapter covers the path that exists for everything LDAP doesn't cover: writing a real UserStorageProvider in Java against Keycloak's Service Provider Interface (SPI), packaging it as a JAR, and deploying it into a running server. Every piece of this chapter's lab was actually built, compiled, and run against a real Keycloak 26.8.2 instance — including the real mistakes hit along the way, kept in rather than edited out, because they're some of the most useful material here.

    Why this matters

    Real organizations rarely keep every user in LDAP. A 20-year-old proprietary HR system, a SaaS vendor's own customer database, a mainframe-era membership system — none of these speak LDAP, and none of them can realistically be migrated into Keycloak overnight just so Keycloak can authenticate against them. An IAM specialist who only knows "click through the admin console" or "configure the built-in LDAP provider" hits a wall the moment a client's real directory isn't one of those two shapes. The User Storage SPI is Keycloak's answer: write a thin Java bridge once, and every protocol this course has already covered — direct grant, authorization code, SAML, the Admin REST API — works against that external store exactly as if it were native Keycloak data, with no changes anywhere else.

    Sources for this chapter: Keycloak's own Server Developer Guide — User Storage SPI (version 26.8.2, fetched live for this chapter); Maven Central (search.maven.org and repo1.maven.org), queried live to pin exact dependency coordinates; and this chapter's own lab, run against a real, disposable Keycloak 26.8.2 + PostgreSQL 17 Docker Compose stack this chapter owns — the exact docker-compose.yml, Java source, and Maven build file are all given below, no repository required.

    What concept is this?

    Chapter 1 named extensibility — "a plugin or SPI-style architecture so an organization can add custom authentication steps, custom data sources, or custom branding without forking the product" — as one of the common features a mature IAM system provides, and pointed forward to Part VIII for the details. Chapter 4 named the deeper reason federation exists at all: "an organization almost never wants to migrate an existing directory's population into a separate IAM product," so the IAM system should connect to whatever already holds the truth instead. Chapter 19 (Keycloak's architecture) did not, on inspection, cover the SPI concept itself in any depth — it's a gap this chapter's "What concept is this?" recall would normally point back to, but there's honestly nothing substantial there to recall yet. This chapter is where "custom data source, added without forking the product" (chapter 1) and "connect to the store that's already authoritative instead of migrating it" (chapter 4) finally meet code: a Service Provider Interface is a set of Java interfaces a vendor defines and a third party implements, discovered automatically at server boot through the standard Java ServiceLoader mechanism — Keycloak's own built-in LDAP provider (chapter 32) is written against this exact same SPI; it is not special-cased.

    Two classes, one lifecycle: Factory and Provider

    Every Keycloak SPI follows the same two-class pattern, and the User Storage SPI is no exception. Per Keycloak's own developer guide, confirmed directly against the real interfaces on Maven Central for this chapter (see the next slide):

    • A Factory class, implementing UserStorageProviderFactory<T>, is discovered once, at server boot, via ServiceLoader — the mechanism behind the plain-text META-INF/services/org.keycloak.storage.UserStorageProviderFactory file this chapter's JAR bundles, listing nothing but the factory's fully qualified class name. Its getId() is the id that shows up as an option wherever a realm picks a User Federation provider; its init(Config.Scope) runs once and is where this chapter's factory loads the toy CSV directory into memory.
    • A Provider class, implementing UserStorageProvider (plus whichever optional capability interfaces it needs), is created per Keycloak transaction by the factory's create(KeycloakSession, ComponentModel) — cheap to construct, because the real work (loading the directory) already happened once in the factory.

    "Capability interfaces" are how a provider opts into only the behavior it actually supports. This chapter's provider implements exactly two, deliberately kept minimal per this chapter's own scope: UserLookupProvider (resolve a user by username/id/email) and CredentialInputValidator (check whether a submitted password is correct). It does not implement UserQueryMethodsProvider — the capability that would let the Admin Console's user-search screen or a GET /admin/realms/{realm}/users?username=... partial search enumerate users from this provider. That specific, real gap is confirmed live in this chapter's lab below, not assumed.

    A real, intentional risk, named honestly

    The password column is plaintext, on purpose. That is an honest stand-in for a genuinely common real-world failure mode, not a shortcut taken to save code: a decades-old internal HR system built long before argon2/bcrypt were standard practice really can store plaintext or weakly-reversible credentials, and a hospital cannot simply "turn it off" overnight. A custom User Storage SPI provider is exactly how Keycloak sits in front of a store like that without being able to fix what's inside it — the provider bridges the store; it does not, and cannot, repair it.

    AbstractUserAdapter: read-only is the default, not a restriction added on top

    LegacyStaffUserAdapter adapts one StaffRecord into the UserModel shape Keycloak core actually works with, by extending AbstractUserAdapter (from keycloak-model-storage). Per Keycloak's own javadoc, this class "provides implementations for everything but getUsername()," and — critically for a bridge to a legacy system this provider has no way to write back into — every update method throws ReadOnlyException unless explicitly overridden. This lab overrides nothing on the write side at all, because there is genuinely nothing to override: the read-only default behavior is the correct behavior here, not a corner this lab cut.

    public class LegacyStaffUserAdapter extends AbstractUserAdapter {
    private final StaffRecord record;
    public LegacyStaffUserAdapter(KeycloakSession session, RealmModel realm,
                                   ComponentModel storageProviderModel, StaffRecord record) {
        super(session, realm, storageProviderModel);
        this.record = record;
    }
    @Override public String getUsername()  { return record.username(); }
    @Override public String getFirstName() { return record.firstName(); }
    @Override public String getEmail()     { return record.email(); }
    // getAttributes() also returns "legacyEmployeeId" and "department" -- fields the
    // legacy system carries that Keycloak's built-in UserModel has no dedicated slot for.
}

    One thing AbstractUserAdapter does not provide a default for, confirmed the hard way during this chapter's own build (see the lab below): UserModel.credentialManager(). Keycloak's newer credential-manager API left this method abstract all the way down even on this "provides everything but getUsername()" base class. The fix is Keycloak core's own bridge class, org.keycloak.credential.UserCredentialManager (also in keycloak-model-storage), which forwards isValid()/ isConfiguredFor() calls straight through to this provider's own CredentialInputValidator — a federated, legacy-style provider like this one never has to implement SubjectCredentialManager's full surface itself:

    @Override
public SubjectCredentialManager credentialManager() {
    return new UserCredentialManager(session, realm, this);
}

    ProsCons
    The legacy system stays the single source of truth — no migration project, no risk of two copies of staff data drifting apartNo admin-console configuration screen exists unless you build one yourself — LDAP federation's rich settings UI (chapter 32) is specific to that provider
    Exposes organization-specific fields natively (e.g. legacyEmployeeId, department) without configuring attribute mappers the way LDAP federation needsNo built-in sync/caching behavior — LDAP federation's periodic sync and cache policy are specific to that provider; a custom provider must build its own if it needs one

    Case study: Riverside Health's legacy HR directory

    Case study — Riverside Health

    Riverside Health runs a hospital network whose clinical and administrative staff accounts have lived for two decades in an internal HR system built in-house — its own proprietary database schema, its own (dated) password storage, no LDAP interface, no REST API, and no realistic budget or appetite to replace it just to satisfy a new identity platform. Riverside still wants every clinician and administrator logging into the new patient-portal-adjacent tooling (chapters 46-47 build the fuller HIPAA patient-portal case study later) through one centralized Keycloak realm, with the same MFA and session policies (chapter 30) applied uniformly — but migrating every staff account's credentials into Keycloak's own store is explicitly off the table: it's a legacy system HR still actively uses day to day, and a one-way migration would immediately create two diverging copies of "who currently works here." A custom User Storage SPI provider — exactly this chapter's lab, scaled up — is how Riverside Health's IAM specialist would actually bridge the two systems: Keycloak brokers every login through the provider, HR's system remains the untouched source of truth, and nothing about Keycloak's downstream configuration (clients, roles, MFA policy) has to know the difference.

      package com.riversidehealth.keycloak.legacyhr;

import java.io.BufferedReader;
import java.io.IOException;
import java.io.InputStream;
import java.io.InputStreamReader;
import java.io.UncheckedIOException;
import java.nio.charset.StandardCharsets;
import java.util.HashMap;
import java.util.Map;

/**
 * A tiny read-only, in-memory stand-in for Riverside Health's real legacy HR system's own data
 * access layer.
 *
 * <p>In real life this class's five methods (or something very like them) would instead issue a
 * query against that system's own proprietary database or API. The point of this lab is the
 * Keycloak-facing SPI code built on top, not the toy store underneath it — a flat CSV bundled as a
 * classpath resource is the simplest thing that is still a genuinely separate, external user
 * store Keycloak itself does not understand natively (unlike LDAP, which chapter 32 covered with
 * Keycloak's own built-in federation provider, requiring no custom code at all).</p>
 */
public final class LegacyStaffDirectoryStore {

    private final Map<String, StaffRecord> byUsername;
    private final Map<String, StaffRecord> byEmail;

    private LegacyStaffDirectoryStore(Map<String, StaffRecord> byUsername, Map<String, StaffRecord> byEmail) {
        this.byUsername = byUsername;
        this.byEmail = byEmail;
    }

    /**
     * Loads every row of the bundled CSV once. Called exactly once, from the provider factory's
     * {@code init()}, and the resulting store is shared read-only across every provider instance
     * {@code create()} hands back for the lifetime of this deployment — there is no per-request
     * re-parsing.
     */
    public static LegacyStaffDirectoryStore loadFromClasspath(String resourcePath) {
        Map<String, StaffRecord> byUsername = new HashMap<>();
        Map<String, StaffRecord> byEmail = new HashMap<>();

        try (InputStream in = LegacyStaffDirectoryStore.class.getResourceAsStream(resourcePath)) {
            if (in == null) {
                throw new IllegalStateException(
                        "Bundled legacy staff directory CSV not found on the classpath at " + resourcePath
                                + " -- check that it's under src/main/resources and the JAR actually contains it.");
            }
            try (BufferedReader reader = new BufferedReader(new InputStreamReader(in, StandardCharsets.UTF_8))) {
                String line = reader.readLine(); // header row, discarded
                while ((line = reader.readLine()) != null) {
                    if (line.isBlank()) {
                        continue;
                    }
                    String[] fields = line.split(",", -1);
                    if (fields.length != 7) {
                        throw new IllegalStateException("Malformed row in " + resourcePath + ": " + line);
                    }
                    StaffRecord record = new StaffRecord(
                            fields[0].trim(),  // username
                            fields[1].trim(),  // password (plaintext in this toy store -- see StaffRecord's javadoc)
                            fields[2].trim(),  // firstName
                            fields[3].trim(),  // lastName
                            fields[4].trim(),  // email
                            fields[5].trim(),  // employeeId
                            fields[6].trim()); // department
                    byUsername.put(record.username().toLowerCase(), record);
                    byEmail.put(record.email().toLowerCase(), record);
                }
            }
        } catch (IOException e) {
            throw new UncheckedIOException("Failed reading bundled legacy staff directory CSV at " + resourcePath, e);
        }

        return new LegacyStaffDirectoryStore(Map.copyOf(byUsername), Map.copyOf(byEmail));
    }

    public StaffRecord findByUsername(String username) {
        if (username == null) {
            return null;
        }
        return byUsername.get(username.toLowerCase());
    }

    public StaffRecord findByEmail(String email) {
        if (email == null) {
            return null;
        }
        return byEmail.get(email.toLowerCase());
    }

    public int size() {
        return byUsername.size();
    }
}
      package com.riversidehealth.keycloak.legacyhr;

import org.keycloak.component.ComponentModel;
import org.keycloak.credential.UserCredentialManager;
import org.keycloak.models.KeycloakSession;
import org.keycloak.models.RealmModel;
import org.keycloak.models.SubjectCredentialManager;
import org.keycloak.models.UserModel;
import org.keycloak.storage.adapter.AbstractUserAdapter;

import java.util.HashMap;
import java.util.List;
import java.util.Map;

/**
 * Adapts one {@link StaffRecord} from Riverside Health's legacy HR directory into the
 * {@link UserModel} shape Keycloak core actually works with.
 *
 * <p>{@code AbstractUserAdapter} (from {@code keycloak-model-storage}) implements every
 * {@code UserModel} method except {@link #getUsername()} with a reasonable read-only default, and
 * every write method ({@code setEmail}, {@code setFirstName}, ...) throws
 * {@code org.keycloak.storage.ReadOnlyException} unless overridden. That is exactly the right fit
 * here: this lab's provider has no way to write back into the real legacy HR system even if it
 * wanted to, so there is nothing to override on the write side at all -- the read-only default
 * behavior <em>is</em> the correct behavior, not a shortcut taken to save code.</p>
 */
public class LegacyStaffUserAdapter extends AbstractUserAdapter {

    private final StaffRecord record;

    public LegacyStaffUserAdapter(KeycloakSession session, RealmModel realm, ComponentModel storageProviderModel,
                                   StaffRecord record) {
        super(session, realm, storageProviderModel);
        this.record = record;
    }

    @Override
    public String getUsername() {
        return record.username();
    }

    @Override
    public String getFirstName() {
        return record.firstName();
    }

    @Override
    public String getLastName() {
        return record.lastName();
    }

    @Override
    public String getEmail() {
        return record.email();
    }

    @Override
    public boolean isEmailVerified() {
        // The legacy HR system is itself the source of truth for staff email addresses -- treat
        // every address it hands over as already verified rather than re-running Keycloak's own
        // email-verification required action against staff who never signed up through Keycloak.
        return true;
    }

    @Override
    public Map<String, List<String>> getAttributes() {
        Map<String, List<String>> attributes = new HashMap<>();
        attributes.put(UserModel.USERNAME, List.of(getUsername()));
        attributes.put(UserModel.FIRST_NAME, List.of(record.firstName()));
        attributes.put(UserModel.LAST_NAME, List.of(record.lastName()));
        attributes.put(UserModel.EMAIL, List.of(record.email()));
        // Two attributes the legacy system carries that Keycloak's built-in UserModel fields have
        // no slot for at all -- exactly the kind of extra, organization-specific data a custom SPI
        // provider can expose that Keycloak's native LDAP federation (chapter 32) would need an
        // explicit attribute mapper configured for instead.
        attributes.put("legacyEmployeeId", List.of(record.employeeId()));
        attributes.put("department", List.of(record.department()));
        return attributes;
    }

    @Override
    public List<String> getAttribute(String name) {
        return getAttributes().getOrDefault(name, List.of());
    }

    @Override
    public SubjectCredentialManager credentialManager() {
        // UserModel.credentialManager() is abstract all the way down -- AbstractUserAdapter does
        // not implement it on a subclass's behalf (confirmed the hard way: this class failed to
        // compile without this override, with javac naming the missing method directly). Keycloak
        // core's own org.keycloak.credential.UserCredentialManager (from keycloak-model-storage) is
        // the standard bridge that forwards isValid()/isConfiguredFor() calls straight through to
        // this provider's own CredentialInputValidator implementation, so a federated, legacy-style
        // provider like this one never has to implement SubjectCredentialManager's full surface
        // itself.
        return new UserCredentialManager(session, realm, this);
    }
}

import org.keycloak.models.credential.PasswordCredentialModel;
import org.keycloak.storage.StorageId;
import org.keycloak.storage.UserStorageProvider;
import org.keycloak.storage.user.UserLookupProvider;

/**
 * Keycloak-facing provider instance for Riverside Health's legacy staff directory.
 *
 * <p>This is the object chapter 33's diagram calls "the provider" -- created fresh per Keycloak
 * transaction by {@link LegacyStaffDirectoryUserStorageProviderFactory#create}, sharing the one
 * factory-owned, already-loaded {@link LegacyStaffDirectoryStore} rather than re-reading the CSV
 * on every call. It implements the two SPI capabilities this lab actually needs:</p>
 * <ul>
 *   <li>{@link UserLookupProvider} -- so Keycloak core can resolve a username/id/email to a
 *       {@code UserModel} it didn't create or store itself.</li>
 *   <li>{@link CredentialInputValidator} -- so Keycloak's own direct-grant and browser login flows
 *       can ask "is this password correct for this user?" without this provider needing to
 *       implement an entire custom authenticator.</li>
 * </ul>
 */
public class LegacyStaffDirectoryUserStorageProvider implements UserStorageProvider, UserLookupProvider,
        CredentialInputValidator {

    private final KeycloakSession session;
    private final ComponentModel model;
    private final LegacyStaffDirectoryStore store;

    public LegacyStaffDirectoryUserStorageProvider(KeycloakSession session, ComponentModel model,
                                                     LegacyStaffDirectoryStore store) {
        this.session = session;
        this.model = model;
        this.store = store;
    }

    @Override
    public UserModel getUserById(RealmModel realm, String id) {
        // Keycloak hands federated users an id of the form "f:<componentId>:<externalId>"
        // (org.keycloak.storage.StorageId's own convention) wherever a user's UUID would normally
        // go. StorageId.externalId() strips the "f:<componentId>:" prefix back off.
        String externalId = StorageId.externalId(id);
        return getUserByUsername(realm, externalId);
    }

    @Override
    public UserModel getUserByUsername(RealmModel realm, String username) {
        StaffRecord record = store.findByUsername(username);
        if (record == null) {
            return null;
        }
        return new LegacyStaffUserAdapter(session, realm, model, record);
    }

    @Override
    public UserModel getUserByEmail(RealmModel realm, String email) {
        StaffRecord record = store.findByEmail(email);
        if (record == null) {
            return null;
        }
        return new LegacyStaffUserAdapter(session, realm, model, record);
    }

    @Override
    public boolean supportsCredentialType(String credentialType) {
        return PasswordCredentialModel.TYPE.equals(credentialType);
    }

    @Override
    public boolean isConfiguredFor(RealmModel realm, UserModel user, String credentialType) {
        return supportsCredentialType(credentialType) && store.findByUsername(user.getUsername()) != null;
    }

    @Override
    public boolean isValid(RealmModel realm, UserModel user, CredentialInput input) {
        if (!supportsCredentialType(input.getType())) {
            return false;
        }
        StaffRecord record = store.findByUsername(user.getUsername());
        if (record == null) {
            return false;
        }
        // A real provider for a real legacy system would call that system's own authentication
        // API or compare against whatever hash format it actually uses. This toy store's plaintext
        // comparison is the honest, simplest possible stand-in -- see StaffRecord's javadoc and
        // this chapter's pitfall callout for why that's a real-world risk, not a code shortcut to
        // ignore.
        return record.password().equals(input.getChallengeResponse());
    }

    @Override
    public void close() {
        // Nothing provider-instance-scoped to release: the CSV-backed store is loaded once by the
        // factory and is shared, read-only, across every per-transaction provider instance.
    }
}

    Common mistakes

    • If you see an XML parse error in a POM pointing at a comment, the cause is very often two consecutive hyphens (--) somewhere inside that comment's text — XML comments cannot contain that sequence anywhere in their body, with no escape mechanism; this chapter's own pom.xml hit this exact error twice while documenting a shell command.
    • If you see "is not abstract and does not override abstract method credentialManager()" while extending AbstractUserAdapter, the cause is that class's own real gap: it implements almost all of UserModel except that one method, which Keycloak's newer credential-manager API left abstract. Bridge it with new UserCredentialManager(session, realm, this).
    • If a bind-mounted provider JAR shows up as a directory inside the container (confirm with ls -la — a d in the permissions column, not a -), the cause is that the source file didn't exist on the host at the moment the container was created. Docker silently creates an empty directory at that path, on both sides, rather than failing — rebuild the real JAR, confirm it with ls on the host first, then bring the container up.
    • If a kcadm.sh create components call for a User Federation provider returns 201 with no error, but the provider never actually resolves any user, the cause is very often a parentId set to the realm's name instead of its real UUID id — list any of the realm's other default components (kcadm.sh get components -r <realm>) to see the real UUID every other component actually uses.
    • If a custom attribute your provider's getAttributes() genuinely returns doesn't show up anywhere in the Admin REST API's user representation, the cause is almost always the realm's Declarative User Profile: an attribute not declared in its schema is dropped unless unmanagedAttributePolicy is set to allow it — the same gap chapters 22 and 24 already hit for ordinary local users, not something specific to federated providers.
    • If you see Keycloak throw a ClassCastException or silently fail to find your provider after a version upgrade, a frequent cause (not personally reproduced in this chapter's run, since the coordinates were verified live before writing the POM — see two slides back) is a provider JAR built against a different Keycloak minor version than the one actually running it, or a provider JAR that shades (bundles) its provided-scope Keycloak dependencies instead of leaving them out — either way putting two different copies of the same SPI classes on the server's classpath at once.
    • If your provider never appears at all in serverinfo's componentTypes, with no error anywhere, double-check the exact filename META-INF/services/org.keycloak.storage.UserStorageProviderFactory and its contents (one fully qualified class name, no leading/trailing whitespace issues) — ServiceLoader fails this kind of registration silently, by simply not finding the provider, rather than with a loud error.

    Glossary terms introduced here

    Takeaways

    • A Keycloak User Storage SPI provider is two classes: a Factory (discovered once, at boot, via Java's standard ServiceLoader mechanism) and a Provider (created fresh per transaction by the factory), and nothing more exotic than that.
    • A provider implements only the "capability interfaces" it actually needs — UserLookupProvider and CredentialInputValidator here, deliberately not UserQueryMethodsProvider, which is why this provider's users don't show up in the Admin Console's search but do authenticate correctly, confirmed live.
    • As of Keycloak 26.4+, UserStorageProvider/UserStorageProviderFactory/ AbstractUserAdapter live in keycloak-model-storage, not keycloak-server-spi alone — confirmed for the exact 26.8.2 version this course runs by inspecting both Maven Central's metadata and the real jars inside the running server image, with no nearest-version substitute needed.
    • Both Keycloak dependencies belong at scope=provided: the server supplies these exact classes at runtime, and bundling them into the provider's own JAR risks a real classloading conflict.
    • AbstractUserAdapter implements nearly all of UserModel with sensible read-only defaults — except credentialManager(), which must be bridged explicitly via Keycloak core's own UserCredentialManager, confirmed the hard way via a real compile error in this chapter's own build.
    • A Docker bind-mounted provider JAR that doesn't exist on the host at container-creation time becomes a silently-created, empty directory on both sides — build and confirm the real file exists with ls before bringing the stack up, not after.
    • A realm-level component's parentId must be the realm's actual UUID id, never its human-readable realm name — getting this wrong creates a 201-returning, silently orphaned component that Keycloak's federation machinery never consults.
    • A federated provider's custom attributes are subject to the exact same Declarative User Profile unmanagedAttributePolicy gate as any local user's attributes (chapters 22/24) — confirmed live by watching legacyEmployeeId/department vanish from, then reappear in, the Admin REST representation purely by changing a realm setting, with zero code changes.
    • A custom User Storage SPI provider and Keycloak's built-in LDAP federation (chapter 32) are two options for the same job, not a hierarchy — reach for LDAP federation when the store actually speaks LDAP, and for a custom SPI provider when it doesn't and can't realistically be migrated.

    Click a question to reveal a model answer. Try answering it yourself first — the point is to check your own reasoning against it, not to read the answer first.

    1. Why does a minimal custom User Storage SPI provider need two classes — a Factory and a Provider — rather than just one?

      Model answerThey solve different lifecycle problems. The Factory is discovered exactly once, at server boot, via ServiceLoader, and is the right place to do expensive one-time setup — this chapter's factory loads the entire CSV directory into memory in its init(). The Provider is created fresh by the factory's create() for every Keycloak transaction, which has to be cheap, because it happens constantly; it's cheap here specifically because the expensive work already happened once in the factory and is simply shared, read-only, with every provider instance. Collapsing both into one class would force either repeated expensive setup per transaction, or an awkward static/singleton workaround instead of the lifecycle Keycloak already manages correctly.

    2. Why did it matter, concretely, that UserStorageProvider/ UserStorageProviderFactory moved from keycloak-server-spi into keycloak-model-storage as of Keycloak 26.4+?

      Model answerA POM written against only keycloak-server-spi/keycloak-server-spi-private — a reasonable guess based on earlier Keycloak versions, or based on the names alone — would fail to compile against 26.8.2, because the two classes this provider's factory directly implements (UserStorageProvider, UserStorageProviderFactory) genuinely aren't in either of those jars anymore; confirmed directly by unzipping both and finding no such classes inside. This chapter's POM instead declares both keycloak-server-spi (for KeycloakSession, CredentialInputValidator, etc.) and keycloak-model-storage (for the two classes that moved), both pinned to the exact 26.8.2 version confirmed to exist on Maven Central and inside the real running image.

    3. Walk through why LegacyStaffUserAdapter had to override credentialManager() even though it extends AbstractUserAdapter, which is documented as implementing "everything but getUsername()."

      Model answerThat documentation turned out to have one real exception, found by the compiler rather than by reading ahead: UserModel.credentialManager() is left abstract all the way down through AbstractUserAdapter, because Keycloak's newer credential-manager API was added after that base class's original "everything but getUsername" design. Without an override, the class failed to compile with javac naming the missing method directly. The fix bridges to Keycloak core's own org.keycloak.credential.UserCredentialManager, constructed with this adapter's own session/realm/this, which forwards isValid() calls straight through to this class's own CredentialInputValidator implementation — so the adapter never has to implement SubjectCredentialManager's much larger surface itself.

    4. A colleague registers your provider with -s parentId="riverside-health" instead of the realm's actual UUID. What goes wrong, and why does it fail silently instead of with a clear error?

      Model answerA realm's REST id field is a generated UUID, distinct from its human-readable realm name field — confirmed directly in this chapter by querying kcadm.sh get realms/riverside-health --fields id,realm and seeing two genuinely different values. The component creation call still succeeds (HTTP 201) because nothing in the Admin REST API validates that a given parentId actually corresponds to a real realm before accepting it — the component is created, but as an orphaned record with no real parent, so Keycloak's federation machinery never consults it when resolving a login. The failure mode downstream (a direct-grant login returning user_not_found for a user who genuinely exists in the CSV) looks exactly like the provider itself is broken, when the actual bug is one misidentified field in the registration call.

    5. A teammate says "I added legacyEmployeeId to getAttributes(), so of course it shows up in the Admin REST API's response" — and it doesn't. What's actually going on, and how do you fix it?

      Model answerReturning an attribute from a UserModel's getAttributes() is necessary but not sufficient for it to appear in the REST representation — the realm's Declarative User Profile (chapters 22/24's concept) governs which attributes are exposed at all. An attribute not declared in that schema is an "unmanaged attribute," and with the realm's unmanagedAttributePolicy left unset (the effective default), it is silently dropped from the representation with no error — confirmed directly in this chapter by watching legacyEmployeeId and department vanish from a federated user's JSON despite the provider genuinely returning them. The fix is a realm configuration change, not a code change: PUT /admin/realms/{realm}/users/profile with unmanagedAttributePolicy set to ADMIN_VIEW (or a broader option), after which both attributes reappeared with zero changes to the provider itself.

    6. Why does this chapter's provider extend AbstractUserAdapter rather than AbstractUserAdapterFederatedStorage, and when would the opposite choice be the right one?

      Model answer AbstractUserAdapter fits a provider whose backing store already holds every field the adapter needs to expose (username, name, email, custom attributes) and that has no way to accept writes back from Keycloak at all — exactly this chapter's situation, where the legacy HR system is read-only from Keycloak's point of view and every update method throwing ReadOnlyException by default is the correct behavior, not a limitation worked around. Per Keycloak's own javadoc, AbstractUserAdapterFederatedStorage instead stores profile fields as attributes in Keycloak's own federated-storage tables, which is the right choice when a provider's external store is missing some fields Keycloak itself needs to track (session-related metadata, data a read-only external system has no field for) — letting Keycloak's own database fill the gap around an external store that's deliberately only partially authoritative, rather than fully authoritative the way this chapter's CSV is treated.
