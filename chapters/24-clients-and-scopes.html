24. Clients, Client Scopes & Protocol Mappers

Chapter 13 gave you OAuth's abstract Client and Scope vocabulary. Chapter 15 showed you that a provider can add a custom claim to a token, and promised the mechanism — a Keycloak protocol mapper — would get full depth "in chapter 24." This is that chapter: registering a real OAuth client in the northwind-apps realm, giving it client-scoped roles, bundling protocol mapper configuration into a reusable client scope, and watching a real custom department claim land in a real access token, ID token, and UserInfo response — pulled straight from a Keycloak user attribute, no code written, no application involved.

Why this matters

Registering a client is the single most common configuration task an IAM specialist does on Keycloak, and it is also the single most common place security gets quietly weakened: a confidential client marked public by mistake, a redirect URI wildcard broader than it needs to be, a claim an application depends on that silently never arrives because of a Keycloak behavior nobody read the release notes for. This chapter's lab hit exactly that last failure mode live, for real, while building the department-claim mapper below — and fixing it, not just describing it, is the chapter's most useful lesson.

Recall from chapters 13 and 15

Chapter 13 defined OAuth's Client role ("the app" requesting access on a resource owner's behalf) and Scope ("a client-requested, space-separated identifier naming a slice of access") in the abstract, vendor-agnostic terms RFC 6749 uses. Chapter 15 then showed that OIDC's standard scopes (openid, profile, email) unlock only a fixed, advertised bundle of claims — and that a custom claim (its example was a hypothetical tenant_id) requires the provider to define and advertise one itself, closing with: "in Keycloak, this is exactly what a client scope's protocol mappers configure... the admin-console screen for configuring it is covered in chapter 24." Every section below is that promise getting kept, concretely, against a real running Keycloak instance.

Registering a client: confidential vs. public, for real

A Keycloak client is the realm-scoped record of one OAuth/OIDC Client (chapter 13's role) — northwind-apps plays the Authorization Server, and every application that wants to authenticate against it needs its own client record. Two settings decide almost everything else about how that client behaves:

  • Confidential vs. public (Keycloak's publicClient field). A confidential client can keep a secret — it runs somewhere an attacker can't read its source (a backend server), so Keycloak issues it a client secret and requires that secret at the token endpoint alongside any authorization code. A public client runs somewhere an attacker genuinely can read everything — a browser SPA, a mobile app's decompiled binary — so it gets no secret at all; chapter 13's PKCE mechanism is what protects its code exchange instead.
  • Standard flow, direct access grants, service accounts (Keycloak's standardFlowEnabled, directAccessGrantsEnabled, and serviceAccountsEnabled toggles) — which of chapter 13-14's grant types this specific client is allowed to use at all. A client with every toggle off can't obtain a token through any grant; Keycloak doesn't infer sensible defaults from how you plan to use it.

Pitfall — tying back to chapter 13's redirect_uri lesson, now with a Keycloak-specific wrinkle

Keycloak's own Server Administration Guide (fetched live for this chapter) confirms the same exact-match rule chapter 13 taught against RFC 6749: "Exact (case sensitive) string matching is used to compare valid redirect URIs." But Keycloak's Valid Redirect URIs field also supports a trailing wildcard (https://host.com/path/*) — and the docs are explicit that a bare * ("allow any http or https redirect URI") "should not be used in production environments." A wildcard that's broader than it needs to be reintroduces exactly the risk chapter 13's live demo-server finding demonstrated: the narrower the registered pattern, the less surface an attacker gets. This chapter's lab registers a path-scoped wildcard (https://dashboard.northwindapps.internal/*) rather than a bare *, for exactly this reason.

If you see this: a protocol mapper configured correctly, but the claim never shows up anywhere

Before suspecting the protocol mapper itself, check whether the source attribute is even being stored. A Keycloak 26 realm's declarative User Profile only persists attributes it has explicitly declared; anything else is silently discarded on write unless unmanagedAttributePolicy is set to ENABLED (or one of the admin-only variants) on that realm's user profile configuration. The failure mode is specifically deceptive because nothing errors anywhere in the chain — the kcadm.sh update call reports success, the mapper's own configuration is perfectly correct, and the claim is simply, quietly, never there.

Client roles: scoped to one client, not the whole realm

Chapter 23's realm roles (tenant-admin, support-agent, platform-engineer) are visible and assignable across the entire northwind-apps realm. A client role is different in exactly one way that matters: it only means something to the one client it belongs to. "Admin of the Northwind Dashboard app" is not the same permission as "admin of the whole realm," and Keycloak models that distinction by attaching the role to the client's own role list, not the realm's.

Client scopes: reusable bundles of claim configuration

Chapter 13 defined OAuth's Scope as a client-requested identifier naming a slice of access. A Keycloak client scope is the concrete object that makes a scope name mean something: a named, realm-level, reusable bundle of protocol mappers (each one adding one claim) and role-scope mappings, which can be attached to any number of clients as either a default scope (included automatically in every token this client requests — no scope= parameter needed) or an optional scope (only included if a token request explicitly asks for it by name). Reusability is the point: define northwind-profile once, attach it to every Northwind-internal client that needs the same claim, and a later change to the mapper updates every one of them at once.

  1. Register northwind-dashboard itself — a confidential, standard-flow client, with a narrowly-scoped wildcard redirect URI per the pitfall above:

    $ kcadm.sh create clients -r northwind-apps \
    -s clientId=northwind-dashboard \
    -s name="Northwind Dashboard" \
    -s description="Staff-facing internal dashboard for Northwind Apps employees" \
    -s publicClient=false -s standardFlowEnabled=true \
    -s directAccessGrantsEnabled=false -s serviceAccountsEnabled=false \
    -s 'redirectUris=["https://dashboard.northwindapps.internal/*"]' \
    -s 'webOrigins=["https://dashboard.northwindapps.internal"]' -i

Protocol mappers: the department claim, paying off chapter 15

A protocol mapper is the single rule that decides one claim: where its value comes from (a user attribute, a hardcoded value, a role name, a group membership) and which token types it's allowed into. Three independent boolean flags on every mapper — id.token.claim, access.token.claim, userinfo.token.claim — control exactly chapter 15's "ID token vs. UserInfo" distinction per claim, per mapper, not as a single global switch.

  1. Add the department mapper to the northwind-profile scope:

    $ SCOPE_ID=11192168-40ec-49ef-a419-2abd01c09fcd

$ kcadm.sh create client-scopes/$SCOPE_ID/protocol-mappers/models -r northwind-apps \
    -s name=department -s protocol=openid-connect \
    -s protocolMapper=oidc-usermodel-attribute-mapper \
    -s 'config={"user.attribute":"department","claim.name":"department",
         "jsonType.label":"String","id.token.claim":"true",
         "access.token.claim":"true","userinfo.token.claim":"true",
         "multivalued":"false"}' -i

Key idea

Nothing about this mechanism is OIDC-specific magic — it's a declarative rule ("read this attribute, write it under this claim name, into these token types") evaluated fresh every time a token is issued. That's exactly why the claim showed up in a token requested via direct access grants with no code changed anywhere: the mapper lives on the client scope, not on any particular grant type, and every grant that reaches the token endpoint runs the same mapper pipeline.

Case study — Northwind Apps' two very different clients

Northwind Apps's own engineers need an internal tool to manage customer tenants, review support tickets, and check platform health — northwind-dashboard, the confidential, standard-flow client this chapter actually built. It runs on a server Northwind controls, so it can safely hold a client secret, and its dashboard-admin client role grants admin rights within that one tool only — not realm-wide, and not transferable to any other Northwind application. Separately, Northwind's actual product — the thing its B2B customers log into — will eventually be a single-page application running in a browser Northwind doesn't control at all, registered as northwind-spa: a public client with no secret, PKCE doing the work a secret would otherwise do, built for real in chapter 35's SPA-integration lab. Naming it here, now, rather than building it, mirrors a real platform team's own sequencing: internal tooling clients get registered and iterated on long before the customer-facing product's own OIDC integration is ready to ship.

Common mistakes

  • If you see a claim that a correctly-configured protocol mapper should produce simply never appear anywhere — not in the ID token, not in the access token, not in UserInfo — the cause, before suspecting the mapper, is very likely that the source user attribute was never actually persisted: Keycloak 26's declarative User Profile silently drops any attribute not declared in the realm's schema unless unmanagedAttributePolicy is enabled. Check kcadm.sh get users/profile and the user's own stored attributes before touching the mapper.
  • If you see a public client with a client secret configured "just in case," the cause is confusing "has a secret" with "is secure" — a secret embedded in browser-readable or decompiled mobile code isn't a secret at all; the fix is marking the client public and relying on PKCE, not hiding a secret somewhere a determined attacker can still extract it.
  • If you see a client's Valid Redirect URIs field set to a bare * "to make testing easier," the cause is the exact gap chapter 13's live demo-server finding demonstrated — Keycloak's own documentation explicitly warns against this in production for the same reason.
  • If you see a reader assign a client role the way they'd assign a realm role and expect it to show up in a different application's permission check, the cause is missing that a client role's meaning — and its visibility in a token's resource_access claim — is scoped to the one client it was created under, never realm-wide.
  • If you see a client scope attached but its claims still missing from a token, check whether it was attached as a default scope or an optional one — an optional scope only shows up in a token if the request's own scope= parameter names it explicitly.

Glossary terms introduced here

Takeaways

  • A Keycloak client is the realm-scoped record of chapter 13's abstract OAuth Client role; publicClient, standardFlowEnabled, directAccessGrantsEnabled, and serviceAccountsEnabled together decide what it's allowed to do.
  • Confidential clients get a real client secret and are meant to run somewhere that secret stays hidden; public clients get no secret and rely on PKCE instead — mismatching the two is a real, exploitable security mistake, not a style choice.
  • Keycloak's Valid Redirect URIs field enforces the same exact-match comparison RFC 6749 requires (chapter 13), with a documented, narrowly-scoped wildcard extension — and an explicit warning against the bare * wildcard in production.
  • Client roles are scoped to the one client they're created under — distinct from chapter 23's realm roles, which apply across the whole realm — confirmed live by checking that a client role never appears in the realm's own role list.
  • A client scope is a reusable, named bundle of protocol mapper configuration, attachable to any number of clients as either a default scope (always included) or an optional scope (only included if explicitly requested) — the concrete Keycloak mechanism behind chapter 13's abstract OAuth "Scope."
  • A protocol mapper's three flags — id.token.claim, access.token.claim, userinfo.token.claim — are independent per mapper, letting a single claim be routed to exactly the token types it's actually needed in.
  • This chapter's lab minted a real token for a real user and confirmed, by decoding it directly, a real custom department claim present in the access token, the ID token, and the UserInfo response — paying off chapter 15's forward-reference to "a custom claim via a Keycloak protocol mapper" with an actual working example, not a narrated one.
  • A live, genuinely encountered Keycloak 26 behavior — declarative User Profile silently dropping undeclared attributes — is exactly the kind of failure a correctly-configured protocol mapper can't fix on its own, because the problem is upstream of the mapper entirely.
  • northwind-spa is named, not built, in this chapter — deliberately, mirroring how a real platform team registers its internal tooling clients long before its customer-facing product's own OIDC integration is ready; chapter 35 builds it for real.
