    Part VII — Fine-Grained Authorization ~60 min Hands-on lab

    37. Keycloak Authorization Services

    Every chapter since 23 has asked Keycloak one kind of question: "does this subject hold this role?" That's enough for an admin to pre-decide who can do what, in advance, for an entire application. It is not enough for a document-sharing API where one customer's user wants to let one specific colleague view one specific document, a decision no admin pre-assigned and no static role can express. Authorization Services is Keycloak's answer: turn a client into a real resource server that registers its own protected resources, scopes, and policies with Keycloak, and asks it — per request, at runtime — "can this specific subject do this specific thing to this specific resource?" This chapter builds exactly that, for real, and runs the whole UMA 2.0 exchange end to end: a real permission ticket, a real Requesting Party Token, one real permitted call, and one real denied one.

    Why this matters

    An IAM specialist who only knows RBAC hits a wall the moment a product needs resource-level, delegated, or relationship-shaped access — "share this file with Priya," "only the clinicians currently treating this patient," "only during this maintenance window." Keycloak's Authorization Services is the concrete, testable place Part I's authorization-model survey (chapter 6) stops being theory. This chapter's lab also hits two genuinely non-obvious findings worth knowing before you ever rely on them in production: a resource must already carry the scope you intend to protect it with before a permission can reference that pair, and Keycloak 26.8.2 has fully removed the JavaScript/"script" policy type from its REST API — not deprecated, not hidden behind a flag, gone — confirmed live in this chapter's own lab, not assumed from older documentation.

    What concept is this?

    Chapter 6 surveyed ACL, RBAC, ABAC, PBAC, ReBAC, and Zero Trust as authorization models in the abstract — rules that decide what a subject can do. Keycloak's Authorization Services is a concrete policy-based access control (PBAC) engine, built on top of chapter 24's clients/ client-scopes and chapter 23's roles/groups, that can express ABAC-flavored and ReBAC-flavored policies on top of its own resource/scope model. It is also this course's first real encounter with UMA 2.0 (User-Managed Access), the OAuth-based protocol chapter 7's "resource owner in the loop" federation concept was always building toward.

    A resource server, concretely: your app as PEP, Keycloak as PDP

    Up to chapter 36, a client's token simply carried roles, and the application decided for itself what those roles meant. Authorization Services inverts that: the application becomes a thin Policy Enforcement Point (PEP) — it intercepts the request and enforces whatever Keycloak decides — while Keycloak itself becomes the Policy Decision Point (PDP), the place policy is actually evaluated. This chapter's lab plays both roles directly against Keycloak's own REST surface, with no separate downstream application, so every HTTP exchange shown is the real protocol, not a simulation layered on top of it.

    In Keycloak

    A client becomes a resource server the moment Authorization Enabled is switched on under its Settings tab (requires a confidential client — publicClient=false — since the client itself must authenticate to call Keycloak's Protection API). That one toggle adds an entire Authorization tab with Resources, Authorization Scopes, Policies, and Permissions sub-tabs — exactly the REST sub-resources this chapter's lab drives directly.

    Resources, (authorization) scopes, policies, and permissions — how they connect

    Four new objects, each with one job, chained together into a single yes/no decision:

    • Resource — the protected thing itself: a document, a tenant, an account. Has a name, an optional type, optional URIs, and an owner (the client, by default, or a specific user if owner-managed access is turned on).
    • Authorization scope — a named action a resource can be accessed through (e.g. view, edit), attached to one or more resources. Not the same thing as an OAuth scope — the next slide draws that line explicitly, since this course has already overloaded the word "scope" twice.
    • Policy — a reusable rule (role-based, user-based, time-based, …) that evaluates to a vote, independent of any specific resource. The same policy can back many permissions.
    • Permission — ties a resource (or a scope, for scope-based permissions) to one or more policies, and declares a decision strategy for combining their votes into one PERMIT/DENY.
    Pitfall — confirmed live in this chapter's lab

    Creating a resource and a scope separately is not enough to reference both together from a scope-based permission. This lab's first attempt to create the view-quarterly-report permission failed outright with Scope [view] is not associated with any of the resources set to the permission [invalid_request] — the resource has to be updated to list that scope in its own scopes array first. Creating a resource and a scope that both exist in the same resource server does not implicitly attach one to the other.

    Two different "scopes" — naming the overload explicitly

    This course has now used the word scope for three genuinely different things, and conflating them is one of the easiest mistakes to make once Authorization Services enters the picture:

    The word "scope" across this course — three distinct mechanisms, not variations of one idea
    OAuth scope (chapters 13, 24)Authorization scope (this chapter)
    Negotiated when a token is requested — part of the authorization/token request itself (scope=openid profile)Attached to a resource, ahead of time, in the resource server's own authorization model — never appears in a token request

    Chapter 24's client scope and this chapter's authorization scope are genuinely unrelated mechanisms that happen to share a name purely by historical accident in the OAuth/UMA ecosystem — treat them as two different vocabularies, not one concept with two names.

    Policy types — and a real finding about JavaScript policies

    Keycloak ships several built-in policy types. This chapter's lab queried the live policy-provider list directly from a running 26.8.2 instance rather than trusting any cached memory of older documentation:

    GET /admin/realms/northwind-apps/clients/<resource-server-id>/authz/resource-server/policy/providers

  {"type":"role","name":"Role","group":"Identity Based"},
  {"type":"resource","name":"Resource-Based","group":"Permission"},
  {"type":"scope","name":"Scope-Based","group":"Permission"},
  {"type":"client","name":"Client","group":"Identity Based"},
  {"type":"time","name":"Time","group":"Time Based"},
  {"type":"user","name":"User","group":"Identity Based"},
  {"type":"client-scope","name":"Client Scope","group":"Identity Based"},

  {"type":"aggregate","name":"Aggregated","group":"Others"} ]
    Live-verified finding

    JavaScript ("script") policies do not appear in this list at all — and this lab went a step further: attempting to create one by calling the old .../policy/js endpoint directly returned Resource not found for url: .../authz/resource-server/policy/js, a plain HTTP 404. This is not a disabled feature flag or a hidden console toggle — the REST endpoint for script policies simply does not exist in this build. If you're reading older Keycloak material that shows a "JavaScript policy" tab, it describes a feature this version has fully removed, not deprecated; plan any policy logic that would have needed custom JS as a role/user/group/time/client/aggregate combination instead, or as a custom Policy SPI provider (chapter 39 covers writing one).

    Role, User, Client, Group, Client Scope policies all check identity-shaped conditions (does the subject/client hold this role, is it this specific user/client, is it in this group, did the token carry this client scope). Time checks a notBefore/expires window and day-of-week/hour range. Resource-Based and Scope-Based aren't really policies at all in the same sense — they're how permissions themselves are categorized. Aggregated nests other policies as one reusable unit with its own internal decision strategy, distinct from setting a decision strategy directly on a permission (next slide draws that distinction out).

    Decision strategies: combining multiple policy votes into one answer

    A permission can reference more than one policy. When it does, its decision strategy decides how their individual votes combine into one PERMIT/DENY:

    • Unanimous (Keycloak's default) — every referenced policy must vote PERMIT. One DENY anywhere fails the whole permission.
    • Affirmative — at least one referenced policy voting PERMIT is enough, even if every other one votes DENY.
    • Consensus — majority rules: more PERMIT votes than DENY votes wins; a tie denies.

    The exact same mechanism exists one level up, inside an Aggregated policy, which nests several child policies and applies its own decision strategy to produce a single combined vote — useful when the same "role OR time-window" combination needs to be reused across many permissions without restating it each time.

    UMA 2.0 end to end: ticket first, token second

    UMA 2.0 (User-Managed Access, an OAuth-based profile originally from the Kantara Initiative) is the wire protocol underneath all of this. Its defining move: a request for a protected resource is always rejected first — not with a login redirect, but with a permission ticket — and only a second, separate exchange at the token endpoint can turn that ticket into a real, scoped Requesting Party Token (RPT).

    In a real deployment, step 3's 401 genuinely carries a WWW-Authenticate header of the form UMA ticket="...", as_uri="https://.../realms/northwind-apps" so the client knows both the ticket and where to exchange it. This lab calls Keycloak's Protection API directly to obtain the ticket (playing the resource-server half of step 2-3 itself) rather than fronting it with a separate web-server process — the wire format of steps 2, 4, and 5 is identical either way, and that format is exactly what this lab's own curl commands show next.

    Case study: Northwind Apps needs resource-owner delegation, not just roles

    Case study — Northwind Apps

    Northwind Apps, the B2B SaaS company running multi-tenant customer workspaces since chapter 2, ships a document-sharing feature inside its product: any customer's user can create a document and decide, themselves, which specific colleagues may view it — a decision made by that document's owner, per document, not pre-assigned by a Northwind admin the way chapter 23's realm/client roles are. A static role like document-viewer can't express "Priya specifically, for this one quarterly report, and no other document" — that's exactly UMA's resource-owner-in-the-loop model chapter 7 previewed conceptually, and exactly what this chapter builds for real: Northwind's northwind-docs-api resource server registers each shared document as its own Resource, and a role-based policy stands in for "has editor-level trust on this workspace" as the first cut — a later, more advanced Northwind feature (chapter 38 previews this) could swap the role policy for a genuine per-document ReBAC-style ownership check without changing anything else in this chapter's resource/scope/permission structure.

    1. A fresh permission ticket (tickets carry their own expiry and are meant to be single-use, so a second attempt gets its own ticket, not the one amara already redeemed), then the identical exchange — same resource, same scope, same policy — but as sam.chen, who was deliberately never granted northwind-editor:

      curl -s -i -X POST "http://localhost:18137/realms/northwind-apps/protocol/openid-connect/token" \
  -H "Authorization: Bearer <sam's own access token>" \
  --data-urlencode "grant_type=urn:ietf:params:oauth:grant-type:uma-ticket" \

  --data-urlencode "client_id=northwind-docs-api" \

      HTTP/1.1 403 Forbidden
Content-Type: application/json

{"error":"access_denied","error_description":"request_submitted"}

      A real, clean 403 Forbidden — confirmed reproducible across two separate fresh tickets, so this isn't a ticket-reuse artifact. The genuine surprise is the error_description itself: "request_submitted", not something like "not_authorized". Report this plainly rather than over-interpreting it: this is simply the error-description string Keycloak 26.8.2 happens to return for a UMA ticket denial under this configuration, confirmed live by this lab, not a documented, stable contract to build application logic against — an application should key its own error handling off the 403 status and "access_denied" error code, not off this specific description text.

    Common mistakes

    • A real finding from writing this chapter: creating a resource and an authorization scope separately does not attach one to the other. If a scope-based permission rejects with Scope [...] is not associated with any of the resources set to the permission, the fix is to update the resource itself to list that scope in its own scopes array — confirmed directly in this chapter's own lab, on the very first attempt.
    • Do not assume Keycloak 26.8.2 still supports JavaScript/"script" policies because older tutorials show one — this lab confirmed live that the REST endpoint for creating one (.../policy/js) returns a flat 404, and the policy-provider list never lists a js/script type at all. Model that logic with role/user/group/time/client/ aggregate policies instead, or a custom Policy SPI provider (chapter 39).
    • Don't confuse an OAuth scope (chapters 13, 24 — negotiated when a token is requested) with an authorization scope (this chapter — attached to a resource, evaluated at decision time) just because both are called "scope" — they are unrelated mechanisms that happen to share a name.
    • If a UMA ticket exchange returns 403 access_denied, don't assume the specific error_description text (e.g. "request_submitted") carries stable meaning across versions or configurations — key error handling off the HTTP status and the error field, not the description string, which this lab confirmed can read surprisingly even when nothing is actually "submitted" anywhere.
    • Reusing an already-redeemed permission ticket for a second subject does not work — tickets are meant to be exchanged once; this lab always requested a fresh ticket per exchange rather than reusing one across both amara's and sam's requests.
    • Setting a permission's decision strategy to AFFIRMATIVE "to make testing easier" and then shipping it that way quietly weakens every policy attached to that permission down to "any one of these is enough" — this lab deliberately reverted back to UNANIMOUS with a single, genuinely necessary policy once the decision-strategy demonstration was done.

    Glossary terms introduced here

    Takeaways

    • Authorization Services turns a confidential client into a real resource server: your application becomes a Policy Enforcement Point, and Keycloak itself becomes the Policy Decision Point that actually evaluates access.
    • A resource, an authorization scope, a policy, and a permission each have one job — a permission is the join point that ties a resource+scope pair to one or more policies and a decision strategy.
    • A resource must list its authorization scopes in its own scopes array before a scope-based permission can reference that resource+scope pair — confirmed live, not assumed, when this lab's first attempt failed with exactly that error.
    • "OAuth scope" and "authorization scope" are two genuinely unrelated mechanisms that share a name by historical accident — one is negotiated when a token is requested, the other is attached to a resource and evaluated at decision time.
    • Keycloak 26.8.2's live policy-provider list is regex/role/resource/scope/client/time/user/ client-scope/group/aggregate — JavaScript ("script") policies are fully removed from the REST API in this version, confirmed by a 404 on the old endpoint, not merely deprecated.
    • Decision strategy (Unanimous/Affirmative/Consensus) genuinely changes outcomes — this chapter's lab proved it live: the identical request from the identical role-less user flipped from 403 to 200 purely by changing a permission's decision strategy from Unanimous to Affirmative.
    • UMA 2.0's defining shape is two separate exchanges: a permission ticket first (from the Protection API), then a ticket-for-RPT exchange at the token endpoint — never one combined step.
    • A Requesting Party Token's authorization.permissions claim names, concretely, which resource and scope this exact subject was just granted — computed at request time from live policy evaluation, unlike a pre-assigned role.
    • Keycloak's "Policy evaluate" tool simulates a policy decision for a specific user without issuing any real tokens — a faster debugging loop than a full UMA round trip once resources and policies already exist.
    • Northwind Apps's document-sharing feature needs UMA's resource-owner-in-the-loop model precisely because a static, pre-assigned role can't express "this one person, for this one document" the way a per-resource permission can.

    Self-check

    Click a question to reveal a model answer. Try answering it yourself first — the point is to check your own reasoning against it, not to read the answer first.

    1. A colleague says "Authorization Services just lets Keycloak check roles, like chapter 23 already does." What's wrong with that description?

      Model answerIt understates what's new. Chapter 23's roles are pre-assigned, statically, independent of any specific resource — Keycloak never evaluates them against a particular document or record at request time. Authorization Services introduces per-resource, per-scope, runtime decisions: a permission ties a specific resource+scope pair to one or more policies (which can be role-based, but can equally be time-based, user-based, or aggregated) and evaluates that combination fresh on every request, through a real PEP/PDP exchange — not a cached role check.

    2. This chapter's lab got "Scope [view] is not associated with any of the resources set to the permission" on its first attempt to create a permission. What was actually missing, and why didn't creating the resource and the scope separately already solve it?

      Model answerThe resource's own scopes array never listed the view scope — creating a resource and creating a scope are two independent REST calls that don't implicitly link to each other. A scope-based permission references a resource+scope pair, and Keycloak requires that pairing to already exist on the resource itself before a permission can be built on top of it. The fix was a separate update call adding the scope to the resource's scopes array.

    3. Distinguish an OAuth scope from an authorization scope, using this chapter's own client scope vs. authorization scope comparison.

      Model answerAn OAuth scope (chapter 13/24) is negotiated when a token is requested — it limits what a token carries before any specific resource is ever involved, and in Keycloak it's implemented as a client scope: a reusable protocol-mapper/role-mapping bundle attached to a client. An authorization scope (this chapter) is attached to a resource inside a resource server's own authorization model, names an action like "view" or "edit," and is evaluated by policy at decision time, long after the token already exists — it never appears in a token request at all. They share a name purely by historical accident.

    4. This chapter's lab confirmed Keycloak 26.8.2 has no JavaScript/"script" policy type. What exactly was checked to confirm that, and why is that stronger evidence than just not seeing one in the admin console?

      Model answerTwo things were checked live: the policy-provider list (GET .../policy/providers), which lists regex/role/resource/scope/client/time/user/client-scope/group/aggregate with no js/script entry, and a direct attempt to create one via the old .../policy/js REST endpoint, which returned a flat 404 ("Resource not found for url"). The second check is stronger because a missing console tab could just mean a UI feature flag is off while the underlying REST capability still exists — a 404 on the endpoint itself means the capability genuinely isn't there to call, by any client.

    5. In this chapter's decision-strategy demo, sam.chen (who never held the northwind-editor role) got a 403 under Unanimous and a 200 under Affirmative for the exact same request. Explain why, referencing the specific policies involved.

      Model answerThe permission referenced two policies: a role policy (requires northwind-editor, which sam.chen lacked — votes DENY for him) and a client policy (votes PERMIT for any token issued to the northwind-docs-api client, which is true for every token in this lab, including sam's). Under Unanimous, every referenced policy must vote PERMIT, so the role policy's DENY failed the whole permission (403). Under Affirmative, only one PERMIT vote is needed, and the client policy's PERMIT alone was enough to flip the outcome to 200 — with no change to sam's actual role membership at all.

    6. Why does UMA 2.0 require two separate exchanges — a permission ticket first, then a token request — instead of just returning an RPT directly on the first request?

      Model answerThe first request usually doesn't yet carry a usable, correctly-scoped credential from the requesting party at all — it may be genuinely unauthenticated, or carry a token that was never going to be evaluated against this specific resource. The permission ticket exists to name, precisely, which resource and scope the eventual access decision will be about, independent of who ends up presenting it. Splitting the flow lets the requesting party authenticate (or use an existing token) and present it alongside that specific ticket at the token endpoint, so Keycloak can evaluate policy against a real, known subject and a precisely scoped request in one well-defined step, rather than trying to collect both an unauthenticated resource request and a valid identity in a single round trip.
