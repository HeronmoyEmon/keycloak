    36. Service-to-Service & Machine-to-Machine Auth

    Not every caller of a protected API is a person sitting at a browser. A nightly batch job, a fraud-scoring pipeline, or a monitoring agent needs to authenticate too — with no user to log in, no browser to redirect, and ideally no standing password baked into a config file. Keycloak's answer is the service account: a dedicated, non-human identity attached to a client, reachable only through the OAuth 2.0 client credentials grant, and governed by the exact same role-mapping mechanics as any human user. This chapter builds one for real, scopes it down to the narrowest access that still does its job, and proves — with real HTTP responses, not assumptions — exactly where that scope boundary actually sits.

    Why this matters

    Machine-to-machine (M2M) credentials are a favorite target precisely because nobody is watching a login screen for them — a service account with broad, unreviewed access is a standing, silent liability until the day it's abused. An IAM specialist who can only secure human logins has covered half the attack surface. This chapter's lab also puts chapter 27's kc-admin-api finding to the test for the first time against a client that doesn't get it for free: correct role mappings alone were not enough to call the Admin REST API in this chapter's own test run — the kc-admin-api scope chapter 27 noticed on admin-cli's token turned out to be a separate, required gate, and a custom client has to be wired up for it deliberately. The resulting distinction — authentication failing versus authorization failing, a flat 401 versus a clean 403 — is exactly the kind of debugging instinct this role needs.

    What concept is this?

    Chapter 13 defined the client credentials grant (RFC 6749 §4.4): the client authenticates directly to the token endpoint with its own credentials — a client ID and secret, no user, no browser, no redirect — and receives an access token scoped to itself, not to any resource owner. Chapter 14 drilled that mechanic further with introspection and revocation against a public demo server's m2m client. This chapter is that same grant, for the first time against a real Keycloak realm this course controls, with a concrete payoff: Keycloak's own service account feature is simply "give a client a dedicated user, so the client credentials grant has someone to issue a token as."

    Recall: the client credentials grant, no user involved at any point

    Before touching Keycloak specifically, the shape of the grant chapter 13 taught is worth having fresh: two parties, one request, no redirect.

    Chapters 13-14 ran this grant against a public demo server's m2m client, which simply existed already. This chapter's open question is the one that mattered less there: who, inside Keycloak, is the subject of the token this grant produces — and the answer turns out to be a real, addressable user record, not an abstraction.

    Service accounts: a dedicated user record, not a special case

    Enable Service accounts roles on a confidential client and Keycloak does something very literal: it creates a real User record in that realm, named service-account-<clientId>, permanently tied to that one client. This chapter's lab confirmed it directly — a plain GET users?username=service-account-fraud-detection-service returns a real user object, with a real internal id, indistinguishable in shape from any human user's record.

    In Keycloak

    A client's Service account roles tab in the Admin Console is a UI front end over exactly the same mechanism this lab used via REST: it edits role mappings on that client's dedicated service-account user, through the identical users/{id}/role-mappings/clients/{clientUuid} resource any human user's client-role assignment goes through. There is no separate "service account permission system" — it is the ordinary user-role-mapping machinery chapter 23 covered, pointed at a user Keycloak happens to have created for you.

    Least privilege for a machine caller: why the exact role you pick matters

    Keycloak's own built-in realm-management client ships a full menu of admin capabilities as client roles — view-users, manage-users, view-clients, manage-realm, and more — each independently grantable. A fraud-detection service that only ever needs to read account data to score it for risk has no legitimate reason to hold manage-users, which can create, modify, and delete any user in the realm. Chapter 9's threat landscape named exactly this risk: a compromised service credential with broad standing access turns one leaked secret into a realm-wide breach, where a narrowly scoped credential limits the same leak to whatever that one role actually permits. Chapter 23 already showed this mechanism (client roles, composite roles) for human users; this chapter is the identical mechanism applied to a non-human caller, where the stakes of over-granting are arguably higher, because nobody is watching a login screen to notice the account behaving strangely.

    A narrowly-scoped view-users role versus a broad manage-users role, for a read-only M2M caller like Meridian Trust's fraud-detection service
    view-users (narrow, read-only)manage-users (broad, read-write)
    A leaked client secret only ever lets an attacker read user data, never alter or delete itA leaked client secret lets an attacker create, modify, or delete any user in the realm
    Matches exactly what a read-only scoring service actually needs to do its jobGrants far more than the service's own stated purpose requires
    An auditor reviewing this client's access sees a role name that matches its actual behaviorAn auditor has to separately verify the service never actually uses its write access, rather than reading that fact off the role name
    Composite role already includes query-users/query-groups — covers realistic read needs without extra grantsComposite role includes everything view-users does, plus write — no way to "opt out" of the write half once granted
    Pitfall

    "It's just an internal service, nobody will misuse it" is not a least-privilege argument — it's an argument that the blast radius of a credential leak doesn't matter, which is precisely backwards. The whole point of scoping a service account narrowly is that it still protects you on the day the credential leaks anyway, which chapter 9 already established is a question of when, not if, at sufficient scale.

    Case study: Meridian Trust scopes its fraud-detection service down to read-only

    Case study — Meridian Trust

    Meridian Trust, the retail bank running under PCI-DSS obligations since chapter 11, operates a nightly fraud-scoring pipeline that pulls account and user metadata out of its Keycloak-backed identity layer to feed a risk model — never a browser session, never a human operator, running unattended on a schedule. Before this chapter's redesign, that pipeline's Keycloak client held manage-users "just in case a later feature needed write access" — exactly the over-provisioning chapter 9 warns against, and exactly the kind of finding a PCI-DSS assessor reviewing least-privilege controls would flag on sight. This chapter's lab is that fix, concretely: a fraud-detection-service client whose service account holds view-users alone, proven — not assumed — to still complete its actual job (reading account data) while a write attempt now fails loudly and immediately, long before any assessor ever has to ask about it.

    Lab: the real fix — a separate, scope-gated audience check

    Inspecting the realm's own client scopes turned up the exact kc-admin-api scope chapter 27 had already named on admin-cli's token, with a self-describing definition confirmed live on this realm, not guessed:

    docker compose exec keycloak /opt/keycloak/bin/kcadm.sh get client-scopes -r meridian-trust
    {
  "name": "kc-admin-api",
  "description": "Grants access to the Keycloak Admin REST API by adding its required audience to the token",
  "protocolMappers": [ { "protocolMapper": "oidc-admin-api-audience-mapper", ... } ]
}

    That scope was present in the realm but not among fraud-detection-service's default or optional client scopes — so its tokens never requested or received it, and the Admin REST API's authentication layer rejected the token before role mappings were even considered. Adding it as a default scope and re-requesting a token fixed it:

    docker compose exec keycloak /opt/keycloak/bin/kcadm.sh update \
  "clients/$CID/default-client-scopes/<kc-admin-api scope id>" -r meridian-trust

    A fresh token now decodes with "scope": "kc-admin-api email profile" and an aud array that gained http://localhost:8080/admin/realms/meridian-trust alongside realm-management and account — the exact audience that scope's own mapper promises to add.

      curl -s -X POST -H "Authorization: Bearer <same token>" \

      A real, clean 403 — a valid, authenticated token (it passed Gate 1 from Figure 36.3) rejected purely on permission (Gate 2). No user named should-not-be-created exists afterward. The scope boundary from Figure 36.2 is not theoretical — it's an enforced, confirmed fact.

    3. Contrast case: a second client, no-roles-service, with service accounts enabled, the kc-admin-api scope added (so it clears Gate 1), but no realm-management role mapping at all:

      curl -s -i -H "Authorization: Bearer <no-roles-service token>" \
  "http://localhost:8080/admin/realms/meridian-trust/users"
      HTTP/1.1 403 Forbidden
{"error":"HTTP 403 Forbidden"}

      Note the difference from this chapter's earlier mistake: this is a clean 403, not a 401 — because this token does carry the right scope (Gate 1 passes), it's simply carrying zero realm-management roles at all (Gate 2 fails completely). A no-role-mappings service account isn't rejected for being unrecognized; it's rejected for being recognized and granted nothing.

    Common mistakes

    • A real finding from writing this chapter: if you see a service account with correctly confirmed realm-management role mappings still get a flat 401 Unauthorized against the Admin REST API, the cause is very likely a missing kc-admin-api client scope on that client — the same scope chapter 27 noticed on admin-cli's token, but which a custom client does not get automatically. It's a separate, scope-gated audience check that runs before role mappings are even consulted. Correct roles do not help if the token never clears this earlier gate. Check whether the realm's admin-cli client (which has this scope by default) succeeds against the same endpoint as a quick sanity comparison.
    • If you see a 403 Forbidden instead, the token already cleared the scope gate — the problem is a genuinely missing or wrong role mapping, not a scope issue. Don't "fix" a 403 by adding more client scopes; fix it by checking the role mapping on the service account's actual user id.
    • Confusing a client role with a realm role for a service account is an easy mistake going in the other direction: realm-management's roles (view-users, manage-users, etc.) are client roles, scoped to that one client's namespace, not realm roles — mapping them requires --cclientid realm-management on add-roles, not a bare --rolename alone, and a bare realm-role mapping attempt against a client-role name will simply fail to find it.
    • If the Admin Console's own Service Account Roles tab on a client's detail page looks empty or confusing, remember it is editing role mappings on that client's dedicated service-account user, not on the client resource itself — the same confusion this chapter's REST-based lab sidesteps by addressing the user id directly, but one worth recognizing if you later work in the console UI instead.
    • Granting manage-users (or worse, a broad composite admin role) to a service account "to save time" because the exact read-only role wasn't obvious is the least-privilege failure Meridian Trust's case study exists to warn against — the narrow role existed (view-users) and did everything the actual job required; the broad grant only added risk with no corresponding benefit.
    • If a service account's token seems to have more effective roles than you explicitly granted, check whether the role you mapped is a composite role first (as view-users is, in this chapter's own lab) before assuming something else over-granted it — a composite role's sub-roles appear in the token automatically and are not a separate mistake to chase down.

    Takeaways

    • Enabling a Keycloak client's service account creates a real, dedicated user record (service-account-<clientId>) with its own internal id — confirmed live, not inferred — and that id is what every later role mapping and token subject actually points at.
    • Mapping a role onto a service account uses the exact same mechanism as mapping a role onto any human user — the same add-roles subcommand and the same users/{id}/role-mappings/... endpoint, addressed by the service account's own user id.
    • realm-management's client roles (view-users, manage-users, etc.) are independently grantable — picking the narrowest one that still satisfies a service's real job is a direct application of chapter 9's threat-landscape reasoning and chapter 23's role-mapping mechanics to a non-human caller.
    • Chapter 27 already flagged that admin-cli's token carries a kc-admin-api scope; this chapter's lab is the first time this course hit the consequence directly — a custom client's service account does not get that scope automatically, and calling the Admin REST API without it fails before role-based authorization is ever consulted.
    • A 401 Unauthorized from the Admin REST API with otherwise-correct role mappings points at that missing scope (an authentication-layer rejection); a 403 Forbidden points at an actually insufficient role (an authorization-layer rejection) — they are different failures with different fixes, confirmed as genuinely distinct in this chapter's own lab.
    • Keycloak's response body itself can carry scoping information directly — this lab's GET users call returned "access": {"manage": false} per user record, confirming the caller's own limits without a second request.
    • A service account with the right scope but zero role mappings gets a clean 403 on every protected call — recognized and authenticated, but granted nothing — distinct from an unrecognized/unscoped token's 401.
    • Meridian Trust's fraud-detection service moving from an over-provisioned manage-users grant to a narrowly-scoped view-users grant is exactly the least-privilege correction a PCI-DSS access-control review expects to find already in place, not flagged as an open finding.
    • Built-in Keycloak clients like admin-cli ship pre-wired with the kc-admin-api scope; any custom service account intended to call the Admin REST API has to be wired up for it deliberately — it is not implied by role mappings alone.

    Self-check

    Click a question to reveal a model answer. Try answering it yourself first — the point is to check your own reasoning against it, not to read the answer first.

    1. A colleague says "service accounts are a special Keycloak feature with their own permission system, separate from normal user roles." Correct this precisely.

      Model answerThat's wrong. Enabling a client's service account simply creates an ordinary user record (service-account-<clientId>) with its own real user id. Granting it access uses the identical role-mapping mechanism chapter 23 covered for any human user — the same add-roles subcommand and the same users/{id}/role-mappings/clients/{clientUuid} endpoint — just pointed at the id Keycloak happened to create for that client. There is no separate permission system to learn.

    2. This chapter's lab got a 401 Unauthorized on its first real attempt to call the Admin REST API, even though the role mapping was already confirmed correct. What was the actual cause, and why didn't correct role mappings prevent it?

      Model answerThe client's token never carried the kc-admin-api client scope, which adds the Admin REST API's own required audience to the token. That scope gates a separate, earlier check — "can this token even call the admin API at all" — that Keycloak evaluates before it ever reads the token's role mappings. Correct role mappings only matter once a token has already cleared that first, scope-gated check; they can't substitute for it.

    3. Distinguish, for the Admin REST API specifically, what a 401 response tells you versus what a 403 response tells you, using this chapter's own lab results as the example.

      Model answerA 401 means the token itself was rejected before any permission was checked — in this lab, because it lacked the kc-admin-api scope entirely. A 403 means the token was accepted as valid and authenticated, but the specific operation requested exceeds what its role mappings allow — in this lab, the view-users-only service account got a 403 specifically on a user-creation attempt, which needs manage-users. The 401 is an authentication failure; the 403 is an authorization failure, and they require different fixes (add the missing scope, versus add the missing role).

    4. Why does granting view-users instead of manage-users to Meridian Trust's fraud-detection service matter in practice, given that the service was never going to intentionally write data anyway?

      Model answerIt matters because the scoping decision only pays off in the scenario where something goes wrong — a leaked client secret, a compromised host running the service, or a bug that calls the wrong endpoint. In all of those cases, intent doesn't protect anything; only the actual granted role does. With view-users alone, any of those failure modes is limited to read access. With manage-users "just in case," the exact same failure modes allow creating, modifying, or deleting any user in the realm — a dramatically larger blast radius for a service whose legitimate job never needed that power in the first place.

    5. A service account with the kc-admin-api scope but no realm-management role mappings at all calls GET /admin/realms/meridian-trust/users. What HTTP status does it get, and why is that different from a client that never requested kc-admin-api in the first place?

      Model answerIt gets a 403 Forbidden, confirmed directly in this chapter's lab with the no-roles-service client. That's different from the 401 a client without the kc-admin-api scope gets, because this token already clears the scope-gated authentication check (Gate 1) — Keycloak recognizes it as a legitimate, properly-scoped caller. It simply carries zero roles on the realm-management client, so the role-gated authorization check (Gate 2) finds nothing to permit the request with. Recognized-but-granted-nothing (403) and never-cleared-the-gate-at-all (401) are genuinely different failures.

    6. Explain why view-users showed up in this lab's decoded token as three roles — view-users, query-users, and query-groups — rather than just the one role that was actually mapped.

      Model answerview-users is a composite role (confirmed by its own "composite": true field when this lab queried it), meaning it bundles other roles underneath it — in this case query-users and query-groups. A token carrying a composite role automatically carries everything that role composes, the same composite-role mechanic chapter 23 introduced for human users, applied here to a service account with no extra steps needed to make the bundled roles appear.
