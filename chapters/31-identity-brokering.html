    Part VI — Federation & Integration ~50 min Hands-on lab

    31. Identity Brokering

    Chapter 7 defined identity brokering in the abstract: delegating the act of authentication to an external Identity Provider the user already has an account with, rather than storing or checking a password locally. This chapter builds exactly that, for real, inside a single running Keycloak instance — one realm playing the external corporate IdP, a second realm brokering to it — and proves the full round trip with nothing but curl and a cookie jar: a real login at the external IdP, a real redirect back, and a real, just-in-time-provisioned user record confirmed afterward through the Admin REST API.

    Why this matters

    "Can our enterprise customers log in with their own corporate identity instead of a password we issue them?" is one of the most common requests an IAM specialist fields, and identity brokering is the feature that answers it. Getting it wrong is expensive in a specific way: a misconfigured redirect URI or a mismatched issuer doesn't fail loudly in a code review, it fails at 2am when a real enterprise customer's engineers can't log in, with an error message that points at the wrong layer of the stack. This chapter's lab deliberately walks through the exact failure this course's own authoring process hit while drafting it, not just the happy path, because debugging a broken brokering integration is a core, recurring task for this role.

    What concept is this?

    Chapter 7 named the formal roles — Identity Provider (IdP), the relying Service Provider (SP) or Relying Party (RP) — and drew a hard line between brokering (delegating one login event to an external IdP the user already has an account with) and federation (reusing an existing directory, chapter 32's subject). It also introduced JIT (just-in-time) provisioning: the first successful brokered login silently creates a matching local identity, through the same "federated/brokered creation" door chapter 2's identity lifecycle named and deferred. Everything in this chapter is that vocabulary made concrete: Keycloak's Identity Provider resource is the trust configuration chapter 7 said has to exist before brokering can work at all, and this chapter's lab is JIT provisioning witnessed directly, not described.

    The full brokering sequence, end to end

    Before touching any configuration, here is the complete shape this chapter's lab reproduces with real HTTP calls: a user tries to log into Northwind Apps's northwind-apps realm, gets redirected to their own employer's identity provider instead of seeing a Northwind-issued password form, authenticates there for real, and lands back in northwind-apps with a brand-new local user record nobody at Northwind had to create by hand.

    Key idea

    Nothing about this sequence requires two different companies' servers. Brokering is a protocol relationship between an IdP and an SP/RP — it doesn't care whether those two roles happen to be two realms on the same Keycloak instance (this chapter's lab, for scriptability) or two servers run by two different organizations (the real Acme Corp scenario this lab stands in for). The trust configuration and the redirect chain are identical either way.

    Keycloak's Identity Provider resource: chapter 7's trust triangle, made concrete

    Chapter 7 said trust between an IdP and an SP/RP has three ingredients, configured in advance, never assumed: metadata, certificates/signing keys, and registered redirect URIs. A Keycloak Identity Provider — a realm-scoped resource identified by an alias (this chapter uses northwind-corporate-idp, matching the realm it points at, though the two names don't have to match) — is exactly that trust configuration, with each ingredient landing on a specific field.

    A fourth field doesn't map to any of chapter 7's three ingredients, but every OIDC Identity Provider needs it anyway: clientId/clientSecret — the confidential client credentials northwind-apps itself authenticates with when it calls northwind-corporate-idp's token endpoint, exactly the OAuth client-credentials mechanics chapter 13 already covered, now reused for one realm to talk to another.

    First Broker Login: where JIT provisioning actually happens

    Chapter 25 already named the First Broker Login flow as one of Keycloak's built-in flows, run exactly once per user the first time they authenticate through a given broker. This chapter is where that flow's actual decision logic matters: a successful external login does not automatically mean a new local account gets created. Keycloak checks for an existing link first.

    In Keycloak

    Every brokered login leaves a federated identity record — confirmed directly in this chapter's lab via GET users/{id}/federated-identity — pairing the local user's id with the external IdP's own user id and username. That record, not anything stored on the user object itself, is what lets Keycloak recognize "this is the same external person logging in again" on every subsequent login.

    Skipping the picker: kc_idp_hint and the default Identity Provider

    With an Identity Provider configured and not hidden, Keycloak's realm login page normally shows a picker: the realm's own username/password form, plus a button per configured external IdP. For Northwind's actual enterprise-SSO use case — Acme Corp's employees should always land straight at Acme's own login, never see a Northwind-issued password field at all — that picker is the wrong default. Two real mechanisms skip it, and this chapter's lab uses the first one directly.

    Pitfall

    A misspelled or nonexistent kc_idp_hint value does not error — Keycloak silently falls back to the ordinary picker page instead. If you see a brokering integration that seems to "just not redirect," check the hint value against the IdP's actual configured alias character for character before assuming anything else is broken.

    What travels with a brokered login: mappers, sync mode, linking

    A successful brokered login hands northwind-apps whatever claims northwind-corporate-idp's ID token and (optionally) UserInfo response carry — this chapter's lab used given_name/family_name/email directly, the same claims chapter 15 already named. Three settings decide what Keycloak does with that data and with the identity it represents:

    Three Identity Provider settings this chapter's lab relied on or should know about
    SettingWhat it controls
    Identity Provider mapperA realm-scoped rule that copies an external claim/attribute into a local user attribute, role, or group — the Keycloak mechanism behind "map the external IdP's department claim onto a Northwind group."     Two more real, per-IdP settings are worth knowing even though this chapter's lab left them at their Keycloak defaults: First Login Flow (which authentication flow runs the first time a user logs in via this IdP — defaults to the realm's own First Broker Login flow, but can be pointed at a different one per IdP) and Post Login Flow (a flow Keycloak runs after the external IdP login finishes, on every login, not just the first) — the mechanism a realm would use to demand an extra MFA step for brokered logins specifically, the kind of step-up pattern Meridian Trust would reasonably want layered on top of trusting an external bank-partner IdP.

    Case study: Northwind Apps brokers to Acme Corp's own identity provider

    Case study — Northwind Apps

    Chapter 27's bulk-onboarding script manually created a tenant-admin account named acme-admin for Acme Corp, one of Northwind's named enterprise customers — a real, necessary step at the time, but one that doesn't scale past Acme's first handful of users, and one Northwind's ops team has to repeat, by hand, every time Acme hires someone new or someone leaves. This chapter's lab is the fix: once northwind-apps trusts Acme's own corporate identity provider (northwind-corporate-idp standing in for it here), any Acme employee with a real account there — this chapter used ben.carter, a newly hired Acme engineer who never had a Northwind-issued password at all — gets a working northwind-apps identity automatically on their very first login, with zero manual provisioning on Northwind's side. Acme's own IT department keeps managing who counts as "a current Acme employee" in their own directory, exactly the separation of responsibility chapter 7's brokering-versus-federation distinction predicts: Northwind never stores or sees Ben's real Acme password, it only trusts Acme's assertion that he is who he says he is.

    Common mistakes

    • If you see a broker login that silently falls through to the realm's own password form instead of redirecting to the external IdP, the cause is almost always a misspelled or stale kc_idp_hint value — it fails open to the picker rather than erroring, so check it against the IdP's actual alias character for character.
    • If you see invalid_redirect_uri at the external IdP's own authorize step, the cause is the broker-endpoint convention (/realms/<broker realm>/broker/<alias>/endpoint) not being registered, byte for byte, as a valid redirect URI on the client the external realm's own admin created for the broker to use.
    • A real finding from writing this chapter: an earlier draft of this lab ran the browser-facing authorize request through one host/port and configured the Identity Provider's backend-facing tokenUrl/userInfoUrl through a different one (an artifact of this chapter's own isolated test environment, remapped off the standard port for parallel testing). That split produced a real Wrong issuer from token error, followed by a second, independent Invalid token issuer rejection from the UserInfo endpoint itself — because Keycloak's realm issuer is tied to whichever host the browser's original request used, not to whichever host a later backend call happens to use. If you see either error with a Keycloak instance running behind a reverse proxy, the cause is almost always a mismatch between the proxy's externally visible hostname and whatever hostname Keycloak's backend-to-backend calls actually resolve — not a broken broker configuration otherwise. This chapter's own working lab avoids the problem entirely by using one consistent http://localhost:8080/... base URL for every field, browser-facing and backend-facing alike.
    • If you see a brokered user's local account reappear with completely stale name/email data after their information changed at the external IdP, the cause is syncMode=IMPORT — it copies attributes once, at first login, and never again automatically. FORCE re-syncs on every login instead.
    • If you see a brokered login silently link to an existing local account instead of creating a new one, the cause is usually working as designed, not a bug: the external IdP's email matched an existing local user and Trust Email is enabled for that IdP — check the First Broker Login decision (Figure 31.3) before assuming something is broken.
    • If you see someone try to query or manage an external IdP's users directly from the broker realm's Admin Console, the cause is forgetting that brokering never gives one realm visibility into another's user store — the only connection is the federated-identity link record, confirmed after the fact, not a live read-through.

    Takeaways

    • A Keycloak Identity Provider resource is chapter 7's abstract IdP/SP trust relationship made concrete: its authorizationUrl/tokenUrl/jwksUrl fields are the metadata, jwksUrl+useJwksUrl is the certificate/signing-key trust, and the fixed broker-endpoint URL convention is the registered redirect URI — none of it optional or inferred.
    • Brokering works identically whether the external IdP is a separate company's server or, as in this chapter's lab, a second realm on the same Keycloak instance — the trust relationship is a protocol concept, not a deployment-topology one.
    • JIT provisioning is not unconditional: Keycloak checks for an existing federated-identity link first, then — only for a genuinely new external identity — runs First Broker Login, which itself chooses between linking to a matching existing local account (if Trust Email is on and the email matches) and creating a brand-new local user.
    • Every brokered login leaves a federated-identity record pairing the local user's id with the external IdP's own user id — confirmed live via GET users/{id}/federated-identity — and that record, not anything on the user object, is what later logins are recognized against.
    • kc_idp_hint on a single authorization request, or marking an IdP as a realm's Default Identity Provider, are the two real mechanisms that skip Keycloak's IdP picker page; a bad hint value fails open to the picker rather than erroring.
    • Sync mode (IMPORT vs. FORCE) decides whether a brokered user's attributes update on every subsequent login or only ever reflect what the external IdP returned the very first time.
    • This chapter's own authoring process hit a real Wrong issuer from token error from configuring browser-facing and backend-facing Identity Provider URLs through two different hostnames — a genuine, production-relevant gotcha for Keycloak deployed behind a reverse proxy, not a hypothetical.
    • Brokering never gives the broker realm visibility into the external IdP's own user store — the only artifact that crosses the boundary is the federated-identity link, confirmed after the fact via the Admin REST API.
    • Northwind Apps brokering to Acme Corp's own identity provider replaces chapter 27's manual, repeated acme-admin-style bulk onboarding with zero-touch provisioning for any real Acme employee — Acme's own IT department remains the authority on who counts as a current employee, exactly the responsibility split chapter 7 predicted for brokering.

    1. Ben Carter logs into northwind-apps via the broker for the first time ever. Walk through, in order, which Keycloak decision points his login actually passes through before a token is issued, and why each one resolves the way it does for him specifically.

      Model answerFirst, the federated-identity check: since Ben has never logged in before, no link exists, so First Broker Login actually runs (Figure 31.3's "NO" branch) rather than being skipped. Inside that flow, the second decision checks whether his email matches an existing local northwind-apps user with Trust Email enabled — it doesn't, because Ben never had a Northwind account at all — so the flow takes the "otherwise" branch and just-in-time provisions a brand-new local user rather than linking to anything existing. Only after that does Keycloak mint real northwind-apps tokens for the originally requested client.

    2. Explain, concretely, what the registered redirect URI on the northwind-apps-broker client (inside northwind-corporate-idp) actually has to equal, and why getting even one path segment wrong breaks the whole flow at a specific, identifiable step.

      Model answerIt has to equal Keycloak's fixed broker-endpoint convention exactly: /realms/northwind-apps/broker/northwind-corporate-idp/endpoint, on whatever host/port the browser is actually using. This is the URL northwind-corporate-idp redirects the browser back to after a successful login there, carrying the real authorization code. If even one segment is wrong — the realm name, the IdP alias, or "endpoint" itself — northwind-corporate-idp's own authorize step rejects the request immediately with an invalid-redirect-uri error, before the user ever sees a login form, not sometime later in the flow.

    3. A colleague says "brokering means northwind-apps can see and manage all of Acme Corp's employee accounts now." Correct this, precisely.

      Model answerThat's wrong — brokering delegates one login event at a time; it does not give northwind-apps any visibility into northwind-corporate-idp's user store at all. The only thing that crosses the boundary is a federated-identity record, created per user, per IdP, only after that specific person has actually logged in through the broker at least once — confirmed in this chapter by querying GET users/{id}/federated-identity after the fact, not by querying Acme's realm directly, which northwind-apps has no standing access to do.

    4. This chapter's own lab hit a real "Wrong issuer from token" error during an earlier draft. What specifically caused it, and why did switching every Identity Provider URL to one consistent host/port fix it?

      Model answerThe browser-facing authorize request went through one host/port (an isolated test port), while the Identity Provider's backend-facing tokenUrl/userInfoUrl fields were configured through a different one (the container's internal port). Keycloak's realm issuer is tied to whichever host the browser's original request used, not to whichever host a later backend call happens to use — so the id_token's actual iss claim didn't match the issuer value a request arriving through the other port expected. Using one consistent base URL for every field removed the mismatch entirely, because every request — browser-facing and backend-facing — then resolved to the exact same issuer.

    5. Why does northwind-corporate-idp's own OIDC discovery document matter for this lab, given that northwind-apps's Identity Provider config sets authorizationUrl/tokenUrl/jwksUrl by hand rather than pointing at a discovery URL directly?

      Model answerEven configured by hand, every one of those URLs has to match the real, live endpoints northwind-corporate-idp actually serves — the discovery document is where those real values were read from in this chapter's lab (GET /realms/northwind-corporate-idp/.well-known/openid-configuration), rather than guessed from a naming convention. A hand-configured field that drifts from what the realm's real discovery document says — after a realm rename, say — would fail exactly like a wrong redirect URI does: silently, at whichever specific step tries to reach the stale URL, not with an obvious top-level error.

    6. If Northwind's Acme Corp customer later disables Ben Carter's account in their own corporate directory, does that automatically disable his northwind-apps account too? Why or why not, and what does this imply operationally?

      Model answerNo, not automatically. Brokering with syncMode=IMPORT only copies attributes at first login and establishes a federated-identity link; it does not continuously synchronize account status, and this chapter's lab never configured any live deprovisioning hook back to northwind-corporate-idp. Operationally, this means Northwind needs a separate, deliberate offboarding mechanism for brokered accounts (disabling the local user directly, or configuring something that reacts to the external IdP's own signals) rather than assuming "Acme disabled him there" automatically means "he can't log into northwind-apps anymore" — the two account lifecycles are linked by one login event, not kept in ongoing lockstep.
