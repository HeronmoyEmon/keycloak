15. OpenID Connect

Chapters 13 and 14 covered OAuth 2.0 in full — a framework for delegated authorization (letting an application act on a resource owner's behalf) that deliberately says nothing about who the resource owner is. OpenID Connect (OIDC) is the thin identity layer built on top of OAuth 2.0 that answers exactly that question: it adds a standardized "who just logged in" token, a way for a client to discover an identity provider's capabilities without hardcoding them, and a standard way to ask for more profile data about the person who authenticated. This chapter covers all three, using the same Duende demo IdentityServer and device-flow mechanism chapter 14 used — real discovery JSON, a real device-flow token request, and the real UserInfo endpoint's documented behavior.

Why this matters

Every "Login with Google," every SPA that shows "Welcome, Dr. Chen" immediately after redirecting back from a login page, and every mobile app that reads a user's verified email without a second API round trip is built on OIDC's ID token and UserInfo endpoint. An IAM specialist configuring Keycloak as an OIDC provider spends real time deciding exactly two things this chapter prepares you for: which scopes a client should request, and which claims should land in the ID token versus require a UserInfo call — decisions with real performance and privacy consequences, not just checkbox-ticking.

Recall from chapter 7

Chapter 7 defined Metadata as a machine-readable description of an IdP's or SP/RP's endpoints and capabilities, exchanged so each side can configure itself correctly instead of guessing — one of the three ingredients of Trust between an IdP and a relying application, alongside signing keys and registered redirect URIs. OIDC's discovery document, below, is the concrete, standardized, JSON implementation of exactly that idea. Where chapter 7 left "metadata" and "trust" as general vocabulary that SAML (chapter 17) and OIDC would each implement differently, this chapter is where OIDC's implementation gets filled in.

OIDC in one sentence

OpenID Connect reuses OAuth 2.0's authorization code, device, and other grants exactly as chapters 13-14 described them, and adds three things on top: a new scope (openid) that tells the authorization server "also issue an identity token," a new token type (the ID token) carrying claims about who authenticated, and two supporting mechanisms — the discovery document and the UserInfo endpoint — that make the whole thing self-describing and extensible. Nothing about the OAuth mechanics you already know changes; OIDC is additive, not a replacement protocol.

Pitfall

"OAuth" and "OIDC" are not interchangeable, even though most real logins use both at once. OAuth alone has no standardized concept of "who logged in" — an OAuth access token's only formally guaranteed job is authorizing API calls. If an application needs to know the user's identity (name, email, a stable subject identifier) rather than just needing to call an API on their behalf, it needs the openid scope and an ID token, not just an OAuth access token.

The discovery document

Every OIDC provider publishes a single, well-known JSON document describing its own endpoints and capabilities, at a fixed, predictable path: /.well-known/openid-configuration, appended to the provider's issuer URL. A client that knows only the issuer URL can fetch this document once and learn everything else it needs — which URL to redirect a user to for login, which URL to call to exchange a code for tokens, which URL to call for UserInfo, which public keys to use to verify a signature, and which scopes and claims the provider actually supports — instead of the integrator hardcoding a half-dozen URLs by hand and hoping they never change.

What a client does with each discovery field
FieldLets the client learn
issuerThe exact string that must appear in every token's iss claim from this provider — a verifier checks this to prevent mix-up attacks (chapter 18) where a token from a different, untrusted issuer is accepted by mistake.
authorization_endpointWhere to redirect the browser to start a login (the same endpoint chapter 13's authorization code flow and chapter 14's other grants build requests against).
token_endpointWhere to exchange a code/device code/refresh token for actual tokens.
userinfo_endpointWhere to call, with an access token, to fetch claims about the authenticated user — this chapter's second lab target.
jwks_uriWhere to fetch the public keys needed to verify an ID token's signature. The client never hardcodes a key; it fetches the current key set and looks one up by kid — full mechanics in chapter 16, not duplicated here.
scopes_supportedWhich scopes (standard and provider-specific) a client is allowed to request at all — requesting an unsupported scope is simply ignored or rejected, not silently granted.
claims_supportedWhich claims the provider is willing to return, in an ID token or from UserInfo, across all its supported scopes — the advertised ceiling of what "asking for more data" can ever get a client.
In Keycloak

Every Keycloak realm publishes its own discovery document at /realms/<realm>/.well-known/openid-configuration. Which scopes and claims show up in scopes_supported/claims_supported is driven directly by that realm's configured client scopes and protocol mappers — the admin-console screen covered in depth in chapter 24.

The ID token: structure and claims

When a client includes the openid scope in an authorization or token request, the provider returns, alongside the usual OAuth access (and optionally refresh) token, a new token: the ID token. Structurally, an ID token is a JWT — three base64url-encoded, dot-separated parts (header, payload, signature) — but this chapter deliberately stops at the payload's claims. How that signature is computed and verified, and how a verifier finds the right key via the jwks_uri you just saw, is chapter 16's job in full; conflating the two is exactly the beginner mistake chapter 16 names directly, so this chapter won't pre-empt it.

At the JSON-claims level, every ID token issued for a successful login carries roughly this shape (field values below are representative of what a provider in this course's reach would issue — see the lab callout further down for exactly which of these claims are confirmed live for the demo server versus standard by spec):

{
  "iss": "https://demo.duendesoftware.com",
  "sub": "88421113",
  "aud": "device",
  "exp": 1762760130,
  "iat": 1762756530,
  "auth_time": 1762756528,
  "nonce": "n-0S6_WzA2Mj",

  "name": "Bob Smith",
  "given_name": "Bob",
  "family_name": "Smith",
  "preferred_username": "bob",
  "email": "BobSmith@email.com",
  "email_verified": true
}
ID token claims: required by spec vs. carried because of requested scopes
ClaimSourceMeaning
iss, sub, aud, exp, iat Always present (OIDC Core §2)Issuer, subject (stable user identifier), intended audience (the client_id this token was issued for), expiry, and issued-at time — the minimum any ID token must carry to be verifiable at all.
auth_timePresent if requested or if max_age was used When the user actually authenticated — distinct from iat (when this particular token was issued), which matters once refresh tokens are in play and a new ID token can be minted well after the original login.
nonceEchoed back only if the client sent oneA client-supplied random value, echoed back unchanged, that lets the client verify this specific ID token was issued in response to this specific request — a replay/mix-up defense covered in full in chapter 18.
name, given_name, family_name, preferred_usernamePresent only if profile scope was requestedStandard profile claims (see Standard vs. custom scopes, below).
email, email_verifiedPresent only if email scope was requestedStandard email claims — email_verified specifically distinguishes "this address was confirmed via a verification flow" from merely "a user typed this into a form."
Pitfall

An ID token is proof of authentication (who logged in, and when) — it is not an access token, and a resource server should not accept an ID token in place of one just because both are JWTs with similar-looking claims. The aud claim is exactly how a well-behaved verifier tells them apart in practice: an ID token's audience is the client itself, not an API.

The UserInfo endpoint

Not every claim needs to ride inside the ID token. A client can instead call the discovery document's userinfo_endpoint with a valid access token (one issued with at least the openid scope) and get the same kind of standard claims back as a plain JSON object — useful when the ID token was kept small, when claims might have changed since login and need a fresh read, or when an access token is all a particular part of the system was handed.

Hands-on lab: the device flow, reused from chapter 14

Chapter 14 already established that the device client on Duende's public demo server is this course's primary "real tokens, real human step" lab, because the device authorization grant needs no registered redirect_uri at all. This chapter reuses that exact mechanism — same client, same grant — rather than inventing a second interactive flow, this time requesting openid profile email so the resulting access token is valid at the UserInfo endpoint. Everything below through step 4 was run live for this chapter on 2026-11-10; step 5 is what you run yourself, because completing it requires a human clicking through a real login page in a real browser — something this chapter's author (an agent, not a person with a browser) cannot do, and additionally the agent's own tool-use policy blocked even a scripted attempt to submit the demo server's test-account password on your behalf, as an extra safety layer worth knowing about rather than quietly working around.

    $ curl -s https://demo.duendesoftware.com/connect/userinfo \
    -H "Authorization: Bearer <your real access_token>"

    Per the discovery document's claims_supported list confirmed in this chapter and OIDC Core's standard claims set, expect a JSON object shaped like:

    {
  "sub": "88421113",
  "name": "Bob Smith",
  "given_name": "Bob",
  "family_name": "Smith",
  "preferred_username": "bob",
  "email": "BobSmith@email.com",
  "email_verified": true
}

    Note the overlap with the ID token payload shown earlier — both are populated from the same underlying claims, filtered by the same requested scopes; UserInfo is a second way to ask for the same data, not a different dataset.

Pitfall

If you see a UserInfo call fail with 401 invalid_token, the two most common causes in practice are: the access token simply expired (they're short-lived by design — chapter 8), or the token was issued without the openid scope at all, so it's a perfectly valid OAuth access token that was never entitled to call an OIDC-specific endpoint in the first place. Check which scopes the original token request actually included before assuming the token is broken.

Standard vs. custom scopes and claims

OIDC defines a small set of standard scopes, each unlocking a fixed bundle of standard claims — confirmed directly against the demo server's own scopes_supported/claims_supported fields above:

Standard OIDC scopes and the claims they unlock
ScopeRequired?Unlocks these standard claims
openidYes — this is what makes a request an OIDC request at all, rather than plain OAuthsub (and the other always-present ID-token claims: iss, aud, exp, iat)
profileNoname, given_name, family_name, middle_name, nickname, preferred_username, profile, picture, website, gender, birthdate, zoneinfo, locale, updated_at
emailNoemail, email_verified
offline_accessNoNot a claim — it's what makes the token response include a refresh token at all (chapter 14/8), listed here only because it appears alongside the claims-bearing scopes above in real requests.

A real application almost always needs more than this fixed bundle — a tenant ID, a subscription tier, an internal employee number. OIDC doesn't forbid this: a provider can define and advertise custom scopes and custom claims of its own, as long as it's honest about them in its own claims_supported list. The demo server used for this lab doesn't expose any (its claims_supported list, shown earlier, is exactly the standard set) — a concrete example of what a custom claim looks like in practice is deferred to the "In Keycloak" callout below, since that's exactly what a Keycloak protocol mapper is for.

In Keycloak

A Keycloak client scope bundles a set of protocol mappers, each one deciding what one claim gets added to an ID token, an access token, or a UserInfo response, and from where (a user attribute, a hardcoded value, a role name). Northwind Apps adding a tenant_id claim so every connected customer application can tell which tenant a logged-in user belongs to without a second API call is exactly this mechanism — the admin-console screen for configuring it is covered in chapter 24.

Case study — Riverside Health

Riverside Health's patient portal requests the openid profile email scopes when a patient logs in. Once the browser returns from login, the portal decodes the ID token's claims directly — no second network call — and uses preferred_username to greet the patient by their chosen name, and email_verified to decide, in real time, whether to show a "please verify your email to enable appointment reminders" banner. Because both claims already rode inside the ID token from the profile and email scopes the portal requested, there's nothing further to fetch: the portal's home page can render immediately after the redirect completes, which matters for a patient population that skews older and less tolerant of a slow, multi-step login. If the portal later needs a claim it didn't request at login time, or needs to re-check whether an email was verified since login (say, the patient just clicked a verification link in another tab), that's exactly when it would fall back to a live UserInfo call instead of trusting a potentially stale ID token.

Common mistakes

  • If you see a client hardcoding an IdP's authorization/token/UserInfo URLs instead of fetching the discovery document once at startup, the cause is skipping the one mechanism OIDC provides specifically so those URLs never need to be hardcoded or manually kept in sync when a provider changes them.
  • If you see code that treats an ID token as if it were an access token (e.g. sending it to a resource server's API), the cause is missing that an ID token's aud claim names the client itself, not an API — it was never meant to authorize anything beyond proving who logged in.
  • If you see a UserInfo call fail with invalid_token, check which scopes the original token request included before assuming the token or the endpoint is broken — a token issued without openid simply never earns UserInfo access.
  • If you see an application re-requesting the full profile scope just to get one extra field it doesn't otherwise use, the cause is not understanding that claims_supported is a fixed, advertised ceiling — if a needed claim isn't in that list at all, no scope combination will ever produce it, and the real fix is a custom claim/protocol mapper on the provider side, not a different scope request.
  • If you see an integration confusing "the user is logged in" with "the user's email is verified," the cause is skipping the email_verified claim specifically — OIDC deliberately separates "this person authenticated" from "this specific contact detail was confirmed," and a portal that conflates the two can send sensitive notifications to an unconfirmed address.

Takeaways

  • OpenID Connect is an identity layer added on top of OAuth 2.0, not a replacement for it — the same grants from chapters 13-14 are reused unchanged; OIDC adds the openid scope, the ID token, discovery, and UserInfo.
  • The discovery document (/.well-known/openid-configuration) is the concrete, JSON implementation of chapter 7's general "metadata" and "trust" concepts, letting a client learn an IdP's endpoints and capabilities without hardcoding them.
  • An ID token's always-present claims (iss, sub, aud, exp, iat) are what make it independently verifiable; profile- and email-scoped claims are only present if those scopes were actually requested.
  • An ID token proves authentication, not authorization — its audience is the client itself, never a resource server, and it should never be sent to an API in place of an access token.
  • The UserInfo endpoint returns the same kind of standard claims as the ID token, fetched live with a valid access token, rather than decoded from a token the client is already holding — useful when claims might have changed since login or when only an access token was available.
  • scopes_supported and claims_supported in the discovery document are an advertised ceiling: a scope that isn't listed won't be honored, and a claim that isn't listed can never be produced by any scope combination.
  • Custom claims (a tenant ID, a subscription tier) are added by the provider, not invented by the client — in Keycloak, this is exactly what a client scope's protocol mappers configure.
  • email_verified is deliberately a separate claim from the mere presence of email — treating "logged in" as proof an email address was confirmed is a real, consequential mistake, not a pedantic distinction.
  • This chapter's lab reused chapter 14's device-flow mechanism rather than inventing a second interactive flow — the same device client, now requesting openid profile email so the resulting access token is valid at the UserInfo endpoint.
