This chapter builds that mental cheat sheet deliberately, instead of leaving it to accumulate by accident.

    Pitfall — two to recognize, never reach for

    Resource Owner Password Credentials (ROPC) and Implicit both appear in older material and in some SDKs' defaults, but both are legacy, discouraged grant types per the OAuth 2.0 Security Best Current Practice (chapter 18) — ROPC because it has the client handle the user's raw password directly, Implicit because it returns an access token straight in a URL fragment with no code-exchange step to hide it behind. Recognize them so you can flag them in a review; don't design new integrations around either.

    Cheat sheet: how a Keycloak realm fits together

    This relationship — a realm containing clients, users, groups, and roles, with client scopes as a separate reusable layer clients attach to — is the single structural fact chapters 21-24 spend the most words establishing. Here it is as one picture, grounded in the real northwind-apps realm built across chapters 20-26 and extended in the capstone.

    In Keycloak

    Realm roles live under Realm roles; client roles live under a specific client's own Roles tab, in that client's private namespace (chapter 24). Client scopes are a top-level Client scopes list, each one independently attachable to any client as default or optional (chapter 24) — the capstone's tenant-context scope is exactly this pattern, carrying a custom protocol mapper that stamps a tenant_id claim onto every token a client requesting it gets.

    Cheat sheet: token types compared

    Chapter 8 introduced tokens conceptually; chapters 15-16 gave the OIDC/JWT-specific ones full mechanical depth; chapter 37 added the UMA-specific RPT. Side by side:

    Token types used across this course, compared
    TokenProvesAudience (aud)Typical lifetimeWhere it shows up
    Access tokenAuthorization to call a resource serverThe resource server/APIShort — minutes, by designEvery protected API call (ch. 8, 34)
    ID tokenAuthentication — who logged in, and whenThe requesting client itself, never an APISimilar to the access token's sessionOIDC logins only, never sent to an API (ch. 15, 35)
    Refresh tokenNothing by itself — it's exchanged for new access/ID tokensThe authorization server's token endpointLong — hours to days, a direct security/convenience trade-offKept by the client to avoid re-login (ch. 8, 13)
    Requesting Party Token (RPT)A specific, scoped grant computed from a live UMA policy evaluationThe specific resource server that registered the resourceShort, like an ordinary access tokenFine-grained authorization checks after a ticket exchange (ch. 37)
    Pitfall

    Sending an ID token to an API in place of an access token is a recurring beginner mistake — its aud claim names the client, not the API, so a correctly implemented resource server should reject it. If an API call with an ID token "works," the resource server isn't validating aud, which is itself a bug worth flagging (chapter 15).

    Takeaways

    • This chapter introduces no new concepts — it curates and cross-references material from all 49 preceding chapters into scannable cheat sheets.
    • Five OAuth grant types matter for this course: authorization code+PKCE, client credentials, device authorization, the refresh token grant, and the UMA ticket-for-RPT exchange.
    • A realm's structure is: clients, users/groups, and roles live inside it; client scopes are a separate reusable layer attached to clients as default (always included) or optional (requested explicitly).
    • Access tokens prove authorization to an API; ID tokens prove authentication to the client itself; refresh tokens exchange for new tokens; RPTs are UMA's live-policy-computed access token variant.
    • ACL, RBAC, ABAC, PBAC, and ReBAC differ in what the access decision is computed from — Keycloak natively covers RBAC and ABAC/PBAC well, but has no first-class ReBAC engine.
    • SAML and OIDC solve the same federation problem with different wire formats (XML vs. JSON); neither has made the other obsolete.
    • Northwind Apps, Riverside Health, and Meridian Trust map to three different compliance drivers and IAM shapes — contractual/security expectations + multi-tenancy, HIPAA + dual populations, and PCI-DSS + fraud-aware step-up auth, respectively.
    • glossary.html, quizzes.html, labs.html, and exams.html are standing reference tools meant to outlive the linear 50-chapter structure.

    Self-check

    Click a question to reveal a model answer.

    1. A colleague asks which OAuth grant type fits a headless CI job that needs to call an internal API with no human present at all. Which one, and why not authorization code?

      Model answerClient credentials — there's no resource owner or browser involved, which is exactly what this grant type is for. Authorization code requires a human to complete a browser-based login step, which a headless CI job has no way to do.

    2. What's the practical difference between a default and an optional client scope, and why would a chapter-24-style custom claim mapper normally live on a default scope rather than an optional one?

      Model answerA default scope is included in every token the client requests automatically; an optional one only appears if the request's scope= parameter names it. A claim like tenant_id that an application always needs belongs on a default scope, so no caller has to remember to ask for it — making it optional would silently break any client that forgot the scope= parameter.

    3. Someone sends an ID token to a resource server's API instead of an access token, and the API accepts it. What's actually wrong here, and whose bug is it?

      Model answerIt's the resource server's bug, not the client's — an ID token's aud claim names the requesting client, never the API, so a correctly implemented resource server should reject it on audience-validation grounds. The fact that it "worked" means the API isn't checking aud at all, which is a real security gap, not a quirk to work around.

    4. Riverside Health needs "a nurse can only view charts for patients currently assigned to their shift and department." Which authorization model from the cheat sheet fits best, and why does plain RBAC fall short here?

      Model answerABAC — the decision depends on live attributes (current shift, department, which patients are assigned right now), not a static role assignment. RBAC alone would need a new role for every shift/department/patient-assignment combination, which explodes combinatorially and still can't express "currently assigned" without being re-computed constantly, which is what ABAC does natively at request time.

    5. A reader finishes all 50 chapters and asks "now what, when I forget something six months from now?" What's the honest answer this chapter gives?

      Model answerglossary.html, quizzes.html, labs.html, and exams.html are built to outlive the linear chapter structure specifically for this — re-reading a chapter front to back isn't the expected workflow six months later; looking up one term, retaking one quiz, or re-running one lab against a fresh Keycloak instance is.
