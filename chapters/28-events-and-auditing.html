    Part V — Keycloak Operations ~40 min Hands-on lab

    28. Events, Auditing & Monitoring

    Chapter 27 formalized how to act on northwind-apps through the Admin REST API and kcadm.sh. This chapter asks the opposite question: once an action has already happened — a login, a role change, a realm setting flipped — how does anyone, including the person who didn't do it, find out it happened at all? Keycloak's answer is its events subsystem: two independently switched streams (login/user events and admin events) plus a separate, unrelated pair of operational endpoints (/health and /metrics) that exist to tell a monitoring system whether the server itself is alive and busy — a different question entirely from "who did what." This chapter enables both event streams for real on the shared northwind-apps realm, generates one real admin event and one real login event, fetches both back through the REST API, and shows exactly what Keycloak does and does not expose toward an external SIEM.

    Why this matters

    An IAM specialist is the person an auditor, an incident responder, or a compliance officer comes to with "prove that only these three people could have made this change" or "tell me everything this account did in the last 90 days." If the IAM system wasn't configured to record that in the first place, there is no amount of after-the-fact log archaeology that recovers it — the record either exists because someone turned it on before the event happened, or it doesn't exist at all. Chapter 27 taught how to automate changes against Keycloak; this chapter teaches how to make those changes (and every login) reconstructable after the fact, which is the actual deliverable most compliance frameworks are buying when they say "audit trail."

    What concept is this?

    Chapter 3 named Accounting as the third formal part of AAA — the continuous, structured recording of identity and access events, distinct from audit, the later activity of reviewing what accounting produced. This chapter is where that distinction stops being abstract: Keycloak implements accounting as its realm Events subsystem, and the kcadm.sh get events/get admin-events calls later in this chapter are, literally, an audit — someone reviewing what the accounting subsystem already recorded. Chapter 9's threat-landscape material adds the other half of the motivation: you cannot detect credential stuffing, an anomalous spike of failed logins, or an admin account doing something it's never done before if the system never recorded the individual events in the first place. Detection is a query over a record that has to already exist; this chapter is about making sure it does.

    Two independent streams, four switches

    Keycloak does not have one "turn on logging" switch. Per the REST API's own RealmEventsConfigRepresentation schema (confirmed by reading the official REST API reference directly, not assumed from the Admin Console's layout), a realm's event configuration is six independent fields, and the two streams — login/user events and admin events — are each controlled by their own boolean, with no shared master switch:

    RealmEventsConfigRepresentation fields, per the official REST API reference
    FieldTypeControls
    eventsEnabledBooleanWhether login/user events (the left-hand stream below) are recorded at all.
    eventsExpirationLong (seconds)How long a recorded login/user event is retained before it ages out.
    eventsListenersList of stringWhich Event Listener SPI provider(s) receive every event as it occurs — jboss-logging is the built-in default on every realm, enabled or not.
    enabledEventTypesList of stringWhich specific login/user event types actually get saved — the realm default (confirmed live below) already lists every type Keycloak knows about.
    adminEventsEnabledBooleanWhether admin events (the right-hand stream below) are recorded at all — independent of eventsEnabled.
    adminEventsDetailsEnabledBooleanWhether a recorded admin event also carries the full JSON representation of what was created/updated/deleted — independent again, a second switch layered on top of the first.

    Event types: what actually gets recorded

    Per Keycloak's own Server Administration Guide (fetched live for this chapter, version matching the lab's 26.8.2), login/user event types fall into a handful of documented groups. The guide's own descriptions, quoted directly:

    A sample of documented login-event types, quoted from the official Server Administration Guide
    EventOfficial description
    Login"A user logs in."
    Register"A user registers."
    Logout"A user logs out."
    Code to Token"An application, or client, exchanges a code for a token."
    Refresh Token"An application, or client, refreshes a token."
    User disabled by permanent/temporary lockout"Brute force protection disabled the user account permanently/temporarily due to too many login failures."
    Update Credential"The password or (time-based) one-time Password (OTP/TOTP) settings for an account changes."

    The guide lists these as human-readable groups (login events, brute-force events, identity-brokering events, OAuth events, account events), but the REST API's actual enabledEventTypes field is a flat list of specific type constants — and the realm default is not a short list. Reading it back live (captured in the lab below) shows the out-of-the-box default already contains 102 distinct type constants (counted directly from the captured array, not estimated), covering everything from LOGIN/LOGIN_ERROR to niche ones like VERIFIABLE_CREDENTIAL_PRE_AUTHORIZED_GRANT_ERROR. "Each event has a corresponding error event" per the guide — that pattern (a success type and an _ERROR twin) holds for essentially every entry in that list, which is also why the list is roughly double the size of the human-readable groups the guide names.

    Health and metrics: a different question, a different port

    /health and /metrics do not answer "who did what" at all — they answer "is the server itself okay right now," which is a monitoring concern, not an audit one, and this course keeps the two separate on purpose. Per Keycloak's own Health checks guide (fetched live for this chapter) and confirmed live in the lab below, both are served on a separate management interface, port 9000 by default — not the main port 8080 that serves the Admin Console, Admin REST API, and every event endpoint this chapter has used so far.

    /health/live"Checks whether Keycloak is running. If this fails the application should be discarded."{"status":"UP","checks":[]}

    Key idea — Keycloak has no built-in SIEM connector

    Nothing this chapter ran sends events anywhere external on its own. "SIEM-style export" in practice means one of three real mechanisms, all confirmed to exist but none of them a one-click integration: (1) poll GET /admin/realms/{realm}/events and /admin-events on a schedule and forward the results, exactly like this chapter's own kcadm.sh get events calls, just automated; (2) point a log shipper (Filebeat, Fluentd, a sidecar) at the org.keycloak.events log category the built-in jboss-logging listener already writes to, which chapter 26's caching material and this chapter's own log line both confirm is a real, standard Java logging category, not a database table; or (3) write a custom Event Listener SPI provider (chapter 39's subject) that pushes each event to a message queue or SIEM API directly as it happens, instead of waiting to be polled. This chapter deliberately did not build any of the three end-to-end — doing so honestly would require a real external SIEM target, which is out of this chapter's scope — but every mechanism named above is real and REST-confirmed, not invented.

    Case study: Riverside Health's audit-controls requirement

    Case study — Riverside Health

    Riverside Health runs under the HIPAA Security Rule, and chapter 11 already pinned down the exact citation this chapter's mechanism answers: Audit controls (45 CFR §164.312(b)), which chapter 11 described as "accounting/audit trail by another name — hardware, software, and procedural mechanisms that record and examine ePHI system activity." That is not an abstract requirement once admin events with adminEventsDetailsEnabled=true are switched on: it is, concretely, the exact JSON this chapter's lab captured for priya.patel's role change — a timestamped record with authDetails.userId naming who made the change, operationType/resourceType/resourcePath naming what was touched, and representation showing the exact before/after value.

    Picture the same mechanism on Riverside's own realm instead: a clinician's access is elevated from "scheduling only" to "full chart access" for a shift, then revoked at shift's end. With admin events enabled exactly as configured in this lab, Riverside's compliance team can answer an auditor's "who had full chart access, when, and who approved it" with the same two-record pattern this chapter just produced for Northwind — a CREATE on a role-mapping resource followed by a later DELETE, each one independently timestamped and attributed to a specific admin user id. The one deliberate choice Riverside's team would need to make that Northwind's didn't: whether adminEventsDetailsEnabled's full representation field is itself safe to store for a PHI-adjacent resource, since that field can capture more of the underlying record's contents than a HIPAA minimum-necessary review might want sitting in a database long after the change happened — the pitfall below covers this concretely.

    Common mistakes

    • If you see admin events recorded but login events never showing up (or the reverse), the cause is almost always forgetting that eventsEnabled and adminEventsEnabled are two completely independent booleans on the same config object — there is no single "turn events on" switch, and flipping one does nothing to the other.
    • If you see an admin event's representation field missing even though admin events are clearly being recorded, the cause is almost always that adminEventsDetailsEnabled was left at its default false — adminEventsEnabled controls whether the event exists at all, adminEventsDetailsEnabled controls whether it carries the JSON body, and they are a third/fourth independent pair layered on the eventsEnabled/adminEventsEnabled pair above.
    • If you see a resource-owner-password-credentials grant fail with "error_description": "Account is not fully set up" even though the user's requiredActions array is empty, the cause — confirmed directly in this chapter's own run — can be a declarative user-profile field (here, firstName/lastName) the realm marks required that the user record simply never had set; the events stream's own error: "resolve_required_actions" record is the fastest way to confirm this rather than guessing from the generic OAuth error alone.
    • If you see a realm's representation fields on admin events carrying more of a user's underlying attributes than a compliance review is comfortable with, the cause is that adminEventsDetailsEnabled captures the full submitted JSON verbatim with no field-level filtering — a HIPAA- or PCI-scoped realm should decide this is acceptable deliberately, not discover it after the fact in an audit.
    • If you see curl http://localhost:8080/health (or /metrics) return 404 on a Keycloak 26.x instance even with KC_HEALTH_ENABLED=true set, the cause is that both endpoints live on the separate management interface (port 9000 by default), not the main HTTP port — confirmed live in this chapter's own run (200 on 9000, 404 on 8080 for the identical path).
    • If you see /metrics return 404 even though /health already works, the cause is that KC_METRICS_ENABLED is a separate opt-in from KC_HEALTH_ENABLED — enabling one does not enable the other, the same independent-switches pattern this whole chapter keeps running into.
    • If you see someone describe Keycloak as "exporting to our SIEM" with no further detail, the cause is usually treating the events REST API's mere existence as the integration — in reality someone still has to build the polling script, the log-shipper pipeline, or the custom Event Listener SPI provider; none of the three assembles itself.

    Glossary terms introduced here

    Takeaways

    • Keycloak's events subsystem is Keycloak's concrete implementation of chapter 3's "Accounting" — the continuous recording that a later "audit" (a human or a tool reviewing the record) depends on; without it, there is nothing to detect chapter 9's threats against or to show a chapter 11 auditor.
    • Login/user events and admin events are two fully independent streams, each gated by its own boolean (eventsEnabled / adminEventsEnabled) on the same RealmEventsConfigRepresentation — there is no single master "enable events" switch.
    • adminEventsDetailsEnabled is a third, independent switch layered on top of adminEventsEnabled: it controls whether the recorded event also carries the full JSON representation of what was created, updated, or deleted.
    • A freshly created realm already has jboss-logging as its event listener and a 102-entry enabledEventTypes default list — only the two main booleans are off by default; nothing about "what to record" needs configuring before "whether to record" does.
    • This chapter's own lab run hit a real, unplanned bug — a resource-owner-password-credentials grant failing with "Account is not fully set up" due to missing required profile fields — and the events stream's own resolve_required_actions record was the fastest real diagnostic path to the cause, which is itself a demonstration of why this chapter's subject matters operationally, not just for compliance paperwork.
    • Admin events answer "who changed what, from where, to what exact value, and when" via authDetails, operationType, resourceType, resourcePath, and representation together — the literal shape HIPAA's Audit controls provision (45 CFR §164.312(b)) asks for, as chapter 11 already named.
    • /health and /metrics answer a different question than events do — whether the server itself is alive and busy, not who did what — and in Keycloak 26.x both live on a separate management interface (port 9000 by default), confirmed live to 404 on the main port.
    • KC_METRICS_ENABLED and KC_HEALTH_ENABLED are separate opt-ins with the same default-off pattern; enabling one does not enable the other.
    • Keycloak ships no built-in SIEM connector. A real external integration still requires one of: polling the events REST API on a schedule, shipping the org.keycloak.events log category to an external pipeline, or writing a custom Event Listener SPI provider (chapter 39) — this chapter confirmed each mechanism exists without building one end-to-end.
    • Every JSON example in this chapter's lab sections is real, captured output from an actual run against a real Keycloak container — including the one genuine failure this session hit and fixed live.

    Self-check

    Click a question to reveal a model answer. Try answering it yourself first — the point is to check your own reasoning against it, not to read the answer first.

    1. Explain why eventsEnabled and adminEventsEnabled are independent booleans rather than one switch. Give a concrete scenario where an organization would deliberately want one on without the other.

      Model answerLogin/user events and admin events answer two different questions — who authenticated versus who changed configuration — and organizations have independent reasons to care about each at different volumes and risk levels. Keycloak's own RealmEventsConfigRepresentation models them as two separate booleans precisely so a deployment can tune each one against its own cost and risk profile instead of being forced into all-or-nothing. Concretely: a realm under active, frequent reconfiguration during a migration project might turn adminEventsEnabled off temporarily to avoid drowning in expected admin noise, while keeping eventsEnabled on because real user logins still need monitoring the whole time; a mostly-static production realm with rare admin changes but heavy daily login traffic might do the reverse, prioritizing the ability to trace every configuration change over storing high-volume login events it doesn't yet have a use for.

    2. Walk through exactly what adminEventsDetailsEnabled adds to an admin event record, and explain why a HIPAA- or PCI-regulated organization should weigh turning it on deliberately rather than reflexively enabling every flag "for compliance."

      Model answeradminEventsDetailsEnabled adds the full representation field — the raw JSON body of what was created, updated, or deleted — on top of the base fields (operationType, resourceType, resourcePath, authDetails) that adminEventsEnabled alone already provides. Without it, an auditor can see that something changed and who changed it, but not the actual before/after value. A HIPAA- or PCI-regulated organization should weigh it deliberately because, as this chapter's pitfall notes, representation captures the submitted JSON verbatim with no field-level filtering — meaning it can store more of a user's or patient's underlying attributes in the events database, for the whole retention window, than a "minimum necessary" review would want. The right approach is a documented decision per resource type, not a reflex "turn everything on for compliance."

    3. This chapter's own lab hit "Account is not fully set up" on a password grant. What was the real cause, and why did checking the user's requiredActions array alone fail to reveal it?

      Model answerThe real cause was that priya.patel's user record was missing mandatory declarative user-profile fields (firstName/lastName) that the realm's user profile configuration requires — not a pending required action on the account. Checking requiredActions alone fails to reveal this because that array only lists explicitly assigned actions like "update password" or "verify email"; it has nothing to do with the user-profile validation layer, which is a separate mechanism that rejects the login before required actions even come into play. The only place the real cause actually surfaced was the login event's own error: "resolve_required_actions" record with reason: "Account is not fully set up".

    4. Why do /health and /metrics live on a different port than the events endpoints in Keycloak 26.x, and what operational purpose does keeping them separate actually serve?

      Model answer/health and /metrics live on Keycloak's separate management interface (port 9000 by default) rather than the main port (8080, which serves the Admin Console, Admin REST API, and the events endpoints) because they serve a fundamentally different audience: automated infrastructure (a container orchestrator's liveness probe, a Prometheus scraper) that polls constantly, rather than human administrators or applications. Keeping them on a separate port lets an operator firewall the management interface off from the public internet entirely — since nothing outside the infrastructure layer needs it — while still exposing the Admin REST API on 8080 to the administrators and applications that legitimately need it, without either traffic pattern interfering with or being exposed alongside the other.

    5. Using the real admin-event JSON this chapter captured for Priya's role change, explain concretely how an auditor would use operationType, resourceType, resourcePath, and representation together to answer "who changed what, when" for a HIPAA audit.

      Model answerFor the CREATE event, operationType: "CREATE" and resourceType: "REALM_ROLE_MAPPING" tell the auditor what kind of action happened (a role was granted, not revoked); resourcePath (users/aa775ccf.../role-mappings/realm) identifies exactly which user's role mapping was touched; representation shows the exact role granted (platform-engineer, by id and name); and authDetails.userId/ipAddress identifies which admin account made the change and from where, with the record's own time field giving the timestamp. Read alongside the paired DELETE event (support-agent removed one second earlier, same resourcePath), the auditor can reconstruct the complete before/after state change — attributable to a specific admin, at a specific time, from a specific location — which is exactly the "who changed what, when" shape 45 CFR §164.312(b) asks for.

    6. Keycloak's built-in jboss-logging listener, by default, only writes error events to the server log. What would a real external SIEM integration need beyond what this listener already provides, based on what this chapter actually confirmed?

      Model answerA jboss-logging-only setup gives error-level login events in the server's text log, but a real SIEM integration needs one of the three mechanisms this chapter confirmed actually exist: a scheduled poller hitting GET /admin/realms/{realm}/events and /admin-events and forwarding the results — the same calls this chapter ran manually, just automated; a log shipper (Filebeat, Fluentd, a sidecar) pointed at the org.keycloak.events log category to capture more than just error-level entries and ship them off-box; or a custom Event Listener SPI provider (chapter 39) that pushes every event to a message queue or SIEM API as it happens, instead of waiting to be polled. None of these exist out of the box — Keycloak ships no built-in SIEM connector, so one of the three has to actually be built.
