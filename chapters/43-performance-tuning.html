    43. Performance Tuning & Database Considerations

    A Keycloak realm that works perfectly in a chapter-20-style single-node lab can still fall over the first week it carries real traffic — not because anything is "broken," but because nobody sized the database connection pool, the JVM heap, or the cache for what production actually asks of it. This chapter is about that sizing: where load really concentrates in a running Keycloak deployment, and the specific, live-verified knobs — database choice and tuning, the connection pool, JVM/GC flags, and cache sizing — that keep it responsive once real users (and real automation) show up.

    Sources digested: Keycloak's own Configuring the database, High Availability, Getting started: Scaling and tuning, and Observability guides, plus the Keycloak Benchmark project's JVM options reference — all live-checked against keycloak.org on 2026-11-11 against the current release, Keycloak 26.8.2.

    Why this matters

    An IAM specialist doesn't get credit for standing up Keycloak — they get paged when it's slow. Chapter 41 proved that clustering and Infinispan caching keep a session visible across nodes; chapter 29 explained what state Keycloak actually tracks per user. Neither chapter answers a question every production deployment eventually asks: why is the token endpoint suddenly slow at 9 a.m. on a Monday, and which of the five knobs above is the one to turn? This chapter builds the diagnostic vocabulary and the specific, sourced tuning knobs to answer that — using Meridian Trust's high-volume banking traffic as the running example, because its login/refresh/step-up-auth volume is exactly the shape Keycloak's own capacity guidance is written to size for.

    What concept is this?

    Three earlier chapters already built the pieces this chapter tunes. Chapter 19 drew Keycloak's architecture diagram with a database and an embedded cache sitting next to the server, and promised "chapter 43 covers performance tuning and database sizing in depth." Chapter 29 explained what state Keycloak actually tracks per user — sessions, refresh tokens, offline sessions — the thing that has to live somewhere and be found quickly. Chapter 41 explained how that state stays consistent across multiple nodes via Infinispan, and which caches are genuinely distributed versus local. This chapter doesn't re-explain any of that; it asks the operational question those three leave open: given that architecture and that state, how big does each moving part — the database connection pool, the JVM heap, the cache itself — actually need to be, and what breaks first if you get it wrong?

    Two migration-mechanics facts matter more for tuning than the version numbers themselves. First, schema changes are entirely Keycloak's own responsibility via its connections-jpa provider's migrationStrategy option — update (the default, applies pending changes automatically), manual (writes a SQL file for a DBA to review and run), or validate (fails startup if the schema isn't already current). Hand-editing Keycloak's own tables or adding ad-hoc indexes outside that mechanism risks breaking an assumption a future migration relies on — it is not a sanctioned tuning lever. Second, a MySQL-specific gotcha: starting with MySQL 8.0.30, a server-level setting called sql_generate_invisible_primary_key can auto-generate primary keys for tables created without one, which collides with Keycloak's own schema initialization and fails migrations with a "Multiple primary key defined" error — it must be set to OFF before installing or upgrading Keycloak on MySQL 8.0.30+.

    Common mistake

    If a fresh Keycloak install on MySQL fails startup with a "Multiple primary key defined (1068)" error, the cause is almost never a Keycloak bug — it's sql_generate_invisible_primary_key still set to its MySQL 8.0.30+ default. Check that server setting before filing a bug report.

    Vendor-specific tuning knobs that actually move the needle

    Beyond picking a supported version, Keycloak's own database guide documents several vendor-specific behaviors that directly affect throughput under real load — not generic database advice, but things Keycloak itself configures or assumes:

    • PostgreSQL asynchronous commits. Transactions that only touch ephemeral tables — persisted user sessions, client sessions, or events — use PostgreSQL's synchronous_commit = off by default, trading a small window of durability risk on a crash for lower write latency on exactly the high-volume, low-stakes writes session/event traffic generates. Logouts still force a synchronous commit, because losing a logout record has real security consequences. This can be disabled with --spi-connections-jpa--quarkus--async-commit=false if an organization's durability requirements demand it.
    • Writer/reader instance targeting (PostgreSQL/Aurora). When PostgreSQL or Amazon Aurora PostgreSQL runs with separate writer and reader instances, Keycloak must always connect to the writer — it sets the JDBC driver's targetServerType property to primary by default specifically to avoid ever landing on a read replica during a failover or switchover. A team that assumes it can point Keycloak's read traffic at a cheaper reader instance to save cost is working against a deliberate safety default, not an oversight.
    • MySQL/MariaDB connection lifetime vs. wait_timeout. Keycloak defaults db-pool-max-lifetime to 7 hours 50 minutes specifically because MySQL/MariaDB's own default wait_timeout is 8 hours — a pooled connection must be recycled by Keycloak before the server itself silently closes it, or the pool starts handing out dead connections that fail with "No operations allowed after connection closed." If an organization lowers its own wait_timeout without lowering db-pool-max-lifetime to match, this exact failure reappears.
    • Transaction isolation under concurrent logins (MySQL/MariaDB). Keycloak's optional stateless feature (next slide) sets the isolation level to READ COMMITTED specifically to avoid deadlocks caused by gap locks on upsert statements under concurrent logins — a real, documented failure mode under exactly the kind of login-burst traffic a bank's morning rush produces.
    Case study — Meridian Trust

    Meridian Trust runs PostgreSQL with a writer and two reader replicas for its broader banking platform, and an early design review proposed pointing Keycloak's read-heavy traffic (session/token lookups) at a reader to offload the writer. Keycloak's own targetServerType=primary default exists precisely to prevent this: Keycloak's reads and writes are tightly coupled to the same transaction boundaries (a login reads and writes a session in close succession), so a reader instance that lags the writer even slightly can serve stale or missing data mid-login. The reader replicas stay reserved for the bank's other, genuinely read-only reporting workloads instead.

    Sizing the connection pool: Agroal, confirmed by name

    Keycloak's Quarkus distribution does not name its JDBC connection pool technology in the prose of its own database guide — but it doesn't have to, because the pool's own metric names give it away directly. Keycloak's observability guide documents three database connection pool metrics: agroal_available_count (idle connections), agroal_active_count (connections in active use), and agroal_awaiting_count (threads waiting for a connection to free up). Those names confirm, straight from Keycloak's own current documentation, that the underlying pool is Agroal — the connection-pool implementation built into Quarkus itself, not HikariCP or any other library a Java developer might expect by default.

    Keycloak's documented connection-pool options (confirmed against keycloak.org/server/db)
    OptionControlsDefault
    db-pool-initial-sizeConnections opened immediately at startupNot stated — treat as 0 unless set
    db-pool-min-sizeFloor the pool shrinks back to when idleNot stated — treat as 0 unless set
    db-pool-max-sizeCeiling the pool grows to under load100
    db-pool-max-lifetimeHow long a connection stays open before forced recyclingVendor-dependent (MySQL/MariaDB: 7h50m, per the previous slide)

    Keycloak's own High Availability guide gives one specific, quotable recommendation that overrides the intuition that "bigger max is always safer": set initial, min, and max to the same value. Two independent reasons back this up. First, opening a brand-new database connection is itself slow — doing it mid-request delays that specific response, and a traffic spike that forces many new connections open at once (a "stampede") makes the slowdown worse, not better. Pre-opening the full pool at startup avoids ever paying that cost during real traffic. Second, an open connection lets the database cache the query plans run on it — PostgreSQL, for instance, only promotes a query to a server-side prepared statement after it has run roughly five times on the same connection. Closing and reopening connections constantly (what a 0-floor pool does under light load) throws that cache away repeatedly, which costs more than the memory a few idle connections uses.

    Common mistake

    If agroal_awaiting_count climbs under load, the instinctive fix is "raise db-pool-max-size." Keycloak's own observability guide warns this isn't always right — a larger pool can simply push the bottleneck onto the database itself, which then becomes the slow part. It also recommends checking whether http-pool-max-threads (the HTTP worker thread count) is set higher than the database can actually support, and lowering it to match instead of growing the pool — fewer, well-matched threads reduce contention rather than just moving it downstream.

    JVM heap and garbage-collection tuning

    Keycloak's Quarkus distribution still runs on a JVM (there is no native-image option for the features this course relies on), so standard JVM heap and GC flags apply — but Keycloak's own benchmark project scopes the recommendation down to a short, specific list rather than every flag the JVM supports:

    JVM flags named in Keycloak's own benchmark/tuning guidance
    FlagPurpose
    -XX:MaxRAMPercentage / -XX:MinRAMPercentage / -XX:InitialRAMPercentageSize the heap as a share of visible memory — the right choice in a container, where the JVM can see the container's memory limit
    -Xms / -XmxAbsolute initial/maximum heap size — the right choice outside a container, on a fixed host
    -XX:+UseG1GCEnable the G1 garbage collector
    -XX:MaxGCPauseMillisTarget maximum GC pause time
    -Xlog:gc:file=<path>Write GC activity to a log file for later analysis

    Two pieces of general guidance matter more than any single flag value. First, Keycloak's own Scaling and tuning guide advises profiling before resizing: "it is best to determine what is contributing to the increased footprint using a heap dump" rather than guessing at a bigger number. Second, the same guide states a clear preference — "adjusting the memory request and limit is preferable to horizontal scaling" — when the problem is genuinely memory pressure rather than raw request throughput; adding nodes doesn't fix an undersized heap on each one. A heap set too small makes GC run more often (shorter pauses, but constant ones); a heap set too large lengthens individual pauses — the right size sits between those two failure modes, found by measuring under real load, not guessed in advance.

    The getting-started guide also names a signal worth recognizing before touching the JVM at all: excessive response times that trace back to an oversized HTTP work queue often mean the fix is load shedding (rejecting or queuing less aggressively) rather than more memory — a symptom that looks like "needs more heap" but is actually "is accepting more concurrent work than it can finish."

    Cache-tuning trade-offs, building on chapter 41

    Chapter 41 already established the mechanics: Keycloak's embedded Infinispan splits caches into distributed ones (sessions and their variants, replicated across nodes) and local ones (realms, users, keys, authorization, crl — kept fresh by cross-node invalidation, falling back to the database on a miss). This chapter only adds the tuning layer on top of that split.

    Two concrete tuning levers follow directly from that model. First, cache size is a real setting, not just an on/off switch — Keycloak's High Availability guide recommends growing the users cache by roughly 2x and the realms cache by roughly 4x the number of concurrently active clients once that count exceeds about 2,500, specifically because an undersized cache evicts entries that are still being actively used, forcing database round trips that a bigger cache would have avoided entirely. Second, watch the warm-up gap: caches start empty on every restart and only reach their steady-state hit ratio after real traffic refills them, so a capacity plan based on post-warm-up measurements alone will under-provision for the minutes right after every deploy or failover.

    A newer, more fundamental trade-off is now fully supported rather than experimental: Keycloak 26.8.0 promoted an optional stateless feature (--features=stateless, off by default) from preview to supported. Enabled, it moves volatile data — authentication sessions, action tokens, brute-force failure counters — out of Infinispan and into the database instead, eliminating the external-cluster complexity chapter 41 covers entirely. The documented cost is concrete, not hand-waved: roughly 8-10ms of added latency per authentication interaction, and database CPU/IOPS load roughly doubling, because state that used to be a memory lookup becomes a database round trip on every request. For a single cluster, it mainly trades cache-rebalance disruption for steady extra database load; for a multi-site deployment it also demands a synchronously replicated database with sub-10ms inter-site latency, which rules it out across real geographic regions. It is a genuine option, not yet the default, and sizing a database for roughly double its current load is the real price of choosing it.

    Common mistakes and pitfalls

    • If connections keep timing out under load, the cause is often not a too-small pool but http-pool-max-threads set higher than the database can actually serve — check and lower thread count before raising db-pool-max-size.
    • If the pool is "sized" but still feels slow on a cold start, the cause is usually db-pool-initial-size/db-pool-min-size left at their defaults (0) while only db-pool-max-size was tuned — the pool is still opening connections on demand during exactly the traffic it was supposed to absorb instantly.
    • If MySQL/MariaDB throws "No operations allowed after connection closed" under sustained traffic, the cause is almost always db-pool-max-lifetime left larger than (or equal to) the database server's own wait_timeout — the server is closing connections the pool still thinks are alive.
    • If a fresh MySQL 8.0.30+ install fails migration with "Multiple primary key defined (1068)", the cause is sql_generate_invisible_primary_key still on at the server level, colliding with Keycloak's own schema initialization — not a Keycloak defect.
    • If GC pauses or memory pressure show up after a traffic increase, the cause is rarely "needs a bigger number" without evidence — Keycloak's own guidance is to take a heap dump first and resize based on what it shows, not to guess-and-check in production.
    • If cache hit ratios look fine in steady state but the deployment struggles right after every rolling restart, the cause is the cache warm-up gap — caches start empty and need real traffic to refill, which a steady-state-only capacity plan doesn't account for.
    • If someone proposes pointing Keycloak's reads at a database read replica to save cost, the cause of the resulting bugs is ignoring why targetServerType=primary is the default — Keycloak's reads and writes inside one login are too tightly coupled to tolerate replica lag.

    Takeaways

    • Load on a real Keycloak deployment isn't uniform — browser logins, client-credential grants, bulk Admin REST automation, and event writes stress the cache and the database in very different proportions, and "Keycloak is slow" is really four different possible problems.
    • Keycloak's officially supported database versions change every release — this chapter's own tested-version table (PostgreSQL 18, MariaDB 11.8, MySQL 8.4, MSSQL 2022, Oracle 23.5, live-verified 2026-11-11 against 26.8.2) is exactly the kind of fact to re-verify, not memorize.
    • Schema changes belong entirely to Keycloak's own migrationStrategy mechanism (update/manual/validate) — hand-tuning indexes or editing Keycloak's own tables directly is not a sanctioned lever.
    • Keycloak's connection pool metric names (agroal_active_count, agroal_available_count, agroal_awaiting_count) confirm the underlying technology is Agroal, the pool built into Quarkus — not HikariCP.
    • Keycloak's own High Availability guide recommends setting db-pool-initial-size/min/max all equal, to avoid both connection-creation stampedes under load and the loss of server-side statement caching every time a connection closes and reopens.
    • A bigger connection pool is not automatically a safer one — it can just move the bottleneck onto the database; matching http-pool-max-threads to actual database capacity is often the better first fix.
    • JVM heap sizing should start from a heap dump, not a guess, and vertical resizing (more memory/CPU per node) is Keycloak's own stated preference over horizontal scaling when the problem is genuinely memory pressure.
    • Chapter 41's local caches (realms/users/keys) are a read-through accelerator, not a second source of truth — a miss always falls through to the database and refills the cache, and both cache size and the post-restart warm-up gap are real, separate tuning levers.
    • Keycloak's stateless feature (now supported as of 26.8.0, off by default) trades Infinispan's cross-node cache replication for a database that has to absorb roughly double the CPU and IOPS load and ~8-10ms of added per-login latency — a real option, not a free upgrade.
    • Keycloak's own capacity guidance gives concrete per-vCPU throughput budgets for password logins, client-credential grants, and refresh requests, plus a database IOPS budget per 100 req/s — numbers this chapter applied directly to a Meridian Trust-shaped traffic target rather than treating capacity planning as guesswork.

    Self-check

    Click a question to reveal a model answer. Try answering it yourself first — the point is to check your own reasoning against it, not to read the answer first.

    1. A colleague says "Keycloak is slow" without any more detail. What four distinct traffic shapes would you ask about first, and why does each one stress a different backend resource?

      Model answerBrowser password/refresh logins (mostly session-cache traffic, light on the database once a session exists), service-to-service client-credential grants (high raw request rate from automation, but mostly stateless signing), bulk Admin REST API calls from provisioning/CI automation (writes that hit the database directly and can't be served from a read cache), and event writes if event persistence is enabled (an append-heavy database write per login, which scales with user volume rather than admin activity). "Slow" means something different depending on which of these dominates, so the diagnosis has to start by identifying which traffic shape is actually growing.

    2. Why does Keycloak's own High Availability guide recommend setting the connection pool's initial, minimum, and maximum size to the same value, instead of leaving initial/min low to save resources when idle?

      Model answerTwo reasons. Opening a new database connection is itself slow, so a pool that creates connections on demand pays that cost during real traffic, and a sudden spike that needs many new connections at once makes it worse (a connection-creation stampede). Second, keeping connections open preserves server-side statement caching — PostgreSQL, for example, only promotes a repeated query to a cached prepared statement after it runs several times on the same connection, so a pool that keeps closing and reopening connections under light load throws that caching benefit away constantly. The small resource cost of a few idle, pre-opened connections is worth avoiding both problems.

    3. Agroal's own metrics are named agroal_active_count, agroal_available_count, and agroal_awaiting_count. If agroal_awaiting_count is climbing under load, what are two different fixes to consider, and why isn't "just raise db-pool-max-size" always the right one?

      Model answerOne option is raising db-pool-max-size so more connections are available. The other, which Keycloak's own observability guide calls out explicitly, is lowering http-pool-max-threads so the number of concurrent HTTP workers actually matches what the database can support. Simply raising the pool size risks pushing the real bottleneck onto the database itself — more connections competing for the database's finite capacity can make the database the slow part instead of fixing anything, whereas matching the thread count to database capacity reduces contention at the source.

    4. Explain, in your own words, why Keycloak defaults to connecting only to a PostgreSQL/Aurora writer instance (targetServerType=primary) rather than letting read traffic go to a cheaper reader replica.

      Model answerA single login or token operation reads and writes session/token state within the same tight transaction boundary — for example, reading whether a session exists and then immediately updating it. A reader replica can lag the writer by even a small amount, which is enough for a read immediately following a write to see stale or missing data mid-login. Keycloak's reads and writes are too tightly coupled for that lag to be safe, so it defaults to always hitting the writer, even though that forgoes the cost savings a reader replica could otherwise offer for genuinely read-only traffic elsewhere in an organization's systems.

    5. What does Keycloak's stateless feature actually trade away, and under what condition would you NOT recommend enabling it even though it's now a supported (not preview) feature as of 26.8.0?

      Model answerIt moves volatile state (authentication sessions, action tokens, brute-force counters) out of Infinispan and into the database, which eliminates the operational complexity of running and maintaining an external Infinispan cluster (chapter 41's subject) — but at the documented cost of roughly double the database's CPU and IOPS load, plus about 8-10ms of extra latency per authentication interaction, because state that used to be a memory lookup becomes a database round trip. It would be a poor fit for a deployment whose database is already close to its capacity ceiling, since doubling its load could make the database the new bottleneck; it's also a hard requirement mismatch for any genuinely multi-region deployment, since it needs a synchronously replicated database with sub-10ms inter-site latency that real geographic regions can't provide.
