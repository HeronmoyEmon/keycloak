    41. High Availability & Clustering

    One Keycloak node is a single point of failure for every application that trusts it — chapter 1's "new single point of failure" con, made concrete. This chapter answers the obvious follow-up: run more than one node. The hard part isn't starting a second process; it's making sure a session created on node A is still recognized on node B, so a load balancer can send the next request anywhere without forcing a re-login. This chapter stands up two real Keycloak 26.8.2 nodes, clusters them for real, and proves — with real HTTP transcripts — that the second node recognizes a session it never created.

    Why this matters

    An IAM specialist who has only ever run Keycloak as one container doesn't yet know what "production-ready" actually requires. Every real deployment with uptime expectations runs more than one node, and the single thing that makes that work — not break SSO, not force every user to log in again every time a load balancer picks a different backend — is session state that every node can see. This chapter makes that mechanism concrete instead of abstract: which cache technology Keycloak embeds, how two nodes find each other without a hand-maintained host list, and exactly what breaks (twice, for real, while building this chapter) if you get the details wrong.

    Sources for this chapter: Keycloak's own Configuring distributed caches guide and High Availability introduction and guides (both fetched live for Keycloak 26.8.2 — see the next slides for exactly which claims came from the docs versus the running server itself); the real quay.io/keycloak/keycloak:26.8.2 image's own start --help-all output and bundled conf/cache-ispn.xml, inspected directly; and this chapter's own two-node lab (the docker-compose.yml given on this chapter's own lab slide), run against a real, disposable two-node Keycloak + PostgreSQL Docker Compose stack this chapter owns.

    What concept is this?

    Chapter 19 introduced Keycloak's architecture at a high level and named Infinispan as the embedded cache "previewed here; full depth and hands-on configuration in chapter 41" — this is that chapter. Chapter 29 then went deep on what a session actually is inside one Keycloak node: an SSO session with child client sessions, tracked in an in-memory cache, identified by a sid claim. This chapter is where those two threads meet production reality — a session created on one node has to be visible to another node for "high availability" to mean anything more than "two processes that happen to share a database." That visibility problem is exactly what Infinispan's cache replication solves, and exactly what this chapter's lab proves end to end rather than asserts.

    From one node to a cluster: what actually changes

    A single Keycloak node already has an in-memory cache — it just never needs to talk to anyone else, because there's no one else to talk to. Add a second node behind the same load balancer and database, and two new problems appear at once: the two nodes need to find each other (discovery), and once found, they need to keep certain in-memory state consistent between them (replication) — otherwise a request routed to node B has no idea the user already has a live session on node A.

    A real distinction, confirmed from the running server, not assumed

    Keycloak embeds several named Infinispan caches, not one undifferentiated blob of "state." Checking the real 26.8.2 server's own start --help-all output directly shows an exact, documented split: some per-cache size options are explicitly annotated "Available only when embedded Infinispan clusters configured" — those are the caches that actually get distributed/replicated across nodes. Others carry no such annotation — those are local caches, present on every node regardless of clustering, kept roughly in sync by cross-node invalidation messages rather than full replication, falling back to the database on a miss.

    Keycloak 26.8.2's own embedded cache names, split by how each one behaves across a cluster -- confirmed directly from `start --help-all`, not inferred

    Why this distinction matters

    It's tempting to assume "clustering" means "every cache is now replicated everywhere." It doesn't, and conflating the two leads to wrong assumptions about consistency. Realm and user data doesn't need full replication because the database is always the authoritative source and an invalidation message is enough to keep a local cache from serving stale data after a write. Session data is different: a session genuinely has no other durable home by default (offline sessions are the one exception, persisted to the database specifically so they survive a restart) — so if session caches weren't actually replicated, this chapter's entire premise would be false. The lab below checks exactly this, directly, rather than taking the distinction on faith.

    JGroups, and the discovery protocol this version actually defaults to

    Keycloak's clustering is built on two layers: Infinispan (the cache/data-grid library itself) running on top of JGroups (the group-communication toolkit that handles node discovery and message delivery between cluster members). Live-verified directly against the real 26.8.2 image's start --help-all output — not assumed from older Keycloak versions' documentation, which this chapter checked and found materially different:

    • --cache controls whether clustering is even attempted: ispn (the production-mode default) clusters nodes together; local (the start-dev default) disables clustering outright, giving every node its own isolated, non-clustered cache. This chapter's lab runs start-dev (matching every other chapter's lab, no TLS/hostname ceremony needed) but must explicitly pass --cache=ispn to override that dev default — otherwise the two "nodes" would just be two unrelated servers that happen to share a database, and this entire lab would silently be a no-op.
    • --cache-stack selects the discovery mechanism, and its documented default as of 26.8.2 is jdbc-ping — nodes discover each other by writing and reading rows in a small table inside the same database Keycloak already connects to for everything else, with no separate discovery service, no static host list, and no multicast network support required. The same help text explicitly marks kubernetes, jdbc-ping-udp, tcp, udp, ec2, azure, and google as deprecated stack options — confirming the brief's own suspicion that older TCP/UDP-list-based guidance no longer reflects this version's real default for a non-Kubernetes deployment.
    • JGroups traffic between nodes is encrypted with mTLS by default (--cache-embedded-mtls-enabled, default true) whenever a TCP-based stack is used — which jdbc-ping is. With no keystore/truststore configured, Keycloak generates and rotates ephemeral certificates automatically. Confirmed live in this chapter's own lab boot log, unprompted: "JGroups Encryption enabled (mTLS)".

    Meridian Trust: why a bank can't run one node

    Case study — Meridian Trust

    Meridian Trust is a retail bank (chapter 9/11: PCI-DSS, fraud-aware authentication). Online banking logins are not an 8-to-5 activity, and a bank's SLA pressure is existential in a way a smaller SaaS tool's isn't: an identity outage during a payroll-day rush, or during a fraud-driven step-up-authentication spike, has direct financial and regulatory consequences, not just an annoyed support queue. A single Keycloak node is a hard outage risk that chapter 1 already named abstractly as a trade-off of centralizing identity at all — "a new single point of failure." Running a cluster doesn't remove that trade-off; it's the concrete, operational answer to it: multiple nodes behind a load balancer mean a lost node (a crash, a patch restart, a deploy) doesn't take down every connected application's login at once, and the session a customer already holds survives the node that minted it going away.

    This is also precisely the chapter where "centralizing authentication" (chapter 1's thesis) stops being free. A single node is operationally simple; a cluster adds real complexity — shared database contention, cache-coherency behavior to understand, and (as this chapter's own lab found, twice) genuinely non-obvious cross-node configuration requirements. Meridian Trust accepts that complexity because the alternative — one node, one failure, one outage — is unacceptable for a regulated bank's customer-facing banking application.

    Lab, real bug #1: a login rejected before the cluster ever mattered

    With the cluster confirmed, the first direct-grant login attempt for a fresh test user (priya.teller, Meridian Trust's realm) failed immediately — before clustering was even relevant to the failure:

    {"error":"invalid_grant","error_description":"Account is not fully set up"}

    The user had a password credential and an empty requiredActions list, which made this confusing at first. Real cause, confirmed by checking the realm's registered required actions directly: VERIFY_PROFILE is enabled by default and gets dynamically resolved for any user whose profile is missing attributes the realm's Declarative User Profile expects (email, first/last name here) — it doesn't need to appear in that user's own requiredActions array to fire, and a direct grant has no browser to satisfy an interactive required action with, so it's rejected outright. This is the same VERIFY_PROFILE-shaped gotcha chapters 24 and 39's labs already hit independently — a recurring trap, not a one-off. Fixed for this lab by disabling the action realm-wide:

    curl -X PUT ".../authentication/required-actions/VERIFY_PROFILE" \
  -d '{"alias":"VERIFY_PROFILE", ..., "enabled": false}'   # 204, then login succeeded

    Lab, real bug #2: the actual clustering bug, found on the very first cross-node test

    With login working, the first attempt at this chapter's real point — presenting node A's refresh token to node B — failed too, but for a reason that has nothing to do with whether session replication itself was working:

    {"error":"invalid_grant","error_description":
  "Invalid token issuer. Expected 'http://localhost:18142/realms/ch41-meridian-trust'"}

    Keycloak derives a token's iss (issuer) claim from the request's own Host header unless told otherwise. Node A, reached on port 18141, minted a token with iss=...:18141; node B, reached on port 18142, computed its own expected issuer as ...:18142 and rejected the mismatch — a real, reproducible bug, not a hypothetical. Every real multi-node deployment avoids this by sitting behind one load balancer with one public hostname, so every node computes the identical issuer regardless of which one actually serves a given request. This lab's fix models that directly: both nodes are configured with the identical KC_HOSTNAME=http://localhost:18141, even though node B is still reached on its own distinct port 18142 for every curl command below — the forced shared hostname is this lab's stand-in for "behind one load balancer," without needing a third (nginx/HAProxy) container.

    Worth remembering

    If a multi-node Keycloak deployment rejects tokens with an issuer mismatch, the fix is almost never in the cache/clustering layer at all — it's a hostname configuration problem. Clustering and hostname consistency are two separate requirements that both have to be right before cross-node session recognition can work; this chapter's lab hit both, in that order, by accident rather than by design, which is exactly why it's worth documenting honestly.

    Lab: proving it a second way — and proving it's bidirectional

    The refresh-token proof shows node B can read a session node A created.     Real result from this run: of three active sessions, the one revoked through node B was immediately absent from node A's own session listing, while the other two, untouched, remained visible on both.     Common mistakes

    • If a multi-node deployment rejects a token with an issuer mismatch ("Invalid token issuer"), the cause is almost never the cluster or cache layer — it's every node computing a different iss claim from its own request Host header. Fix it by giving every node the same KC_HOSTNAME (in production: put every node behind one load balancer with one public hostname), not by debugging Infinispan.
    • Don't assume start-dev's cache behavior matches production. Dev mode defaults to --cache=local, which silently disables clustering outright — a lab or a quick local test using start-dev with no explicit --cache=ispn will never cluster, with no error or warning at all.
    • Don't assume every Infinispan cache replicates the same way. sessions/ clientSessions/offlineSessions/offlineClientSessions are genuinely distributed; realms/users/keys are local caches kept fresh by invalidation, not full replication — confirmed directly from the real server's own --help-all output, not assumed from the word "clustering" alone.
    • If "Account is not fully set up" appears for a brand-new test user in any multi-node (or single-node) lab, suspect the realm's VERIFY_PROFILE dynamic required action before suspecting anything about clustering — this is the fourth chapter in this course to hit it independently (24, 39, and now 41).
    • Older Keycloak documentation, blog posts, or Stack Overflow answers describing TCPPING with a hand-maintained static member list, or UDP multicast discovery, are describing a deprecated discovery stack for this version — confirmed directly from the live 26.8.2 help text, which marks tcp, udp, and several cloud-specific stacks deprecated in favor of jdbc-ping as the current non-Kubernetes default.
    • Don't mistake "the cluster view shows both nodes" for "the lab is done." Forming a cluster view is necessary but not sufficient — this chapter's own first cross-node refresh attempt failed for an unrelated issuer-mismatch reason even with a healthy two-member cluster view already confirmed in the logs.
    • A single Docker host running two Keycloak containers is a real test of cross-node cache logic, but it is not a test of real host failure or network partition behavior — don't cite this kind of lab as proof of failover resilience without naming that limitation explicitly, the same honesty this chapter's own lab section leads with.

    Glossary terms introduced here

    Takeaways

    • A single Keycloak node is chapter 1's "new single point of failure" trade-off made literal; clustering is the operational answer, not a way to make that trade-off disappear.
    • Clustering requires solving two separate problems: discovery (finding other nodes) and replication (keeping the right in-memory state consistent between them).
    • As of 26.8.2, Keycloak's documented default discovery stack for a non-Kubernetes deployment is jdbc-ping — nodes discover each other through the same database they already use, with tcp/udp/cloud-specific stacks confirmed deprecated.
    • Not every embedded cache replicates the same way: session-family caches (sessions, clientSessions, offline variants) are genuinely distributed; realms/users/keys are local caches kept fresh by invalidation, falling back to the always-authoritative database.
    • start-dev's default cache mode is local, which silently disables clustering — a lab or quick test must explicitly pass --cache=ispn to actually cluster, with no warning if you forget.
    • JGroups traffic between embedded Infinispan nodes is mTLS-encrypted by default on a TCP-based stack (which jdbc-ping is), with Keycloak auto-generating and rotating ephemeral certificates if none are configured.
    • A token's issuer (iss) claim is derived per-node from the request's own hostname unless KC_HOSTNAME is forced identically across every node — the real cause behind an "Invalid token issuer" error in a freshly built cluster, and the reason every real multi-node deployment sits behind one load balancer with one public hostname.
    • This chapter's lab proved cross-node session recognition two independent ways — a cross-node refresh-token grant, and a cross-node Admin REST session list/revoke — confirming replication works in both directions (reads and writes), not just one.
    • Proving session replication on one Docker host with two containers is genuinely different from proving real multi-host failover or network-partition behavior — this lab is explicit about which one it actually demonstrates.

    Self-check

    Click a question to reveal a model answer. Try answering it yourself first.

    1. A colleague says "we clustered Keycloak, so now every cache is replicated across every node." What's wrong with that statement, and what's actually true?

      Model answerIt overgeneralizes. Only the session-family caches (sessions, clientSessions, offlineSessions, offlineClientSessions) plus a few coordination caches (authenticationSessions, actionTokens, work) are genuinely distributed/replicated when clustering is enabled. Caches like realms, users, and keys are local to each node and kept fresh via invalidation messages, not full replication — they fall back to the database, which is always the authoritative source for that data. Confirmed directly from Keycloak's own --help-all output, which only annotates the session-family cache options as "available only when embedded Infinispan clusters configured."

    2. A freshly started two-node start-dev lab shows no clustering errors, but a session created on one node isn't visible on the other. What's the single most likely cause, and why wouldn't there be an error?

      Model answerMost likely: neither node was told --cache=ispn, so both are silently running start-dev's own default, --cache=local, which disables clustering outright. There's no error because local is a fully valid, deliberately supported mode — it's just not a clustered one, and Keycloak doesn't warn that you probably wanted clustering, since a single dev node choosing local is the expected, common case.

    3. Explain, to a developer unfamiliar with this chapter's lab, why presenting node A's refresh token to node B is a more decisive test of session replication than just checking that the cluster's log shows a two-member view.

      Model answerA healthy cluster view only proves the two JGroups/Infinispan processes can see and talk to each other — it says nothing about whether application-level session data actually replicates correctly. Presenting a refresh token minted by node A to node B forces node B to look up that specific session by its sid in its own (supposedly replicated) sessions cache and validate it before minting a new token; if replication weren't actually working, node B would have no record of that session and the refresh would fail with invalid_grant, regardless of how healthy the cluster view log looked.

    4. This chapter's lab hit an "Invalid token issuer" error on its first cross-node test. Was that a clustering bug? What was it actually, and how was it fixed?

      Model answerNot a clustering bug — a hostname/issuer configuration issue. Keycloak computes a token's iss claim from the request's own Host header by default, so node A (reached on port 18141) and node B (reached on port 18142) were minting/expecting tokens with two different issuer values, and node B rejected node A's token on that mismatch alone — the session replication underneath was never even reached. Fixed by setting the identical KC_HOSTNAME on both nodes, modeling what a real deployment achieves by putting every node behind one load balancer with one public hostname.

    5. Could this chapter's two-container, one-Docker-host lab be cited as proof that a real Keycloak cluster would survive a data-center outage? Why or why not?

      Model answerNo. This lab proves that Keycloak's embedded Infinispan cache-replication logic correctly keeps session state consistent across two server processes — a genuine and useful thing to confirm. But both "nodes" share one kernel, one Docker bridge network, and one physical machine; nothing about a real host actually failing, a real network partition, or cross-data-center latency was exercised. Demonstrating real failover resilience needs at least two genuinely separate hosts (or a real multi-node Kubernetes deployment, chapter 42) — citing this lab as proof of that would overstate what it actually tested.

    6. Why does Meridian Trust's case for clustering go beyond "more throughput"?

      Model answerA retail bank under PCI-DSS with fraud-aware, step-up authentication has existential uptime and regulatory exposure if identity goes down — a single Keycloak node failing (a crash, a routine patch restart) would take every connected banking application's login down with it, during hours that are never predictably quiet the way a typical business's 9-to-5 might be. Clustering's real value here isn't handling more requests per second; it's removing the single point of failure chapter 1 already named as an unavoidable cost of centralizing authentication in the first place.
