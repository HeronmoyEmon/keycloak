    32. User Federation: LDAP & Active Directory

    Almost no organization adopting Keycloak is starting from zero accounts. A bank, a hospital, or a mid-size company nearly always already has a directory — LDAP or Active Directory — holding every employee's account, built and maintained long before anyone proposed adding Keycloak. This chapter is about the Keycloak feature that lets those two facts coexist: user federation, Keycloak's native LDAP provider that reads (and optionally writes) an external directory directly, so a specialist never has to choose between "migrate thousands of real employee accounts into Keycloak" and "don't adopt Keycloak for workforce identity at all."

    Why this matters

    Migrating an existing staff directory into a new identity system is slow, risky, and in a regulated environment often simply not allowed — the directory of record has its own change control, its own backup/DR posture, and its own owning team who did not sign up to hand their data to a new system overnight. Federation is the alternative every real deployment with an existing directory reaches for: Keycloak becomes a consumer of the existing directory's identities rather than a second, competing copy of them. An IAM specialist who only knows how to create users by hand in Keycloak's own store cannot onboard a single enterprise customer with their own AD — this chapter is where that limitation ends.

    What concept is this?

    Chapter 4 built the vocabulary this whole chapter assumes: a directory service is a read-optimized, hierarchical data store for records about people and systems; its data lives in a Directory Information Tree made of entries, each addressed by a Distinguished Name; LDAP is the protocol most real directories — including Active Directory — expose for talking to that tree; and a bind operation is how a client proves a credential against one entry. Chapter 7 then named federation as connecting an IAM system to one of these existing directories instead of migrating its population, with the directory itself staying the authoritative source of truth. Every one of those words becomes a literal field in a Keycloak admin-console screen in this chapter: the LDAP connection URL, the Bind DN, the Users DN, the object classes a user entry must carry. Nothing here is a new concept — it's chapter 4's vocabulary made concrete and clickable.

    Where the data lives, and where authentication actually happens

    The single most important mental model for this chapter: federating Keycloak against an LDAP directory does not make LDAP "part of" Keycloak's database, and it does not make a user's password pass through Keycloak's own credential store. Two separate things happen, on two separate schedules:

    • Sync copies profile data — username, name, email, group membership, whatever a mapper is configured to read — from LDAP into Keycloak's own user table, either once on demand or on a periodic schedule. This is what makes a federated user show up in GET /admin/realms/{realm}/users and in the Admin Console's user list at all.
    • Authentication (a login, or — as this chapter's lab uses for verification — a direct-grant token request) does not consult that synced copy's password field at all. In the default (import, read-only) configuration this chapter's lab uses, Keycloak performs a real-time LDAP bind operation against the directory itself, every time, using the credential the caller just supplied. The directory, not Keycloak, is still the one system that ever checks a password.

    This is exactly chapter 7's federation definition made concrete: the directory remains the authoritative store for the credential, and Keycloak only ever borrows an answer from it.

    Key idea

    A "synced" LDAP user in Keycloak's user list is a local, searchable copy of profile data, not a migrated account. Delete the federation provider and that copy becomes orphaned, read-only data — the real account, and the real password, never left the directory.

    Edit mode: who is allowed to write what, and to where

    Keycloak's LDAP provider has exactly three edit modes, each a different answer to "what happens when an admin or the user themselves tries to change a federated user's data in Keycloak":

    Keycloak's three LDAP federation edit modes
    Edit modeWrites from Keycloak reach LDAP?Typical fit
    READ_ONLYNo — Keycloak cannot write back to the directory at all; a change attempted through the Keycloak Admin Console or API on a federated attribute is rejected.The common case for workforce federation, and the mode this chapter's lab uses: the directory team owns the data, full stop.
    WRITABLEYes — a write made through Keycloak (e.g. resetting a password, editing a profile field) is pushed back into the directory in real time.When Keycloak is meant to be a genuine administration front-end for the directory, not just a consumer of it — rarer, and requires a bind credential with write permission.
    UNSYNCEDNo, but differently from READ_ONLY — Keycloak stores its own local override copy of the changed attribute instead of rejecting the write or pushing it to LDAP.Letting Keycloak hold one or two Keycloak-only attributes (or a locally-reset password) on top of an otherwise read-only federated identity, without touching the source directory.

    This chapter's lab deliberately uses READ_ONLY — the realistic default for a bank's existing staff directory, where the directory team, not Keycloak's admins, owns write access to employee records.

    LDAP mappers: the real translation layer, and where it silently goes wrong

    Adding an LDAP provider auto-creates a handful of built-in LDAP mappers — one per Keycloak user-model field (username, first name, last name, email, creation/modify dates) — each pointing at one LDAP attribute to read that field from. These defaults are tuned for the classic inetOrgPerson schema, but "tuned" does not mean "always correct for your data," and this chapter's own lab hit exactly that gap, not a hypothetical one.

    Keycloak's default first name mapper reads the LDAP cn (common name) attribute — which, per the X.500/LDAP schema convention chapter 4 introduced, conventionally holds a person's full display name, not their given name alone. A directory that instead populates givenName with just the first name (as Meridian Trust's does, and as this chapter's seed data does) will sync every federated user's full name into the firstName field — confirmed directly in this chapter's own lab run below, not described abstractly.

    Beyond the built-in five, any other LDAP attribute an application cares about — this chapter's lab adds one for Meridian Trust's employeeType attribute — needs its own explicit User Attribute LDAP Mapper, and group membership needs its own separate Group LDAP Mapper pointed at the directory's groups subtree. Neither exists by default; both are added and proven live in this chapter's lab.

    Deciding point: native LDAP federation vs. a custom Storage SPI

    Chapter 33 covers Keycloak's UserStorageProvider SPI — writing real Java to federate against a store that isn't LDAP. Before reaching for that, it's worth being explicit about why this chapter's native provider is almost always the right first choice whenever the external store genuinely speaks LDAP:

    Native Keycloak LDAP federation vs. a custom User Storage SPI, when the external store speaks LDAP
    Native LDAP federation (this chapter)Custom User Storage SPI (chapter 33)
    Zero custom code — admin-console/REST configuration only, as this chapter's entire lab demonstratesRequires writing, testing, packaging, and deploying real Java against Keycloak's SPI contracts
    Maintained and patched by the Keycloak project itselfMaintained by whoever wrote it, indefinitely, including through Keycloak upgrades
    Covers the overwhelming majority of real workforce-directory federation needs out of the box (import, mappers, edit modes, Kerberos)Only justified when the external store is not LDAP-speaking at all — chapter 33's case study is a legacy non-LDAP staff database with no directory interface to federate against

    If an external store can be reached over LDAP at all — even a non-AD, non-OpenLDAP product that merely exposes an LDAP interface for interoperability (several HR and identity-governance products do, per chapter 4's framing of LDAP as the common interoperability protocol) — this chapter's native provider should be the first thing tried, not a custom SPI.

    Case study: Meridian Trust federates its existing staff directory

    Case study — Meridian Trust

    Meridian Trust is a retail bank under PCI-DSS, and like almost every established bank it already runs an on-premises directory holding every employee's account — tellers, loan officers, fraud analysts, branch managers, IT administrators — long before Keycloak enters the picture. Migrating that directory into Keycloak outright would mean asking the bank's directory-operations team to hand over the one system PCI-DSS auditors already know how to assess, in exchange for a brand-new one with no track record — a non-starter. Federating instead means Keycloak becomes a consumer of the existing directory: employees keep logging in with the same credential the directory has always checked, the directory team keeps full ownership and write access (READ_ONLY edit mode, this chapter's lab setting), and Keycloak gains exactly what it needs — searchable profile data and group membership — without duplicating a single password. This chapter's lab stands up a realistic stand-in for that directory (five staff accounts across five job-function groups) and federates a real local Keycloak against it end to end.

    Common mistakes

    • If you see a federated user's first name contain their full name, the cause is Keycloak's default "first name" LDAP mapper reading cn — which many directories (including this chapter's seed data) use for a full display name, not a given name alone. Confirmed directly in this chapter's lab: the fix is repointing that one mapper's LDAP attribute at whatever field your directory actually uses for a first name (commonly givenName), then re-syncing.
    • If an LDAP attribute your application needs (a job title, a cost center, an employee type) never shows up on the synced Keycloak user no matter how many times you sync, the cause is almost always that no mapper exists for it — the five built-in mappers cover only username/first name/last name/email/timestamps. Add a User Attribute LDAP Mapper for it explicitly, as this chapter's lab did for employeeType.
    • If group membership doesn't appear on federated users even though the directory clearly has group entries, the cause is the same gap one level up: there is no Group LDAP Mapper configured by default, and without one Keycloak has no idea the directory's ou=groups subtree exists at all.
    • If creating or testing an LDAP provider fails with something like {"errorMessage":"AuthenticationFailure"} from the Admin Console's "Test authentication" button (or the underlying POST /admin/realms/{realm}/testLDAPConnection call with action: testAuthentication) — confirmed live in this chapter by deliberately supplying a wrong bind credential and getting exactly this response, HTTP 400 — the cause is the Bind DN or Bind Credential field, not the connection URL or network path. Test testConnection (reachability) and testAuthentication (the bind credential) as two separate checks before troubleshooting anything else.
    • If you see a sync report zero users with no error at all, the cause is almost always the Users DN or Custom User LDAP Filter pointing above, below, or beside where the real user entries actually live in the tree — a sync with a wrong Users DN doesn't fail loudly, it just finds nothing to import.
    • If a write made through the Keycloak Admin Console on a federated attribute silently appears to succeed in the UI but is gone on the next page load, the cause is very likely READ_ONLY edit mode rejecting the underlying write — check the provider's edit mode before assuming a UI bug.
    • If you're building your own seed/bootstrap LDIF for an OpenLDAP container like this chapter's lab does, and a plain add-only file is mistakenly processed with ldapmodify instead of ldapadd (error: modify operation type is missing), the cause — hit directly while writing this chapter's own seed file — can be as simple as the literal word LDAP uses to mark a modify-style record appearing anywhere in the file, including in a comment; the bootstrap script's add-vs-modify detection is a plain text search, not a real LDIF parse.

    Takeaways

    • User federation lets Keycloak consume an existing LDAP/Active Directory population instead of migrating it — the directory remains the authoritative store for the credential, exactly as chapter 7 defined federation in the abstract.
    • Sync and authentication are two separate paths on two separate schedules: sync copies profile data into Keycloak's own user table for visibility/search; authentication performs a live LDAP bind against the directory every time, confirmed in this chapter by a successful direct grant and a rejected one for a wrong password.
    • Keycloak's three edit modes — READ_ONLY, WRITABLE, UNSYNCED — answer "where does a write made in Keycloak actually end up," not "can Keycloak read this attribute" (which sync/mappers answer separately).
    • Only five LDAP mappers exist by default (username, first name, last name, email, two timestamps); any other attribute (this chapter used employeeType) needs its own explicit User Attribute LDAP Mapper, and group membership needs its own separate Group LDAP Mapper.
    • A default mapper existing is not the same as a default mapper being correct for your directory's actual schema usage — this chapter's own lab hit a real mismatch (first name mapper defaulting to cn, which held a full display name in this directory) and fixed it live rather than describing the fix abstractly.
    • testLDAPConnection's two actions, testConnection and testAuthentication, isolate "can I reach the server" from "is my bind credential correct" — confirmed live by deliberately breaking only the bind credential and getting exactly the authentication-specific failure.
    • Native LDAP federation requires zero custom code and should be the default choice whenever the external store speaks LDAP at all; chapter 33's custom Storage SPI is for stores that don't.
    • A real-world federated directory is operated by a separate team with its own change control — Meridian Trust's case study is the realistic reason READ_ONLY, not WRITABLE, is the common real-world default.
    • Seeding a disposable lab LDAP container has its own real gotchas independent of Keycloak entirely — this chapter's own build hit two failed seeding approaches (a single-file mount, then a directory mount the image silently emptied) before landing on one that actually works reliably across repeated resets.

    Self-check

    Click a question to reveal a model answer. Try answering it yourself first — the point is to check your own reasoning against it, not to read the answer first.

    1. A colleague says "we federated Keycloak against our AD, so now all our employee passwords are stored in Keycloak." What's wrong with that statement, precisely?

      Model answerIt's backwards. In the default import/read-only federation setup this chapter uses, Keycloak never stores a federated user's password at all — there's no password field for an LDAP-sourced user in Keycloak's own credential store to steal or store. Every authentication is a live LDAP bind performed against the directory itself, at the moment of login, using whatever the caller just typed. What Keycloak stores is a synced profile copy (name, email, group membership) — useful for search and display, but not a credential. This chapter confirmed the distinction directly: a direct-grant request with the real password succeeded, and the identical request with a wrong password was rejected — exactly the behavior a live bind check produces, not a locally cached one.

    2. Walk through why this chapter's first sync reported "5 imported users, 0 failed" and yet the data was still wrong. Doesn't "0 failed" mean the sync worked correctly?

      Model answer"0 failed" only means every LDAP entry Keycloak tried to read and write into its own user table succeeded as an operation — it says nothing about whether the *mapping* from LDAP attribute to Keycloak field was the mapping you actually wanted. This chapter's sync genuinely succeeded: every user really was created, with real data, straight from LDAP. The bug was a mapper configuration choice (reading cn instead of givenName for "first name"), not a sync failure — which is exactly why it needed inspecting the actual resulting user data, not just the sync's own success/fail counters, to catch.

    3. Why does a wrong Bind DN or Bind Credential typically surface as an authentication error on a specific test action, while a wrong Users DN typically surfaces as "zero users synced, no error at all"? What does that difference tell you about what each field controls?

      Model answerThe Bind DN/Credential controls whether Keycloak itself is allowed to talk to the directory at all — it's a precondition checked up front, so a wrong value produces an immediate, specific authentication failure (confirmed live in this chapter: HTTP 400, {"errorMessage":"AuthenticationFailure"}). The Users DN, by contrast, controls where in the tree an otherwise-successful, otherwise-authenticated search looks for user entries — a wrong value doesn't break the connection or the bind, it just means the search legitimately finds nothing under that (wrong) point in the tree, which to Keycloak looks exactly like "this directory happens to have no users," not an error.

    4. Riverside Health is considering WRITABLE edit mode so clinicians can reset their own passwords through Keycloak's self-service account console. What's the real trade-off they're making, and what would READ_ONLY plus a different mechanism look like instead?

      Model answerWRITABLE mode means every password reset (and any other profile write) done through Keycloak is pushed directly into the real directory in real time — convenient, but it hands Keycloak's bind credential genuine write authority over a system the directory-operations team may have its own change-control and audit requirements for, and it means a Keycloak misconfiguration or bug could now modify real directory data, not just misread it. A READ_ONLY alternative keeps the directory fully protected from any Keycloak-originated write and instead routes password resets through whatever mechanism the directory team already uses (their own self-service tool, a helpdesk process, or a directory-side password-reset flow) — more friction for the clinician, but zero new write surface on the system of record.

    5. Why does this chapter recommend trying native LDAP federation first for any LDAP-speaking external store, even an unusual one, rather than reaching for chapter 33's custom Storage SPI as a "more flexible" option?

      Model answerThe native provider needs zero custom code — this entire chapter's lab, including finding and fixing a real mapper bug, was done through the Admin REST API with no Java written at all — and it's maintained by the Keycloak project itself across upgrades. A custom SPI, by contrast, is code the adopting organization now owns forever: writing it, testing it, and re-validating it against every future Keycloak upgrade. "More flexible" is only a real advantage when the native provider genuinely can't express what's needed; chapter 33's own case study is deliberately a store with no LDAP interface at all, which is the actual bar for reaching for a custom SPI, not mere unfamiliarity with the LDAP provider's configuration fields.
