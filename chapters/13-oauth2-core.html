13. OAuth 2.0 Core

Chapter 7 gave you the role vocabulary for SSO and federation in the abstract — IdP, SP, RP — and a one-line promise that "full mechanics in chapter 13." This is that chapter. OAuth 2.0 is the protocol most modern SSO, API access, and "login with X" integrations are actually built on, and it brings its own role vocabulary that only partly overlaps with chapter 7's. You'll get the four OAuth roles, a survey of grant types, the authorization code flow in full mechanical detail with a real sequence diagram, a PKCE pair you compute yourself and verify by hand, and a hands-on lab against a live, public OAuth2/OIDC server — including a genuinely surprising, live-verified finding about what happens when redirect URI validation isn't enforced the way the spec requires.

Why this matters

Almost every "Sign in with Google," every mobile app that talks to a backend API, and — starting chapter 20 — every Keycloak client registration you will ever configure, runs on OAuth 2.0 underneath. An IAM specialist who can't read an authorization code exchange, explain what PKCE actually defends against, or say precisely why a redirect URI has to match exactly rather than loosely, cannot debug a broken login integration, review a client registration for security problems, or explain to a security team why a given mobile app's OAuth setup is or isn't safe. This chapter is also the one place in the course where you'll watch a real public authorization server fail to enforce part of the spec correctly, live, which turns out to be one of the clearest ways to learn why that part of the spec exists at all.

The four OAuth roles

OAuth 2.0 (RFC 6749) defines four roles. They are not the same four names chapter 7 gave you, and getting the mapping precisely right — including where it doesn't hold — matters more than memorizing the list.

  • Resource Owner — the entity capable of granting access to a protected resource. In the overwhelming majority of real scenarios, this is a human end user. (OAuth allows the resource owner to be a non-human entity too, but that's unusual in practice.)
  • Client — the application requesting access to a protected resource on the resource owner's behalf. This is the OAuth term for what you'd colloquially call "the app" — Northwind's SPA, a mobile app, a backend service.
  • Authorization Server — the server that authenticates the resource owner, obtains their authorization, and issues access tokens to the client after doing so.
  • Resource Server — the server hosting the protected resources, capable of accepting and responding to requests using access tokens. In plain language: an API.
Recall from chapter 7 — and where the mapping breaks

Chapter 7 gave you IdP (Identity Provider) and SP/RP (Service Provider / Relying Party) as the two roles in an SSO/federation relationship. OAuth's Authorization Server is roughly the IdP role — it's the system that authenticates the resource owner and vouches for the result to someone else. But the mapping is not a clean 1:1 rename, and treating it as one will cause real confusion later:

  • OAuth has no name for the end user as a role in the IdP/SP vocabulary — chapter 7 never needed to name "the person being authenticated" as a formal role, because SSO/federation is about the relationship between IdP and SP/RP. OAuth, by contrast, names the end user directly: Resource Owner. This exists because OAuth is fundamentally a delegation protocol — it's about a resource owner granting a client limited access to something the resource owner controls — not purely an authentication handshake between two systems.
  • OAuth's Resource Server has no equivalent at all in chapter 7's vocabulary. SAML and plain OIDC brokering/federation never needed to name "a protected API" as a role, because those patterns are about logging a user into an application, not about a client calling an API on a user's behalf. Chapter 15 will show that OIDC — which is built as a layer on top of OAuth — adds back an ID-token-and-UserInfo pattern that makes the RP/Client and Resource-Server-caller roles blur together in the common "login + call your own backend" case.
  • OAuth's Client is not quite the same shape as SP/RP. An SP/RP authenticates a user and then runs its own session for them. An OAuth Client requests and holds tokens so it can call APIs — authenticating the end user is OpenID Connect's job (chapter 15), layered on top of plain OAuth, not something OAuth itself promises to do.

The short version: reuse "Authorization Server ≈ IdP" as a memory aid, but don't try to force Resource Owner or Resource Server into chapter 7's two-role picture — they're genuinely new concepts OAuth introduces because it's solving a different problem (delegated, scoped access to resources) than SSO/federation alone (authenticating a user once, trusted by multiple apps).

In Keycloak

A Keycloak realm plays the Authorization Server role. A registered client in that realm is the OAuth Client. The Resource Owner is whichever user logs in. Keycloak doesn't run your Resource Server for you — that's your own API, configured to validate tokens Keycloak issued — but Keycloak client scopes can describe what that API expects. Full client registration screen in chapter 24.

Grant types: a survey (depth comes later)

A grant type is a defined way for a client to obtain an access token. OAuth defines several; this chapter covers the authorization code grant in full mechanical detail below (it's the one every interactive, browser-based login flow uses). Client credentials and device code get a one-line preview here — chapter 14 is where they get the same full treatment.

Pitfall — two grant types you should recognize, but not use

Resource Owner Password Credentials (ROPC) has the client collect the user's username and password directly and trade them for a token in one request — no redirect, no Authorization Server login page at all. Implicit returns an access token directly in the browser's URL fragment, skipping the code-exchange step entirely. Both exist in the original RFC 6749 and both are now considered legacy/discouraged by current best practice — ROPC because it trains users to type passwords into arbitrary client apps (defeating the entire point of centralizing authentication) and defeats the Authorization Server's ability to add MFA or step-up checks of its own; Implicit because an access token sitting in a URL fragment is exposed to browser history, referrer leakage, and any script that can read the current URL, with no code-exchange step as a buffer. Chapter 18 covers the full security reasoning (and current OAuth 2.0 Security Best Current Practice guidance) behind retiring both. If you see either one in a real client registration today, that's worth a second look, not a shrug.

The authorization code flow, in full mechanical detail

This is the flow behind essentially every "click a login button, get redirected, log in, land back in the app, now logged in" experience. Four phases:

  1. The client redirects the browser to the Authorization Server's authorization endpoint (/authorize), including which client is asking, what scopes it wants, and where to send the browser back to (redirect_uri).
  2. The user authenticates (and, depending on configuration, consents) directly with the Authorization Server — the client never sees the password.
  3. The Authorization Server redirects the browser back to the client's registered redirect_uri, with a short-lived, single-use authorization code attached as a query parameter.
  4. The client — this part happens server-to-server, not via the browser — exchanges that code at the token endpoint (/token) for an access token (and, if requested, an ID token and refresh token).

The code itself is deliberately not very useful on its own: it's short-lived (usually a window of seconds to a few minutes), single-use, and bound to the specific client and redirect URI that requested it. The whole point of the extra round trip through the code is that the browser — the least trustworthy place to put a long-lived, powerful access token — only ever sees the short-lived code, never the access token itself.

PKCE: protecting the code exchange

PKCE (Proof Key for Code Exchange, RFC 7636, pronounced "pixy") closes a specific gap: if a malicious app on the same device, or a network observer, manages to intercept the authorization code in step 3/4 of Figure 13.2, could it redeem that code for tokens itself? Without PKCE, yes — the code alone is enough. PKCE adds a second secret the client itself generates and never sends to the Authorization Server in plaintext until the very last step:

  • code_verifier — a high-entropy random string (43-128 characters, per RFC 7636 §4.1), generated fresh by the client for this one authorization attempt and kept only on the client.
  • code_challenge — derived from the verifier by SHA-256 hashing it and base64url-encoding the result (code_challenge_method=S256), sent in the clear in step 1 (the /authorize redirect).
  • At the token exchange (step 5), the client sends the original plaintext verifier, never the challenge. The Authorization Server independently recomputes SHA-256(verifier), checks it matches the challenge it recorded back in step 1, and only then issues tokens.

Whoever intercepts the code in steps 3-4 never saw the verifier (it was never transmitted — only its one-way hash was, in step 1, and a SHA-256 hash can't be reversed back into the original string). Without the matching verifier, the intercepted code is useless at the token endpoint.

Computed for real — not invented example values

Rather than making up a code_verifier/code_challenge pair that merely looks plausible, here is one actually generated and independently cross-checked for this chapter:

# Generate a code_verifier: 64 characters from the RFC 7636 §4.1 unreserved
# alphabet [A-Za-z0-9-._~], well inside the required 43-128 character range.
$ openssl rand -base64 96 | tr -d '=+/\n' | cut -c1-64
1z3WfdiVIG2BrhYi5ELjNrSGDgJ7e9SvsEho2fbjUXO4bN4T86VEkmfMMvS6VEjm

# Derive code_challenge = BASE64URL(SHA256(ASCII(code_verifier))), no padding.
$ printf '%s' '1z3WfdiVIG2BrhYi5ELjNrSGDgJ7e9SvsEho2fbjUXO4bN4T86VEkmfMMvS6VEjm' \
    | openssl dgst -sha256 -binary | openssl base64 | tr '+/' '-_' | tr -d '='
3aPn7lZkllR8WMnw1GvGsVqXxZC5FGX_tZnHrQf3mRc

Cross-checked independently with Python's own hashlib/base64 (not just trusting one tool's output):

>>> import hashlib, base64
>>> v = "1z3WfdiVIG2BrhYi5ELjNrSGDgJ7e9SvsEho2fbjUXO4bN4T86VEkmfMMvS6VEjm"
>>> base64.urlsafe_b64encode(hashlib.sha256(v.encode("ascii")).digest()).decode().rstrip("=")
'3aPn7lZkllR8WMnw1GvGsVqXxZC5FGX_tZnHrQf3mRc'   # matches the openssl output exactly

This exact pair is reused in the live lab below — it's the one actually submitted to a real authorization server's /authorize and /token endpoints, not a illustrative stand-in.

Key idea — PKCE isn't just for "public" clients anymore

PKCE was originally designed for public clients (mobile and single-page apps) that can't hold a client secret safely. Current best practice (chapter 18 covers this in full, with the specific BCP guidance) recommends PKCE for every authorization code flow, confidential clients included — it's cheap to add and closes the code-interception gap regardless of whether the client also has a secret. The live lab below uses a public client specifically (no secret at all), which is exactly the case PKCE was built for.

What the redirect_uri check protects — and a live, surprising finding about it

Chapter 7 already told you a registered redirect URI is one of the three ingredients of trust between an IdP and a relying application. Here's precisely why, in OAuth's own terms, and then something worth knowing that direct testing turned up.

What RFC 6749 actually requires

Per RFC 6749 §3.1.2.3: "When a redirection URI is included in an authorization request, the authorization server MUST compare and match the value received against at least one of the registered redirection URIs... using simple string comparison" — i.e. exact match, not a prefix or substring check. §3.1.2.4 adds: on a missing, invalid, or mismatching redirect URI, the server "MUST NOT automatically redirect the user-agent to the invalid redirection URI."

Why exact-match, rather than "starts with" or "same domain"? Because an attacker who can register — or get accepted — a redirect URI that merely resembles the legitimate one (a different path on the same domain, a subdomain they control, a URL that happens to share a prefix) gets the authorization code redirected to a destination they control, instead of the real application. Whoever receives that code can attempt to exchange it for tokens issued on behalf of whichever user just authenticated — effectively hijacking their login.

A live, verified finding — not what you'd expect from a spec-compliant server

While preparing this lab, the exact-match behavior above was tested directly against interactive.public on the live demo server — by substituting redirect_uri=https://evil.example.com/callback (a domain this course doesn't own) in place of the real one, keeping everything else (the PKCE challenge, the login as bob) identical. The authorization server completed the flow anyway: it redirected the browser to https://evil.example.com/callback?code=... with a real, valid authorization code, and that code exchanged successfully at /connect/token for a real access_token/id_token for bob's identity — exactly as if the redirect URI had been the registered one.

This directly contradicts what RFC 6749 §3.1.2.3-3.1.2.4 require. The most likely explanation is that this specific public demo client is deliberately configured to accept arbitrary redirect URIs, precisely so any visitor can test against it with their own callback endpoint without needing to ask Duende to register one — a reasonable trade-off for a public demo server with no real protected data behind it, but not something you would ever want to see from a production Authorization Server. This wasn't fabricated to make a point — it's exactly what the live server returned when tested, and it's the clearest possible demonstration of why the exact-match check matters: on a server where it isn't enforced, redirecting a real user's authorization code to an attacker-controlled destination is trivially easy, and the server will hand over real tokens for it.

Case study — Northwind Apps registers a customer-integration client

Northwind Apps is onboarding a new enterprise customer that wants to build its own internal dashboard against Northwind's API, using OAuth to let its employees log in with their own Northwind accounts. Northwind's security team insists on registering the exact, full callback URL the customer's dashboard will use — https://dashboard.customer-co.example/auth/callback — rather than accepting a broader pattern like "anything under customer-co.example" for convenience during setup.

This is not bureaucratic friction. If Northwind's Authorization Server validated redirect URIs by substring or domain match instead of exact string match — the way the demo server above was just shown to do, in effect, by accepting any URI at all — an attacker who controlled any page under customer-co.example (a forgotten marketing subdomain, a misconfigured S3 bucket serving that domain, a second app the customer runs there with its own vulnerabilities) could redirect a legitimate Northwind login's authorization code to themselves, and — exactly as demonstrated above — exchange it for a real access token scoped to whichever Northwind employee just authenticated. Exact-match registration closes that off entirely: the code only ever gets redirected to the one, specific, pre-approved URL, and nothing else qualifies, no matter what else happens to live on that domain. Keycloak's own client redirect-URI configuration, which enforces exactly this kind of match, is covered concretely in chapter 24.

Common mistakes

  • If you see someone describe PKCE as "only for mobile apps," the cause is treating it as a legacy public-client-only workaround instead of current best practice for every authorization code flow, confidential clients included (chapter 18 covers why).
  • If you see a redirect_uri registered as a wildcard or a domain prefix ("anything under *.example.com") "to make testing easier," the cause is exactly the gap this chapter's live demo-server finding demonstrated — it trades exact-match security for convenience, and the convenience isn't worth it once there's real user data behind the token.
  • If you see someone try to read an access token straight out of a redirect URL in the authorization code flow, the cause is confusing it with the deprecated Implicit grant — in the authorization code flow, only a short-lived code ever appears in the browser; the access token only ever arrives via the server-to-server token exchange.
  • If you see "invalid_grant" from a token endpoint and assume it specifically means "wrong PKCE verifier," the cause is over-reading a deliberately generic error — the same error also covers an expired code, an already-used code, or a code issued to a different client, by design.
  • If you see someone call the Authorization Server "the IdP" and leave it at that without ever naming Resource Owner or Resource Server, the cause is importing chapter 7's two-role picture wholesale instead of recognizing OAuth introduces genuinely new roles for a genuinely different problem (delegated resource access, not just login).

Glossary terms introduced here

Takeaways

  • OAuth 2.0 defines four roles — Resource Owner, Client, Authorization Server, Resource Server — and only Authorization Server maps cleanly onto chapter 7's IdP; Resource Owner and Resource Server are genuinely new concepts, not renamed ones.
  • The authorization code flow exists specifically so the browser only ever handles a short-lived, single-use code, never the access token itself — the token is only ever exchanged over a direct server-to-server call.
  • PKCE adds a client-generated secret (code_verifier) that never travels in plaintext until the final token exchange, so an intercepted authorization code alone isn't enough to obtain tokens.
  • Current best practice recommends PKCE on every authorization code flow, not just for public clients that lack a secret.
  • Resource Owner Password Credentials and Implicit are both legacy, discouraged grant types — recognize them, don't reach for them in new designs.
  • RFC 6749 requires exact, simple-string-comparison redirect URI matching, specifically to prevent an attacker from redirecting a real user's authorization code to a destination they control.
  • A live test against a real public demo server found it does not enforce exact-match redirect URI validation for one of its clients — a concrete, verified demonstration of exactly what that check is supposed to prevent, not a hypothetical.
  • A token endpoint returning the same generic error (invalid_grant) for a bad code, a reused code, and a wrong PKCE verifier is deliberate, not sloppy — specific errors here would help an attacker.
  • Client credentials and device code grants exist for machine-to-machine and no-browser scenarios respectively — both get full treatment in chapter 14, which also hosts this course's primary "real human step" completed round-trip lab.
