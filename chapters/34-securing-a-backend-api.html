    34. Securing a Backend API

    Every chapter through 33 ended with Keycloak issuing a token. This chapter is about the other half of the transaction: a real API that receives that token on every request and has to decide, by itself, whether to trust it and what it allows. The app built here — a small Spring Boot OAuth2 Resource Server fronting a Northwind Apps billing API — was actually written, actually compiled, and actually run against a real local Keycloak instance for this chapter, including a real, well-documented gotcha this lab hit (and deliberately reproduced again, live, to show it honestly) rather than just described.

    Why this matters

    An IAM specialist's work doesn't stop at the identity provider. Every team that owns a backend API eventually asks the same question: "a request just arrived carrying a bearer token — how do I actually verify it, and how do I turn it into an authorization decision?" Getting this wrong in either direction is a real incident: accept tokens too loosely and any caller gets in; wire up roles incorrectly and either everyone gets a 403 or — worse — nobody is actually being checked at all. This chapter shows the real mechanics, including the single most common real-world mismatch between Keycloak's token shape and a generic OAuth2 library's default assumptions.

    Sources for this chapter: Spring Security's own OAuth 2.0 Resource Server — JWT reference documentation (current stable version, fetched live); Spring Boot's Spring Security reference page; Maven Central's own maven-metadata.xml for org.springframework.boot:spring-boot, queried live (repo1.maven.org) to pin the exact current Spring Boot version rather than guess it; and this chapter's own lab, run against a real, disposable Keycloak 26.8.2 + PostgreSQL 17 Docker Compose stack (the same one chapter 20 brought up, unmodified) plus a real Spring Boot app this chapter gives you the complete source for, file by file, in the lab below.

    What concept is this?

    Chapter 8 named the model this entire chapter depends on: a bearer token is "a token whose only required proof of authorization is possession of the token itself" — whoever holds it can use it, with no further handshake, until it expires. Chapter 8 also named the problem this creates: a resource server has to decide, on every single request, whether to trust a token it never issued itself. Chapter 16 named exactly how that trust decision is made without ever contacting the issuer synchronously: a JWT's JWS signature is checked against a public key pulled from the issuer's JWKS (JSON Web Key Set), the token's issuer claim is checked against the resource server's own configured issuer, and its expiry claims are checked against the current time — three independent checks, all local, none of them a network round-trip back to Keycloak at request time (beyond the periodic JWKS refresh).

    This chapter is where that abstract description becomes one real dependency (spring-boot-starter-oauth2-resource-server) and one real configuration line (an issuer-uri) that makes Spring Security perform exactly those three checks, automatically, on every request to this chapter's billing API — before any of this chapter's own controller code ever runs.

    What actually happens when a request arrives

    Chapter 13 covered OAuth 2.0's roles in the abstract, naming "Resource Server" as one of them. This is that role, concretely, for a request carrying an Authorization: Bearer <token> header aimed at this chapter's billing API:

    The filter chain itself, in SecurityConfig:

    http
    .sessionManagement(session -> session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
    .csrf(AbstractHttpConfigurer::disable)
    .authorizeHttpRequests(authorize -> authorize
        .requestMatchers("/api/public/**").permitAll()
        .requestMatchers("/api/invoices/**").hasAnyRole("billing-reader", "billing-admin")
        .anyRequest().authenticated()
    )
    .oauth2ResourceServer(oauth2 -> oauth2
        .jwt(jwt -> jwt.jwtAuthenticationConverter(jwtAuthenticationConverter()))
    );

    Two deliberate choices worth naming explicitly, not left implicit: stateless session policy — this app creates no server-side session at all, because every request is expected to carry its own bearer token, exactly chapter 8's bearer-token model; and CSRF protection disabled — CSRF defends cookie-authenticated, browser-submitted requests against a forged cross-site form post, and this API never authenticates via a cookie at all, so there is nothing for CSRF protection to defend here (chapter 18 covers CSRF defenses in flows that genuinely need them, e.g. a browser-based SPA holding a session cookie).

    The one piece Spring Security doesn't get right by default against Keycloak

    Spring Security's spring-boot-starter-oauth2-resource-server ships a default JwtGrantedAuthoritiesConverter that looks for a flat, space-separated scope or scp claim — the shape a generic OAuth2 authorization server's access token typically carries. A Keycloak-issued access token carries its roles in a completely different, nested, Keycloak-specific claim instead:

    "realm_access": {
  "roles": ["billing-admin", "offline_access", "uma_authorization", "default-roles-northwind-apps"]
}

    Spring Security's default converter never looks at realm_access at all. The result is not an error anywhere — it's silence: the token is perfectly valid, signature and issuer and expiry all check out, authentication succeeds, and the request is still rejected with 403, because zero authorities were ever extracted from a token that genuinely carries the right role. This chapter's lab reproduces that exact 403 live, on purpose, a few slides ahead — not simulated, the real behavior with the real default converter temporarily restored.

    The fix is this chapter's own KeycloakRealmRoleConverter, a ~15-line Converter<Jwt, Collection<GrantedAuthority>> that reads realm_access.roles directly and prefixes each role ROLE_ so hasRole(...)/hasAnyRole(...)/@PreAuthorize("hasRole(...)") all work the way Spring Security expects:

    public class KeycloakRealmRoleConverter implements Converter<Jwt, Collection<GrantedAuthority>> {
    @Override
    public Collection<GrantedAuthority> convert(Jwt jwt) {
        Map<String, Object> realmAccess = jwt.getClaim("realm_access");
        if (realmAccess == null || !(realmAccess.get("roles") instanceof List<?> roles)) {
            return List.of();
        }
        return roles.stream()
                .map(Object::toString)
                .map(role -> new SimpleGrantedAuthority("ROLE_" + role))
                .collect(Collectors.toList());
    }
}

    Case study: Northwind Apps' billing API

    Case study — Northwind Apps

    Northwind Apps is a B2B SaaS company (introduced chapter 2), and like most multi-tenant SaaS products, billing and invoicing is a real internal API, not just a UI page — Northwind's own customer-facing billing dashboard calls it on behalf of a logged-in customer, Northwind's internal finance team calls it directly, and an internal nightly reconciliation job calls it with no human involved at all. All three callers are different in almost every way (a human with a browser session upstream of the call, a human at a terminal, an unattended cron job) but arrive at this API identically: an HTTP request carrying a Keycloak-issued bearer token. This chapter's lab realm (northwind-apps) models that directly with two realm roles — billing-reader (any caller that should see invoice data: the dashboard, finance staff doing lookups) and billing-admin (anything allowed to create or modify invoices: finance staff with write access, and the nightly reconciliation job's own service account) — and this chapter's lab proves, with real tokens, that a caller holding only billing-reader genuinely cannot create an invoice through this API, no matter what the caller claims about itself in any other field.

      A real, second gotcha hit in this exact step, worth including honestly rather than editing it out of the commands above: the first attempt created each user without firstName/lastName, and every direct-grant token request for that user failed with:

      {"error":"invalid_grant","error_description":"Account is not fully set up"}

      Checking that user's own representation showed "requiredActions" : [ ] — no required action was ever explicitly assigned, which made the error look like a false positive at first. The actual cause, confirmed by adding firstName/lastName and immediately retrying successfully: Keycloak's realm-wide Declarative User Profile (chapters 22/24/33's concept) marks firstName/lastName as required attributes by default, and a profile-completeness check (VERIFY_PROFILE) is computed dynamically against that schema at login time rather than stored as a per-user required action — a documented Keycloak behavior (confirmed against independent 2026 community reports of the identical message on Keycloak 26.7.3, consistent with this chapter's own 26.8.2 run), not something this chapter's own code or configuration introduced. The fix was adding the two attributes the commands above already include — no realm-setting change was needed this time, unlike chapter 33's version of this same profile-completeness gap.

    4. Create src/main/java/com/northwindapps/billing/SecurityConfig.java:

      package com.northwindapps.billing;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.method.configuration.EnableMethodSecurity;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.annotation.web.configurers.AbstractHttpConfigurer;
import org.springframework.security.config.http.SessionCreationPolicy;
import org.springframework.security.oauth2.server.resource.authentication.JwtAuthenticationConverter;
import org.springframework.security.web.SecurityFilterChain;

/**
 * Wires this app up as an OAuth2 Resource Server: every request is authenticated (or rejected)
 * based solely on a bearer JWT's validity against the realm named in
 * {@code spring.security.oauth2.resourceserver.jwt.issuer-uri} -- no session, no cookie, no
 * login form of its own. This is "What concept is this?" territory recalled concretely: chapter
 * 8 named the bearer-token model and chapter 16 named signature verification against a JWKS;
 * this class is where Spring Security actually performs both, automatically, once
 * {@code spring-boot-starter-oauth2-resource-server} is on the classpath and an issuer-uri is
 * configured -- fetching {@code <issuer-uri>/.well-known/openid-configuration} to learn the
 * token issuer and jwks_uri, then verifying every incoming token's signature, issuer, and
 * expiry against that JWKS automatically on every request (see this chapter's validation-flow
 * diagram).
 *
 * <p>The one piece Spring Security does <em>not</em> do automatically, correctly, out of the
 * box against a Keycloak-issued token is turn that token's roles into Spring Security
 * authorities -- see {@link KeycloakRealmRoleConverter}'s javadoc for the real gotcha this
 * chapter's lab hit and how {@code jwtAuthenticationConverter()} below fixes it.
 */
@Configuration
@EnableMethodSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            // This API is a pure resource server: every caller presents a fresh bearer token on
            // every request, so there is no server-side session to create or maintain.
            .sessionManagement(session -> session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            // A resource server validating only bearer tokens (never a browser form submission)
            // has no CSRF-vulnerable session-cookie-based state to protect -- CSRF protection is
            // a defense for cookie-authenticated, browser-based requests, which this API never
            // accepts (chapter 18 covers CSRF defenses for flows that genuinely need them).
            .csrf(AbstractHttpConfigurer::disable)
            .authorizeHttpRequests(authorize -> authorize
                .requestMatchers("/api/public/**").permitAll()
                .requestMatchers("/api/invoices/**").hasAnyRole("billing-reader", "billing-admin")
                .anyRequest().authenticated()
            )
            .oauth2ResourceServer(oauth2 -> oauth2
                .jwt(jwt -> jwt.jwtAuthenticationConverter(jwtAuthenticationConverter()))
            );
        return http.build();
    }

    /**
     * Combines Spring Security's default JWT claim extraction ({@code sub} as the principal
     * name) with {@link KeycloakRealmRoleConverter}'s realm-role-to-authority mapping, instead
     * of the default {@code JwtGrantedAuthoritiesConverter} that looks for a {@code scope}/
     * {@code scp} claim Keycloak's access tokens don't carry in that shape.
     */
    private JwtAuthenticationConverter jwtAuthenticationConverter() {
        JwtAuthenticationConverter converter = new JwtAuthenticationConverter();
        converter.setJwtGrantedAuthoritiesConverter(new KeycloakRealmRoleConverter());
        return converter;
    }
}

    5. Create src/main/java/com/northwindapps/billing/KeycloakRealmRoleConverter.java:

      package com.northwindapps.billing;

import java.util.Collection;
import java.util.List;
import java.util.Map;
import java.util.stream.Collectors;

import org.springframework.core.convert.converter.Converter;
import org.springframework.security.core.GrantedAuthority;
import org.springframework.security.core.authority.SimpleGrantedAuthority;
import org.springframework.security.oauth2.jwt.Jwt;

/**
 * Converts a Keycloak-issued JWT's {@code realm_access.roles} claim into Spring Security
 * {@link GrantedAuthority} instances, each prefixed {@code ROLE_} so {@code hasRole(...)} and
 * {@code @PreAuthorize("hasRole(...)")} work the way Spring Security expects.
 *
 * <p>This class exists because of a real, well-documented gap -- confirmed the hard way while
 * building this chapter's lab, not assumed up front: Spring Security's own default JWT-to-
 * authorities converter ({@code JwtGrantedAuthoritiesConverter}) looks for a {@code scope} or
 * {@code scp} claim (space-separated OAuth2 scopes), which is the shape a generic OAuth2
 * authorization server's access token carries. Keycloak's access tokens carry roles in a
 * differently-shaped, Keycloak-specific claim instead:
 *
 * <pre>
 * "realm_access": { "roles": ["billing-reader", "offline_access", "uma_authorization"] }
 * </pre>
 *
 * Without this converter, every endpoint protected with {@code hasRole("billing-reader")} or
 * similar returns 403 for every caller, no matter how correctly that caller's token was issued
 * and signed -- the token is valid and authenticated, but Spring Security never extracts any
 * authority named {@code ROLE_billing-reader} from it, because it was never looking at
 * {@code realm_access} in the first place. This chapter's "common mistakes" section covers the
 * exact 403 this produces and how it was diagnosed.
 */
public class KeycloakRealmRoleConverter implements Converter<Jwt, Collection<GrantedAuthority>> {

    private static final String REALM_ACCESS_CLAIM = "realm_access";
    private static final String ROLES_CLAIM = "roles";
    private static final String ROLE_AUTHORITY_PREFIX = "ROLE_";

    @Override
    public Collection<GrantedAuthority> convert(Jwt jwt) {
        Map<String, Object> realmAccess = jwt.getClaim(REALM_ACCESS_CLAIM);
        if (realmAccess == null || !(realmAccess.get(ROLES_CLAIM) instanceof List<?> roles)) {
            return List.of();
        }
        return roles.stream()
                .map(Object::toString)
                .map(role -> new SimpleGrantedAuthority(ROLE_AUTHORITY_PREFIX + role))
                .collect(Collectors.toList());
    }
}

/**
 * Three endpoints at three different protection levels, exactly as chapter 34's brief asks for:
 *
 * <ul>
 *   <li>{@code GET /api/public/health} -- no token required at all.</li>

 *       with method-level {@code @PreAuthorize} instead of the filter chain, to show both
 *       enforcement styles for real in the same small app.</li>
 * </ul>
 *
 * <p>Invoice data is an in-memory stand-in (no database) -- this chapter's subject is the
 * security boundary in front of the API, not the billing domain behind it.
 */
@RestController
@RequestMapping("/api")
public class BillingController {

    private final List<Map<String, Object>> invoices = new java.util.concurrent.CopyOnWriteArrayList<>(List.of(
            Map.of("id", 1001, "customer", "Acme Robotics", "amountUsd", 4200.00, "status", "paid"),
            Map.of("id", 1002, "customer", "Blue Harbor Logistics", "amountUsd", 980.50, "status", "overdue")
    ));
    private final AtomicLong nextId = new AtomicLong(1003);

    @GetMapping("/public/health")
    public ResponseEntity<Map<String, Object>> health() {
        return ResponseEntity.ok(Map.of(
                "status", "up",
                "service", "northwind-apps-billing-api",
                "time", Instant.now().toString()
        ));
    }

    @GetMapping("/invoices")
    public ResponseEntity<Map<String, Object>> listInvoices(JwtAuthenticationToken auth) {
        Jwt jwt = (Jwt) auth.getCredentials();
        return ResponseEntity.ok(Map.of(
                "invoices", invoices,
                "requestedBy", jwt.getClaimAsString("preferred_username") != null
                        ? jwt.getClaimAsString("preferred_username")
                        : jwt.getSubject(),
                "callerAuthorities", auth.getAuthorities().stream().map(Object::toString).toList()
        ));
    }

    @PostMapping("/invoices")
    @PreAuthorize("hasRole('billing-admin')")
    public ResponseEntity<Map<String, Object>> createInvoice(@RequestBody Map<String, Object> body) {
        long id = nextId.getAndIncrement();
        Map<String, Object> invoice = Map.of(
                "id", id,
                "customer", body.getOrDefault("customer", "Unknown"),
                "amountUsd", body.getOrDefault("amountUsd", 0.0),
                "status", "draft"
        );
        invoices.add(invoice);
        return ResponseEntity.status(201).body(invoice);
    }

    @GetMapping("/invoices/{id}")
    public ResponseEntity<Map<String, Object>> getInvoice(@PathVariable long id) {
        return invoices.stream()
                .filter(inv -> ((Number) inv.get("id")).longValue() == id)
                .findFirst()
                .<ResponseEntity<Map<String, Object>>>map(ResponseEntity::ok)
                .orElse(ResponseEntity.notFound().build());
    }
}

    Common mistakes

    • If every request to a protected endpoint returns 403 despite a token that decodes cleanly and clearly carries the expected role, the cause is very often exactly this chapter's gotcha: Spring Security's default JwtGrantedAuthoritiesConverter reads a flat scope/scp claim, not Keycloak's nested realm_access.roles — supply a custom Converter<Jwt, Collection<GrantedAuthority>> and wire it into jwtAuthenticationConverter(), confirmed live in this chapter's own lab by reproducing the exact 403 and then fixing it with zero other changes.
    • If every request instead returns 401, the problem is earlier in the pipeline than roles entirely: a missing/malformed Authorization header, a token whose iss claim doesn't match the configured issuer-uri exactly (including scheme and port — http://localhost:8080/... and http://localhost:18134/... are different issuers to a token verifier even though they're the same Keycloak realm), or a genuinely expired token. 401 means authentication itself failed; 403 means authentication succeeded and authorization refused — conflating the two wastes debugging time looking in the wrong half of the pipeline.
    • If a POM's own explanatory comment causes a build to fail before any Java compiles, check for a double-hyphen (--) anywhere inside an XML comment's text — this chapter hit the exact same real bug chapter 33's lab did, independently, in an unrelated file.
    • If a direct-grant token request fails with "Account is not fully set up" for a brand-new user with an apparently empty requiredActions list, check the realm's Declarative User Profile's required attributes (typically firstName/ lastName) before assuming a stuck required action — this chapter's own lab hit this for real, confirmed by adding both attributes and watching the identical request succeed with no other change.
    • If the Spring Boot app fails to start with a connection error pointing at the configured issuer-uri, Keycloak almost certainly isn't up (or isn't finished booting) yet — this app resolves the realm's OpenID Connect discovery document once at startup and has no built-in retry loop for "try again in a few seconds," so start Keycloak first and confirm its own readiness check (chapter 20's /realms/master/.well-known/openid-configuration returning 200) before starting this app.
    • Double-checking an issuer mismatch is worth doing explicitly: this chapter's own isolated test run (port 18134) had to point its issuer-uri at 18134, not the reader-facing 8080 shipped in application.properties — a resource server configured with the wrong issuer doesn't silently work "close enough"; it rejects every otherwise-valid token with 401, because the issuer string in the token simply won't match.

    Glossary terms introduced here

    Takeaways

    • An OAuth2 Resource Server's whole job is deciding, per request, whether to trust a bearer token it never issued — spring-boot-starter-oauth2-resource-server performs the signature/issuer/expiry checks automatically once an issuer-uri is configured, exactly chapter 8 and chapter 16's bearer-token and JWKS-verification concepts made concrete.
    • Spring Security's default JWT-to-authorities converter reads a scope/ scp claim, not Keycloak's realm_access.roles — a valid, correctly signed, correctly scoped token still produces zero authorities and a 403 without a custom converter, confirmed live by this chapter's own lab deliberately reproducing the bug.
    • 401 means authentication failed (missing/invalid/expired/wrong-issuer token); 403 means authentication succeeded but the token's authorities don't satisfy the endpoint's requirement — this chapter's full response-code table demonstrates both, for real, for every combination that matters.
    • Spring Boot's own current version has to be live-verified against Maven Central's real metadata, not recalled — 4.1.2 was the newest GA release at the moment this chapter was written, with 4.2.0 existing only as a release candidate.
    • A resource server's server.port must be chosen with the rest of a chapter's (or a real system's) topology in mind — this app ships with 8081 specifically because Keycloak already owns 8080/9000 in every lab since chapter 20.
    • URL-level authorization (hasAnyRole(...) in the filter chain) and method-level authorization (@PreAuthorize(...) on a controller method) are two legitimate, complementary enforcement points, not competing alternatives — this chapter's own app uses both for real, on different endpoints.
    • Client credentials (service-account) tokens and direct-grant (human) tokens are consumed identically by a resource server — the same filter chain, the same converter, the same role check — even though they represent very different kinds of caller in Northwind Apps' real system.
    • A Declarative User Profile's required attributes can silently block a direct-grant token request with a confusing "Account is not fully set up" error that has nothing to do with the username/password being tested — this chapter's lab hit this independently of, and for a different reason than, chapter 33's version of the same underlying profile-completeness gap.
    • Disabling CSRF protection is correct for a pure bearer-token resource server with no server-side session, specifically because CSRF defends cookie-authenticated requests this kind of API never accepts — it is not a blanket "CSRF doesn't matter" rule.

    Self-check

    Click a question to reveal a model answer. Try answering it yourself first — the point is to check your own reasoning against it, not to read the answer first.

    1. A teammate says "the token is definitely valid — I decoded it myself and it has the right role in it — but the API still returns 403." What's the single most likely explanation, and why doesn't a valid, correctly-scoped token guarantee a 200?

      Model answerThe most likely cause is exactly this chapter's gotcha: Spring Security's default JWT-to-authorities converter reads a scope/scp claim, not Keycloak's realm_access.roles, so it extracts zero authorities from an otherwise perfectly valid token. A token being "valid" only means it passed signature, issuer, and expiry checks — authentication succeeded. Authorization is a separate, later check against whatever authorities were actually extracted, and if the converter never looked at the claim holding the real role, there are no authorities to check against, producing 403 regardless of how correct the token's contents are.

    2. Why does this chapter's resource server disable CSRF protection, and would that same choice be correct for a server-rendered web app that logs users in with a session cookie?

      Model answerCSRF protection defends against a forged request riding on a browser's automatically-attached session cookie — it matters only when a cookie alone authenticates a request. This chapter's API is stateless and accepts only an explicit Authorization: Bearer header that a malicious site cannot make a victim's browser attach automatically, so there's nothing for CSRF protection to defend. A server-rendered app authenticating via a session cookie is exactly the opposite case — disabling CSRF there would be a real vulnerability, not a simplification.

    3. Walk through what Spring Security actually does, automatically, when spring.security.oauth2.resourceserver.jwt.issuer-uri is set to http://localhost:8080/realms/northwind-apps — name every step.

      Model answerAt startup, it fetches <issuer-uri>/.well-known/openid-configuration to learn the realm's actual token issuer string and its jwks_uri. On every incoming request carrying a bearer token, it fetches (or reuses a cached copy of) that JWKS to get the current signing keys, verifies the token's JWS signature against the matching key, checks that the token's iss claim exactly matches the configured issuer, and checks the token's expiry claims against the current time. Only if all of that passes does it hand the token to the configured jwtAuthenticationConverter() to extract authorities, which are then checked against whatever the filter chain or a method's @PreAuthorize requires.

    4. Why did this chapter pin Spring Boot to exactly 4.1.2 rather than 4.2.0, when Maven Central's metadata showed a 4.2.0-RC2 already existed at the time of writing?

      Model answerAn -RC2 suffix means release candidate, not a final release — Maven Central's own metadata distinguished latest/release (4.2.0-RC2, the newest artifact of any kind) from the newest version without a pre-release qualifier (4.1.2). Shipping a teaching lab pinned to a release candidate risks the exact version disappearing or changing behavior once the real 4.2.0 GA ships and supersedes it; 4.1.2 is a permanent, already-finished release that won't move out from under a reader following this chapter later.

    5. This chapter's lab created both a client-credentials client and a direct-grant client in the same realm. Why not just use one grant type for everything?

      Model answerThey model two genuinely different kinds of real caller this chapter's resource server has to support identically. Client credentials matches Northwind Apps' nightly reconciliation job: no human, no password, a token that carries only a client identity. Direct grant matches a human tester needing two distinct identities (amara.reader vs. devon.admin) to prove the billing-reader/billing-admin distinction actually works, with a real sub/preferred_username in the resulting token for accountability. Using only one grant type would leave one of those two real scenarios unverified by this chapter's own lab.
