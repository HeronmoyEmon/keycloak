16. JWT & Applied Cryptography

Chapter 8 introduced claims and tokens as pure concepts, deliberately leaving the wire format unopened. Chapters 14 and 15 then handed you real access, refresh, and ID tokens out of a live OAuth/OIDC server. This chapter finally opens the envelope: how a JWT is actually built out of bytes, why most of it is readable by design rather than hidden, and exactly how a verifier decides which key to trust — including the mechanics behind key rotation, which chapter 8 could only name.

Why this matters

An IAM specialist is routinely the person who has to explain, calmly, why putting a secret inside a JWT claim was never safe — and the person who has to design a key-rotation plan that survives a suspected compromise without breaking every session in production at once. Both of those conversations require the same handful of mechanics: the difference between signing and encrypting, what a JWT's three segments actually contain, and how a verifier picks the right key out of a published key set. This chapter is also a hard prerequisite for chapter 17's SAML contrast and chapter 18's security hardening — you can't reason about algorithm-confusion attacks or token-storage trade-offs until the structure underneath them is concrete.

Recall — chapter 8

Chapter 8 defined a claim as a key-value assertion an issuer vouches for, and named signing-key rotation as one of four partial mitigations for the revocation problem — a blunt instrument that invalidates everything signed with the old key at once, deferred to "chapter 16 for full mechanics." This is that chapter. Everything below assumes you already have claims, issuer/audience/validity-window claims, and the revocation problem fresh from chapter 8 — this chapter doesn't re-teach them, it makes their wire format concrete.

JWS vs. JWE: signing and encryption are not the same thing

A JSON Web Token is a container format, and that container can be built two structurally different ways:

JWS vs. JWE — what each one actually protects
JWS (JSON Web Signature)JWE (JSON Web Encryption)
What it protectsIntegrity and authenticity — proves the content wasn't altered and (for asymmetric algorithms) identifies which key signed it. Confidentiality — hides the content from anyone without the decryption key.
Can anyone read the payload?Yes. Signing does not hide anything; it only detects tampering.No. The payload is ciphertext until decrypted.
How common in this course's tokensThe default. Every access token and ID token this course has decoded in chapters 14-15 is a JWS.Rare in everyday OAuth/OIDC deployments — used when the claims themselves must stay confidential from anyone but the intended recipient, not just tamper-evident.
Pitfall

"It's a JWT, so it's encrypted" is one of the most common and consequential beginner misconceptions in all of IAM. It is false for the plain JWS tokens this course has used throughout chapters 13-15. Concrete example: an engineer at Northwind Apps once added a customer's internal account-tier discount code directly into an access token's payload as a custom claim, reasoning "it's inside the token, so only our API can see it." The claim is base64url-encoded JSON, not ciphertext — any browser extension, proxy log, or curious user who copies the token out of a dev-tools network tab can decode that claim in seconds with nothing more than a text editor, exactly as you will below. If a value must stay hidden from the token's bearer, it does not belong in a JWS payload at all — it belongs server-side, looked up by a claim that is safe to expose (like a customer id), or inside an actual JWE if the architecture specifically calls for one.

JWT structure: three base64url segments, not one blob

A JWT using JWS's compact serialization — the dot-separated form you have already seen in chapters 14-15's lab output — is exactly three segments: header.payload.signature, each one independently base64url-encoded. Base64url is a text-safe encoding (RFC 4648 §5): it swaps the `+`/`/` characters regular base64 uses for `-`/`_` so the result survives being placed in a URL or HTTP header, and it is fully reversible by anyone — no key, no secret, nothing hidden by the encoding itself.

To make this concrete without depending on any particular lab's output still being valid, here is a minimal JWT built and verified for this chapter (HS256, a symmetric algorithm covered below), with its real base64url segments:

Try it

No tool required beyond a terminal. Take the header segment above — or, better, the header segment from a real access token you obtained in chapter 14 or 15's lab — and run it through base64url decoding by hand: echo 'eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCIsImtpZCI6ImRlbW8ta2V5LTEifQ' | tr '_-' '/+' | base64 -d (pad with trailing = if your `base64` complains about input length). You'll get back plain JSON. Do the same for the payload segment. Then try it on the signature segment — it decodes to meaningless bytes, because unlike the other two it was never JSON to begin with.

JWK and JWKS: how a verifier gets the key without being handed a secret

A verifier that didn't issue a token still needs the right cryptographic material to check its signature. A JWK (JSON Web Key, RFC 7517) is a single key represented as JSON; a JWKS (JSON Web Key Set) is a JSON document holding an array of JWKs — normally every signing key an issuer currently considers valid. Chapter 15's discovery document already handed you the mechanism that advertises where to find this: its jwks_uri field.

Key idea — live-verified

Fetching https://demo.duendesoftware.com/.well-known/openid-configuration (the same discovery document chapter 15 used) and reading its jwks_uri field gives: https://demo.duendesoftware.com/.well-known/openid-configuration/jwks — confirmed live while writing this chapter, not guessed. Fetching that URL returned a JSON Web Key Set with exactly one currently-active key:

kty is the key type (RSA here), use says it's for signing, alg names RS256, n/e are the RSA public key's modulus and exponent (the actual verification material), and x5c/x5t carry an X.509 certificate chain and thumbprint for the same key — extra material some verifiers use, not required to check a signature with n/e alone. Note this live response shows a single key with no second key present, which is the normal steady state — a second key only appears in this array during an active rotation's overlap period, covered next.

kid-based key lookup

A JWT's header carries a kid (key id) claim. A verifier reads that value, fetches (or uses an already-cached) JWKS response, and scans its keys array for the one JWK whose own kid matches. That match is what tells the verifier which key's public material to use for this particular token — not the only key in the set, necessarily, and not the newest one by default, specifically the one named by the token.

In Keycloak

Realm Settings → Keys (chapter 21) lists every signing key a realm currently has, each tagged active/passive and with its own `kid` — the admin-console view of exactly the JWKS entries described here. Full hands-on depth lands there.

Key rotation, concretely

Chapter 8 named signing-key rotation only as a blunt revocation mitigation. Here is precisely how it works, now that kid-based lookup is on the table:

  1. Steady state. One active signing key (call it Key A) is in the JWKS response. Every token in circulation was signed with Key A and verifies against it.
  2. Rotation begins — the overlap period. A new key, Key B, is published into the JWKS response alongside Key A, before anything is signed with it. The issuer then switches to signing new tokens with Key B. Tokens already out there, still signed with Key A, keep verifying correctly, because Key A is still present in JWKS.
  3. Overlap ends. Once every token Key A ever signed has expired (or the chosen overlap window has passed), Key A is removed from the JWKS response. Any token still claiming to be signed by Key A — which, if the overlap was sized correctly, should not exist — would now fail verification, because a verifier can no longer find a matching `kid`.
Pitfall

If you see an outage immediately after a "routine" key rotation, the cause is very often step 3 happening before step 2 finished its job — someone removed the old key from JWKS while tokens it signed were still unexpired and in active use. The fix is not "don't rotate keys"; it's sizing the overlap period to be at least as long as the longest-lived token type still being verified (and, for refresh tokens specifically, remembering they can live far longer than access tokens — chapter 8).

Symmetric vs. asymmetric signing

The algorithm named in a JWT's alg header falls into one of two families, and the choice has a direct consequence for whether a JWKS endpoint can safely exist at all:

HS256 (symmetric) vs. RS256/ES256 (asymmetric)
Symmetric — HS256Asymmetric — RS256 / ES256
Key(s) involvedOne shared secret, used to both sign and verify.A private key (signs) and a mathematically related public key (verifies) — RSA for RS256, elliptic-curve for ES256.
Can you publish the verification key in a public JWKS?No — publishing the HMAC secret would hand out the ability to forge tokens, not just verify them. Yes — the public key only lets you check a signature, never create a valid one. This is exactly why the live Duende JWKS example above safely publishes n/e.
Typical fitClosed systems where every verifier is trusted with the secret (e.g. one service verifying its own tokens).Open, multi-party systems — any number of resource servers can verify tokens from one issuer without ever holding anything secret.

This is also why the hand-built example earlier in this chapter used HS256 — easy to compute and verify by hand with one shared secret, to make the base64url mechanics concrete — while the live demo server's real tokens use RS256, the asymmetric choice that actually makes a public JWKS endpoint a safe thing to run in production.

Deep dive — algorithm confusion

A verifier that blindly trusts the alg value out of an untrusted token's own header, rather than enforcing an algorithm it already expects for that key, opens the door to a real, named class of attack called algorithm confusion — for example, tricking an RS256 verifier into treating a known-public RSA key's bytes as if they were an HMAC secret, letting an attacker forge a validly-"signed" token with no private key at all. This chapter only names the problem; chapter 18 covers the defenses (pin the expected algorithm server-side, never read it from the token) in full.

Case study — Riverside Health

Riverside Health's patient portal verifies ID tokens from its hospital-wide identity provider using RS256 and a cached JWKS response fetched at service startup. Because the system correctly caches by `kid` and refreshes the JWKS periodically rather than once forever, a routine key rotation at the IdP — new clinical-systems vendor onboarded, keys rotated as part of standard hygiene — doesn't require a coordinated restart of every downstream service that verifies tokens; each service simply picks up the new key the next time it refreshes its cached JWKS.

Common mistakes

  • If you see a secret, password, or anything meant to stay hidden inside a JWT payload claim, the cause is someone confusing base64url encoding with encryption — a JWS payload is readable by anyone who has the token.
  • If you see a verification outage right after a key rotation, the cause is usually an overlap period that was too short, or skipped entirely, for the longest-lived token type still in use.
  • If you see a verifier configured to read its expected signing algorithm from the token's own `alg` header rather than enforcing one server-side, the cause is a design vulnerable to algorithm confusion — chapter 18 covers the fix.
  • If you see a symmetric HMAC secret published at a JWKS-style public endpoint "to make verification easier for other teams," the cause is a misunderstanding of why RS256/ES256, not HS256, is the family that was ever meant to be published that way.
  • If you see someone decode a JWT's signature segment expecting readable JSON, the cause is forgetting that only the header and payload are JSON — the signature is opaque bytes, checked by recomputation, never decoded for meaning.

Glossary terms introduced here

Takeaways

  • JWS (signing) proves integrity and authenticity but leaves the payload readable; JWE (encryption) hides the payload. Most access and ID tokens in this course, and in most real deployments, are JWS.
  • A JWT is not automatically encrypted — base64url is a reversible encoding anyone can decode, not a secret, and putting anything sensitive directly in a JWS payload claim exposes it to the bearer.
  • A JWT's compact serialization is exactly three base64url segments: header.payload.signature.
  • The header and payload decode to plain JSON; the signature segment is opaque bytes, verified by recomputing it over the exact signing input (header_b64 + "." + payload_b64), never "decoded."
  • A JWK is a single key as JSON; a JWKS is a published set of them, usually reachable via the discovery document's `jwks_uri` field — confirmed live on Duende's demo server during this chapter's research.
  • A token's header `kid` tells a verifier which JWKS entry to use — the exact mechanism that makes key rotation possible without immediately breaking every already-issued token.
  • Key rotation concretely means: publish the new key into JWKS before using it, sign new tokens with it, keep the old key listed for an overlap period so already-issued tokens keep verifying, then remove the old key once everything it signed has expired.
  • Symmetric (HS256) signing uses one shared secret for both signing and verifying and cannot be safely published; asymmetric (RS256/ES256) signing lets a public verification key be published openly, because it can check a signature but never forge one.
  • Algorithm confusion is a real, named attack class against verifiers that trust a token's own `alg` header instead of enforcing an expected algorithm server-side — named here, defended against in chapter 18.
  • Meridian Trust's response to a suspected key compromise — shortening the rotation overlap period deliberately — is the same blast-radius-shrinking logic chapter 8 introduced, now applied to an entire signing key rather than one token.
