18. OAuth/OIDC Security Best Practices

Chapters 13-17 taught OAuth 2.0 and OpenID Connect as mechanisms — roles, grants, tokens, assertions — the way the specs define them. This chapter asks the harder question a real deployment has to answer: given that a client talks to a real browser, a real network, and sometimes more than one authorization server, where specifically does the mechanism break, and what closes each gap? This is also Part III's answer to a debt chapter 9 opened: it forward-pointed token theft, token replay, and session hijacking to "chapter 18" without saying what chapter 18 actually does about them. This chapter pays that off.

Why this matters

An IAM specialist who can draw the authorization code flow from memory but can't explain why PKCE is now recommended for confidential clients too, or what a mix-up attack even is, will configure a client correctly against the spec and still ship something exploitable — because the spec text alone doesn't flag which of its own optional protections are the ones that matter in practice. The guidance in this chapter comes from a single, consolidated, current IETF document written specifically to close that gap: it exists because real deployments kept making the same mistakes, and the working group wrote down the fix once instead of leaving every implementer to rediscover it.

Key idea

As of this writing (confirmed live, 2026-11-10), the OAuth 2.0 Security Best Current Practice is a published, final RFC, not a draft: RFC 9700, also catalogued as BCP 240, published January 2025 by the IETF OAuth working group. It formally updates the threat model and advice that used to be spread across RFC 6749 (OAuth 2.0 core), RFC 6750 (bearer token usage), and RFC 6819 (an earlier, now-superseded OAuth threat model), consolidating years of real-world attack research into one normative document. Everything this chapter calls "the BCP" or "the security BCP" refers to RFC 9700 specifically, not to a work-in-progress draft — it's safe to cite it by RFC number in an interview or a design review.

RFC 9700 doesn't only apply to browser-based authorization-code flows. A second, newer document specifically for single-page applications and other browser-based OAuth clients — RFC 10017 / BCP 212, "OAuth 2.0 for Browser-Based Applications" — reached final RFC status even more recently (August 2026, confirmed live). This chapter's token-storage section draws on it directly, since it's the document that actually works through where a browser app can and can't safely keep a token.

PKCE, everywhere — not just for public clients

Chapter 13 introduced PKCE (Proof Key for Code Exchange) as the mechanism a public client (one that can't hold a secret, like a mobile app or SPA) uses to stop an attacker who intercepts its authorization code from redeeming it: the client generates a random code_verifier, sends its hashed form (code_challenge) with the authorization request, and must later present the original code_verifier at the token endpoint — a value only the real client ever had. That's the mechanics. This chapter adds the current policy point on top of it, which is a distinct thing to know, not a restatement: RFC 9700 §2.1.1 says public clients MUST use PKCE, and goes further to say PKCE is RECOMMENDED for confidential clients too — this course calls that second half "PKCE-everywhere."

Why would a confidential client — one that does hold a client secret, like Northwind Apps' own server-side backend — need PKCE at all? Because the client secret protects the token endpoint exchange (proving "I am the registered client"); it does nothing to stop someone from intercepting the authorization code itself before it ever reaches that exchange. An authorization code can leak through channels that have nothing to do with whether the client is confidential: a referrer header leaking a code-bearing URL to a third-party script, a malicious app on a shared device registering the same custom URI scheme a confidential native client uses for its redirect, a misconfigured proxy or log aggregator capturing full request URLs. In every one of those cases, the attacker who grabs the code still can't redeem it without also having generated the original code_verifier — which never left the legitimate client. PKCE closes a gap at the authorization-code layer that a client secret, which only matters one step later, was never positioned to close.

In Keycloak

A client's Advanced settings tab carries a "Proof Key for Code Exchange Code Challenge Method" field (S256 or plain) that can be set for any client, confidential or public — turning PKCE-everywhere from a policy recommendation into an enforced setting. Full walkthrough in chapter 24.

Mix-up attacks: when a client talks to more than one authorization server

A mix-up attack targets a client that's configured to work with more than one authorization server — not an unusual setup: Northwind Apps might let a customer sign in either through Northwind's own realm or through that customer's own corporate identity provider, brokered side by side. The attack works by getting the client confused about which authorization server a given authorization response actually came from.

Concretely: an attacker who controls (or has compromised) one of the authorization servers the client trusts can redirect the user's browser to start a flow against the honest authorization server, but arrange for the client to believe the resulting code or token came from the attacker's server instead — or the reverse. If the client doesn't verify which server actually issued what it received, it can end up sending a legitimate authorization code, or even a client credential, to the wrong authorization server, or accepting a token that didn't come from where it thinks it did. RFC 9700 §2.1 and §4.4 treat this as a required defense, not an edge case, specifically because the harm (credential/code disclosure to an attacker-controlled server) is serious and the root cause — a client with more than one trusted AS and no way to tell them apart from the response alone — is common.

Key idea

The preferred defense, per RFC 9700 §2.1 pointing at RFC 9207, is for the authorization server to include an iss parameter in every authorization response (including error responses) stating its own issuer identifier, and for the client to compare that value against the issuer it expected before doing anything else with the response — and abort the flow entirely on any mismatch. This is `iss` validation. Where a given authorization server doesn't support the iss parameter, RFC 9700 §4.4.2.2 describes a weaker fallback: giving each trusted authorization server its own distinct, dedicated redirect URI, so the client can infer which AS a response is for from which URI it arrived at — explicitly framed as a "should only be used if other options are not available" fallback, not the preferred mechanism.

CSRF defense: what the state parameter actually does

The authorization code flow's redirect-based handshake is itself a target for cross-site request forgery: an attacker can start their own legitimate authorization flow (logging in as the attacker, or linking the attacker's own account), capture the resulting callback URL, and trick a victim's browser into completing that callback instead of one the victim actually initiated. If the client doesn't check anything, the victim's browser session ends up linked to the attacker's identity — a forged callback masquerading as a normal login completion.

The state parameter defends against exactly this: the client generates a random, unguessable value before redirecting to the authorization server, stores it tied to the browser session that's initiating the request (e.g. in a server-side session or a cookie the client set), and requires the callback to echo that same value back. A forged callback — one started by the attacker's own flow, not the victim's browser — carries the attacker's state value, not one bound to the victim's session, so the client's comparison fails and the flow is rejected. RFC 9700 §2.1 states this plainly: clients MUST prevent CSRF, either by relying on PKCE (when the authorization server supports it, since the code_verifier itself provides equivalent protection) or by using a one-time CSRF token carried in state that is securely bound to the user agent. The value should be single-use — invalidated by the client immediately after the callback is checked, per RFC 9700 §4.2.4 — so a captured callback URL can't be replayed a second time either.

Pitfall

Treating state as "just an opaque echo value the server sends and gets back" misses the actual security property. The protection isn't that state survived the round trip — it's that the value was generated for, and bound to, this specific browser session before the redirect happened. If a client generates state but never actually ties it to the session that initiated the request (for example, storing it only client-side where any page can read or guess it), the CSRF defense is decorative — present in the request, doing nothing.

Token storage: where a browser-based client keeps what it's given

Chapter 9 named the failure mode without naming the fix: a bearer token (ch. 8) is usable by whoever holds it, and cross-site scripting (ch. 9) is exactly how an attacker gets to hold one it was never issued to them. The missing piece is: where should a browser-based client actually keep its tokens, given that the browser is the thing XSS runs inside of?

  • localStorage / sessionStorage — plain JavaScript- accessible, origin-scoped storage. Convenient (any script on the page can read and write it directly, no server round-trip needed) and exactly that: any script running on the page, including one an attacker injected via an XSS flaw, can read it too. There is no way to mark a value in either store as off-limits to JavaScript — the access model doesn't support it. RFC 10017 (the "OAuth 2.0 for Browser-Based Applications" BCP, confirmed live, published August 2026) names this directly: malicious code from an XSS attack "has the same privileges as the legitimate application code" and can "steal data from origin-based storage mechanisms."
  • httpOnly cookies — a cookie attribute that makes the cookie's value invisible to JavaScript entirely (document.cookie simply never returns it); only the browser itself attaches it to outgoing requests, and only the server reads it. This closes the specific XSS-reads- the-token exposure completely — stolen page script has nothing to read. It doesn't make the cookie immune to everything: a cookie the browser attaches automatically is exactly the thing CSRF existed to exploit before state/SameSite existed to stop it, so an httpOnly, cookie-based session needs its own CSRF defense (a SameSite attribute, a CSRF token, or both) — it trades one risk for a different, better-understood one, not a risk for nothing.

RFC 10017 goes a step further than just "pick a safer storage API": its most strongly recommended pattern is a Backend-for-Frontend (BFF) — a server-side component that holds the actual OAuth tokens itself and gives the browser only an httpOnly, Secure, SameSite session cookie, so the token never reaches browser-readable storage, or even browser-visible JavaScript, at all. The RFC calls this pattern "strongly recommended for business applications" specifically because it removes the token-in-the-browser exposure as a category, rather than hardening the place the token sits.

In Keycloak

Keycloak doesn't control how a client-side application stores the tokens it's handed — that's the application's own architecture decision, which is exactly why this chapter's guidance exists independent of any specific IAM vendor. What Keycloak does control: short default access-token lifetimes (shrinking how long a stolen token stays useful regardless of where it was stolen from) and per-session revocation, both covered in chapter 29; and a client confidential/public distinction and PKCE enforcement, covered in chapter 24.

Case study: Northwind Apps' token theft, revisited

Case study

Northwind Apps — recall chapter 9's incident: a Northwind enterprise customer built its own browser-based integration against Northwind's API, that integration had an XSS flaw in code Northwind never wrote, and an attacker who exploited it could read whatever the browser session was holding — including the bearer token Northwind issued for API access. Chapter 9 could only say the damage was bounded by the token's scope and lifetime, because chapter 9 came before this chapter's defenses existed in the course. Looking at the same incident now: the proximate cause of the theft wasn't the XSS flaw alone — XSS flaws happen, and no IAM provider can prevent a customer's own code from having one. The proximate cause of the token being readable once the flaw existed was the customer's integration keeping that bearer token somewhere JavaScript-accessible, almost certainly localStorage or a plain in-memory variable exposed to the page. If that same token had instead been held behind an httpOnly cookie — or, better, never reached the browser at all because the integration used a BFF — the XSS flaw would still exist, but the attacker's injected script would have had nothing to read. The vulnerability and the exposure are two different things, and this chapter's token-storage guidance is specifically about shrinking the second one even when the first one is outside your control. Northwind's own token scope and short lifetime (ch. 9's actual mitigation) still mattered and still limited the blast radius once the token was stolen — but "the token should not have been stealable in the first place" is the best-current-practice answer chapter 9 was waiting for this chapter to supply.

  • If a confidential (server-side, secret-holding) client skips PKCE on the theory that "the secret already protects it," the cause is confusing what the secret protects (the token-endpoint exchange) with what PKCE protects (the authorization code in flight before that exchange) — see "PKCE, everywhere" above.
  • If a client trusts more than one authorization server and takes the incoming response's identity on faith, the cause is missing `iss` validation, not an unavoidable risk of multi-IdP setups — see "Mix-up attacks" above.
  • If a client generates and checks a state value but the CSRF protection still fails in review, the cause is usually that the value was never actually bound to the initiating browser session (e.g. stored somewhere any page can read), not that state doesn't work.
  • If an SPA keeps its access token in localStorage "because it's simpler than cookies," the cause is treating convenience as equivalent to security review, when the two storage choices have categorically different exposure to the same XSS flaw.
  • If a team believes moving a token into an httpOnly cookie "fixes" its security posture completely, the cause is forgetting that an httpOnly cookie reintroduces CSRF exposure that localStorage never had — it's a trade, not a strict improvement with no new cost.

Takeaways

  • The OAuth 2.0 Security Best Current Practice is a published, final RFC — RFC 9700 / BCP 240, January 2025 — consolidating threat-model advice that used to be scattered across RFC 6749, 6750, and the now-superseded RFC 6819.
  • PKCE is no longer "the public-client thing" — RFC 9700 recommends it for confidential clients too, because it protects the authorization code in flight, a layer a client secret never covered.
  • A mix-up attack exploits a client that trusts more than one authorization server and has no way to verify which one actually issued a given response.
  • `iss` validation (RFC 9207) is the preferred mix-up defense: the authorization server states its own identity in the response, and the client compares it before doing anything else.
  • The `state` parameter's security property comes from being bound to the specific browser session that initiated the request — not merely from surviving the round trip unchanged.
  • `localStorage`/`sessionStorage` are JavaScript-readable by design, which means any XSS flaw on the page can read a token kept there directly — this is the mechanism behind chapter 9's Northwind Apps token-theft incident, named explicitly for the first time in this chapter.
  • An httpOnly cookie removes the JS-readable-token exposure entirely, but reintroduces CSRF exposure that needs its own defense (`SameSite`, a CSRF token, or both) — no storage choice is free of trade-offs.
  • RFC 10017's Backend-for-Frontend (BFF) pattern goes further than picking a safer storage API: it keeps the token out of the browser altogether, which is why the RFC calls it "strongly recommended" for real applications rather than merely one more option.
  • Revisiting chapter 9's Northwind incident: the XSS flaw and the token's readability were two separate failures, and this chapter's guidance targets the second one even when the first is outside an IAM specialist's control.
