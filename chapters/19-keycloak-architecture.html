    19. Keycloak Architecture & Deployment Options

    Eighteen chapters in, Keycloak has been mentioned constantly and installed never. This chapter is the hinge: before chapter 20 brings up a real local Keycloak via Docker Compose, you need a map of what you're about to run — what it's built on, what it needs next to it (a database, maybe a cache), how it scales from a laptop to a bank's production estate, and which of this course's three running orgs would actually choose which deployment shape and why. No lab yet — this is the blueprint you'll build from starting next chapter.

    Why this matters

    An IAM specialist is routinely the person who has to answer "can we actually run this ourselves, and what does that commit us to?" — a question chapter 12 already raised at the market level (Keycloak vs. a commercial alternative) and this chapter now answers at the infrastructure level. Getting the deployment model wrong is expensive to walk back: standing up Keycloak as a single uncached instance for a bank-scale workload, or over-provisioning a clustered multi-node deployment for a three-person internal tool, are both real mistakes specialists get hired to prevent. Everything here is foundational for Parts IV-IX — every later chapter's lab runs on the shape of Keycloak this chapter introduces.

    Recall from chapter 13

    Chapter 13 named Authorization Server as one of OAuth 2.0's four roles — the party that authenticates the resource owner, obtains their authorization, and issues access tokens — and promised "full depth from chapter 19 on." This chapter pays that off concretely: a Keycloak realm is Keycloak's instantiation of the Authorization Server role. Chapters 13-15 used a third party, Duende Software's public demo IdentityServer, to play that role in curl-only labs. Starting chapter 20, the reader stands up their own Authorization Server — a Keycloak realm — and every later OAuth/OIDC lab in this course talks to it instead of a borrowed public one.

    The Quarkus-based distribution

    Keycloak's server is built on Quarkus, a Java framework designed specifically for fast startup and a low memory footprint in containerized environments — the opposite design goal from the older general-purpose Java application servers Keycloak originally ran on. This isn't a cosmetic implementation detail: it's why a Keycloak container can realistically start in a few seconds instead of the much longer cold-start times a traditional Java EE application server needed, which matters directly for container orchestration (a Kubernetes pod that takes a long time to become ready is a worse citizen in an autoscaling cluster) and for this course's own labs (chapter 20's Docker Compose stack needs to come up fast and repeatably, every time a reader tears it down and re-runs it).

    A brief, live-verified historical note: Keycloak originally shipped on a WildFly-based (Java EE) distribution. Keycloak's own project announced in October 2021 that, starting with Keycloak 17 (released December 2021), the Quarkus-based distribution would become fully supported and the WildFly-based distribution would be deprecated; sources differ slightly on exactly which later release dropped the WildFly build entirely (accounts point to somewhere in the Keycloak 18-20 range, roughly through mid-2022), but the direction and rough timing are consistent across the project's own announcement and its release history. The practical upshot for this course: every version this course uses, including the pinned 26.8.2, is Quarkus-only — there is no WildFly option to accidentally reach for in current docs.

    The most important operational consequence of the Quarkus distribution is a hard split between two kinds of configuration:

    Build-time vs. runtime configuration in the Quarkus-based Keycloak distribution
    AspectBuild-time configurationRuntime configuration
    When it's setBaked in during kc build — produces an optimized, pre-compiled server image tailored to the chosen optionsRead fresh every time the server starts, via kc start/kc start-dev, environment variables, or conf/keycloak.conf
    ExamplesWhich database vendor (--db), whether clustering/caching is enabled, which features are turned onThe database connection URL/credentials, hostname, HTTP(S) port, log level
    Changing itRequires re-running kc build to re-optimize the server — a deliberate, slower stepJust restart the server with new values — fast, routine
    Why the split existsBaking stable, rarely-changed decisions (database vendor, feature set) into the build lets Quarkus pre-compile and optimize far more aggressively than a server that has to stay fully dynamic for everythingKeeps genuinely environment-specific values (secrets, hostnames) out of the build step entirely, so the same built image can be promoted across dev/stage/prod with only runtime values changing
    Pitfall (previewed here, chapter 20 covers it in depth)

    kc start-dev is a development-only convenience mode — it auto-enables an in-memory (dev-file) database, disables HTTPS requirements, and skips several production checks specifically so a first run is frictionless. Running it in production is one of the most common real-world Keycloak misconfigurations: it's fast to reach for during a demo and easy to forget to swap out before going live. Chapter 20's lab uses start-dev deliberately for local learning and says so explicitly, then shows what changes for a production-mode run.

    Database backends

    Keycloak needs a relational database to persist realms, users, credentials, clients, sessions (depending on deployment mode), and everything else an admin configures — it is not a database-free product. Live-checked against Keycloak's own current documentation, the officially supported database vendors as of 26.x are:

    Database backends officially supported by Keycloak 26.x (live-verified against keycloak.org's own server guide)
    --db valueVendor(s) it coversNotes
    postgresPostgreSQL, EnterpriseDB Advanced, Amazon Aurora PostgreSQLThis course's own lab environment (chapter 20 onward) uses Postgres 17 — the most common production choice and the one every later chapter's lab assumes.
    mariadbMariaDB Server 
    mysqlMySQL 
    mssqlMicrosoft SQL Server, Azure SQL Database, Azure SQL Managed Instance 
    oracleOracle DatabaseThe Oracle JDBC driver is not bundled with Keycloak and must be installed separately before it can be used.
    dev-fileAn embedded file-based database, development only The default when no --db is set. Keycloak's own docs explicitly deprecate relying on this default in production mode — you must name a real vendor explicitly.
    dev-memAn embedded in-memory database, development only Data does not survive a restart — strictly for quick local experimentation.

    The database isn't an implementation detail the reader can ignore: it's the system of record for every realm, and (depending on the HA architecture chosen, covered below) it can also become the shared store that lets multiple Keycloak nodes agree on session state. Chapter 43 covers performance tuning and database sizing in depth; this chapter only needs the reader to know which vendors are a legitimate choice and that dev-file/dev-mem are never a legitimate production choice.

    A worked example of why the vendor choice is rarely free: Meridian Trust is a retail bank, and retail banks very often already run Oracle Database for their core banking systems, with an Oracle DBA team, licensing, and operational runbooks already in place. Picking --db oracle for Keycloak lets Meridian Trust's identity layer slot into infrastructure and expertise that already exists, at the cost of a build-time step the Postgres path doesn't need — installing the Oracle JDBC driver separately before kc build can even target it. A greenfield team with no existing database standard, by contrast, has no such pull toward Oracle and would default to postgres — this course's own lab choice — precisely because nothing forces a different vendor on them.

    Standalone, containerized, and Kubernetes: a deployment spectrum

    Keycloak can run in three broadly different shapes, and they aren't competing "right answers" — they sit on a spectrum of operational complexity traded for scale and resilience:

    The Keycloak deployment spectrum
    ShapeWhat it looks likeFitsWhere this course covers it
    Standalone deploymentA single kc process running directly on a VM or bare host, talking to a database on the same or a nearby hostSmall internal tools, quick evaluation, a single team's low-traffic appMentioned here as the simplest point on the spectrum; not this course's primary lab shape
    Containerized deploymentKeycloak and its database each run as a container, wired together by Docker Compose (or a single docker run for the quickest case)Local development, this course's own labs, small-to-mid production setups that don't yet need orchestration-level self-healingChapter 20 — this course's own lab environment runs exactly this shape (Keycloak 26.8.2 + PostgreSQL 17 via Docker Compose), and every chapter 20-40 lab builds on it

    Clustering and high availability: Infinispan, briefly

    A single Keycloak node is a single point of failure and a hard ceiling on throughput. Keycloak's answer to both problems is to run multiple nodes as a cluster, sharing session and authentication-session state so a request can land on any node and still see consistent data. The component that makes this possible is Infinispan, a distributed, in-memory data grid Keycloak embeds for exactly this purpose — live-verified against Keycloak's own current high- availability documentation, Infinispan is still the caching layer behind Keycloak 26.x clustering, configured by default through conf/cache-ispn.xml.

    At a conceptual level (full depth in chapter 41, which is where this course actually configures a multi-node setup), Keycloak's own documentation describes more than one way to put nodes together:

    • A single-cluster deployment: nodes in one cluster share an embedded Infinispan cache directly between themselves, with no external dependency beyond the shared database — the simplest HA shape, suited to a single site/region.
    • A multi-site (multi-cluster) deployment, for organizations that need resilience across more than one data center or region: Keycloak's own docs describe more than one approach here, including one that relies on a separate external Infinispan cluster per site and a newer approach that leans on the database itself to carry session state across sites instead, trading one kind of operational cost (running extra Infinispan infrastructure) for another (more database load). This is exactly the kind of multi-site trade-off chapter 41 covers in depth; this chapter only needs the reader to recognize that "clustering" and "multi-site HA" are related but distinct problems.

    A realm is a concrete Authorization Server

    Chapter 13's OAuth 2.0 role vocabulary named the Authorization Server abstractly. Inside Keycloak, that role is filled by a realm — a completely isolated management namespace within one Keycloak server: its own users, credentials, clients, roles, groups, identity providers, and authentication flows, invisible to and unreachable from every other realm on the same server. One Keycloak installation can host many realms side by side, each independently playing the Authorization Server role for its own set of clients and users. (Keycloak ships with a built-in master realm, reserved for managing the Keycloak server itself — chapter 20 deliberately leaves it alone and creates a separate realm, northwind-apps, for this course's own labs, rather than mixing application realms into the one that administers Keycloak itself.)

    This closes a loop that's been open since chapter 13: demo.duendesoftware.com was a real, working Authorization Server, just not one the reader controlled or could inspect from the admin side. Starting chapter 20, the reader creates and administers their own — able to see every setting that produces the tokens their curl commands received, not just the tokens themselves.

    Case study: which deployment model fits each org?

    Case study

    Northwind Apps fits the containerized-to- Kubernetes end of the spectrum: its CIAM traffic (thousands of end-customer logins across many tenant companies, chapter 12's defining CIAM shape) is bursty and needs to scale elastically with sign-up/login spikes rather than running permanently over-provisioned — exactly the elastic scaling and self-healing a Kubernetes-managed deployment (chapter 42) is built for, once the business outgrows a fixed containerized footprint.

    Riverside Health fits self-hosted, on-premises standalone or containerized deployment: chapter 12's HIPAA-driven data-residency reasoning (wanting full control over where identity data physically lives, rather than handing that control to a SaaS vendor or even an external cloud region) pushes toward infrastructure the hospital network directly controls, sized to its own clinician-workforce population rather than consumer-scale traffic.

    Meridian Trust fits clustered, highly-available deployment: a retail bank's authentication system going down is a business-stopping, possibly regulator-notifying event, not a minor outage — the uptime expectations chapter 12's PCI-DSS context implies push directly toward the multi-node, Infinispan-backed clustering this chapter previewed and chapter 41 configures in full, rather than accepting a single node as an acceptable risk.

    Common mistakes

    • Running start-dev in production because it was the fastest way to get a demo working, then forgetting to switch to a real database vendor and production mode before real traffic arrives.
    • Treating "no license fee" (chapter 12) as "no infrastructure decisions required" — standalone vs. containerized vs. Kubernetes, and clustered vs. single-node, are real choices Keycloak doesn't make for you.
    • Assuming a build-time option (like the database vendor) can be changed with a simple restart — it requires re-running kc build, a slower, deliberate step.
    • Confusing "clustering" (multiple nodes sharing session state via Infinispan, for throughput and failover within one site) with "multi-site HA" (resilience across multiple data centers/regions) — they're related but solve different failure scenarios, and chapter 41 treats them as distinct.
    • Picking Kubernetes by default because it sounds more "production-grade," without the operational capacity to run a Kubernetes cluster well — a containerized Docker Compose deployment (this course's own lab shape) is a legitimate, durable production choice for many organizations, not just a toy.

    Glossary terms introduced here

    Takeaways

    • Keycloak's server runs on Quarkus, a Java framework built for fast startup and a small footprint in containers — it replaced an earlier WildFly-based distribution, with Quarkus becoming fully supported starting Keycloak 17 (December 2021) and the WildFly build phased out over the following releases.
    • The Quarkus distribution splits configuration into build-time (baked in via kc build, needs a rebuild to change) and runtime (read fresh via kc start, just needs a restart) — knowing which bucket a setting falls into changes how expensive it is to change later.
    • start-dev mode is a development convenience (in-memory database, relaxed checks) and is never an appropriate production configuration.
    • Keycloak 26.x officially supports PostgreSQL (including EnterpriseDB Advanced and Amazon Aurora PostgreSQL), MariaDB, MySQL, Microsoft SQL Server (including Azure SQL variants), and Oracle Database as production database backends — dev-file/dev-mem are development-only and explicitly deprecated as a production default.
    • Keycloak runs across a deployment spectrum — standalone, containerized, Kubernetes — trading operational complexity for scale and self-healing; this course's own labs (chapter 20 onward) use the containerized point, with Kubernetes covered separately in chapter 42.
    • Infinispan is the distributed, in-memory data grid Keycloak embeds for clustering — multiple nodes share session and authentication-session state through it so a request can land on any node and still see consistent data; full configuration lands in chapter 41.
    • Clustering (multiple nodes, one site) and multi-site high availability (resilience across data centers/regions) are related but distinct problems, with more than one documented architecture for the latter trading an external Infinispan cluster per site against extra database load.
    • A Keycloak realm is the concrete implementation of chapter 13's OAuth 2.0 Authorization Server role — a fully isolated namespace of users, clients, roles, and flows; one server can host many realms side by side, each playing that role independently.
    • The three case-study orgs map onto three different points on the deployment spectrum for different, defensible reasons: Northwind Apps toward containerized/Kubernetes elasticity, Riverside Health toward self-hosted on-premises control, Meridian Trust toward clustered high availability.

    Self-check

    Click a question to reveal a model answer. Try answering it yourself first — the point is to check your own reasoning against it, not to read the answer first.

    1. Explain, in your own words, why Keycloak's build-time/runtime configuration split exists — what would be lost if every setting were simply read at startup with no distinction?

      Model answerThe split exists because baking stable, rarely-changed decisions (database vendor, clustering/caching, enabled features) into the build step lets Quarkus pre-compile and optimize the server far more aggressively than if every setting had to stay dynamic. If every setting were read fresh at startup with no distinction, Keycloak would lose that aggressive build-time optimization — it would have to stay flexible enough to handle any database vendor or feature combination at runtime, undermining the fast-startup, low-footprint design Quarkus was chosen for in the first place. It would also blur the operational signal of which changes are safe, routine restarts (hostname, DB credentials) versus which require a deliberate rebuild (switching database vendors), making day-to-day operations riskier.

    2. Why is dev-file an acceptable database choice while learning this course's labs but an unacceptable one in any real deployment?

      Model answerdev-file is an embedded, file-based database meant purely for quick local experimentation with zero setup — exactly what a reader working through labs on a laptop needs. But Keycloak's own docs explicitly deprecate relying on it in production: it doesn't give the durability, concurrent-access guarantees, or operational tooling (backups, replication, monitoring) that a real vendor like PostgreSQL provides, and it can't act as the shared store multiple clustered nodes rely on to agree on session state. What's a convenience for a disposable local environment becomes a liability the moment real users, uptime expectations, or multiple nodes are involved.

    3. Pick one of the three case-study orgs and argue for a different deployment model than this chapter assigned it — what would have to change about that org for your alternative to become the better call?

      Model answerTake Riverside Health, assigned self-hosted standalone/containerized here. One could argue it should instead move toward Keycloak on Kubernetes if the hospital network grew sharply — say it expanded from a single hospital network into a multi-state health system with many more clinics and a much larger, more volatile patient-portal login volume. At that point the fixed-capacity containerized deployment this chapter assigned it would no longer flex with demand, and the elastic scaling and self-healing Kubernetes offers (chapter 42) could outweigh the HIPAA data-residency case for staying purely self-hosted — provided the Kubernetes cluster itself still ran inside infrastructure the hospital directly controlled, preserving data residency while gaining elasticity.

    4. What specifically does Infinispan solve that a single Keycloak node with no cache at all could not? Be precise about what state has to be shared and why.

      Model answerInfinispan solves the problem of session and authentication-session state consistency across multiple Keycloak nodes. A single node with no cache has no such problem because there's only one place that state can live — but the moment a load balancer spreads requests across multiple nodes, a user's login session (and any in-progress authentication-session, such as being mid-way through an MFA step) has to be visible no matter which node happens to handle their next request. Without a shared, replicated mechanism like Infinispan, a request landing on a different node than the one that started the login would see no session at all, breaking the flow. Infinispan is what lets any node see consistent session/auth-session data, independent of the durable system-of-record data (realms, users, clients) that lives in the database instead.

    5. Explain, without looking back at the text, how a Keycloak realm concretely fills the Authorization Server role chapter 13 defined abstractly — what, specifically, does a realm contain that makes it capable of doing that job?

      Model answerChapter 13 defined the Authorization Server abstractly as the OAuth 2.0 party that authenticates the resource owner, obtains their authorization, and issues access tokens. A Keycloak realm fills that role concretely because it is a fully isolated namespace that owns everything needed to do that job for its own clients: its own users and their credentials (to authenticate the resource owner), its own authentication flows (to actually run that authentication and obtain consent), and its own clients, roles, and groups (to know who it's issuing tokens to and what those tokens should claim). Because a realm is isolated from every other realm on the same server, each one can independently play the Authorization Server role for a different set of applications and users without interfering with another realm doing the same thing.

    6. Why might an organization deliberately choose a containerized Docker Compose deployment over Kubernetes even if it could run Kubernetes well? What is it trading away, and what is it avoiding?

      Model answerIt's avoiding the real operational overhead Kubernetes adds — cluster administration, more moving parts to monitor and secure, and a steeper day-to-day operational burden — when its actual traffic and resilience needs don't demand elastic autoscaling or self-healing across many nodes. It's trading away some of that elasticity and automated self-healing, but for an organization whose Keycloak workload is small-to-mid scale and predictable, a containerized Docker Compose deployment is a legitimate, durable production choice (as this chapter states) rather than a toy — it avoids paying the complexity cost of infrastructure it doesn't actually need yet.
