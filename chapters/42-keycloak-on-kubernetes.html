    42. Keycloak on Kubernetes

    Chapter 20 ran Keycloak as a single container under Docker Compose. This chapter runs the same Keycloak 26.8.2 under Kubernetes instead — not by hand-writing Deployment YAML, but through the Keycloak Operator, the officially recommended way to run Keycloak on Kubernetes. Every command below was actually run against a real local kind cluster, deleted the moment verification finished — not narrated.

    Why this matters

    Docker Compose is a fine way to run one Keycloak instance on one machine, which is exactly why chapter 20 used it. It stops being enough the moment an organization needs Keycloak to survive a node failure, scale out under load, or live inside the same Kubernetes platform every other production service already runs on — which, for most organizations past a certain size, is the actual deployment target. An IAM specialist who can only "run Keycloak" via docker compose up cannot answer the question a platform team will actually ask: how does this fit into the cluster we already operate? This chapter also puts this course's "live-verify, don't trust an old blog post" rule under real pressure — Keycloak's Kubernetes story has visibly changed over the product's history, and a popular third-party path (the Bitnami Helm chart) turned out, on live verification, to no longer be the safe default it once was.

    What concept is this?

    Chapter 19 placed Keycloak's deployment options on a spectrum — standalone process, containerized (chapter 20's Docker Compose), and Kubernetes — and chapter 20 is the "What concept is this?" anchor this chapter keeps pointing back at: everything that was a docker-compose.yml service, an environment variable, and a bind-mounted volume there becomes a Kubernetes custom resource, a Secret, and a PersistentVolume (or, in this lab's dev-only case, an emptyDir) here. The actual Keycloak server underneath is unchanged — same image, same realms-and-tokens behavior chapters 21-30 already covered — only the thing orchestrating it is different. Chapter 41's Infinispan clustering material is the other direct callback: once this chapter's spec.instances field goes above 1, chapter 41's session-replication concerns stop being theoretical.

    Live-verified, 2026-11-11: Operator vs. Bitnami Helm chart

    This is exactly the kind of claim CLAUDE.md's "no invented facts" rule exists for — the honest answer in 2026 is not the same answer a 2022 blog post would give. Checked directly against Keycloak's own current documentation (keycloak.org/operator/installation and /operator/basic-deployment) and current reporting on Bitnami's catalog changes:

    • The Keycloak Operator is Keycloak's own project, versioned and released alongside the server itself — the 26.8.2 Operator install commands below are pinned to the exact same version as this course's Keycloak image. It is actively maintained and is the path this chapter uses.
    • The Bitnami Keycloak Helm chart, a long-popular community path, genuinely degraded: Bitnami (now part of Broadcom) moved its free public container image catalog to a "legacy" repository starting around August 2025 that no longer receives updates or security patches — new images now require a paid subscription. This isn't a style preference against Bitnami; it's a real, dated maturity gap this chapter's live-verification turned up.

    What an Operator actually does

    A Kubernetes Operator is an ordinary controller program plus one or more Custom Resource Definitions (CRDs) that teach the Kubernetes API server a new resource type — here, Keycloak, KeycloakRealmImport, KeycloakOIDCClient, and KeycloakSAMLClient. You never create a StatefulSet or a Service for Keycloak by hand; you create one Keycloak custom resource (CR) describing what you want, and the Operator's control loop does the rest, continuously, not just once at apply time.

    Key idea

    A plain kubectl apply -f deployment.yaml is a one-time instruction. A CR plus an Operator is a standing contract: if a pod dies, if the StatefulSet drifts, if the CR changes, the Operator notices and corrects it on its own, continuously — the same "declare desired state, let a controller enforce it" idea every built-in Kubernetes controller (Deployments, StatefulSets themselves) already uses, extended to a resource type (Keycloak) Kubernetes never shipped with.

    Hands-on: ephemeral Postgres, a DB secret, and a dev TLS cert

    Files you'll need for this lab
    • example-postgres.yaml — an ephemeral, dev-only PostgreSQL StatefulSet + Service (below).
    • example-kc.yaml — the Keycloak custom resource the Operator reconciles into a running server (next slide).

    Also needs: the local kind cluster and Operator install the previous slide already walked through, plus kubectl and openssl (both covered by chapter 0's environment setup).

    The Operator docs' own example uses an ephemeral, emptyDir-backed PostgreSQL StatefulSet for development — data doesn't survive a restart, which is fine here since the whole cluster gets deleted at the end anyway. Create a file named example-postgres.yaml with exactly this content:

    # Ephemeral, development-only PostgreSQL for the Keycloak Operator lab (chapter 42).
# Copied in structure from https://www.keycloak.org/operator/basic-deployment's own
# "Dev PostgreSQL Database" example (same StatefulSet/Service shape, same emptyDir
# storage -- data is lost if the pod restarts, which is fine for this lab since the
# whole kind cluster gets deleted at the end anyway). Namespaced to `keycloak` to
# match the operator's default namespace-scoped install.
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgresql-db
  namespace: keycloak
spec:
  serviceName: postgresql-db-service
  replicas: 1
  selector:
    matchLabels:
      app: postgresql-db
  template:
    metadata:
      labels:
        app: postgresql-db
    spec:
      containers:
        - name: postgresql-db
          image: postgres:15
          volumeMounts:
            - mountPath: /data
              name: cache-volume
          env:
            - name: POSTGRES_USER
              value: testuser
            - name: POSTGRES_PASSWORD
              value: testpassword
            - name: PGDATA
              value: /data/pgdata
            - name: POSTGRES_DB
              value: keycloak
          ports:
            - containerPort: 5432
      volumes:
        - name: cache-volume
          emptyDir: {}
---
# NOTE: the Service Keycloak actually connects to is named `postgres-db` (not
# `postgresql-db`, the StatefulSet's name) -- the docs' own example has this same
# one-letter naming mismatch between the two objects, and it is easy to typo when
# copying by hand. `type: LoadBalancer` stays <pending> on kind (no cloud LB
# controller), but the ClusterIP it also gets assigned is all Keycloak needs.
apiVersion: v1
kind: Service
metadata:
  name: postgres-db
  namespace: keycloak
spec:
  type: LoadBalancer
  ports:
    - port: 5432
      targetPort: 5432
  selector:
    app: postgresql-db

    Apply it:

    $ kubectl apply -f example-postgres.yaml
statefulset.apps/postgresql-db created
service/postgres-db created

$ kubectl -n keycloak create secret generic keycloak-db-secret \
    --from-literal=username=testuser --from-literal=password=testpassword
secret/keycloak-db-secret created

    The Operator's HTTPS configuration (http.tlsSecret) needs a real certificate — the docs themselves give this exact openssl one-liner as their own "for development purposes" shortcut, so this isn't an invented workaround:

    $ openssl req -newkey rsa:2048 -nodes -keyout key.pem -x509 -days 3 \
    -out cert.pem -subj "/CN=localhost"
$ kubectl -n keycloak create secret tls example-tls-secret --cert cert.pem --key key.pem
secret/example-tls-secret created

    Hands-on: applying the Keycloak CR

    Create a file named example-kc.yaml with exactly this content — the second and last file this lab needs:

    # The Keycloak custom resource (CR) the Operator reconciles into a running server.
# apiVersion/kind/field shapes verified live against https://www.keycloak.org/operator/basic-deployment
# (Keycloak 26.8.2). Two fields deviate from that page's own example, both documented
# in the chapter text as this lab's own judgment calls, not something the docs state:
#
#   - hostname.hostname: "localhost" instead of the docs' "test.keycloak.org" --
#     there is no real DNS for a throwaway kind cluster, and setting it to localhost
#     is what makes `kubectl port-forward` + `curl https://localhost:<port>` resolve
#     correctly without extra /etc/hosts or Host-header tricks.
#   - ingress.enabled: false -- kind ships no Ingress controller by default, so a
#     Keycloak-created Ingress object would sit there with no controller to satisfy
#     it. Reaching the service by `kubectl port-forward` instead (see this chapter's
#     verification slide).
apiVersion: k8s.keycloak.org/v2beta1
kind: Keycloak
metadata:
  name: example-kc
  namespace: keycloak
spec:
  instances: 1
  db:
    vendor: postgres
    host: postgres-db
    usernameSecret:
      name: keycloak-db-secret
      key: username
    passwordSecret:
      name: keycloak-db-secret
      key: password
  http:
    tlsSecret: example-tls-secret
  hostname:
    hostname: localhost
  ingress:
    enabled: false

$ kubectl -n keycloak wait --for=condition=ready pod/example-kc-0 --timeout=180s
pod/example-kc-0 condition met

  STATUS: True

    Pitfall

    Notice the admin account: temp-admin, not admin. Unlike chapter 20's Docker Compose install (a persistent admin from fixed KC_BOOTSTRAP_ADMIN_* env vars), the Operator issues a one-time temporary admin with a random password, delivered in a generated example-kc-initial-admin Secret. Trying admin/admin here will simply fail — that's expected behavior, not a broken lab.

    Hands-on: port-forward, admin console, a real token

    With no Ingress controller in this kind cluster, kubectl port-forward straight to the Keycloak Service is the Operator docs' own documented way to reach a deployment "for debugging and development purposes":

    $ kubectl -n keycloak port-forward service/example-kc-service 18443:8443 &

$ curl -sk -o /dev/null -w "HTTP %{http_code}\n" https://localhost:18443/admin/master/console/
HTTP 200

$ curl -sk https://localhost:18443/realms/master/.well-known/openid-configuration
{"issuer":"https://localhost:18443/realms/master","authorization_endpoint":"https://localhost:18443/realms/master/protocol/openid-connect/auth", ...}

$ curl -sk -X POST https://localhost:18443/realms/master/protocol/openid-connect/token \
    -d grant_type=password -d client_id=admin-cli \
    -d username=temp-admin -d password=<decoded from the initial-admin secret>
{"access_token":"eyJhbGciOiJSUzI1NiIs...", "token_type":"Bearer", ...}

    All three real: the admin console answers HTTP 200, the OIDC discovery document is genuine (correct issuer, correct endpoints), and the password-grant call against admin-cli returned a real, signed access token — proof the Operator-deployed server is a fully functioning Keycloak, not just a pod that happens to be "Running."

    Pitfall

    A real gotcha hit while building this: kind's node runs its own containerd inside the node container, entirely separate from the host's Docker image store. Having quay.io/keycloak/keycloak:26.8.2 already cached on the host (from chapter 20's lab) did not stop the node from pulling it fresh again from the internet. kind load docker-image exists to pre-seed a node from a host-side image if that matters for your bandwidth or disk budget — not needed here once the build-cache prune created enough headroom.

    Case study: Northwind Apps' production target

    Case study — Northwind Apps

    Northwind Apps is the B2B SaaS company whose growth is the whole reason this chapter exists. Chapter 20's docker compose up -d was the right choice for a first realm and a first lab; it is not the right choice for a company onboarding new enterprise customers every week, each expecting SSO, federation, and uptime that survives a single node dying at 2am. Northwind's actual platform team would not hand-write a Deployment for Keycloak — they'd commit a Keycloak custom resource, the same shape as this chapter's example-kc.yaml, to the same GitOps repo every other service's manifests live in, point db at their real managed Postgres, set instances above 1 once chapter 41's Infinispan session-replication story is wired up, and let the Operator's reconciliation loop keep it that way — the exact mechanism this chapter's lab just watched happen on a throwaway kind cluster, at real production scale instead.

    Common mistakes and pitfalls

    • If you see a fresh "Pulling image" event inside kind for an image you swear you already have — the cause is the node's own containerd, separate from your host Docker's image store; pre-seed it with kind load docker-image if that matters.
    • If you see the Keycloak pod stuck in CrashLoopBackOff complaining it can't reach host postgres-db — the cause is likely a typo between the Service name (postgres-db) and the StatefulSet name (postgresql-db); only the Service name belongs in db.host.
    • If admin/admin doesn't work against an Operator-deployed instance — the cause is there is no such account; read the real one-time credentials from the generated <cr-name>-initial-admin Secret instead.
    • If an Ingress you created for Keycloak never gets an address — the cause is most clusters (including a stock kind cluster) ship no Ingress controller by default; install one, or use kubectl port-forward for a local lab.
    • If kubectl apply -k 'github.com/...?ref=...' installs a version you didn't expect — the cause is omitting ?ref= entirely, which tracks whatever a default branch resolves to instead of a pinned release.
    • If an OLM-managed Operator upgrades Keycloak on its own, mid-project — the cause is not setting installPlanApproval: Manual on the Subscription, which the Operator's own docs explicitly recommend to avoid exactly this.

    Glossary terms introduced here

    Takeaways

    • The Keycloak Operator — not the Bitnami Helm chart — is this course's live-verified, officially recommended way to run Keycloak on Kubernetes as of 26.8.2.
    • Bitnami's free Keycloak chart images moved to a legacy/paid repository around August 2025 and no longer receive free security updates — a real, dated maturity gap, not a style preference.
    • An Operator is a controller plus one or more CRDs: you declare desired state in a custom resource, and the Operator continuously reconciles the real cluster toward it.
    • The Operator can be installed via OLM (the docs' own "recommended" path, but needs OLM pre-installed), plain kubectl+kustomize (namespace-scoped or a still-preview cluster-wide variant), or an explicitly "Experimental" Helm chart.
    • This chapter's lab used the namespace-scoped kubectl+kustomize path, pinned with ?ref=26.8.2, because it needs no extra in-cluster component and is fully supported for a one-off teaching cluster.
    • The Keycloak custom resource replaces docker-compose.yml as "the file that describes the deployment" — but the Operator issues a one-time temp-admin account via a generated Secret, not a persistent admin like chapter 20's Compose env vars.
    • kind runs the whole control plane inside one Docker container with its own internal containerd — images already cached on your host Docker don't automatically skip a fresh pull inside the kind node.
    • kubectl port-forward to a Service is the Operator docs' own documented way to reach a deployment for debugging, especially when, like kind, the cluster has no Ingress controller installed.
    • The single biggest disk-budget lever on a tight dev machine was pruning Docker's build cache (docker builder prune -af), which freed real space without touching any running container or cached image.
    • Deleting a kind cluster (kind delete cluster) reclaims essentially everything that cluster used, because it was all living inside that one node container.

    Self-check

    Click a question to reveal a model answer. Try answering it yourself first.

    1. In your own words, what problem does the Operator pattern solve that a human running kubectl apply -f by hand, over and over, does not?

      Model answerA manual kubectl apply is a one-time instruction — nothing notices or corrects drift afterward. An Operator watching its CRs continuously reconciles the cluster toward whatever the custom resource currently says, on an ongoing basis: if a pod dies, or the CR changes, the Operator reacts without a human re-running anything.

    2. Why did this chapter's lab use the plain kubectl+kustomize install over OLM, even though Keycloak's own docs call OLM the "recommended" path?

      Model answerOLM is itself an extra component that has to already be installed and running in the cluster, plus its own Subscription/InstallPlan machinery to manage. For a one-off teaching kind cluster that gets deleted right after verification, that's operational weight with no payoff — the plain kubectl+kustomize path is equally official and supported, just simpler for this use case.

    3. What's the real difference between the admin credentials this chapter's Operator-deployed Keycloak produced versus chapter 20's Docker Compose install?

      Model answerChapter 20's Compose setup created a persistent admin account from fixed KC_BOOTSTRAP_ADMIN_USERNAME/_PASSWORD environment variables. The Operator instead issues a one-time temporary account (confirmed live: username temp-admin) with a random password, delivered only through a generated <cr-name>-initial-admin Kubernetes Secret — there is no fixed bootstrap credential to remember.

    4. Explain why kind re-downloaded images (the Operator, Keycloak, Postgres) even though at least one of them was already cached in this machine's host Docker image store.

      Model answerA kind cluster's control-plane node is itself a Docker container, and that container runs its own internal containerd with its own separate image store — it is not the same storage as the host's Docker engine. Pods scheduled on that node pull images through that inner containerd independently, so a host-side cache doesn't help unless you explicitly pre-load it with kind load docker-image.

    5. A colleague suggests the Bitnami Keycloak Helm chart is the "simpler" option for a new production deployment going into 2027. What live-verified fact from this chapter should make you push back?

      Model answerBitnami's free container image catalog — including the images that chart depends on — moved to a legacy repository around August 2025 that no longer receives security updates; current images now require a paid subscription. The official Keycloak Operator, by contrast, remains actively maintained and version-pinned per Keycloak release (this chapter used 26.8.2 end to end). "Simpler to write" isn't the same as "safe to run in production" once one path has a live, dated support gap and the other doesn't.
