    40. Custom Identity Providers & Required Actions

    Chapter 31 brokered logins through Keycloak's built-in generic OIDC broker — real configuration, zero Java. Chapter 39 (built just before this one) wrote custom SPIs for pieces that run during or alongside a login (an authenticator, an event listener, a protocol mapper). This chapter writes two SPIs Keycloak has no built-in equivalent for at all: a brand-new Identity Provider type — a protocol Keycloak was never taught to speak — and a brand-new Required Action — a mandatory step enforced only after a login has already succeeded. Both were actually compiled, actually deployed into a running Keycloak 26.8.2, and actually exercised end to end against a real toy external system this lab stood up itself.

    Why this matters

    Two situations a working IAM specialist eventually runs into, neither solved by configuration alone: an acquired company's identity system speaks a protocol nobody packaged a broker for, and a compliance team needs a brand-new mandatory step inserted into login that no built-in required action covers. Both situations are "write real Java against Keycloak's SPI," not "find the right checkbox." This chapter is where that becomes concrete for two SPI families this course hasn't touched yet.

    Sources for this chapter: Keycloak's own Server Developer Guide — "Implementing an SPI" and Server Administration Guide — Identity Brokering (version 26.8.2, fetched live for this chapter); the actual class files bundled inside the running quay.io/keycloak/keycloak:26.8.2 image, inspected directly with javap (the same live-verification method chapters 33 and 39 used — neither this chapter's Identity Provider SPI contract nor its Required Action SPI contract were assumed to live where an older guide or a different SPI family's chapter might suggest); and this chapter's own lab, run against a real, disposable Keycloak 26.8.2 + PostgreSQL 17 Docker Compose stack this chapter owns — every file it needs is given in full later on this page, no separate repository required.

    What concept is this?

    Two separate recalls, one per component. The custom Identity Provider is the mechanism underneath chapter 7's IdP/SP/RP trust triangle and chapter 31's hands-on brokering lab. Chapter 31 configured Keycloak's built-in generic OIDC identity-provider type — real configuration against a real external Keycloak realm, but every class involved (OIDCIdentityProvider, and so on) already shipped with the server. This chapter writes a brand-new identity-provider type from scratch — the same role chapter 7 named (an external system that authenticates the user and asserts the result back), speaking a protocol ("Cascade SSO," a toy stand-in invented for this lab) that none of Keycloak's thirteen-plus built-in broker types understand at all.

    The custom Required Action is the mechanism underneath chapter 25's required-action configuration. Chapter 25 ordered and configured built-in required actions (Configure OTP, Update Password, Verify Email) inside an authentication flow. This chapter writes a brand-new one: Riverside Health's one-time HIPAA data-handling acknowledgment, discovered and deployed exactly the way chapter 25's built-in actions already work internally, just with code this course wrote instead of code Keycloak ships.

    One Maven module, one jar, two unrelated SPI factories

    This chapter's lab brief asked for two genuinely independent components — a custom Identity Provider for Meridian Trust, a custom Required Action for Riverside Health — and left it to this chapter's judgment whether that means one Maven module or two. It's one, producing one jar, following the exact same "a provider jar can register as many unrelated SPI implementations as it likes" shape Keycloak itself ships (one Keycloak distribution jar routinely contains dozens of unrelated provider factories). The two components here share nothing at runtime — they don't call each other, they don't share config — but they share identical dependency coordinates, the identical target Keycloak version, and the identical "drop one jar into /opt/keycloak/providers" deploy step, so a second Maven module would only have duplicated build-script boilerplate without buying any real isolation. A single jar with two META-INF/services files, one per SPI, is exactly how it was actually built and deployed.

    What a custom Identity Provider actually has to implement

    Decompiling AbstractIdentityProvider's real bytecode (not just its method signatures) showed exactly which methods it leaves as genuine no-ops a subclass must override, versus which ones already have a sane default:

    • performLogin(AuthenticationRequest) — returns null by default. Must be overridden: this is the "redirect-out" half. It receives the exact broker-endpoint redirect_uri Keycloak has already computed (/realms/{realm}/broker/{alias}/endpoint, chapter 31's fixed convention) and an opaque, Keycloak-minted state value that must be carried through unchanged.
    • callback(RealmModel, AuthenticationCallback, EventBuilder) — also returns null by default. Must be overridden to return a small JAX-RS sub-resource object (a "resource locator" pattern) — the "callback-in" half, dispatched to whenever a request lands on that same broker-endpoint URL.
    • getMarshaller() — already has a sane default (DefaultDataMarshaller); no override needed unless the provider stores structured token data.
    • retrieveToken(...) (two overloads) — fully abstract, not implemented at all by AbstractIdentityProvider. A token-less protocol like Cascade SSO has nothing real to return here; this lab's provider implements both with a trivial, honestly-labeled stub rather than pretending there's a token to retrieve.
    Case study: Meridian Trust acquires Cascade Savings Bank

    Meridian Trust (chapter 2's running bank) has just acquired Cascade Savings Bank, a smaller regional institution. Cascade's employees still sign in through Cascade's own 20-year-old proprietary SSO system — a real, common post-acquisition IAM situation (chapters 9 and 11 already flagged "acquired-and-unaudited" systems as a genuine risk category). Migrating every Cascade employee into Meridian Trust's Keycloak realm on day one isn't realistic; brokering to Cascade's existing system while a longer migration happens in the background is. Keycloak ships no broker for "Cascade SSO" because it's not a real, named protocol — which is exactly the situation that calls for this chapter's SPI rather than chapter 31's configuration-only path.

    "Cascade SSO": a teaching stand-in, not a real product

    Cascade SSO is invented for this chapter. It is not a real named vendor system — no genuinely simple real legacy-SSO protocol was found worth reaching for instead of a purpose-built teaching stand-in, so this lab says so plainly rather than pretending otherwise. The protocol is deliberately minimal: a redirect-out, a login the toy IdP handles entirely itself, and a signed redirect-in. Four fields and one shared secret are the whole trust mechanism:

    • Redirect out — Keycloak's performLogin() builds GET {legacyBaseUrl}/legacy-sso/authorize?client_id=...&redirect_uri={broker endpoint}&state={state} and 303s the browser there. No network call from the Keycloak server itself — only the browser ever talks to the toy IdP directly.
    • Authentication happens entirely at the toy IdP — its own login form, its own in-memory user table (standing in for Cascade's real, un-migrated legacy credential store). Keycloak never sees the Cascade password, the same trust-boundary property every real broker (SAML, OIDC, social) also has.
    • Redirect in, signed — on success, the toy IdP 302s the browser to the exact redirect_uri it was given, appending legacy_user, legacy_email, legacy_first_name, legacy_last_name, the same state unchanged, a unix-seconds ts, and sig — an HMAC-SHA256 over "{legacy_user}|{legacy_email}|{state}|{ts}", keyed with a secret shared out-of-band with this provider's own configuration.
    • Verification, not trust-by-default — Keycloak's Endpoint.callback() recomputes that same HMAC and compares it with a constant-time check (MessageDigest.isEqual, not String.equals, to avoid a timing side-channel), rejects a ts older than 300 seconds as a stale/replayed callback, and only then resolves the real Keycloak authentication session behind state via callback.getAndVerifyAuthenticationSession(state).

    Without that signature, anything that can guess the broker-endpoint URL shape could forge a "successful Cascade login" by crafting the right query string directly — the whole point of brokering trust (chapter 7) is that the relying side only accepts an assertion it can verify came from the trusted IdP, never merely one that looks right.

      package com.meridiantrust.keycloak.legacysso;

import javax.crypto.Mac;
import javax.crypto.spec.SecretKeySpec;
import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.security.InvalidKeyException;
import java.util.HexFormat;

/**
 * Shared HMAC-SHA256 signing/verification helper for the toy "Cascade Legacy SSO" protocol.
 *
 * <p>This is deliberately the ONLY cryptographic ingredient the toy protocol uses: a shared secret,
 * known to both this Keycloak provider and the toy legacy IdP server
 * ({@code toy-legacy-idp/legacy_sso_server.py}), used to sign the handful of fields the legacy IdP
 * hands back on its callback redirect ({@code legacy_user}, {@code legacy_email}, {@code state},
 * {@code ts}). Without this signature, anything could forge a "successful legacy login" callback by
 * simply crafting the right query string and sending the browser's own request straight at Keycloak's
 * broker endpoint &mdash; the whole point of brokering trust (chapter 7's IdP/SP trust triangle) is
 * that the relying side only accepts an assertion it can verify came from the trusted IdP, not merely
 * one that *looks* right.</p>
 */
final class LegacySsoUtil {

    private LegacySsoUtil() {
    }

    static String hmacSha256Hex(String secret, String message) {
        try {
            Mac mac = Mac.getInstance("HmacSHA256");
            mac.init(new SecretKeySpec(secret.getBytes(StandardCharsets.UTF_8), "HmacSHA256"));
            byte[] raw = mac.doFinal(message.getBytes(StandardCharsets.UTF_8));
            return HexFormat.of().formatHex(raw);
        } catch (NoSuchAlgorithmException | InvalidKeyException e) {
            throw new IllegalStateException("HmacSHA256 unavailable", e);
        }
    }

    /** Constant-time comparison so a timing side-channel can't leak the expected signature. */
    static boolean constantTimeEquals(String a, String b) {
        if (a == null || b == null) {
            return false;
        }
        return MessageDigest.isEqual(
                a.getBytes(StandardCharsets.UTF_8),
                b.getBytes(StandardCharsets.UTF_8));
    }
}

 * every broker needs can be built and exercised end to end without a real external dependency. See
 * chapter 40's text for why this scenario (an acquired institution's un-migrated legacy IdP) is a
 * realistic reason a real IAM specialist would ever need to write a brand-new broker type instead of
 * reaching for one of Keycloak's built-in OIDC/SAML/social broker implementations (chapter 31).
 *
 * <p>The protocol this class speaks, end to end:</p>
 * <ol>
 *   <li>{@link #performLogin} redirects the browser to the toy IdP's
 *       {@code GET /legacy-sso/authorize} endpoint, carrying {@code client_id}, the
 *       Keycloak-computed {@code redirect_uri} (the fixed broker-endpoint convention from chapter 31 --
 *       {@code /realms/{realm}/broker/{alias}/endpoint}), and the opaque, Keycloak-minted
 *       {@code state} value unchanged.</li>
 *   <li>The toy IdP authenticates the user itself (its own login form, its own user table -- Keycloak
 *       never sees the Cascade credential) and 302-redirects the browser back to that exact
 *       {@code redirect_uri}, appending {@code legacy_user}, {@code legacy_email}, {@code legacy_first_name},
 *       {@code legacy_last_name}, the same {@code state} it was given, a unix-seconds {@code ts}, and an
 *       HMAC-SHA256 {@code sig} over those fields, keyed with a secret shared out-of-band with this
 *       provider's configuration.</li>
 *   <li>Keycloak's generic broker endpoint resolves this provider and calls {@link #callback}, which
 *       hands back {@link Endpoint} -- a small JAX-RS sub-resource that verifies the signature and the
 *       timestamp, resolves the real Keycloak {@link AuthenticationSessionModel} behind the state value,
 *       and -- only if all of that checks out -- builds a {@link BrokeredIdentityContext} and calls
 *       {@code callback.authenticated(...)}, which is what actually lets Keycloak proceed to its own
 *       First Broker Login / JIT-provisioning logic (chapter 31) for the Cascade identity.</li>
 * </ol>
 */
public class MeridianLegacySsoIdentityProvider extends AbstractIdentityProvider<IdentityProviderModel> {

    static final String CONFIG_LEGACY_BASE_URL = "legacyBaseUrl";
    static final String CONFIG_CLIENT_ID = "legacyClientId";
    static final String CONFIG_SHARED_SECRET = "sharedSecret";

    /** Callback signatures older than this many seconds are rejected as a stale/replayed redirect. */
    private static final long MAX_CLOCK_SKEW_SECONDS = 300;

    public MeridianLegacySsoIdentityProvider(KeycloakSession session, IdentityProviderModel config) {
        super(session, config);
    }

    @Override
    public Response performLogin(AuthenticationRequest request) {
        IdentityProviderModel config = getConfig();
        String legacyBaseUrl = config.getConfig().get(CONFIG_LEGACY_BASE_URL);
        String clientId = config.getConfig().get(CONFIG_CLIENT_ID);
        if (legacyBaseUrl == null || legacyBaseUrl.isBlank()) {
            throw new IdentityBrokerException(
                    "Meridian legacy SSO provider '" + config.getAlias() + "' has no " + CONFIG_LEGACY_BASE_URL
                            + " configured.");
        }
        UriBuilder authorizeUri = UriBuilder.fromUri(legacyBaseUrl)
                .path("legacy-sso/authorize")
                .queryParam("client_id", clientId)
                .queryParam("redirect_uri", request.getRedirectUri())
                .queryParam("state", request.getState().getEncoded());
        return Response.seeOther(authorizeUri.build()).build();
    }

    @Override
    public Object callback(RealmModel realm, UserAuthenticationIdentityProvider.AuthenticationCallback callback,
                            EventBuilder event) {
        return new Endpoint(realm, callback, event, this);
    }

    @Override
    public Response retrieveToken(KeycloakSession session, FederatedIdentityModel federatedIdentityModel) {
        // Cascade SSO is a pure redirect-and-assert protocol with nothing resembling an OAuth access
        // token to hand back -- there is no further token to retrieve. This method exists only
        // because UserAuthenticationIdentityProvider declares it abstract for providers (like the
        // OIDC/OAuth2 brokers) that DO have something to return here; a token-less broker like this
        // one legitimately has nothing to put in the body.
        return Response.ok("{\"note\":\"Cascade legacy SSO has no retrievable token.\"}").build();
    }

    @Override
    public Response retrieveToken(KeycloakSession session, FederatedIdentityModel federatedIdentityModel,
                                   UserSessionModel userSession, UserModel user) {
        return retrieveToken(session, federatedIdentityModel);
    }

    @Override
    public void importNewUser(KeycloakSession session, RealmModel realm, UserModel user,
                               BrokeredIdentityContext context) {
        // Mark provenance on the JIT-provisioned local user so an auditor (chapter 11's compliance
        // concerns are exactly this) can tell, years later, that this account's identity originated
        // from the acquired Cascade Savings Bank system rather than a native Meridian Trust signup.
        user.setSingleAttribute("legacySource", "cascade-sso");
        super.importNewUser(session, realm, user, context);
    }

    /**
     * The JAX-RS sub-resource Keycloak's generic broker endpoint dispatches to for every request that
     * lands on {@code /realms/{realm}/broker/{alias}/endpoint} for this provider -- the "callback-in"
     * half of the redirect-out/callback-in sequence.
     */
    public static class Endpoint {

        private final RealmModel realm;
        private final UserAuthenticationIdentityProvider.AuthenticationCallback callback;
        private final EventBuilder event;
        private final MeridianLegacySsoIdentityProvider provider;

        Endpoint(RealmModel realm, UserAuthenticationIdentityProvider.AuthenticationCallback callback,
                 EventBuilder event, MeridianLegacySsoIdentityProvider provider) {
            this.realm = realm;
            this.callback = callback;
            this.event = event;
            this.provider = provider;
        }

        @GET
        @Path("")
        public Response callback(@Context UriInfo uriInfo) {
            String legacyUser = uriInfo.getQueryParameters().getFirst("legacy_user");
            String legacyEmail = uriInfo.getQueryParameters().getFirst("legacy_email");
            String legacyFirstName = uriInfo.getQueryParameters().getFirst("legacy_first_name");
            String legacyLastName = uriInfo.getQueryParameters().getFirst("legacy_last_name");
            String state = uriInfo.getQueryParameters().getFirst("state");
            String ts = uriInfo.getQueryParameters().getFirst("ts");
            String sig = uriInfo.getQueryParameters().getFirst("sig");

            IdentityProviderModel config = provider.getConfig();
            if (state == null || ts == null || sig == null || legacyUser == null) {
                return callback.error(config, "missingCallbackParameters");
            }

            String secret = config.getConfig().get(CONFIG_SHARED_SECRET);
            String expectedMessage = legacyUser + "|" + (legacyEmail == null ? "" : legacyEmail) + "|" + state + "|" + ts;
            String expectedSig = LegacySsoUtil.hmacSha256Hex(secret, expectedMessage);
            if (!LegacySsoUtil.constantTimeEquals(expectedSig, sig)) {
                return callback.error(config, "invalidLegacySsoSignature");
            }

            long tsSeconds;
            try {
                tsSeconds = Long.parseLong(ts);
            } catch (NumberFormatException e) {
                return callback.error(config, "invalidLegacySsoTimestamp");
            }
            long nowSeconds = Instant.now().getEpochSecond();
            if (Math.abs(nowSeconds - tsSeconds) > MAX_CLOCK_SKEW_SECONDS) {
                return callback.error(config, "expiredLegacySsoCallback");
            }

            AuthenticationSessionModel authSession = this.callback.getAndVerifyAuthenticationSession(state);
            if (authSession == null) {
                return callback.error(config, "invalidLegacySsoState");
            }
            // "session" is AbstractIdentityProvider's own protected field; Endpoint, as a nested class
            // of MeridianLegacySsoIdentityProvider, can reach it through a provider instance.
            provider.session.getContext().setAuthenticationSession(authSession);
            provider.session.getContext().setRealm(realm);

            BrokeredIdentityContext context = new BrokeredIdentityContext(legacyUser, config);
            context.setIdp(provider);
            context.setUsername(legacyUser);
            context.setEmail(legacyEmail);
            context.setFirstName(legacyFirstName);
            context.setLastName(legacyLastName);
            context.setBrokerUserId(legacyUser);
            context.setAuthenticationSession(authSession);

            return this.callback.authenticated(context);
        }
    }
}

 * acknowledgment onto Riverside Health clinicians before their login session is allowed to complete.
 *
 * <p>This is the mechanism underneath chapter 25's built-in required-action configuration: chapter 25
 * configured and ordered <em>built-in</em> actions (Configure OTP, Update Password, Verify Email);
 * this class is a brand-new one, discovered the same way (a {@code *Factory} registered in
 * {@code META-INF/services/org.keycloak.authentication.RequiredActionFactory}, scanned from
 * {@code /opt/keycloak/providers}) but with code this course wrote rather than code Keycloak ships.</p>
 *
 * <p><strong>Required action vs. authenticator, the distinction chapter 39 flags from the other
 * side:</strong> a required action (this class) runs <em>after</em> the credential check has already
 * succeeded -- it can never cause a correct password/OTP to be rejected, it can only insert a
 * mandatory extra step between "authentication succeeded" and "session handed to the application."
 * A custom authenticator (chapter 39) runs <em>during</em> the credential check itself and can refuse
 * to let authentication succeed at all. Both can block a login from completing, but at genuinely
 * different points in the timeline -- confusing the two is the single most common beginner mistake
 * with Keycloak's authentication flow model (chapter 25's "common mistakes" section already flagged
 * the built-in-action version of this same confusion).</p>

 * external source -- Keycloak's built-in class is itself the same one-class-implements-both-interfaces
 * pattern used here): one class implements both {@link RequiredActionProvider} (the per-invocation
 * behavior) and {@link RequiredActionFactory} (the registration/discovery metadata), with
 * {@code create(session)} simply returning {@code this} since this provider is stateless.</p>
 */
public class RiversideHipaaAcknowledgmentRequiredAction implements RequiredActionProvider, RequiredActionFactory {

    public static final String PROVIDER_ID = "riverside-hipaa-ack";

    /** User attribute recording when (epoch seconds) the acknowledgment was accepted. */
    static final String ACKNOWLEDGED_AT_ATTRIBUTE = "riversideHipaaAckAt";

    private static final String TEMPLATE = "riverside-hipaa-consent.ftl";
    private static final String FORM_FIELD_CANCEL = "cancel";

    @Override
    public void evaluateTriggers(RequiredActionContext context) {
        // Deliberately a no-op: this lab assigns the action to one specific test user via the Admin
        // REST API (the same per-user assignment chapter 22 did for priya.patel's CONFIGURE_TOTP),
        // not as a realm-wide default-for-every-new-user action. A real Riverside Health deployment
        // could instead check something like "has this clinician ever acknowledged the current policy
        // version" here and call context.getUser().addRequiredAction(PROVIDER_ID) automatically --
        // left out of this lab to keep the one mechanism being taught (the required action itself)
        // separate from a second, independent policy decision (who gets it assigned, and when).
    }

    @Override
    public void requiredActionChallenge(RequiredActionContext context) {
        Response challenge = context.form()
                .setAttribute("user", context.getUser())
                .createForm(TEMPLATE);
        context.challenge(challenge);
    }

    @Override
    public void processAction(RequiredActionContext context) {
        MultivaluedMap<String, String> formData = context.getHttpRequest().getDecodedFormParameters();
        if (formData.containsKey(FORM_FIELD_CANCEL)) {
            context.failure("riversideHipaaAckDeclined");
            return;
        }
        UserModel user = context.getUser();
        user.setAttribute(ACKNOWLEDGED_AT_ATTRIBUTE, List.of(Long.toString(Instant.now().getEpochSecond())));
        context.success();
    }

    @Override
    public String getDisplayText() {
        return "Riverside Health – HIPAA Data Handling Acknowledgment";
    }

    @Override
    public RequiredActionProvider create(KeycloakSession session) {
        return this;
    }

    @Override
    public String getId() {
        return PROVIDER_ID;
    }

    @Override
    public void init(Config.Scope config) {
        // no-op: this provider needs no server-wide configuration.
    }

    @Override
    public void postInit(KeycloakSessionFactory factory) {
        // no-op
    }

    @Override
    public void close() {
        // no-op: stateless, nothing to release.
    }
}

"""A tiny, deliberately minimal stand-in for Cascade Savings Bank's "Cascade SSO" legacy proprietary
single-sign-on system -- a toy protocol invented for chapter 40 of the IAM & Keycloak Mastery course,
NOT a real named vendor product. It exists purely so the chapter's custom Identity Provider SPI
(MeridianLegacySsoIdentityProvider) has something real to redirect to and get a real callback from.

Protocol (teaching-grade, not production-grade -- see the chapter's "common mistakes" section):

  GET /legacy-sso/authorize?client_id=...&redirect_uri=...&state=...
      Serves a plain HTML login form. The redirect_uri and state are carried through as hidden form
      fields so they survive the POST below.

  POST /legacy-sso/authorize  (same path)
      Body: username, password, client_id, redirect_uri, state.
      On a correct username/password match against this server's own in-memory user table (standing
      in for Cascade's real, un-migrated legacy user store -- this is exactly the kind of system an
      acquired institution keeps running after an acquisition, chapter 11's compliance chapter and
      chapter 9's threat-landscape chapter both flag "acquired-and-unaudited" systems like this one as
      a real risk category), responds with a 302 redirect to:
          {redirect_uri}?legacy_user=...&legacy_email=...&legacy_first_name=...&legacy_last_name=...
              &state=...&ts=<unix-seconds>&sig=<hex HMAC-SHA256>
      sig is HMAC-SHA256, keyed with a shared secret given to this process on the command line, over
      the exact string "{legacy_user}|{legacy_email}|{state}|{ts}" -- the same message format and
      algorithm MeridianLegacySsoIdentityProvider's Endpoint.callback() verifies on the Keycloak side.
      On a wrong username/password, re-renders the login form with an error message instead.

  GET /health
      Plain 200 OK, used by the lab's own readiness check before the browser-side round trip starts.

Run:
  python3 legacy_sso_server.py --port 18141 --secret <shared-secret>

Deliberately standard-library only (http.server, hmac, hashlib) -- no pip install needed, matching
this course's "Python 3.12 is available" baseline and keeping the lab's toy IdP auditable in one file.
"""

import hashlib
import hmac
import html

from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

CASCADE_USERS = {

        "email": "j.martinez@cascadesavings.example",
        "first_name": "Javier",
        "last_name": "Martinez",
    },
    "rwong": {

        "email": "r.wong@cascadesavings.example",
        "first_name": "Rachel",

SECRET = None  # set from --secret at startup


def sign(legacy_user, legacy_email, state, ts):
    message = f"{legacy_user}|{legacy_email}|{state}|{ts}".encode("utf-8")
    return hmac.new(SECRET.encode("utf-8"), message, hashlib.sha256).hexdigest()

class Handler(BaseHTTPRequestHandler):
    server_version = "ToyCascadeSSO/1.0"

    def log_message(self, fmt, *args):
        print("[toy-legacy-idp] " + (fmt % args))

    def do_GET(self):
        parsed = urlparse(self.path)
        if parsed.path == "/health":
            self._respond(200, b"ok", "text/plain")
            return
        if parsed.path == "/legacy-sso/authorize":
            qs = parse_qs(parsed.query)
            client_id = html.escape(qs.get("client_id", [""])[0])
            redirect_uri = html.escape(qs.get("redirect_uri", [""])[0])
            state = html.escape(qs.get("state", [""])[0])
            body = LOGIN_FORM_TEMPLATE.format(
                error="", client_id=client_id, redirect_uri=redirect_uri, state=state)
            self._respond(200, body.encode("utf-8"), "text/html")
            return
        self._respond(404, b"not found", "text/plain")

    def do_POST(self):
        parsed = urlparse(self.path)
        if parsed.path != "/legacy-sso/authorize":
            self._respond(404, b"not found", "text/plain")
            return
        length = int(self.headers.get("Content-Length", 0))
        body = self.rfile.read(length).decode("utf-8")
        form = parse_qs(body)
        username = form.get("username", [""])[0]
        password = form.get("password", [""])[0]
        client_id = form.get("client_id", [""])[0]
        redirect_uri = form.get("redirect_uri", [""])[0]
        state = form.get("state", [""])[0]

        user = CASCADE_USERS.get(username)
        if user is None or user["password"] != password:
            error_html = '<p style="color:red">Incorrect Cascade username or password.</p>'
            page = LOGIN_FORM_TEMPLATE.format(
                error=error_html,
                client_id=html.escape(client_id),
                redirect_uri=html.escape(redirect_uri),
                state=html.escape(state))
            self._respond(200, page.encode("utf-8"), "text/html")
            return

        ts = str(int(time.time()))
        sig = sign(username, user["email"], state, ts)
        params = {
            "legacy_user": username,
            "legacy_email": user["email"],
            "legacy_first_name": user["first_name"],
            "legacy_last_name": user["last_name"],
            "state": state,
            "ts": ts,
            "sig": sig,
        }
        location = redirect_uri + ("&" if "?" in redirect_uri else "?") + urlencode(params)
        self.send_response(302)
        self.send_header("Location", location)
        self.end_headers()

    def _respond(self, status, body_bytes, content_type):
        self.send_response(status)
        self.send_header("Content-Type", content_type)
        self.send_header("Content-Length", str(len(body_bytes)))
        self.end_headers()
        self.wfile.write(body_bytes)


def main():
    parser = argparse.ArgumentParser(description="Toy Cascade SSO legacy IdP stand-in")
    parser.add_argument("--port", type=int, default=18141)
    parser.add_argument("--secret", required=True)
    parser.add_argument("--host", default="0.0.0.0")
    args = parser.parse_args()

    global SECRET
    SECRET = args.secret

    server = ThreadingHTTPServer((args.host, args.port), Handler)
    print(f"[toy-legacy-idp] Cascade SSO (toy) listening on http://{args.host}:{args.port}")
    try:
        server.serve_forever()
    except KeyboardInterrupt:
        pass
    finally:
        server.server_close()


if __name__ == "__main__":
    main()

    Pitfall

    If a custom Identity Provider's importNewUser()/updateBrokeredUser() override sets a custom attribute with no error, but a later GET of that user shows no attributes field at all, the cause is almost always the realm's Declarative User Profile unmanagedAttributePolicy defaulting to disabled (chapter 33 hit the exact same thing from a completely different SPI family) — not a bug in the attribute-setting call itself.

    What a custom Required Action actually has to implement

    Decompiling Keycloak's own built-in TermsAndConditions required action (a genuinely close precedent — "accept a notice before continuing" is exactly this chapter's HIPAA acknowledgment's shape) gave this chapter its reference implementation pattern, confirmed from real bytecode rather than guessed:

    • One class can implement both RequiredActionProvider (the per-invocation behavior) and RequiredActionFactory (the registration metadata) — Keycloak's own built-in action does exactly this, with create(session) simply returning this for a stateless provider.
    • requiredActionChallenge(context) renders the page: context.form() returns a LoginFormsProvider; .setAttribute("user", ...) then .createForm("riverside-hipaa-consent.ftl") builds the actual HTTP response, handed to context.challenge(...).
    • processAction(context) reads the submitted form (context.getHttpRequest().getDecodedFormParameters()): a cancel field present means decline — call context.failure(...), which hard-fails the whole login attempt; otherwise call context.success(), which lets the queued session proceed.

    The HTML page itself is deployed as a theme resource, not a whole custom theme: Keycloak's built-in "classpath" Theme Resource Provider (confirmed live via javap against the real ClasspathThemeResourceProviderFactory class) automatically scans every provider jar for a theme-resources/templates/ directory and merges whatever it finds into whichever theme is currently active. One FreeMarker file (theme-resources/templates/riverside-hipaa-consent.ftl), modeled structurally on Keycloak's own built-in terms.ftl (decompiled/extracted from the running image's theme jar as a structural reference only — the HIPAA-specific text is original to this course), was enough; no META-INF/services registration or whole-theme fork was needed for the page itself.

    Required action vs. authenticator: during vs. after

    Chapter 39's custom authenticator and this chapter's custom required action can both block a login from completing — which is exactly why beginners conflate them, the same confusion chapter 25's "common mistakes" section already flagged for the built-in version of each. The distinction holds for custom ones too, and matters more here because both are now code this course wrote, not Keycloak's own:

    Case study: Riverside Health's HIPAA acknowledgment

    Riverside Health (chapter 2's running hospital network) needs every clinician to re-acknowledge its HIPAA patient-data-handling notice at least once before they can proceed past login — a compliance control, not an authentication control. A custom authenticator would be the wrong tool even though it could technically block the same login: it runs during credential verification, which is the wrong conceptual place for "did you acknowledge a policy," and it would wrongly suggest the acknowledgment is part of proving who the clinician is rather than a separate, after-the-fact gate. A required action is the right shape precisely because it models "login succeeded, but one more mandatory step stands between that and a usable session" — exactly Riverside's real requirement.

    Lab: deploying the Required Action — and a genuinely new gotcha

    The Identity Provider SPI and the Required Action SPI differ in one important operational way, found only by actually trying it: a freshly discovered custom Identity Provider shows up immediately in a realm's "Add provider" picker once the jar is deployed. A freshly discovered custom Required Action does not automatically turn on anywhere — confirmed live:

    curl "http://localhost:18140/admin/realms/ch40-riverside-health/authentication/required-actions" \
  -H "Authorization: Bearer $TOKEN" | grep -i riverside
# (no output at all -- not in the list, even though the jar is deployed and the realm exists)

curl "http://localhost:18140/admin/realms/ch40-riverside-health/authentication/unregistered-required-actions" \
  -H "Authorization: Bearer $TOKEN"
# -> [{"providerId":"riverside-hipaa-ack","name":"Riverside Health – HIPAA Data Handling Acknowledgment"}]

    It sits in that "unregistered" list on every realm until explicitly registered, per realm, with its own endpoint:

    curl -X POST "http://localhost:18140/admin/realms/ch40-riverside-health/authentication/register-required-action" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"providerId":"riverside-hipaa-ack","name":"Riverside Health – HIPAA Data Handling Acknowledgment"}'
# -> 204, and the realm's required-actions list now shows it, enabled, priority 1001

    Only then does assigning it to a specific user (chapter 22's exact per-user pattern for priya.patel's CONFIGURE_TOTP) actually do anything at login time:

    curl -X PUT "http://localhost:18140/admin/realms/ch40-riverside-health/users/$USER_ID" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"requiredActions": ["riverside-hipaa-ack"]}'
# -> 204
    Pitfall

    If a user's requiredActions list includes a custom action's provider id but login proceeds straight through as if it weren't there at all, the cause is very likely that the action was never register-required-action'd on that specific realm — a per-realm enable/disable switch the Identity Provider SPI simply doesn't have an equivalent of, which is exactly why this surprised the reader of this lab the first time.

    Common mistakes

    • If mvn clean package fails with Non-parseable POM ... in comment after two dashes (--), the cause is a bare -- inside an XML comment — the exact same trap chapter 33 hit, hit again here while writing this POM's own explanatory comments. Replace with an em dash or split the comment.
    • If compilation fails with package jakarta.ws.rs does not exist despite depending on keycloak-server-spi-private, the cause is assuming Maven pulls it in transitively — it doesn't, here; it needs its own explicit provided-scope dependency, pinned to the exact version the target Keycloak image bundles.
    • If compilation fails on org.keycloak.Config while implementing RequiredActionFactory.init(), the cause is reaching for either server-spi artifact — that class lives in keycloak-core instead.
    • If a custom Identity Provider's JIT-provisioned user is missing a custom attribute the provider clearly set with no error, the cause is almost always the realm's Declarative User Profile unmanagedAttributePolicy defaulting to disabled (chapter 33's gotcha, confirmed to recur independently for this completely different SPI family) — not a bug in the attribute-setting call.
    • If a user's requiredActions includes a custom action's provider id and login still sails straight through, the cause is very likely that the action was never explicitly register-required-action'd on that specific realm — a per-realm switch this SPI has that the Identity Provider SPI simply doesn't.
    • If context.failure("someMessageCode") produces only Keycloak's generic "An error occurred" page instead of anything specific, the cause is that messageCode is a realm message-bundle key, not display text — it only renders custom text if a matching entry exists in a theme-resources/messages/messages_en.properties file (deliberately left out of this lab to keep message-bundle customization, a different topic, separate from the one new mechanism being taught here).
    • If a beginner reaches for a custom authenticator (chapter 39) to enforce a policy acknowledgment like this chapter's HIPAA notice, the fix is recognizing it as a required action instead: anything that should gate "a session becomes usable" after a credential has already verified belongs after authentication, not woven into it.

    Glossary terms introduced here

    Takeaways

    • A custom Identity Provider SPI is the mechanism underneath chapter 31's brokering lab: chapter 31 configured a built-in broker type; this chapter wrote a brand-new broker type from scratch.
    • A custom Required Action SPI is the mechanism underneath chapter 25's required-action configuration: chapter 25 ordered built-in actions; this chapter wrote a brand-new one.
    • AbstractIdentityProvider.performLogin() and .callback() return null by default — a subclass must override both, confirmed directly from the real bytecode, not assumed from the method signature alone.
    • The redirect-out/callback-in shape every broker needs is: build a redirect carrying Keycloak's own broker-endpoint URL and opaque state, let the external system authenticate the user entirely itself, and verify (never just trust) whatever comes back on the callback.
    • A required action runs only after a credential has already verified — it can add a mandatory step, but it can never cause a correct credential to be rejected; a custom authenticator (chapter 39) is the tool for anything that should be able to do that.
    • A freshly discovered custom Identity Provider is usable immediately once deployed; a freshly discovered custom Required Action is not — it must be explicitly registered per realm via register-required-action before assigning it to any user does anything.
    • Theme resources (theme-resources/templates/*.ftl bundled inside a provider jar) let a required action add one new rendered page to the active theme without forking a whole theme.
    • The Declarative User Profile's unmanagedAttributePolicy gotcha from chapter 33 recurred here, independently, for a completely different SPI family — a sign it's a general Keycloak behavior worth remembering, not a one-off quirk of the User Storage SPI specifically.
    • Neither this chapter's toy Cascade SSO protocol nor its toy legacy-IdP server is a real vendor product — both are purpose-built teaching stand-ins, said so plainly rather than implied otherwise.

    Self-check

    Click a question to reveal a model answer. Try answering it yourself first.

    1. A colleague says "I don't see why we need a whole custom Identity Provider for Cascade Savings Bank — can't we just write a custom authenticator that calls out to Cascade's login API during Meridian Trust's own login flow?" What's wrong with that plan?

      Model answerThat plan would require Meridian Trust's Keycloak realm to collect the Cascade password directly and forward it somewhere, which defeats the entire point of brokering: the trust boundary chapter 7 describes depends on the external system authenticating the user itself, with Keycloak never seeing that credential at all. A custom authenticator that proxies a password through is a credential-forwarding anti-pattern, not brokering. The correct shape is exactly this chapter's redirect-out/callback-in Identity Provider: the browser is sent to Cascade's own login form, Cascade authenticates the user with its own credential, and only a signed assertion of the result comes back to Keycloak.

    2. Why does Endpoint.callback() verify an HMAC signature over the callback's fields instead of simply trusting whatever query parameters arrive at the broker endpoint?

      Model answerThe broker endpoint's URL shape (/realms/{realm}/broker/{alias}/endpoint) is a fixed, publicly knowable convention (chapter 31 documented it directly) — without a signature, anyone who can guess or observe that shape could craft a query string claiming to be any Cascade user and have Keycloak JIT-provision or log in as them, with no real authentication having happened at all. The HMAC, keyed with a secret shared only between the toy IdP and this provider's configuration, is what lets Keycloak verify the callback actually originated from the trusted toy IdP rather than merely looking like it did.

    3. Riverside Health's compliance team asks whether the HIPAA acknowledgment required action can ever prevent an employee with a correct password and correct OTP from logging in. What's the accurate answer, and why?

      Model answerNo — not in the sense of rejecting correct credentials. A required action runs only after authentication has already succeeded; it can insert a mandatory extra step (decline it, and the login attempt as a whole fails), but it cannot cause a correct password/OTP combination to be treated as incorrect. That distinction matters for the compliance team specifically: the acknowledgment is a post-authentication gate on session completion, not an authentication control, so it should never be described to an auditor as "part of verifying who the clinician is."

    4. A new custom required action is deployed and its jar is confirmed present in /opt/keycloak/providers, but assigning it to a test user's requiredActions list seems to do nothing at login. Walk through the most likely cause and how to confirm it.

      Model answerThe most likely cause is that the action was never explicitly registered on that specific realm — unlike a custom Identity Provider, a freshly discovered custom Required Action sits in that realm's unregistered-required-actions list until a separate POST .../authentication/register-required-action call runs. Confirm it by GETting /admin/realms/{realm}/authentication/unregistered-required-actions: if the provider id shows up there, that's the cause, and the fix is registering it before expecting the per-user assignment to have any effect.

    5. Why does this chapter's Identity Provider extend AbstractIdentityProvider (from keycloak-server-spi-private) directly instead of extending AbstractOAuth2IdentityProvider the way Keycloak's own built-in Google/GitHub/OIDC providers do?

      Model answerAbstractOAuth2IdentityProvider lives in keycloak-services, a much heavier artifact that pulls in Keycloak's whole REST layer as a transitive dependency, and it bakes in OAuth2-specific assumptions (token endpoints, client secrets, grant types) that the toy Cascade SSO protocol simply doesn't have — it's a plain redirect-and-signed-assertion protocol, not OAuth2-shaped at all. Extending the lighter AbstractIdentityProvider directly keeps the dependency footprint to exactly what this provider actually needs, and avoids inheriting OAuth2 machinery that would never be used.

    6. What, specifically, does "the toy IdP's redirect_uri parameter" actually point at, and who sets that value?

      Model answerIt points at Keycloak's own fixed broker-endpoint URL for this specific Identity Provider alias — /realms/{realm}/broker/cascade-legacy-sso/endpoint, chapter 31's documented convention — and Keycloak itself sets that value, handing it to this provider's performLogin() through the AuthenticationRequest parameter's getRedirectUri(). The provider never invents or hardcodes that URL; it simply forwards the value Keycloak already computed on to the toy IdP as a query parameter, which the toy IdP must then echo back unchanged on its own callback redirect.
