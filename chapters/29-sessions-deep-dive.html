    29. Sessions Deep Dive & SSO Behavior

    Chapter 21 configured ssoSessionIdleTimeout, ssoSessionMaxLifespan, revokeRefreshToken, and the client/offline session fields on northwind-apps — and confirmed each one with a kcadm.sh get read-back. But setting a number on a realm is not the same as watching that number actually do something to a real session. This chapter closes that gap: it creates a real session for a real user, lists it through the Admin REST API, revokes it, and proves the revocation genuinely took effect with an independent second read — not inferred from the revoke call's own (empty) response. It also does the thing chapter 7 could only describe in the abstract: it puts the same browser session in front of two different registered clients in the same realm and shows, with real captured output, that the second one never asks for a password.

    Why this matters

    "Revoke that user's session right now" is one of the most common incident-response requests an IAM specialist receives — a laptop is reported stolen, an account is suspected compromised, an employee is terminated mid-shift — and it has to be answered correctly and quickly, usually without Admin Console access to the specific realm in front of the person who needs the answer. Knowing the exact REST call that actually kills a session, what "killed" provably means (not what you assume it means), and how that differs from merely rejecting one stale token is the difference between a confident two-minute response and a panicked, half-right one. The SSO mechanism itself is just as operationally important in the other direction: understanding why a second application doesn't re-prompt for a password is what lets you debug it correctly when a reader's own app unexpectedly does re-prompt, instead of guessing.

    What concept is this?

    Chapter 7 described an SSO session as state the identity provider keeps for a browser, checked silently on a later redirect from a different connected application so the user isn't asked to log in again. Chapter 8 drew a sharper line: a session is the thing on the IdP side that makes repeat logins unnecessary; tokens are what get handed to applications, each with its own, usually much shorter, independent lifetime. Both chapters described this entirely in the abstract — no running Keycloak existed yet to point at. This chapter makes every piece of that concrete and observable: a real session with a real id, listed and revoked through two real REST calls, and a real demonstration of exactly which cookie and which silent check is the SSO mechanism chapter 7 was describing all along.

    The session hierarchy: one SSO session, many client sessions

    Keycloak's own Server Administration Guide (fetched live for this chapter, version 26.8.2 — the same version this lab ran) states the hierarchy directly, in its description of the Client Session Idle field: "the SSO user session is the parent of zero or more client sessions, one client session is created for every different client app the user logs in." Chapter 21 introduced Client Session Idle/Max as settings; what the guide adds, and what this chapter's lab reproduces for real below, is the shape: one SSO session per browser-realm pair, with one child client session underneath it for every distinct client the browser has authenticated to during that session.

    Three session-shaped objects this chapter distinguishes, confirmed against Keycloak 26.8.2
    ObjectScopeWhat governs its lifetime
    SSO (user) sessionOne per browser per realmSSO Session Idle / SSO Session Max (ch. 21) — the parent object; its own id is the sid claim stamped into every token minted under it, and the id field returned by the REST calls this chapter uses.
    Client sessionOne per client the browser has visited within that SSO sessionClient Session Idle / Max — defaults to 0 on a fresh realm, which per the guide's own wording "uses the same idle timeout [or max lifespan] in the SSO Session Idle [Max] configuration" — 0 means inherit, not unlimited, confirmed by reading a real fresh realm's fields in this chapter's lab.
    Offline sessionOne per client granted offline_accessOffline Session Idle / Offline Session Max Limited (ch. 21) — survives the SSO session's own death; out of this chapter's lab scope, covered conceptually in ch. 21.

    The Admin REST API's session-management surface

    Every endpoint below was fetched directly from Keycloak's published Admin REST API OpenAPI definition (not recalled from memory, not paraphrased from a possibly-stale blog post) and then actually called against a live Keycloak 26.8.2 instance in this chapter's lab — every path, verb, and response code below is independently confirmed twice over.

    Session-management endpoints, quoted from the real OpenAPI definition and exercised live
    EndpointOpenAPI summary (verbatim)Confirmed response code
    GET /admin/realms/{realm}/users/{user-id}/sessions"Get sessions associated with the user"200, body: array of session objects (empty array when none exist — confirmed both ways in this lab)
    DELETE /admin/realms/{realm}/sessions/{session}"Remove a specific user session." "Any client that has an admin url will also be told to invalidate this particular session."204, no body
    POST /admin/realms/{realm}/users/{user-id}/logout"Remove all user sessions associated with the user. Also send notification to all clients that have an admin URL to invalidate the sessions for the particular user."204, no body
    POST /admin/realms/{realm}/logout-all"Removes all user sessions." "Any client that has an admin url will also be told to invalidate any sessions they have."200 (realm-wide — not exercised in this lab; too destructive for a shared realm, documented here, not run)
    GET /admin/realms/{realm}/clients/{client-uuid}/user-sessions"Get user sessions for client. Returns a list of user sessions associated with this client."200 — the per-client mirror of the per-user listing above; not exercised live in this lab, documented from the spec
    Pitfall — the session id is not the user id, and not a token

    DELETE /sessions/{session} takes the session's own id — the same string that shows up as the sid claim inside every token minted under that session, and as the id field in a GET users/{id}/sessions response — not the user's id (used by the other two endpoints) and not an access or refresh token. If you see a 404 from this endpoint, the cause is very often exactly this confusion: a user id or a token value was passed where a session id belongs.

    Session-level revocation vs. refresh-token-level revocation

    This chapter's lab deliberately exercised two different things Keycloak calls "revoking" something, because they are not the same operation and the course's own glossary (chapter 21's Revoke Refresh Token entry) risked reading as if they were:

    1. Session-level revocation. With directAccessGrantsEnabled turned on just long enough to mint one real token (the same lab-only pattern chapter 24 used, and reverted immediately after, per chapter 13's framing of this grant as deprecated for real applications), jane.doe authenticated and received a real session:

      $ curl -s -X POST http://localhost:8080/realms/northwind-apps/protocol/openid-connect/token \
    -d "grant_type=password" -d "client_id=northwind-dashboard" -d "client_secret=<secret>" \
    -d "username=jane.doe" -d "password=Lab_Password_2026!" -d "scope=openid profile email"
      { "access_token": "eyJ...", "refresh_token": "eyJ...", "session_state": "42TBOp47_Tp-ZBsgs5j-K9uv", ... }

      Listed via the Admin REST API — a real, live session, not assumed:

      $ curl -s -H "Authorization: Bearer <admin token>" \
    http://localhost:8080/admin/realms/northwind-apps/users/45382aeb-.../sessions
      [ { "id": "42TBOp47_Tp-ZBsgs5j-K9uv", "username": "jane.doe",
    "clients": { "eb3cb5c6-...": "northwind-dashboard" } } ]

      Revoked by session id, confirmed clean with 204, then confirmed genuinely gone with a second, independent read — not the DELETE call's own (empty) response:

      $ curl -s -o /dev/null -w "%{http_code}\n" -X DELETE -H "Authorization: Bearer <admin token>" \
    http://localhost:8080/admin/realms/northwind-apps/sessions/42TBOp47_Tp-ZBsgs5j-K9uv
204
$ curl -s -H "Authorization: Bearer <admin token>" \
    http://localhost:8080/admin/realms/northwind-apps/users/45382aeb-.../sessions
[]

      And the refresh token minted under that dead session is now provably useless, confirmed by actually trying it, not assumed from the session being gone:

      $ curl -s -X POST http://localhost:8080/realms/northwind-apps/protocol/openid-connect/token \
    -d "grant_type=refresh_token" -d "client_id=northwind-dashboard" -d "client_secret=<secret>" \
    -d "refresh_token=<the refresh token from above>"
      { "error": "invalid_grant", "error_description": "Session not active" }

    2. Refresh-token-level revocation (Revoke Refresh Token, chapter 21), enabled for real this time and confirmed:

      $ kcadm.sh update realms/northwind-apps -s revokeRefreshToken=true
$ kcadm.sh get realms/northwind-apps --fields revokeRefreshToken
      { "revokeRefreshToken" : true }

      A fresh token mint, then its refresh token used once (succeeds, issues a brand-new refresh token RT2) and then reused a second time (the original RT1 again):

      $ curl -s -X POST .../token -d grant_type=refresh_token -d refresh_token=$RT1   # first use
{ "access_token": "...", "refresh_token": "<RT2, different from RT1>", ... }   # succeeds

$ curl -s -X POST .../token -d grant_type=refresh_token -d refresh_token=$RT1   # RT1 again
{ "error": "invalid_grant", "error_description": "Maximum allowed refresh token reuse exceeded" }

      That exact error text — "Maximum allowed refresh token reuse exceeded" — is this chapter's own confirmed, real output, not a guess at Keycloak's wording. It matches the refresh-token rotation and reuse-detection behavior RFC 9700 (the OAuth 2.0 Security Best Current Practice, confirmed live in chapter 18) describes in §2.2.2 and §4.14 as a defense against a leaked refresh token being replayed after the legitimate client has already moved past it. Critically, the session itself was still alive — a follow-up GET users/{id}/sessions still returned the session, with an updated lastAccess. Rejecting a stale refresh token and killing the underlying session are two different, independently-confirmable things.

    Logout mechanisms, and what a no-browser session can and can't claim

    Everything above used the Admin REST API directly — a server-to-client action with no browser in the loop. Keycloak's documentation (fetched live for this chapter) names four separate OIDC logout mechanisms for the browser-driven case, which this chapter can describe accurately but, with no browser tool available, cannot personally click through:

    The four OIDC logout mechanisms Keycloak documents, quoted/paraphrased from the Server Administration Guide
    MechanismHow it works, per the guide
    Session Management"A browser-based logout. The application obtains session status information from Keycloak at a regular basis. When the session is terminated at Keycloak the application will notice and trigger its own logout" — this is what lets logging out in one browser tab trigger automatic logout in other tabs of apps using the Keycloak JavaScript adapter.
    RP-Initiated LogoutA browser redirect to Keycloak's own logout endpoint, "usually... when the user clicks the Log Out link"; Keycloak then sends logout requests to every client attached to that browser's SSO session.
    Front-Channel LogoutRelies on the browser rendering hidden iframes per client. The guide's own caution: this "might be impacted by Content Security Policies" and can be blocked, and a session may survive if the user closes the browser before the logout page finishes rendering.
    Back-Channel LogoutA direct server-to-server logout request to each client's own Back-Channel Logout URL (falling back to its Admin URL if unset) — no browser involvement, which the guide recommends as "a more reliable and secure approach" than front-channel.

    The Admin Console also exposes a realm-wide, timestamp-based revocation policy that this chapter's lab did not exercise (too destructive to run against a shared lab realm, and this course's "real, not narrated" rule means not faking it either): under Sessions → Actions → Revocation, an administrator can set a cutoff date/time — per the guide, "sessions or tokens issued before that time and date are invalid" — and optionally Push that policy to every registered OIDC client running Keycloak's own adapter. This is a different tool from the per-session and per-user REST calls this chapter did run: those target one session or one user precisely; the revocation policy is a blunt, realm-wide "everything before this instant is dead" switch, the kind of thing reached for only in a genuine breach, not routine offboarding.

    Case study: Meridian Trust ends a stolen session, for real

    Case study — Meridian Trust

    Meridian Trust is a retail bank under PCI-DSS, and chapter 11 already named exactly this requirement: the ability to act immediately when an employee's access must be cut. The scenario: a teller's laptop is reported stolen mid-shift, still logged into Meridian's internal banking console through Keycloak. A security operator needs to end that employee's access right now, without waiting for the session to naturally idle out, and without guessing whether it worked.

    This chapter's lab is literally that runbook, run for real against jane.doe standing in for the teller: (1) list the user's active sessions via GET users/{id}/sessions — confirmed live, one real session returned; (2) end it via DELETE sessions/{id} — confirmed 204; (3) never trust step 2's own response — a second, independent GET users/{id}/sessions call confirmed an empty array, i.e. genuinely zero active sessions, not an assumption. When the teller had logged in from two devices (this lab's concurrent-session test), the faster, broader tool was POST users/{id}/logout — one call, every session for that user gone, confirmed the same way. A PCI-DSS auditor asking "how do you know the access was actually revoked, not just that you sent a revoke request" is asking exactly the question this chapter's lab answers with a second, independent read every single time, never the mutating call's own response.

    Common mistakes

    • If you see someone treat a 204 from DELETE sessions/{id} as proof the session is gone, the cause is trusting the mutating call's own response — this chapter's own discipline, and the Meridian Trust case study's point, is that a 204 only means the server accepted the request; the only real proof is a separate, later GET that comes back empty.
    • If you see a 404 from DELETE sessions/{id}, the cause is very often passing a user id or a token value where the endpoint expects the session's own id — the same value that appears as the sid claim inside tokens minted under it.
    • If you see someone set Client Session Idle or Client Session Max to 0 expecting "no limit," the cause is missing the guide's own specific wording: 0 means "inherit the realm's SSO Session Idle/Max value," not unlimited — confirmed live on a fresh realm in this chapter's lab.
    • If you see a reader conflate Revoke Refresh Token with ending a session, the cause is missing that it only rejects a reused, already-rotated-past refresh token — this chapter's lab showed the underlying session staying alive and fully queryable the whole time that error was returned.
    • If you see a second application unexpectedly show a login prompt inside what should be one SSO session, the cause is almost never "SSO is broken" — check first whether the KEYCLOAK_SESSION cookie is actually being sent (third-party cookie blocking, a different top-level domain, or an iframe/embed context are the usual suspects), since that cookie, not some hidden server state alone, is the thing the silent check in Figure 29.2 actually depends on.
    • If you see someone reach for the realm-wide revocation ("Push") policy to end one specific user's access, the cause is reaching for the biggest hammer available instead of the precise one — that policy invalidates everything realm-wide issued before a timestamp, not one user's sessions; DELETE sessions/{id} or POST users/{id}/logout is the targeted tool for exactly the Meridian Trust scenario this chapter walks through.

    Takeaways

    • A Keycloak SSO session is the parent of zero or more client sessions, one per distinct client the browser has authenticated to within that session — confirmed live with a single session object whose clients map listed two different real client UUIDs.
    • Client Session Idle/Max defaulting to 0 means "inherit the SSO session's own value," not "unlimited" — confirmed by reading a real fresh realm's fields, not assumed from the field name.
    • Four real Admin REST API endpoints cover session management: GET users/{id}/sessions (list), DELETE sessions/{id} (revoke one), POST users/{id}/logout (revoke all of one user's sessions), and POST logout-all (revoke every session realm-wide) — all four paths quoted directly from Keycloak's published OpenAPI definition, and the first three exercised live.
    • Never trust a mutating revoke call's own (empty) response as proof of anything — this chapter's lab confirmed every revoke with a separate, independent GET call, the exact discipline a PCI-DSS auditor would ask Meridian Trust to demonstrate.
    • Revoking a session kills every token tied to it — a refresh attempt against a session already ended via the Admin REST API returned a real, captured invalid_grant / "Session not active" error, not a guessed one.
    • Revoke Refresh Token is a different mechanism from session revocation: it rotates the refresh token on every use and rejects a replayed, already-spent one ("Maximum allowed refresh token reuse exceeded," RFC 9700 §2.2.2/§4.14) — while the underlying session, confirmed live, stays alive.
    • The SSO mechanism chapter 7 described in the abstract is, concretely, a KEYCLOAK_SESSION cookie set on Keycloak's own domain: this chapter's cookie-jar demonstration got an immediate authorization-code redirect for a second, independent client with zero credentials submitted, and both redirects carried the exact same session_state value.
    • Keycloak documents four distinct OIDC logout mechanisms (Session Management, RP-Initiated Logout, Front-Channel Logout, Back-Channel Logout) with real trade-offs — front-channel depends on iframes and can be blocked by CSP or a closed browser tab; back-channel is server-to-server and the guide's own recommended, more reliable default.
    • A realm-wide, timestamp-based revocation policy exists (Sessions → Actions → Revocation, optionally "Push"ed to adapters) as a distinct, blunter tool from the per-session/per-user REST calls — reach for it only in a genuine breach scenario, not routine single-user offboarding.

    Click a question to reveal a model answer. Try answering it yourself first — the point is to check your own reasoning against it, not to read the answer first.

    1. Walk through, in your own words, exactly why a 204 response from DELETE sessions/{id} is not, by itself, proof that the session is gone — and what this chapter's lab actually did instead.

      Model answerA 204 only confirms the server accepted and processed the DELETE request; the response body is empty and carries no confirmation of the resulting state. This chapter's lab never treated that 204 as proof — after every DELETE sessions/{id} call, it ran a separate, independent GET users/{id}/sessions call and confirmed the array came back empty before treating the session as genuinely gone, exactly the discipline the Meridian Trust case study frames as what a PCI-DSS auditor would demand.

    2. Explain the real difference this chapter observed between revoking a session outright and Keycloak's refresh-token rotation/reuse-detection under Revoke Refresh Token. What's one scenario where only one of the two would be the correct tool?

      Model answerRevoking a session (DELETE sessions/{id} or POST users/{id}/logout) ends the SSO session itself — every token tied to it, including its refresh token, immediately fails with "Session not active," confirmed by a follow-up GET returning []. Revoke Refresh Token is different: it rotates the refresh token on every use and only rejects a token that has already been spent and replayed ("Maximum allowed refresh token reuse exceeded") — the underlying session itself stays alive and queryable the whole time, as this chapter's lab confirmed directly. Scenario: ending a stolen laptop's access (Meridian Trust) needs outright session revocation, since the goal is killing all access immediately — Revoke Refresh Token alone wouldn't touch a still-valid access token or the live session. Conversely, if the only observed problem is a leaked refresh token being replayed while the legitimate client is still using the session normally, Revoke Refresh Token's rotation/reuse-detection is the correct, narrower tool — revoking the whole session would also log out the legitimate user unnecessarily.

    3. Describe, mechanically, what actually made the second client's authorization request succeed without a login prompt in this chapter's cookie-jar demonstration. What specific thing would have to be missing or blocked for that same request to fail and show a login form instead?

      Model answerThe first login set a KEYCLOAK_SESSION cookie on Keycloak's own domain (not either client's domain), tied to the real SSO session vzx2JU48HbGlFh3OkVZSqNes. When the second /auth request for northwind-support-portal reused the same cookie jar, Keycloak checked that cookie, found a live, matching session, and silently reused it — issuing a fresh authorization code with the same session_state instead of rendering a login form. For that same request to fail and show a login form instead, the KEYCLOAK_SESSION cookie would have to be missing or not sent — for example, third-party cookie blocking, the request crossing a different top-level domain than Keycloak's own, an iframe/embedded context stripping cookies, or the underlying session having already idled out or been revoked.

    4. A fresh realm reads clientSessionIdleTimeout: 0. What does that 0 actually mean, and why would naively assuming "unlimited" lead someone to the wrong operational conclusion?

      Model answerPer Keycloak's own Server Administration Guide, 0 on Client Session Idle/Max means the client session inherits the parent SSO session's own Idle/Max value — it is not a sentinel for "no limit." Assuming "unlimited" would lead someone to conclude a client session could stay alive indefinitely regardless of the realm's SSO Session Idle/Max settings, when in reality it's bound by exactly the same timeout the SSO session itself has — so tightening or loosening SSO Session Idle/Max on a realm with client sessions left at the 0 default changes client-session behavior too, which an "unlimited" assumption would miss entirely.

    5. Meridian Trust's teller had two active sessions (two devices) when the laptop theft was reported. Why was POST users/{id}/logout the better tool than calling DELETE sessions/{id} twice, and under what circumstance would the two-call approach actually be the right choice instead?

      Model answerPOST users/{id}/logout revokes every session belonging to that user in one call, so a security operator doesn't need to first enumerate every session id and then issue one DELETE per id — faster and less error-prone when the goal is "end all of this person's access, full stop," which is exactly Meridian Trust's stolen-laptop scenario. The two-call DELETE sessions/{id} approach would be the right choice instead if only one specific session needed to end while the user's other session(s) should stay alive and unaffected — for example, ending just the session from a device reported lost while deliberately leaving the teller's still-trusted desktop session active.
