    22. Users & Credentials Management

    Chapter 2 gave you four words — identity, identifier, credential, attribute — and a five-stage lifecycle, all in the abstract. Chapter 20 gave you an empty realm. This chapter closes the loop: it creates two real users inside northwind-apps, jane.doe (the exact identity chapter 2 used to teach that vocabulary) and priya.patel (the engineer whose team move chapter 1 and chapter 10 already used as an example), and shows you exactly where each of chapter 2's four concepts lives on Keycloak's Users screen. Every command below was actually run against a real Keycloak 26.8.2 instance — including one real surprise this session hit and had to work around, not narrate around.

    Why this matters

    Creating a user sounds trivial until you've actually had to explain, to a teammate or an auditor, exactly what got stored, where, and under what name. An IAM specialist is routinely the person who has to answer "is this a real account or a leftover test login," "why didn't the new custom field save," and "how do we actually know this password isn't sitting in a database in plain text." This chapter answers all three concretely, against a real instance, including a genuine Keycloak behavior — the declarative User Profile silently dropping an attribute nobody declared — that this session discovered by hitting it directly, not by reading about it first.

    Recall before you create anyone

    Chapter 2 split one person into four separate concepts: identity (the whole record), identifier (the unique lookup value — jane.doe@northwindapps.com), credential (proof of control — a password, a one-time code), and attribute (a recorded fact — department: Engineering). It also generalized every identity's life into create → activate → modify → suspend → delete. Chapter 10 then named the "modify" stage's HR vocabulary — Mover — using exactly this scenario: a Northwind engineer moving from the support team to platform engineering, and the Mover trap of granting the new access without removing the old. None of that was hands-on yet. This chapter is where it all becomes a real Keycloak screen and a real kcadm.sh session.

    User attributes: built-in, custom, and a real surprise

    Chapter 2 defined an attribute as "a fact recorded about an identity that isn't itself proof of anything." Keycloak's Users screen splits attributes into two kinds: a small set of built-in attributes every user has — username, email, firstName, lastName — and an open-ended set of custom attributes an organization defines for its own needs, like the department attribute chapter 2's Jane Doe example used. In Keycloak 26.8.2, that second category is governed by a feature called the Declarative User Profile, and this chapter's lab ran straight into exactly how strict it is by default.

    1. Attempt the obvious thing — set a custom department attribute on jane.doe, the same way chapter 2's table described it:

      docker compose exec keycloak /opt/keycloak/bin/kcadm.sh update users/22c221cf-be7b-4d2f-a228-b9f8d8947681 \
  -r northwind-apps -s 'attributes.department=["Engineering"]'
docker compose exec keycloak /opt/keycloak/bin/kcadm.sh get users/22c221cf-be7b-4d2f-a228-b9f8d8947681 \
  -r northwind-apps
      {
  "id" : "22c221cf-be7b-4d2f-a228-b9f8d8947681",
  "username" : "jane.doe",
  ...
  "enabled" : true,
  ...
}

      No error, no attributes key in the result at all. The command "succeeded" and the attribute simply never arrived.

    2. Check the realm's User Profile configuration to find out why:

      docker compose exec keycloak /opt/keycloak/bin/kcadm.sh get users/profile -r northwind-apps \
  --fields unmanagedAttributePolicy
      { }

      An empty result for that field means it isn't set at all — which, per Keycloak's own documentation, is the default: Disabled.

    3. Enable support for unmanaged attributes on the realm, then retry:

      docker compose exec keycloak /opt/keycloak/bin/kcadm.sh update users/profile -r northwind-apps \
  -s unmanagedAttributePolicy=ENABLED
docker compose exec keycloak /opt/keycloak/bin/kcadm.sh update users/22c221cf-be7b-4d2f-a228-b9f8d8947681 \
  -r northwind-apps -s 'attributes.department=["Engineering"]'
docker compose exec keycloak /opt/keycloak/bin/kcadm.sh get users/22c221cf-be7b-4d2f-a228-b9f8d8947681 \
  -r northwind-apps
      {
  "id" : "22c221cf-be7b-4d2f-a228-b9f8d8947681",
  "username" : "jane.doe",
  "firstName" : "Jane",
  "lastName" : "Doe",
  "email" : "jane.doe@northwindapps.com",
  "emailVerified" : true,
  "attributes" : {
    "department" : [ "Engineering" ]
  },
  "enabled" : true,
  ...
}

      Same command, same syntax — the only thing that changed is the realm-level policy. The same sequence set priya.patel's team attribute to Support afterward, with the same real confirmation.

    Pitfall — this one was personally hit, not just read about

    Keycloak's Server Administration Guide states the mechanism plainly: "Keycloak recognizes only attributes declared in the realm's user profile. The server ignores any other attribute not explicitly defined there." Undeclared attributes are called unmanaged attributes, and a realm-level setting, unmanagedAttributePolicy, controls what happens to them — four values: DISABLED (the default — dropped everywhere), ENABLED (allowed everywhere), ADMIN_VIEW (admin-readable only), and ADMIN_EDIT (admin readable and writable). The silent part is what makes this dangerous: the Admin REST API returned no error at all when the attribute was dropped — the request looked successful. Keycloak's own docs recommend against reaching for ENABLED as a default fix; declaring the attribute formally in the user profile (so it gets real validation) or using ADMIN_EDIT is the better long-term answer. This chapter used ENABLED only because demonstrating the mechanism mattered more here than realm hardening — a real deployment should declare department as a managed attribute instead.

    Credentials: what Keycloak actually stores

    Chapter 2 called a credential "evidence presented to prove control of an identifier," and warned that credentials are the thing that must stay secret. Keycloak's Credentials tab is where that promise gets kept mechanically — and this chapter checked, rather than assumed, what actually lands in storage.

    1. Set a real password credential for jane.doe:

      docker compose exec keycloak /opt/keycloak/bin/kcadm.sh set-password -r northwind-apps \
  --username jane.doe --new-password 'JaneDoe!Lab2026' --temporary=false
      (no output — kcadm.sh prints nothing on success for this command)

    2. Confirm it via the dedicated credentials endpoint, not just the user's totp flag:

      docker compose exec keycloak /opt/keycloak/bin/kcadm.sh get users/22c221cf-be7b-4d2f-a228-b9f8d8947681/credentials \
  -r northwind-apps
      [ {
  "id" : "46901e7d-b694-40c0-9bf0-11d70567ca13",
  "type" : "password",
  "createdDate" : 1794299523205,
  "credentialData" : "{\"hashIterations\":5,\"algorithm\":\"argon2\",\"additionalParameters\":{\"hashLength\":[\"32\"],\"memory\":[\"7168\"],\"type\":[\"id\"],\"version\":[\"1.3\"],\"parallelism\":[\"1\"]}}"
} ]

      The password itself, JaneDoe!Lab2026, appears nowhere in that response — only an Argon2 hash and its parameters. Full depth on password hashing and key material belongs to chapter 16 (JWT & applied crypto) and chapter 30 (password policy); the point here is narrower and concrete: the Credentials tab's "password credential" is this JSON object, not the password, and this is exactly what was confirmed, not assumed.

    3. A real, verified mechanism connecting credentials to required actions: whether set-password forces a change at next login depends entirely on --temporary, and the default is not temporary:

      # without --temporary (or --temporary=false): no required action added
docker compose exec keycloak /opt/keycloak/bin/kcadm.sh set-password -r northwind-apps \
  --username temp.pw.test --new-password 'FirstLoginPass123'
docker compose exec keycloak /opt/keycloak/bin/kcadm.sh get users/<id> -r northwind-apps \
  --fields requiredActions
# { "requiredActions" : [ ] }

# with --temporary=true: Keycloak adds UPDATE_PASSWORD automatically
docker compose exec keycloak /opt/keycloak/bin/kcadm.sh set-password -r northwind-apps \
  --username temp.pw.test --new-password 'AnotherPass456' --temporary=true
docker compose exec keycloak /opt/keycloak/bin/kcadm.sh get users/<id> -r northwind-apps \
  --fields requiredActions
# { "requiredActions" : [ "UPDATE_PASSWORD" ] }

      Both runs shown above are real, captured against a disposable test user created specifically to check this — the exact mechanism an admin relies on when handing a new hire a one-time password they must change on first login.

    The Credentials tab also manages an OTP credential — a one-time-password generator (chapter 5 covered TOTP's mechanics in depth) enrolled through Keycloak's own setup flow, tracked separately from the password credential, and reflected in the user's totp flag once configured. Neither jane.doe nor priya.patel has one yet in this lab — priya.patel's pending Configure OTP required action (next section) is exactly the mechanism that will make her enroll one the first time she logs in.

    Required Actions: enforcement at the next login

    This is genuinely new territory — chapters 1 and 20 both forward-referenced Keycloak's Authentication → Required Actions screen without defining it. Keycloak's own Server Administration Guide defines the mechanism plainly: "Required actions are actions that a user must perform at the first login." They run after the user has already supplied valid credentials — a required action is not an authentication factor, it's a gate between a correct login and a completed one. A user "will not be able to complete the authentication process until these actions are complete," per the same documentation. Some required actions an admin assigns deliberately (as this chapter did for priya.patel); others Keycloak adds automatically — the real --temporary=true mechanism above is exactly one of those.

    Case study — Riverside Health

    Riverside Health's patient portal relies on the same mechanism for a completely different purpose: every self-registered patient account gets a Verify Email required action attached automatically when realm-level email verification is enabled, so a patient can't start viewing lab results or messaging a clinician through an email address nobody confirmed they control. Same gate, same enforcement point — a different required action for a different risk.

    The identity lifecycle, now with real commands

    Chapter 2's lifecycle was deliberately abstract so it would apply to any product. Here it is again, this time mapped to the exact kcadm.sh commands this chapter ran against a disposable demonstration user (not jane.doe or priya.patel — their accounts need to survive into chapters 23-26) to walk every stage for real in one sitting.

    Chapter 2's lifecycle stages, each one actually executed and confirmed in this chapter's lab
    StageCommand runConfirmed result
    Createkcadm.sh create users ... -s enabled=false User exists, "enabled": false — created but not yet usable, matching chapter 2's "create" being a separate step from "activate."
    Activatekcadm.sh update users/<id> -s enabled=true "enabled": true confirmed by a fresh get call.
    Modifykcadm.sh update users/<id> -s 'attributes.team=["Support"]' "attributes": { "team": [ "Support" ] } confirmed.
    Suspendkcadm.sh update users/<id> -s enabled=false "enabled": false again — the record and its history (the team attribute, the user's id) stay fully intact.
    Deletekcadm.sh delete users/<id> A subsequent get users/<id> returned Resource not found for url: .../users/<id> — gone, not just disabled.

    This is a neutral three-column reference table (stage / command / confirmed result), not a two-sided comparison, so it keeps plain table styling rather than the table-compare treatment used elsewhere in this course for pro/con or problem/solution rows.

    Key idea

    The "suspend" and "delete" rows above look similar in the table but are mechanically completely different in Keycloak: suspend is one field flip (enabled: true → false) on a record that otherwise persists untouched; delete removes the record outright, and every follow-up get call for that id returns a real 404. Chapter 2's Meridian Trust case study said auditors specifically care about this distinction — this is Keycloak's own concrete version of exactly that difference, and it's one -s enabled= flag away from being irreversible if you confuse which command you meant to run.

    Case study — Meridian Trust

    Meridian Trust is the clearest case for why the suspend/delete distinction above is not academic. A PCI-DSS audit asks, by name, whether a terminated employee's access was revoked and whether evidence of that account's prior activity can still be produced. Flipping enabled to false on a Meridian teller's account answers both questions at once: the account stops working immediately, and every attribute and credential record an examiner might ask for is still sitting there to retrieve. Running kcadm.sh delete users/<id> instead would destroy exactly the evidence the audit needs — which is why a bank's offboarding runbook should default to disable, not delete, and reserve deletion for genuine data-retention requirements rather than routine offboarding.

    Common mistakes

    • If you see kcadm.sh create users ... -s 'attributes.department=["Engineering"]' "succeed" with no error but the attribute never shows up afterward, the cause is almost certainly unmanagedAttributePolicy sitting at its default, DISABLED — not a syntax mistake in the command itself (this chapter's exact syntax was correct both times; only the realm setting changed between the failing and succeeding attempts).
    • If you see someone trust kcadm.sh get ... --fields attributes (or any nested-field --fields filter) as proof an attribute is empty, the cause may be the filter itself — this chapter observed --fields attributes print { } for a user whose unfiltered get call, moments later, showed the attribute correctly. When a nested field looks suspiciously empty, re-check with a full, unfiltered get before concluding the data isn't there.
    • If you see a reader assume kcadm.sh set-password always forces a change at next login, the cause is missing that this is controlled entirely by --temporary, and the command's own default is not temporary — confirmed directly in this chapter's lab, not assumed from the flag's name alone.
    • If you see "disable the account" and "delete the account" used interchangeably in an incident writeup, the cause is not understanding that only one of them is reversible with the record's history intact — chapter 2's suspend/delete distinction, now backed by this chapter's own 404-on-delete confirmation.
    • If you see a required action assigned to a user who then logs in without ever being prompted for it, check whether the login actually completed a full authentication round trip through Keycloak's own flow (not a cached session or a direct API call) — required actions gate login completion specifically at that point, per Keycloak's own documentation, not at some other stage.

    Takeaways

    • This chapter's lab ran against a real Keycloak 26.8.2 instance — every kcadm.sh command and the output shown (including one genuine failure and its fix) was actually executed, not narrated.
    • jane.doe and priya.patel now exist as real users in northwind-apps, each independently confirmed via a separate get users call — jane.doe with a department attribute and a password credential, priya.patel with a team attribute and a pending CONFIGURE_TOTP required action.
    • Keycloak's Declarative User Profile drops any attribute not declared in the realm's user profile by default (unmanagedAttributePolicy: DISABLED) — silently, with no error — unless the policy is explicitly changed to ENABLED, ADMIN_VIEW, or ADMIN_EDIT.
    • The Credentials tab stores a password as an Argon2 hash plus its parameters, never the password itself — confirmed directly from this chapter's own GET .../credentials response.
    • Whether kcadm.sh set-password forces a change at next login depends entirely on --temporary; its own default is not temporary, and this chapter verified both branches directly rather than assuming either one.
    • Required actions run after a correct credential check, not instead of one — they gate login completion, per Keycloak's own documentation's wording, which this chapter quotes directly rather than paraphrasing from memory.
    • Keycloak's internal user id (a UUID) and the human-facing username are both identifiers in chapter 2's sense — unique, not secret — but only one of them is what a person actually types in.
    • Chapter 2's suspend and delete stages map onto two mechanically distinct Keycloak operations: flipping enabled (reversible, record intact) versus kcadm.sh delete users/<id> (confirmed in this lab to return a real 404 afterward) — not two words for the same thing.
    • For a PCI-DSS shop like Meridian Trust, that same suspend/delete distinction is the difference between an offboarding action an auditor can verify and one that destroys the evidence the audit needs — disable, don't delete, for routine offboarding.
    • priya.patel was deliberately created with no roles or groups in this chapter — her role assignment, and the real replay of chapter 10's Mover-trap scenario, belongs to chapter 23.

    Self-check

    Click a question to reveal a model answer. Try answering it yourself first — the point is to check your own reasoning against it, not to read the answer first.

    1. Walk through what happened, mechanically, the first time this chapter tried to set jane.doe's department attribute and it silently failed. What specifically changed between that attempt and the one that worked?

      Model answerThe first update command returned no error, but the follow-up get showed no attributes key at all — the server accepted the request and then silently discarded it, because department was never declared in the realm's user profile and the realm's unmanagedAttributePolicy was at its default, DISABLED (confirmed by an empty { } when that field was queried directly). What changed between the failing and succeeding attempts was nothing in the command itself — only the realm-level unmanagedAttributePolicy, explicitly set to ENABLED before the identical update command was re-run and the attribute finally appeared.

    2. Why does Keycloak's documentation recommend against leaving unmanagedAttributePolicy set to ENABLED as a long-term fix, even though it "worked" in this chapter's lab?

      Model answerENABLED accepts any undeclared attribute from any caller, with no validation of its name or shape — there's no schema stopping a typo'd attribute name or an unexpected value from being stored just as easily as department was. Declaring the attribute formally in the user profile gets it real validation and defined visibility/permission rules, and ADMIN_EDIT at least restricts writes to admins; ENABLED was used here only to demonstrate the mechanism quickly, not as something a hardened production realm should leave switched on indefinitely.

    3. Explain, using jane.doe's own credentials response, why "Keycloak stores a password" is an imprecise way to describe what's actually in the Credentials tab.

      Model answerThe GET .../credentials response for jane.doe contains no field holding her actual password, JaneDoe!Lab2026, anywhere. It contains an id, a type of password, a createdDate, and a credentialData blob describing an Argon2 hash and its parameters (iterations, memory, parallelism). What's stored is a one-way hash derived from the password, not the password itself — saying "Keycloak stores a password" conflates the secret with its irreversible digest, which is exactly the property that keeps a leaked database from exposing anyone's real password.

    4. A colleague wants every new hire to be forced to set their own password on first login. Which exact flag, on which exact command, makes that happen — and what did this chapter confirm about what happens if that flag is omitted?

      Model answerkcadm.sh set-password --temporary=true. This chapter ran both branches directly: without --temporary (or with it explicitly false), the user's requiredActions stayed empty after the password was set; running the identical command with --temporary=true instead caused Keycloak to automatically add UPDATE_PASSWORD to requiredActions, confirmed by a follow-up get --fields requiredActions call in each case. Omitting the flag does not force a change at next login — that is the command's default behavior, not a safe assumption to skip verifying.

    5. Without naming Keycloak, explain in your own words why a required action is not the same thing as an authentication factor, even though both can block a login from completing.

      Model answerAn authentication factor is evidence presented to prove who you are — a password, a one-time code — and it's evaluated as part of deciding whether the credential check itself succeeds or fails. A required action only runs after that credential check has already succeeded; it's a separate gate that withholds completion of the login (and any token it would produce) until some additional step, like enrolling a one-time-password generator, is finished. A login can fail outright for lacking a valid factor, or it can pass the factor check completely and still not finish because of a pending required action — two different checkpoints in the same flow, not one.

    6. If an auditor asked you to prove that disabling priya.patel's account preserves her access history while deleting it would not, what two real pieces of evidence from this chapter's lab would you point to?

      Model answerFirst, the lifecycle table's "Suspend" row: flipping enabled to false and then re-running get showed the record, its id, and its team attribute all still fully intact — nothing besides the enabled flag changed. Second, the "Delete" row: running kcadm.sh delete users/<id> and then issuing the exact same get users/<id> call returned a genuine Resource not found 404 — the record was actually gone, not just marked inactive. Those two confirmed, contrasting responses are direct evidence of the mechanical difference an auditor is asking about.
