    21. Realms & Realm Settings

    Chapter 20 created northwind-apps and left it as a bare, empty namespace — enabled, but configured with nothing beyond Keycloak's own defaults. This chapter is where that realm stops being a container with nothing in it and starts carrying real decisions: what it's called, how long a login stays trusted, and which self-service options Northwind's customers get on the login page. No users, roles, or clients get created here — that's chapters 22-24's job. This chapter is entirely about the realm-level settings that every one of those later chapters' users, roles, and clients will inherit.

    Why this matters

    Realm settings are the knobs an IAM specialist tunes most often after initial setup, and they're the ones that quietly produce support tickets or security incidents when nobody deliberately chose them. A session timeout set by accident rather than by policy either annoys every user who gets logged out mid-task or leaves a stolen browser session valid for hours longer than the business can tolerate. Getting these settings right — and being able to explain why a specific number was chosen, not just that a form was filled in — is exactly the kind of judgment that separates someone who can click through an admin console from someone who can own an IAM program.

    What concept is this?

    Chapter 19 defined a Keycloak realm as a fully isolated management namespace; this chapter doesn't redefine that — it's about the settings attached to the namespace chapter 20 already created. Chapter 7 defined an SSO session in the abstract: the state an identity provider keeps for a browser so a later redirect from a connected application doesn't force a fresh login. Chapter 8 introduced the token-lifetime trade-off: shorter lifetimes shrink a stolen token's usefulness but add refresh overhead, longer lifetimes do the opposite. Every setting in this chapter is one of those two generic concepts made concrete as a specific field in a specific screen.

    The Realm Settings screens, tab by tab

    No browser tool was available to click through the Admin Console personally in this session. What follows about the Console's tabs and fields is drawn from Keycloak's own current Server Administration Guide (fetched live for this chapter, version matching the lab's 26.8.2), labeled as such — exactly the same discipline chapter 20 used for its own "Create realm" walkthrough. What was personally verified is every field's real effect on the running realm, via kcadm.sh against the Admin REST API later in this chapter.

    Keycloak's Admin Console reaches these screens via the left-hand "Realm settings" link once northwind-apps is the current realm (top-left realm selector, same mechanism chapter 20 used to switch into it). The settings are split across several tabs:

    General tab

    Per the official guide, the General tab carries the realm's Display Name (a human-readable label shown instead of the internal realm id in places like the login screen header) and an HTML variant of it, plus Frontend URL (the base URL Keycloak uses when it needs to generate a URL back to itself, useful behind a reverse proxy) and Require SSL, which the guide documents as three modes: External requests (SSL required for every request except from private/loopback addresses — the default), None ("Keycloak does not require SSL. This choice applies only in development..."), and All requests (SSL required everywhere, no exceptions).

    Login tab

    The Login tab's fields are self-service toggles for the login page itself. Per the guide: enabling Forgot password adds a "Forgot Password?" link to login pages — but it only works once email (SMTP host and a From address) is configured so Keycloak can actually send the reset message; by default, federated users must log in again after a reset while internal database users on the same browser session stay logged in. Enabling Remember Me adds a checkbox that keeps the session alive after the browser closes; disabling it afterward doesn't immediately kill sessions created with the checkbox already selected — invalidation happens the next time that session's cookie or token is actually used, or in a background cleanup process, not instantly. The tab also carries User registration (self-service sign-up), Verify email (require a confirmed mailbox before the account is usable), and Login with email / Duplicate emails allowed (how strictly usernames and email addresses are treated as interchangeable identifiers).

    Tokens and Sessions

    This is where chapter 7's and chapter 8's generic vocabulary gets its concrete Keycloak home. The guide separates token-shape settings from session-lifetime settings, even though both live under the same general area of Realm Settings:

    Token and session fields, quoted from Keycloak's official Server Administration Guide
    FieldOfficial description
    Access Token Lifespan"When Keycloak creates an OIDC access token, this value controls the lifetime of the token."
    Access Token Lifespan For Implicit FlowA separate timeout for access tokens issued by the Implicit Flow, which issues no refresh token.
    Client login timeout"The maximum time before clients must finish the Authorization Code Flow in OIDC."
    Revoke Refresh Token"When Enabled, Keycloak revokes refresh tokens and issues another token that the client must use."
    SSO Session Idle"If a user is inactive for longer than this timeout, the user session is invalidated."
    SSO Session Max"The maximum time before a user session expires."
    SSO Session Idle Remember Me / SSO Session Max Remember MeSeparate, usually longer, idle/max values that apply only when the user checked "Remember Me" at login.
    Client Session Idle / Client Session MaxIdle timeout for a client's own session, and "the maximum time for a client session and before a refresh token expires and invalidates."
    Offline Session Idle"The amount of time the session remains idle before Keycloak revokes its offline token."
    Offline Session Max LimitedFlag controlling whether an Offline Session Max cap applies at all, or whether an offline session only ever expires via idle timeout.

    Three independent clocks

    Key idea

    SSO Session Idle and SSO Session Max are the realm-level settings chapter 7's generic "SSO session" concept actually turns into. Chapter 7 described an identity provider keeping state for a browser so a later redirect to a different connected application skips re-authentication — it deliberately didn't say how long that state lives, because that's an implementation detail, not part of the concept. Keycloak answers it with exactly two numbers: SSO Session Idle (how long inactivity is tolerated before the whole session dies) and SSO Session Max (an absolute ceiling regardless of activity). Access Token Lifespan is a different, shorter-lived number layered on top — chapter 8's bearer-token trade-off — and the three don't move together: a session can stay alive across many access tokens, each one minted and expiring independently while the underlying SSO session persists.

    Security Defenses & Themes tabs — preview only

    Security Defenses tab

    Per the official guide, this tab's Headers section sets security headers like X-Frame-Options and Content-Security-Policy (used, for example, when embedding a reCAPTCHA-protected registration page in an iframe). The same tab also hosts Keycloak's brute-force detection — the documentation's own "Mitigating security threats" material covers locking an account out permanently or temporarily after repeated failed logins. This chapter does not configure either: brute- force detection and password policy are chapter 30's subject in full, once a realm actually has users worth protecting (chapter 22).

    Themes tab

    The Themes tab selects which theme renders each of four surfaces: the Login theme ("username password entry, OTP entry, new user registration, and other similar screens related to login," per the guide), the Account theme (the console end users manage their own account through), the Admin console theme (the skin of the console administrators use), and the Email theme (templates for every email Keycloak sends). A related Localization tab controls Internationalization — enabling it and choosing supported languages lets end users pick a language on the login page, which then applies across login, Account Console, and Admin Console. This chapter leaves every theme at Keycloak's built-in default; branding northwind-apps with its own look and adding a real locale option is chapter 26's job.

    Pitfall

    This session's own run hit exactly this trap: between two kcadm.sh calls, the lab stack was found recreated from scratch (a fresh container, an empty Postgres volume) with no docker compose down run in between — the realm from the previous step had simply stopped existing. The fix was not to assume the realm was still there; it was to re-run get realms and confirm its actual state before continuing, exactly the discipline this chapter asks of every setting change. If you see a command report "already exists" or "not found" when you expected the opposite, the cause is almost always a stale assumption about what's still running, not a bug in the command itself — a quick kcadm.sh get realms --fields realm,enabled settles it either way.

    Case study: Northwind Apps picks its numbers

    Case study — Northwind Apps

    Northwind Apps sells a B2B SaaS dashboard product. Chapter 8 framed the token-lifetime trade-off in the abstract: a shorter lifetime shrinks how long a stolen token stays useful, but every expiry forces a refresh round-trip, and a session that dies mid- task trains users to treat the product as unreliable. Northwind's own customers spend long stretches — sometimes a full workday — inside the dashboard reviewing reports, so the default 30-minute idle timeout and 10-hour absolute session ceiling would log someone out mid-review the moment they stepped away for a client call. Northwind's security team and product team settled on three deliberate, not-default values, each a real trade-off rather than "longer is friendlier":

    • Access Token Lifespan: 600 seconds (10 minutes), up from Keycloak's 300-second default — still short enough that a stolen access token is useless within minutes, but halves how often Northwind's own single-page clients need to hit the token endpoint for a silent refresh.
    • SSO Session Idle: 3,600 seconds (1 hour), up from 30 minutes — long enough to survive a typical meeting-length interruption without forcing re-authentication, which was the single most common support complaint before this change (reported by the subagent's case-study research as the kind of friction this setting class is known to produce; Northwind's own number here is this course's illustrative choice, not a benchmarked industry figure).
    • SSO Session Max: 28,800 seconds (8 hours), down from the 10-hour default — a deliberate tightening, not a loosening: Northwind's security team capped the absolute ceiling at one working day precisely because the idle timeout just got longer, so a session that's technically still "active" (brief check-ins every 50 minutes, say) can't drift on indefinitely. The two numbers move in opposite directions for the same underlying reason: convenience within a work session, but a hard stop at the end of one.

    Northwind left self-service registration off and turned self-service password reset on — their CIAM model provisions customer accounts through each customer company's own admin (chapter 22), but once an account exists, making a forgotten password a self-service flow rather than a support ticket is a pure convenience win with no corresponding exposure, unlike the session numbers above.

    Try it

    Northwind's numbers fit a B2B SaaS dashboard where long, low-stakes work sessions are the norm. Now reason through Meridian Trust, the retail bank: customers check balances and move money, not review reports for hours, and a stolen session is a direct fraud vector rather than an inconvenience. Would you expect Meridian's SSO Session Idle and Max to move in the same direction as Northwind's, or the opposite? (No specific numbers are asserted for Meridian here — this course's PCI-DSS case study in chapter 48 is where that gets worked out properly — but the shape of the answer should already follow from the trade-off this chapter just walked through: a bank's fraud exposure argues for shorter idle/max timeouts than a SaaS dashboard's, even though both realms expose the exact same two knobs.)

    Common mistakes

    • If you see someone treat Access Token Lifespan and SSO Session Max as the same number, the cause is not realizing they're independent clocks — a session can outlive dozens of access-token refresh cycles, and lengthening one does nothing to the other.
    • If you see a realm's SSO Session Idle set longer than its SSO Session Max, the cause is editing the two fields independently without checking they still make sense together — an idle timeout that can never be reached before the max ceiling fires is dead configuration, not a safety margin.
    • If you see "Remember Me" enabled with no separate Remember-Me idle/max values considered, the cause is missing that Keycloak gives Remember-Me sessions their own idle and max fields — leaving those at their own defaults while tightening the regular ones doesn't tighten Remember-Me sessions at all.
    • If you see Forgot Password enabled but reset emails never arrive, the cause is almost always that realm or server-level SMTP settings were never configured — the guide is explicit that the link only works once Keycloak can actually send mail.
    • If you see a reader assume disabling Remember Me immediately kills already-remembered sessions, the cause is missing that invalidation is lazy — it happens the next time that session's cookie/token is used or during a background sweep, not the instant the setting flips.
    • If you see brute-force protection or a custom theme configured here, in chapter 21, the cause is forgetting this chapter is realm-settings-only by design — those are chapters 30 and 26's jobs, previewed here but not configured.

    Glossary terms introduced here

    Takeaways

    • This chapter configures only realm-level settings on northwind-apps — no new users, roles, groups, or clients; those are chapters 22-24's responsibility.
    • Realm Settings in the Admin Console split across tabs: General (display name, frontend URL, Require SSL), Login (registration, forgot password, remember me, verify email), Tokens/Sessions (access token lifespan, SSO/client/offline session timeouts), Security Defenses (headers, brute-force detection — chapter 30), and Themes (login/account/admin/email themes, localization — chapter 26).
    • SSO Session Idle and SSO Session Max are the concrete Keycloak settings that implement chapter 7's generic "SSO session" concept — idle is a relative inactivity timeout, max is an absolute ceiling, and they run independently.
    • Access Token Lifespan is a separate, shorter-lived clock layered on top of the SSO session, not the same thing as it — a session commonly outlives many access-token refresh cycles.
    • Keycloak also tracks Client Session Idle/Max and Offline Session Idle/Max separately from the main SSO session fields, plus distinct Remember-Me variants of the SSO idle/max pair — each one an independent timeout, not an alias for another.
    • Every setting change in this chapter's lab was confirmed with a separate kcadm.sh get realms/northwind-apps --fields ... call, never trusted from the update command's own response alone.
    • Keycloak's realm defaults (300s access token, 1,800s SSO idle, 36,000s SSO max, registration and self-service reset both off) are reasonable generic starting points, not a policy any specific organization should assume fits them without a deliberate review.
    • Northwind's case study shows token/session lifetimes moving in different directions for the same underlying security posture: a longer idle timeout for convenience, paired with a tighter absolute ceiling so that convenience can't drift into an indefinitely "active" session.
    • Security Defenses (brute-force detection) and Themes (branding/localization) exist as real tabs on this same Realm Settings screen but are deliberately out of scope here — full depth lands in chapters 30 and 26 respectively, once a realm has users and a public-facing identity worth protecting/branding.

    Self-check

    Click a question to reveal a model answer. Try answering it yourself first — the point is to check your own reasoning against it, not to read the answer first.

    1. Explain, without looking it up, why Access Token Lifespan and SSO Session Max are independent clocks rather than the same setting under two names — what's a concrete scenario where this distinction actually matters to a user?

      Model answerAccess Token Lifespan governs a short-lived bearer token that gets reminted via refresh many times over a login; SSO Session Max is the absolute ceiling on the underlying session that outlives all of those refresh cycles. Concretely: a user logs into northwind-apps at 9am with a 10-minute access token and an 8-hour session max. Every 10 minutes a silent refresh mints a new access token without the user noticing — that keeps happening dozens of times — but at 5pm the SSO Session Max fires regardless of how recently a token was refreshed, and the user is forced to log in again even though every individual access token along the way was perfectly valid when used.

    2. Northwind lengthened its SSO Session Idle timeout but shortened its SSO Session Max ceiling in the same change. Why do those two moves make sense together, rather than contradicting each other?

      Model answerThey're solving two different problems with the same underlying goal: don't punish normal work patterns, but don't let "normal" quietly become "indefinite." Lengthening SSO Session Idle to one hour tolerates a meeting-length gap in activity without forcing re-login — pure convenience. But a longer idle tolerance means a session that gets a brief check-in every 50 minutes can, in principle, stay "active" forever. Tightening SSO Session Max to 8 hours puts a hard stop on that drift regardless of activity, so the convenience gain on one axis is deliberately paired with a tighter absolute boundary on the other.

    3. Why does enabling "Remember Me" not automatically mean a user's session now obeys the realm's regular SSO Session Idle/Max values?

      Model answerBecause Keycloak gives Remember-Me sessions their own separate pair of fields — SSO Session Idle Remember Me and SSO Session Max Remember Me — rather than reusing the regular SSO Session Idle/Max values. An administrator who tightens the regular idle/max fields but never touches the Remember-Me variants has left Remember-Me sessions running on whatever those separate fields are still set to, which is easy to miss precisely because the checkbox's name suggests it's just a variation on the same timeout rather than a wholly distinct one.

    4. If a reader found Forgot Password enabled on a realm but reset emails never arriving, what's the first thing you'd ask them to check, and why?

      Model answerWhether the realm (or server-level) SMTP settings — host and a working "From" address — are actually configured. The official guide is explicit that the "Forgot Password?" link only works once Keycloak can actually send mail; enabling the toggle just adds the link to the login page, it doesn't configure an email transport. A missing or misconfigured SMTP host is by far the most common reason the link appears but nothing ever arrives.

    5. Why does this chapter recreate northwind-apps from scratch at the start of its lab instead of assuming chapter 20's realm is still sitting there, ready to configure?

      Model answerBecause this course's lab convention is that each chapter's lab starts from a fresh stack, and a realm created in a previous chapter's container run doesn't persist across a clean docker compose up of a new stack (no volumes carried forward). Recreating it explicitly, rather than assuming it survived, is also exactly the discipline the chapter's own pitfall callout describes: verify a resource's actual state with a get call instead of trusting an assumption about what's still running.

    6. Security Defenses and Themes are both real tabs on the same screen this chapter documents. What's the actual reason this chapter doesn't configure either of them, beyond "a later chapter does it"?

      Model answerBoth settings classes depend on things this chapter's realm doesn't have yet. Brute-force detection only matters once there are real user accounts whose login attempts can be tracked and locked out — chapter 22 is where northwind-apps gets its first users. Themes brand a public-facing login/account experience, which is only worth customizing once there's an actual audience and identity to brand for. Configuring either now would be deciding policy before the thing that policy protects or represents exists.
