    35. Securing a Frontend SPA

    Chapter 34 secured a backend API by validating bearer tokens Keycloak issued. This chapter builds the thing that actually obtains those tokens from a human sitting at a browser: a real React single-page application doing OpenID Connect authorization-code-with-PKCE against Keycloak, using react-oidc-context (which wraps oidc-client-ts) instead of hand-rolling the protocol. Riverside Health's patient portal is the running example — built, run, and driven through a real login for real, not narrated.

    Why this matters

    Almost every modern web product a reader will work on is a single-page app talking to one or more APIs, and the single most common way an IAM specialist gets pulled into a frontend team's incident is a token-handling mistake: a secret baked into a public client, a token sitting in localStorage that an XSS bug just exfiltrated, or a silent-renew loop that never fires because an iframe got blocked. This chapter exists so you can tell a frontend engineer, concretely, why their app has no client secret, where their access token should and shouldn't live, and what actually happens — packet by packet — when their login button is clicked. It also hits a real environment constraint head-on: this machine's Node version is older than the current major release of the most popular frontend build tool, and the honest way to handle that live, rather than pretending it isn't a problem, is itself a skill worth having.

    What concept is this?

    Chapter 13 built the authorization-code-with-PKCE flow by hand: a client-generated code_verifier, its SHA-256 derived code_challenge, a redirect to /authorize, a login, a short-lived code redirected back to the client, and a server-to-server exchange at /token that only succeeds if the original verifier is presented. Chapter 15 added OpenID Connect's layer on top: an ID token — a JWT proving who authenticated and when, with an aud claim naming the client itself — returned alongside the access token when the request includes the openid scope. This chapter does not re-teach either of those; it shows you the one client type that flow was designed for from the start. A browser-based SPA is the textbook public client: its entire source — including anything that looks like a "secret" — ships to and is readable by anyone who opens their browser's developer tools. PKCE exists specifically because this class of client cannot hold a confidential secret, and react-oidc-context/oidc-client-ts is simply a library that performs chapter 13's exact handshake for you, correctly, instead of you reimplementing SHA-256-and-base64url by hand inside a React component.

    Why a browser SPA is a public client, not a confidential one

    Chapter 24 will formalize Keycloak's publicClient client setting; this is the concrete reason it exists. A confidential client's secret only provides security if it stays secret — if it's known only to code running somewhere an attacker cannot read. A backend service qualifies: its process memory and source are not handed to the browser. A single-page app does not qualify, no matter how it's built: everything shipped to the browser — JavaScript, environment variables baked in at build time, anything — is visible to whoever opens the Network or Sources tab in their browser's devtools. A "client secret" embedded in a React bundle is not a secret; it's a public constant with a misleading name.

    PKCE (chapter 13) doesn't try to give the SPA a secret it can't actually keep. Instead it adds a value — the code_verifier — that is generated fresh in memory for this one login attempt and never has to be embedded in shipped code at all, because it's created at runtime and discarded right after the token exchange. That's the whole reason PKCE, not a client secret, is the right tool for this exact job.

    Token storage: where should the access token actually live?

    Once Keycloak hands the SPA an access token and ID token in step 5 of Figure 35.1, the app has to keep them somewhere for the rest of the session. This decision has no risk-free option — it's a genuine trade-off between two different attack surfaces, and the right answer depends on what else the app is exposed to.

    Where a browser-based OIDC client can keep its tokens
    Storage locationSurvives a page reload?Exposed to an XSS bug?Notes
    In memory (a JS variable / React context, never persisted) No — a full reload loses it, requiring a fresh silent or interactive sign-in Only while a malicious script is actively running in the same page What oidc-client-ts uses by default when no storage option is configured — and what this chapter's lab leaves in place
    sessionStorage Yes, within the same tab, until the tab closes Yes — any script on the page can read it directly Scoped to one tab, which limits (but doesn't eliminate) the blast radius of a stolen token
    localStorage Yes, indefinitely, across tabs and browser restarts Yes — any script on the page can read it directly The longest-lived, most XSS-exposed option; chapter 18's Token storage glossary entry covers this generally
    Backend-for-frontend (BFF) — token never reaches the browser at all Yes — the server holds the session, not the browser No — there is nothing in the page's JavaScript context for an XSS bug to read Strongest option, but requires a server component the SPA talks to instead of calling Keycloak and the API directly — see the comparison below

    This is a reference table across four storage options, not a single pro/con decision, so it stays a plain table rather than a two-column table-compare.

    Key idea

    An access token is a bearer token (chapter 8): whoever holds it can use it, no questions asked, until it expires. Every storage choice above is really asking "if this app has an XSS bug, how much does the attacker walk away with?" — not "can this app be made XSS-proof," which no storage choice achieves on its own. Keeping tokens in memory and keeping access-token lifetimes short (this lab's token lasted 300 seconds) both shrink that answer; neither eliminates the question.

    Architecture choice: SPA-direct vs. backend-for-frontend

    This chapter's lab builds the simpler, more common pattern — the React app talks to Keycloak and the API directly, which is exactly what chapters 13-15 and this chapter's library assume. The backend-for-frontend (BFF) pattern is the alternative worth knowing exists, because it changes where the hardest problem above (token storage) even applies.

    SPA-direct-to-Keycloak vs. the backend-for-frontend (BFF) pattern
    SPA-direct-to-Keycloak (this chapter's lab)Backend-for-frontend (BFF)
    No extra server component to build, deploy, or operate — the SPA and Keycloak are the whole systemRequires a server-side component the SPA calls instead of Keycloak directly, adding real operational surface
    Faster to stand up for a small team or an early-stage product (Northwind's early SaaS dashboard, for instance)More moving parts before the first login even works
    Access/refresh tokens still exist somewhere in the browser's JS context, however carefully storedTokens never reach the browser at all — the server holds the session, typically via an httpOnly cookie

    Riverside Health's real patient portal, handling HIPAA-covered data, is exactly the kind of application where the security team should eventually ask "should this be a BFF instead" — this chapter builds the simpler SPA-direct version deliberately, both because it's what react-oidc-context is built for and because it's the shape you need to understand before you can explain why a BFF is sometimes worth the extra server.

    Keeping the session alive: silent renewal, and what can break it

    An access token with a short lifetime (this lab's lasted 300 seconds) is good for limiting blast radius, but useless if the user gets logged out every five minutes. oidc-client-ts supports silent renewal: using the refresh token returned alongside the access token (when the offline_access scope or Keycloak's default refresh-token behavior applies) to obtain a new access token in the background, without the user noticing.

    • Refresh-token-based renewal — the approach this lab's tokens support: Keycloak issued a refresh_token alongside the access and ID tokens (see the lab's token response below), and oidc-client-ts can use it directly without any iframe at all.
    • Iframe-based silent renewal (prompt=none) — an older technique some OIDC libraries use: a hidden iframe re-runs the authorization request against the IdP, hoping an existing session cookie lets it complete without showing a login page. This is the technique most exposed to breakage: browsers that block third-party cookies or restrict cross-site iframes (Safari's ITP, for one) can silently fail it, leaving a session that expires with no warning.
    Pitfall

    If you see a SPA's login state randomly expire in Safari but not Chrome, the cause is very often exactly this: iframe-based silent renewal depends on third-party cookie behavior that Safari's Intelligent Tracking Prevention restricts more aggressively than Chromium browsers do. Preferring refresh-token-based renewal over iframe-based silent renewal — the choice this lab's configuration makes implicitly by not enabling prompt=none renewal — sidesteps the whole category of bug.

    Logout has the mirror-image problem: Keycloak needs to end its own session (the authorization server's cookie), not just the SPA's in-memory state, or a later silent renewal could quietly log the user back in. react-oidc-context's removeUser() clears local state; a complete logout also needs Keycloak's end-session endpoint and a registered post_logout_redirect_uri, which is why that value sits right next to redirect_uri in this lab's configuration.

    Case study — Riverside Health's patient portal

    Case study — Riverside Health

    Riverside Health's patient portal is exactly this chapter's running example: patients log in to view appointments, lab results, and messages from their care team — data covered by HIPAA. Riverside's security team settled on the SPA-direct pattern this chapter builds, with three deliberate constraints that map directly onto the sections above:

    • In-memory token storage only — the portal's security review flagged localStorage specifically because a single successful XSS injection (a compromised third-party analytics script was the scenario the review actually tested for) would otherwise hand an attacker a token usable until the patient's refresh token also expired, not just until the page reloaded.
    • A short access-token lifetime matching this lab's realm default, so a worst-case token leak stays useful to an attacker for minutes, not hours.
    • Exact, wildcard-scoped redirect URIs (https://portal.riverside-health.example/* in production; http://localhost:5173/* in this lab) rather than a bare wildcard — chapter 13's live finding about loose redirect-URI matching is precisely the failure mode this guards against for a system holding real patient data.

    Riverside's longer-term roadmap includes evaluating a backend-for-frontend rewrite once the portal adds a mobile app that needs to share the same session — the comparison table above is the exact trade-off their architecture review will have to make explicit.

    Hands-on lab, continued: wiring up AuthProvider

    Three files do the real work. src/oidcConfig.js holds the OIDC settings as a plain object — deliberately with no client_secret field, because this is a public client:

    // labs/react-spa/src/oidcConfig.js
export const oidcConfig = {
  authority: "http://localhost:8080/realms/riverside-health",
  client_id: "patient-portal",
  redirect_uri: "http://localhost:5173/",
  post_logout_redirect_uri: "http://localhost:5173/",
  scope: "openid profile email",
  // oidc-client-ts defaults to an in-memory token store when no userStore
  // is supplied -- exactly the choice this chapter's "token storage" slide
  // argues for, so nothing further needs configuring here.
  onSigninCallback: () => {
    window.history.replaceState({}, document.title, window.location.pathname);
  },
};

    src/main.jsx wraps the whole app in <AuthProvider>:

    // labs/react-spa/src/main.jsx
import { AuthProvider } from "react-oidc-context";
import { oidcConfig } from "./oidcConfig.js";

createRoot(document.getElementById("root")).render(
  <StrictMode>
    <AuthProvider {...oidcConfig}>
      <App />
    </AuthProvider>
  </StrictMode>,
);

    src/App.jsx reads everything it needs from the useAuth() hook — isLoading, isAuthenticated, user.profile (the decoded ID token claims), and signinRedirect()/removeUser() to drive the flow Figure 35.1 diagrams:

    const auth = useAuth();
// ...
if (auth.isAuthenticated) {
  const { profile } = auth.user;
  return <p>Signed in as {profile.preferred_username}</p>;
}
return <button onClick={() => auth.signinRedirect()}>Sign in with Keycloak</button>;
    In Keycloak

    Nothing in this file touches a client secret, a password, or a hand-built redirect URL — signinRedirect() builds and navigates to /authorize itself, with the PKCE pair generated and tracked internally by oidc-client-ts. That's the entire point of using a maintained OIDC library instead of reimplementing chapter 13's handshake by hand in application code.

    Common mistakes

    • If you see a client secret anywhere in a React/Vue/Angular bundle — even "obfuscated" or loaded from an environment variable at build time — the cause is treating a public client as if it were confidential; anything shipped to the browser is readable by definition, and the fix is switching that client to public with PKCE required, not hiding the secret harder.
    • If you see tokens stored in localStorage "because it's easier than managing React state," the cause is optimizing for developer convenience over this chapter's actual trade-off — it maximizes exactly what an XSS bug can walk away with, and for data like Riverside's patient records the in-memory default this lab uses is the safer starting point.
    • If a SPA's login silently stops working in Safari after a while but keeps working in Chrome, the cause is very often iframe-based silent renewal (prompt=none) running into Safari's third-party-cookie restrictions — refresh-token-based renewal, which this lab's configuration uses by not enabling that technique, doesn't hit the same wall.
    • If you register a client's redirect URI as a bare wildcard (*) "to stop fighting with the dev server's port," the cause is the same shortcut chapter 13 warned against — Keycloak explicitly documents the bare wildcard as a production anti-pattern; a path-scoped pattern like this lab's http://localhost:5173/* gets the same convenience without the exposure.
    • If npm install or npm run dev fails with an "unsupported engine" warning or a cryptic native-module build error, the cause is very often exactly what this chapter's lab checked for up front: a build tool's minimum Node version silently outpacing the Node actually installed. Checking npm view <pkg> engines before installing, not after something breaks, is the fix.
    • If you see auth.isAuthenticated flip to true but auth.user stay briefly undefined right after the redirect back, the cause is usually reading the hook's state before onSigninCallback has finished cleaning up the ?code=... query string — guard rendering on auth.isLoading first, as this lab's App.jsx does.

    Takeaways

    • A browser-based SPA is the textbook OAuth public client: everything shipped to it, including anything labeled a "secret," is readable by anyone with devtools open — which is exactly why PKCE, not a client secret, protects its authorization code exchange.
    • react-oidc-context (wrapping oidc-client-ts) performs chapter 13's authorization-code-with-PKCE handshake for you — signinRedirect(), useAuth(), and removeUser() are a thin API over the exact sequence Figure 35.1 diagrams, not a different protocol.
    • Token storage is a genuine trade-off with no risk-free option: in-memory, sessionStorage, localStorage, and backend-for-frontend each shift which attack surface (XSS readability vs. session longevity vs. operational complexity) absorbs the risk.
    • The backend-for-frontend (BFF) pattern removes tokens from the browser's JavaScript context entirely, at the cost of a server component the SPA-direct pattern this chapter builds doesn't need.
    • Iframe-based silent renewal (prompt=none) is more fragile than refresh-token-based renewal specifically because it depends on third-party cookie behavior that varies by browser.
    • The current Vite major (7.x/8.x) requires Node 20.19+/22.12+; Vite 6.x, live-verified here, is the newest major that still supports this machine's Node 18.20.4 — checked, not assumed.
    • A real local Keycloak returns distinct, diagnostic error_description values for a reused code, a wrong PKCE verifier, and a missing verifier — a genuine, useful contrast with chapter 13's demo server, which returned the same generic error for all three.
    • The same local Keycloak instance refuses outright (HTTP 400, no redirect) when given an unregistered redirect_uri — the spec-compliant behavior chapter 13's demo server was found not to enforce, now seen working correctly on a second, real server.
    • This chapter's one honest limitation is identical in shape to chapter 13's: no tool here can physically click a login button, so the exact protocol exchange a click would trigger was driven instead with curl and a cookie jar against a real Keycloak — the mechanics are completely real, the mouse click is the only thing simulated by hand.

    Self-check

    Click a question to reveal a model answer. Try answering it yourself first — the point is to check your own reasoning against it, not to read the answer first.

    1. A new engineer suggests "let's just put the client secret in an environment variable so it's not hardcoded" for a React SPA. Explain precisely why this doesn't solve the actual problem.

      Model answerAn environment variable used in a frontend build is baked into the compiled JavaScript bundle at build time — it ends up as a plain string in the shipped code, exactly like a hardcoded value, just one extra step removed. Anyone who opens the browser's devtools and reads the bundle (or the built dist/ output directly, as this chapter's lab did with grep) can read it. The problem isn't where the secret is written in source control; it's that a browser SPA has no execution context an attacker can't eventually read, so nothing it holds can function as a real secret. PKCE is the actual fix because it doesn't depend on any value staying hidden in shipped code.

    2. Using this chapter's token-storage table, argue for and against using sessionStorage instead of in-memory storage for Riverside Health's patient portal specifically.

      Model answerFor: sessionStorage survives a page reload within the same tab, so a patient who accidentally refreshes mid-session doesn't get bounced back to a login screen — a real usability win for a possibly less technical patient population. Against: it's directly readable by any script running on the page, so a single XSS bug (the compromised-analytics-script scenario the case study names) can read the token just as easily as from localStorage, for data covered by HIPAA. Riverside's security review chose in-memory specifically because, for this app, the usability cost of occasionally re-authenticating after a reload was judged smaller than the exposure cost of a persistent, script-readable token holding patient data.

    3. Walk through what a backend-for-frontend (BFF) rewrite of the patient portal would change about the "token storage" problem this chapter spends a whole slide on. Does the problem disappear, or move?

      Model answerIt moves, not disappears. In a BFF, the access and refresh tokens live on the server, typically tied to a session identified by an httpOnly cookie the browser can't read via JavaScript — so the specific "which browser storage API" question this chapter raises no longer applies to the SPA at all. But the server now has to protect that session store and cookie correctly (CSRF defenses, secure cookie flags, session fixation) — a different, server-side version of "protect the thing that proves who's logged in," not the absence of the problem.

    4. This chapter's lab found that a real Keycloak instance returns a distinct error_description for a wrong PKCE verifier versus a missing one, while chapter 13's demo server returned the same generic error for every failure cause. Does this make Keycloak's behavior a security weakness relative to that demo server? Justify your answer using chapter 13's own reasoning about generic errors.

      Model answerNot necessarily a weakness — chapter 13's reasoning was that a specific error can function as an oracle helping an attacker iteratively correct a forged request, which is a real concern. But whether that matters depends on what's actually being distinguished: Keycloak's three messages here ("code not valid" / "verifier mismatch" / "verifier not specified") all still require the attacker to already have intercepted a real, in-flight authorization code to get this far — none of them help forge one from scratch. A legitimate developer debugging a broken integration benefits meaningfully from the distinction; whether that convenience is worth the marginal information leak to an attacker who already has a stolen code is a judgment call a real security review would need to make explicitly, not something answerable in the abstract.

    5. Explain the specific mechanism by which iframe-based silent renewal can fail silently in a browser like Safari, and why refresh-token-based renewal doesn't have the same failure mode.

      Model answerIframe-based silent renewal works by loading a hidden iframe that re-runs the authorization request against the identity provider, hoping the browser sends along an existing session cookie so the IdP can approve it without showing a login page (prompt=none). Browsers with aggressive third-party cookie restrictions — Safari's Intelligent Tracking Prevention is the named example — can block that cookie from being sent inside the iframe's cross-site context, causing the silent attempt to fail (often without a clear error reaching the app) instead of silently succeeding. Refresh-token-based renewal doesn't route through a third-party browser context at all — the SPA's own JavaScript POSTs the refresh token directly to the token endpoint, a same-origin-initiated request not subject to third-party cookie policies, so it isn't exposed to this particular failure mode.

    6. Meridian Trust is evaluating whether its mobile banking web app (a SPA, used from inside a webview) should switch from localStorage to in-memory token storage. What's the real cost of that switch from the user's point of view, and is it worth it for a banking app specifically?

      Model answerThe real cost: in-memory storage doesn't survive a page reload or the webview being backgrounded and reloaded by the OS, so the user has to re-authenticate more often than with localStorage, which persists indefinitely. For a banking app specifically, that's very likely worth it — the asset at risk (account access, transaction capability) is high-value enough that minimizing the window a stolen token stays useful (an in-memory token is gone the moment the page unloads, with no persistent copy for an XSS bug or a compromised device to find later) outweighs the friction of more frequent logins. This is exactly the same trade-off Riverside Health's case study made for patient data, applied to a different but similarly high-stakes asset.
