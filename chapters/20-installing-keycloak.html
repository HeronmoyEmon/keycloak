20. Installing & Running Keycloak

Every chapter before this one has been either vendor-agnostic theory or a lab against someone else's OAuth/OIDC server. This is the chapter where that changes: Keycloak gets installed, for real, on this machine, and every command below was actually run against it — not narrated. By the end you will have brought up a real Keycloak 26.8.2 instance, logged into it, and created the one realm every chapter from here through chapter 26 builds on: northwind-apps.

Why this matters

An IAM specialist's first real task on a new job is rarely glamorous: stand up the identity server, get a clean admin login, and create the first real tenant boundary — correctly, the first time, because everything else gets built on top of it. Getting this wrong (running a dev-mode convenience config in production, or putting application clients into the wrong realm) is the single most common way a Keycloak deployment starts its life already insecure. This chapter is also the first place the course's "no invented facts" rule gets tested against a tool you can run yourself: every command and every line of output below is real, and every claim about the Admin Console's screens that this session's agent could not personally click through is labeled as coming from Keycloak's own current documentation instead.

Recall before you install it

Chapter 19 established that Keycloak 26.8.2 ships as a Quarkus-based distribution and that this course runs it against PostgreSQL rather than its bundled dev database — this chapter is where that stops being an architecture diagram and becomes a running container. Chapter 0 already had you confirm Docker works on this machine as part of environment setup; this chapter is the first time that Docker installation does real IAM work instead of sitting idle. And chapter 2's identity lifecycle, chapter 7's federation/trust vocabulary, and chapter 8's token/session concepts are all about to get a concrete home: a specific realm, inside a specific Keycloak instance, that chapters 21-26 will keep building on.

The lab environment: bringing the stack up for real

This chapter's lab lives in labs/docker/docker-compose.yml — a two-service stack (Keycloak 26.8.2 + PostgreSQL 17) that every Part IV chapter reuses. It was built and independently confirmed working in an earlier session; this chapter re-ran it from a clean state rather than trusting that confirmation secondhand.

  1. Start the stack from labs/docker/:

  2. Poll the realm discovery endpoint until Keycloak answers. In this run it took about 30 seconds from container start to a 200 — don't assume it's instant:

    for i in $(seq 1 20); do
  code=$(curl -s -o /dev/null -w "%{http_code}" \
    http://localhost:8080/realms/master/.well-known/openid-configuration)
  echo "attempt $i: $code"
  if [ "$code" = "200" ]; then break; fi
  sleep 3
done
    attempt 1: 000
attempt 2: 000
...
attempt 9: 000
attempt 10: 200

    Nine attempts of 000 (connection refused — nothing listening yet) before the tenth attempt gets a real 200. The README's "wait 15-20 seconds" guidance is a reasonable estimate, not a guarantee; polling the discovery endpoint until it actually answers is the correct way to know the server is ready, not a fixed sleep.

  3. Read the real boot log for the two lines this chapter cares about most:

    docker compose logs keycloak | grep -i "temporary admin\|development mode\|started"
    keycloak-1  | Running the server in development mode. DO NOT use this configuration in production.
keycloak-1  | 2026-11-10 08:06:16,520 INFO  [org.keycloak.services] (main) KC-SERVICES0077: Created temporary admin user with username admin
keycloak-1  | 2026-11-10 08:06:16,728 INFO  [io.quarkus] (main) Keycloak 26.8.2 on JVM (powered by Quarkus 3.40.1.1) started in 19.441s. Listening on: http://0.0.0.0:8080.

    Three facts in that log, all load-bearing for the rest of this chapter: the server is explicitly warning you it's in development mode, it created an admin user it itself calls "temporary," and Quarkus's own startup took about 19.4 seconds internally (the extra time before the first 200 is the container runtime plus the TCP listener coming up around that).

The bootstrap admin: what "temporary" actually means

The compose file sets KC_BOOTSTRAP_ADMIN_USERNAME=admin and KC_BOOTSTRAP_ADMIN_PASSWORD=admin_lab_password. Keycloak's own Bootstrapping and recovering an admin account guide (fetched live for this chapter) is specific about what that creates: these options exist "solely for bootstrapping temporary admin accounts," the account is created "only during the initial start" and "only during the initial start... when the master realm doesn't exist yet," and — the key sentence — a bootstrap admin "is temporary" and "should exist only for the duration necessary to perform operations... after that, the account needs to be removed manually."

Key idea

"Temporary" here does not mean "limited" or "read-only." It means meant to be replaced before any real use — but fully functional in the meantime. That's exactly why kcadm.sh could log in with it a moment ago in the lab steps above and create a real realm: nothing about the account's privileges is restricted while it exists. The label is a lifecycle/governance signal (this credential should not outlive the setup task it was created for), not a technical limitation — chapter 10's provisioning/deprovisioning vocabulary applies to this account exactly as it does to any other identity: it should be deprovisioned once a real named administrator exists.

If the server restarts with the master realm already present, those bootstrap options are silently ignored — the docs are explicit that this only ever fires once, on the realm's very first creation. Keycloak also ships a separate bin/kc.sh bootstrap-admin user command for the case where admin access is lost entirely (every node must be stopped first); this chapter doesn't need it, since the compose file's environment variables did the job on first start, but it's worth knowing it exists for a genuine lockout later in the course.

start-dev vs. production mode

The compose file's command: start-dev is the second log line's real cause. Keycloak's own server configuration guide lists exactly what that command relaxes relative to plain start (production mode) — not a vague "it's less secure," but specific, named relaxations:

What start-dev relaxes, per Keycloak's own configuration guide — not assumed, read from the live doc for this chapter
Areastart-devProduction (start)
Hostname checkingStrict hostname resolution is disabledExplicit hostname configuration is expected
TransportPlain HTTP is enabledHTTP is disabled; HTTPS/TLS is required
TLS setupNot required to startKeycloak expects TLS configuration to be available
CachingLocal cache only; no distributed cache for HAClustered/distributed caching supported
Theme & template cachingDisabled (so edits show up without a restart)Enabled (performance over live-editing convenience)
Startup gateStarts with no further configuration at allRefuses to start without explicit configuration — "secure by default"
Pitfall

None of the left column is safe outside a local lab, and the failure mode is specifically that it doesn't look unsafe — the server starts, the Admin Console loads, logins work. Plain HTTP means credentials and tokens cross the network unencrypted; disabled strict hostname checking means Keycloak will build links (password-reset emails, redirect validation) from whatever Host header a request happens to send, which an attacker can manipulate. Production mode's refusal to start without configuration is deliberate friction, not a bug — Keycloak's own docs call this "secure by default" precisely because start-dev exists to remove that friction for exactly one use case: a disposable local lab like this one. Chapter 45 (security hardening) is where the full production checklist — hostname, TLS, reverse proxy placement, database, clustering — gets built out in depth; this chapter is only the first place the distinction matters at all.

Creating the northwind-apps realm, for real

This is the chapter's actual deliverable. The command below is the scriptable equivalent of the four UI clicks above, run against the Admin REST API via kcadm.sh — and it is the one this session actually executed, not narrated.

  1. Authenticate kcadm.sh as the bootstrap admin:

    docker compose exec keycloak /opt/keycloak/bin/kcadm.sh config credentials \
  --server http://localhost:8080 --realm master --user admin --password admin_lab_password
    Logging into http://localhost:8080 as user admin of realm master

    Note the --realm master — you always authenticate to the master realm to get an admin session, even though the realm you're about to act on is a different one entirely.

  2. Create the realm:

    docker compose exec keycloak /opt/keycloak/bin/kcadm.sh create realms \
  -s realm=northwind-apps -s enabled=true
    Created new realm with id 'northwind-apps'

  3. Confirm it exists, independently of the creation command's own success message:

    docker compose exec keycloak /opt/keycloak/bin/kcadm.sh get realms --fields realm,enabled
    [ {
  "realm" : "northwind-apps",
  "enabled" : true
}, {
  "realm" : "master",
  "enabled" : true
} ]

    Two realms now exist on this instance: master (created automatically when Keycloak first started) and northwind-apps (created just now). Chapter 27 goes deep on kcadm.sh and the Admin REST API it wraps — here it's used only as a way to prove each step actually worked, exactly the role it plays in every chapter through 26.

Never use master for applications

Keycloak's own getting-started material states the master realm's purpose plainly: use it "only to create and manage the realms in your system" — administrators manage an organization's own users and applications in other realms. This course's seed reference material opens with the same rule in almost the same words: "Never use the master realm for your applications." It's worth restating exactly why, not just repeating the rule: master is where Keycloak's own administrative accounts and realm-management permissions live. Mixing a company's actual customers, employees, and application clients into that realm means a bug or a breach in an ordinary business application now sits one hop away from the account that can create, delete, or reconfigure every other realm on the instance — including master itself. Keeping them apart is the entire reason this chapter created a second realm instead of just using the one Keycloak gave you for free.

Case study — Northwind Apps

Northwind Apps is the B2B SaaS company chapter 2 introduced — internal staff like Jane Doe and Priya plus thousands of customer-company users who need their own CIAM-style access to the product. Every one of those identities needs somewhere to live that is not master. northwind-apps, created in this chapter, is that somewhere: an empty tenancy boundary today, but the concrete starting point for Northwind's entire IAM program in this course. Common mistakes

  • If you see a reader run docker compose up and immediately try to log in, the cause is skipping the readiness check — Keycloak's own startup (about 19 seconds of Quarkus boot in this run, plus container-runtime overhead) means the first several seconds of requests will fail with a connection error, not a meaningful HTTP error code.
  • If you see someone treat the "Created temporary admin user" log line as a warning to ignore, the cause is misreading "temporary" as "degraded" — it's a fully functional admin account; "temporary" describes how long it should be kept, not how well it works.
  • If you see start-dev running against a database or network reachable from outside a single developer's machine, the cause is treating a convenience flag as a deployment mode — it is explicitly documented as unsafe for anything beyond a local lab.
  • If you see application users or OAuth clients registered inside the master realm, the cause is not realizing a new Keycloak instance ships with exactly one realm and assuming that's "the" realm to use — it's reserved for managing Keycloak itself.
  • If you see a reader authenticate kcadm.sh with --realm northwind-apps instead of --realm master, the cause is confusing which realm you authenticate to (always master, for an admin session) with which realm you're acting on (the -s realm=... argument, or whichever realm a later command targets).

Takeaways

  • This chapter's lab ran against a real Keycloak 26.8.2 + PostgreSQL 17 stack via labs/docker/docker-compose.yml — every command and output shown was actually executed, not narrated.
  • Keycloak's own boot log explicitly says "Running the server in development mode. DO NOT use this configuration in production" — the warning is printed on every single start-dev boot, not a one-time notice.
  • The bootstrap admin created by KC_BOOTSTRAP_ADMIN_USERNAME/_PASSWORD is labeled "temporary" because it's meant to be removed once a real administrator exists, not because it has reduced privileges — it is fully functional, which is exactly why kcadm.sh could use it to create a real realm.
  • That bootstrap creation only ever fires once, when the master realm doesn't exist yet — restarting a Keycloak instance that already has master silently ignores those environment variables.
  • start-dev relaxes specific, named things — strict hostname checking, TLS/HTTPS enforcement, distributed caching, and the startup gate that otherwise refuses to run without explicit configuration — each one a real production requirement, not generic "insecure defaults" hand-waving.
  • The northwind-apps realm was created with kcadm.sh create realms -s realm=northwind-apps -s enabled=true and independently confirmed with a separate get realms call — two different commands agreeing, not one command's own success message taken on faith.
  • The Admin Console's "Create realm" button, the realm-name field, and the realm selector auto-switching to the new realm are described from Keycloak's current official Server Administration Guide, clearly separated in this chapter from what was personally verified via kcadm.sh — because no browser tool was available to click through the Console directly.
  • master exists only to manage Keycloak itself (create/manage other realms); every application's users, roles, and clients belong in a realm created for that purpose — mixing them in puts ordinary application risk one hop away from instance-wide administrative control.
  • The Docker image's lack of a curl/wget binary inside the Keycloak container is itself a real, independently confirmed fact from this chapter's lab run — the official health-check docs independently note the same limitation for exactly this reason.
