    Part VIII — Extending Keycloak ~70 min Hands-on lab

    39. Writing Custom SPIs: Authenticators, Event Listeners, Protocol Mappers

    Chapter 33 wrote one Keycloak Service Provider Interface implementation — a User Storage SPI provider — end to end. This chapter writes three more, chosen because they're the three a working Keycloak developer reaches for most often, not because they're mechanically related to each other: a custom Authenticator (Meridian Trust's business-hours login gate), a custom Event Listener (Riverside Health's failed-login audit log), and a custom Protocol Mapper (Northwind Apps' tenant ID claim). Every command, every piece of Java, and every real failure below actually ran against a real Keycloak 26.8.2 instance while writing this chapter — including an uncaught server exception this chapter's own lab triggered and fixed, kept in rather than edited out.

    Why this matters

    Chapter 1 named "extensibility" — a plugin architecture so an organization can add custom logic without forking the product — as part of what makes a mature IAM system mature, and pointed forward to this Part for the details. An IAM specialist who only knows "configure the built-in options" hits a wall the moment a client's real requirement isn't one of them: a bank that needs a fraud-aware login condition no built-in authenticator covers, a hospital that needs a specific, grep-able audit format no built-in event listener produces, a SaaS company that needs a claim computed from business logic no built-in mapper type expresses. All three of today's providers answer "write a small, focused class against a documented Java interface" — the same answer, three different interfaces.

    Sources for this chapter: Keycloak's own Server Developer Guide (version 26.8.2, fetched live for this chapter — its Authentication SPI and Event Listener SPI sections, specifically; see the next slide for what the guide does not cover); Maven Central, queried live to pin exact dependency coordinates; the real jars inside the running quay.io/keycloak/keycloak:26.8.2 image, inspected directly; and this chapter's own lab, run against a real, disposable Keycloak 26.8.2 + PostgreSQL 17 Docker Compose stack this chapter owns (labs/custom-spis/).

    What concept is this?

    Chapter 1 named extensibility as part of what a mature IAM system provides, and chapter 33 made the mechanism concrete for one SPI (User Storage). This chapter is the same mechanism, applied three more times. One distinction worth drawing explicitly here, because chapter 40 depends on it: an Authenticator (today's first SPI) runs during the credential check itself and can prevent a login from succeeding at all — it is a different insertion point from a Required Action (chapter 40's subject, and already introduced conceptually in chapter 22/25), which only ever runs after authentication has already succeeded, to force an extra step before the session is considered complete. Beginners conflate the two constantly, because both can show the user a form mid-login — the real difference is whether the flow can still fail at that point (Authenticator: yes; Required Action: no, the user is already authenticated).

    One pattern, instantiated four times now

    Chapter 33 described the Factory/Provider/ServiceLoader shape for the User Storage SPI. All three of today's SPIs follow the identical shape — with one real exception, confirmed directly from the actual interfaces rather than assumed (see the Northwind Apps slide below). A Factory class is discovered exactly once, at server boot, via a META-INF/services text file naming its fully qualified class name — the standard Java ServiceLoader convention, read from Keycloak's own /opt/keycloak/providers directory at build/start time. The factory then produces Provider instances on demand.

    A real documentation gap, confirmed live

    Keycloak's own Server Developer Guide has a dedicated walkthrough for implementing an Authenticator ("Implementing an Authenticator" / "Implementing an AuthenticatorFactory") and for Event Listener SPI usage — but, checked directly against the live guide while writing this chapter, it has no equivalent walkthrough for writing a Java ProtocolMapper class; its "Protocol Mapper" coverage is specifically about script-based (JavaScript) mappers, a different mechanism entirely. This chapter's Northwind Apps mapper was built by inspecting the real interfaces on the real jar and the pattern of Keycloak's own built-in mappers (chapter 24's territory) instead — said plainly here rather than implying a guide section exists that doesn't.

    Why one Maven project, not three

    Chapter 33's precedent was one Maven project per lab, because that lab had exactly one provider. This chapter deliberately builds one Maven project producing one JAR containing all three providers, each in its own Java package named for the case-study org it belongs to (com.meridiantrust.keycloak.businesshours, com.riversidehealth.keycloak.loginaudit, com.northwindapps.keycloak.tenantmapper) — not three separate Maven modules.

    The reasoning: all three SPIs are small, have zero dependencies on each other, and share the identical build/deploy mechanics chapter 33 already established (mvn package, bind mount into /opt/keycloak/providers, kc.sh build, restart). Three separate Maven modules would mean three separate JARs, three separate bind mounts in the compose file, and three separate "did I rebuild before restarting" failure points — for no real isolation benefit, since nothing here needs independent versioning or independent deployment. The package-per-org split still documents the separation that actually matters: which org's problem each class solves.

    Meridian Trust: a business-hours login gate

    Case study — Meridian Trust

    Meridian Trust is a retail bank with a fraud-aware authentication posture (chapter 9): online banking logins outside its call center's staffed hours are disproportionately likely to be automated credential-stuffing attempts rather than real customers, so the bank wants a hard gate — not a risk score, not a flag for later review, an outright denial — on logins outside a configured window. No built-in Keycloak authenticator expresses "deny unless the current wall-clock hour falls in this configured range," so it's a genuine case for a custom Authenticator SPI provider.

    public class BusinessHoursAuthenticator implements Authenticator {
    static final String CONFIG_START_HOUR_UTC = "startHourUtc";
    static final String CONFIG_END_HOUR_UTC = "endHourUtc";

    public void authenticate(AuthenticationFlowContext context) {
        AuthenticatorConfigModel configModel = context.getAuthenticatorConfig();
        int startHour = readHourConfig(configModel, CONFIG_START_HOUR_UTC, 9);
        int endHour = readHourConfig(configModel, CONFIG_END_HOUR_UTC, 17);
        int currentHourUtc = ZonedDateTime.now(ZoneOffset.UTC).getHour();

        if (isWithinWindow(currentHourUtc, startHour, endHour)) {
            context.success();
            return;
        }
        context.getEvent().error(Errors.ACCESS_DENIED);
        Response challenge = Response.status(Response.Status.FORBIDDEN)
                .type(MediaType.APPLICATION_JSON)
                .entity("{\"error\":\"access_denied\",\"error_description\":\"...\"}")
                .build();
        context.failure(AuthenticationFlowError.ACCESS_DENIED, challenge);  // see "A real bug" below
    }

    public boolean requiresUser() { return false; }  // decision depends only on the clock
    // action(), configuredFor(), setRequiredActions(), close() -- see labs/custom-spis/ for the rest
}

    requiresUser() returns false deliberately: this authenticator's decision depends only on the wall clock, never on which user is logging in, so it doesn't need the flow to have already resolved a UserModel before it runs. Its AuthenticatorFactory counterpart exposes exactly two admin-configurable properties (startHourUtc, endHourUtc, both defaulting to a 9-17 UTC window) via ConfigurableAuthenticatorFactory — the interface that makes an authenticator show up with real config fields in the Authentication flow editor, rather than a fixed, unconfigurable toggle.

    Riverside Health: a distinguishable failed-login audit trail

    Case study — Riverside Health

    Riverside Health needs a HIPAA-relevant record (chapter 11) of every failed login against clinician/administrative accounts, in a format its compliance team can reliably grep out of server logs — distinguishable from Keycloak's own built-in jboss-logging event listener (chapter 28), which logs every error event at the same log level with no org-specific framing. A custom EventListenerProvider is the mechanism: it sees the exact same event stream the built-in listener does, and can log whichever subset it cares about however it likes.

    public class FailedLoginAuditEventListenerProvider implements EventListenerProvider {
    static final String AUDIT_PREFIX = "RIVERSIDE-HIPAA-LOGIN-AUDIT";

    public void onEvent(Event event) {
        if (event.getType() != EventType.LOGIN_ERROR) return;
        System.out.println(formatLine(event));   // see "Logging mechanism" note below
    }

    public void onEvent(AdminEvent event, boolean includeRepresentation) {
        // Deliberate no-op -- admin events (chapter 28) are a different stream, out of this
        // chapter's scope.
    }
    // formatLine() builds "RIVERSIDE-HIPAA-LOGIN-AUDIT | time=... | realm=... | userId=... | ..."
}

    Logging mechanism, named honestly: this provider writes to System.out directly, not a logging framework call. A real production listener would hook into the organization's actual logging/SIEM pipeline — this lab uses stdout specifically because it's guaranteed to land in docker compose logs regardless of how the server's own logging framework happens to be configured, which is exactly what this chapter's lab needs to capture a real, verifiable transcript. The trade-off is named, not hidden.

    No realm-filtering logic appears anywhere in this class. EventListenerProvider implementations are only ever invoked for a realm that has that provider's id explicitly enabled under that realm's own Events configuration (chapter 28) — confirmed live in this chapter's own lab below, by triggering a failed login against a different realm and confirming zero matching log lines appeared.

    Northwind Apps: injecting a tenant_id claim

    Case study — Northwind Apps

    Northwind Apps runs a multi-tenant B2B SaaS product (chapter 2): every one of its downstream applications needs to know which customer organization ("tenant") a given login belongs to, ideally without an extra lookup call per request. A custom ProtocolMapper that reads a tenant_id user attribute and injects it as a real claim into the access token, ID token, and UserInfo response makes that information available to every application that already trusts Northwind's tokens, with zero changes needed in those applications.

    public class TenantIdProtocolMapper extends AbstractOIDCProtocolMapper
        implements OIDCAccessTokenMapper, OIDCIDTokenMapper, UserInfoTokenMapper {

    static final String USER_ATTRIBUTE_NAME = "tenant_id";  // deliberately hardcoded, see text

    public AccessToken transformAccessToken(AccessToken token, ProtocolMapperModel mappingModel,
            KeycloakSession session, UserSessionModel userSession, ClientSessionContext ctx) {
        setTenantClaim(token, mappingModel, userSession); return token;
    }
    // transformIDToken(...) and transformUserInfoToken(...) call the identical helper --
    // AccessToken extends IDToken, confirmed via javap, so one setTenantClaim(IDToken, ...)
    // method correctly handles access tokens, ID tokens, and the UserInfo response's token shape.

    private static void setTenantClaim(IDToken token, ProtocolMapperModel mappingModel,
            UserSessionModel userSession) {
        UserModel user = userSession.getUser();
        String tenantId = user == null ? null : user.getFirstAttribute(USER_ATTRIBUTE_NAME);
        if (tenantId == null || tenantId.isEmpty()) return;  // omit entirely, not a null claim
        OIDCAttributeMapperHelper.mapClaim(token, mappingModel, tenantId);
    }
}

    The source attribute name is deliberately hardcoded rather than exposed as its own admin-configurable field — chapter 24's built-in UserAttributeMapper already covers the general "pick any attribute, map it to any claim" case; re-deriving that generic config UI here would duplicate chapter 24's own territory instead of teaching this chapter's actual subject.

    Common mistakes

    • If an XML parse error points at a POM comment, the cause is almost always a literal -- sequence inside that comment's prose text — this chapter hit the exact same failure chapter 33 did, independently, by habitually writing a plain-English dash the same way. There is no escape mechanism; rewrite the prose to avoid the sequence.
    • If a custom Authenticator's context.failure(AuthenticationFlowError) call (the single-argument overload) produces a bare HTTP 500 instead of a clean OAuth error on the Direct Grant code path specifically, use the two-argument context.failure(AuthenticationFlowError, Response) overload instead, with an explicitly built JSON Response rather than an HTML error page meant for the browser flow.
    • If "Account is not fully set up" appears for a test user you just created, check whether it's actually your new authenticator's fault before debugging the authenticator — disable it temporarily and reproduce the login attempt; if the error persists, the real cause is almost always a Declarative User Profile gap (missing required fields), not the code you just wrote.
    • If a UserInfo call returns "Lightweight access token not allowed for userinfo endpoint" even though your Protocol Mapper's config correctly includes userinfo.token.claim, check the client's own "Always use lightweight access token" setting — admin-cli has it enabled by default, and it's unrelated to anything the mapper's code or config controls.
    • If a rebuilt provider JAR doesn't seem to take effect after mvn clean package even though the build succeeded, check whether the Keycloak container was only restarted rather than recreated — a plain restart can keep serving the old bind-mounted file's content; recreate the container (docker compose up -d --force-recreate <service>) to force the bind mount to re-resolve against the current host file. This is a different failure mode from chapter 33's "bind-mounted JAR becomes a directory" bug, not the same one recurring.
    • If a custom attribute a Protocol Mapper's getFirstAttribute() call expects to find comes back null even though you just set it via kcadm.sh, check the realm's Declarative User Profile unmanagedAttributePolicy first — chapters 22, 24, 33, and now 39 have all independently hit the same persistence gap.
    • Don't conflate an Authenticator (runs during the credential check, can still fail the login) with a Required Action (chapter 40 — runs only after the login has already succeeded, and cannot fail it). Both can show the user a form mid-login, which is exactly why the two get confused.

    Glossary terms introduced here

    Takeaways

    • Every Keycloak SPI this course has written against — User Storage (ch. 33), Authenticator, Event Listener, and (with one real exception) Protocol Mapper — shares the same Factory/ ServiceLoader/Provider discovery shape.
    • The one real exception: ProtocolMapper extends ProviderFactory itself, and AbstractOIDCProtocolMapper.create() returns this — confirmed directly from the real interface, not assumed from the SPI's name.
    • An Authenticator runs during the credential check and can still fail the login outright; a Required Action (chapter 40) only ever runs after login has already succeeded and cannot fail it — a distinction worth its own callout since it's a common point of confusion.
    • Keycloak's own Server Developer Guide explicitly marks both the Authentication SPI and the Event Listener SPI as "internal" in prose, matching the live KC-SERVICES0047 boot warning this chapter's own lab triggered for all three providers (User Storage, chapter 33, triggered no such warning).
    • The single-argument context.failure(AuthenticationFlowError) overload can throw an uncaught exception on the Direct Grant code path — always supply an explicit challenge Response via the two-argument overload instead.
    • A realm's Declarative User Profile gaps and unmanagedAttributePolicy setting continue to surface as real, independent gotchas across completely different SPIs (Authenticator here, Protocol Mapper here, User Storage in chapter 33) — not a one-off.
    • A bind-mounted provider JAR rebuilt while its container is already running needs the container recreated, not merely restarted, to pick up the new file — a different real Docker gotcha than chapter 33's "becomes an empty directory" one.
    • A client's "Always use lightweight access token" setting (enabled by default on admin-cli) causes the UserInfo endpoint to reject that token outright — unrelated to anything a Protocol Mapper's own code or config controls.
    • One Maven project, three packages (one per case-study org) was this chapter's own judgment call, justified by all three SPIs sharing identical build/deploy mechanics and having zero dependencies on each other — not a Keycloak requirement.

    Self-check

    Click a question to reveal a model answer. Try answering it yourself first — the point is to check your own reasoning against it, not to read the answer first.

    1. Why does Meridian Trust's BusinessHoursAuthenticator return false from requiresUser(), and would it be wrong to return true instead?

      Model answer requiresUser() is an honest signal about what the authenticator's own logic actually needs — this one's decision depends only on the current wall-clock hour, never on which user is logging in, so it genuinely doesn't need the flow to have already resolved a UserModel. Returning true wouldn't necessarily break anything by itself, but it would misrepresent what the authenticator actually does and could force an ordering constraint (this execution must come after one that resolves a user) that this logic doesn't actually need — worth getting right because another developer reading the flow config later will reasonably infer the authenticator touches the user if that flag says so.

    2. A colleague's custom Authenticator denies a Direct Grant login with context.failure(AuthenticationFlowError.ACCESS_DENIED) (the single-argument overload) and gets back an HTTP 500 instead of a clean error. Walk through what's actually happening, confirmed by this chapter's own lab.

      Model answerThe single-argument overload does correctly tag the resulting event (confirmed live: the LOGIN_ERROR event fired with error="access_denied") — the problem is what happens next. That overload assumes there's a browser to render a challenge response for, and on the Direct Grant code path specifically (no browser involved at all), it throws an uncaught AuthenticationFlowException from DefaultAuthenticationFlow.processResult, which the REST layer turns into a bare HTTP 500 unknown_error instead of a clean OAuth error. The fix is the two-argument context.failure(AuthenticationFlowError, Response) overload, supplying an explicit JSON Response as the challenge rather than relying on the framework to build one that doesn't apply to this code path.

    3. Why does Riverside Health's event listener need no realm-filtering code at all, and how was that confirmed rather than assumed?

      Model answer Keycloak only ever invokes an EventListenerProvider's onEvent() for a realm that has that provider's id explicitly listed under that realm's own Events configuration (eventsListeners) — the scoping happens one layer above this class, not inside it. Confirmed live in this chapter's lab, not just assumed: a failed login was triggered against a second realm (meridian-trust) that does not have this listener enabled, and grepping fresh logs immediately afterward found zero matching audit lines for that attempt — proving the scoping is real and enforced by realm configuration, not by any code this class contains.

    4. Why does TenantIdProtocolMapper need only one setTenantClaim(IDToken, ...) helper method to handle both the access token and the ID token, rather than two separate implementations?

      Model answer Confirmed directly via javap on the real 26.8.2 jar before writing the class: org.keycloak.representations.AccessToken extends org.keycloak.representations.IDToken. Since an AccessToken genuinely is an IDToken (not merely a similarly-shaped class), a single method typed to accept an IDToken parameter can be called with either a real access token or a real ID token object, and OIDCAttributeMapperHelper.mapClaim(...) places the claim correctly either way without the method needing to know which one it received.

    5. Explain, in terms a reader who only read this chapter (not chapter 33) could follow, why Protocol Mapper's SPI shape is a genuine exception to the Factory/Provider pattern, rather than this chapter simply skipping a step out of laziness.

      Model answer Authenticator and EventListenerProvider each need a separate Factory class because they model two genuinely different lifecycle stages: something expensive-ish that happens once at boot (discovery, and any setup work), and something cheap that happens per use (the actual instance Keycloak core calls into). ProtocolMapper doesn't need that split because it's cheap and stateless enough on both sides — confirmed directly by inspecting AbstractOIDCProtocolMapper.create() on the real jar, which simply returns this rather than constructing anything new. The SPI's own design collapses Factory and Provider into one class here; this chapter's single-class TenantIdProtocolMapper isn't a shortcut, it's the shape the real interface actually has.

    6. A reader asks: "Since Keycloak's own docs call the Authenticator and Event Listener SPIs 'internal,' should a real organization avoid building on them?" What's the honest answer this chapter gives?

      Model answerNot necessarily avoid them, but go in with eyes open about what "internal" means here: both SPIs are documented with a full walkthrough in Keycloak's own Server Developer Guide, and the live boot-time KC-SERVICES0047 warning this chapter's own lab triggered confirms they're stable enough to actively use — "internal" means Keycloak reserves the right to change the interface across a release without the same backward-compatibility guarantee a clearly public API would carry, not that the interface is unsupported or unreliable today. A real organization building on these should budget for re-testing a custom provider against each major Keycloak upgrade (chapter 45's territory), the same way chapter 33 already flagged for the User Storage SPI's own version-pinning concerns.
