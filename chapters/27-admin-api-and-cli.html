27. Admin REST API & kcadm CLI

Every chapter since 20 has quietly used two different paths to the same result: a described Admin Console click, and a kcadm.sh call used to confirm it actually worked. This chapter stops treating the second path as a footnote. The Admin Console, kcadm.sh, and any script a reader writes are three equally valid clients of exactly one thing — the Admin REST API — and this chapter is where that API's real shape (base URL, bearer-token authentication, pagination, field filtering) and its own command-line client become the subject, not a verification aside. It also covers realm export and import, the backup/migration primitive chapters 44-45 build on later.

Why this matters

An IAM specialist who can only click through an admin console does not scale past one realm and one afternoon. Onboarding 50 customer-admin accounts by hand, re-platforming a staging realm's settings into three environments identically, or feeding a nightly compliance export into a SIEM all require treating Keycloak as a system with a programmable interface, not a web form. The Admin REST API is that interface, and kcadm.sh is the fastest way most teams actually touch it — but it is a thin wrapper, not a separate product, and understanding what it wraps is what lets a specialist debug it when a script's silent "success" turns out not to be one.

What concept is this?

Chapter 3 named Accounting as the third letter of AAA: recording identity and access events as structured, timestamped data, distinct from the later activity of auditing those records. Everything in this chapter is the "A" for Administration made scriptable — and, as the lab below shows directly, every admin action taken through that script is itself an event Keycloak can (and by default does not) record, which is accounting applied recursively to the administrators themselves. Chapter 10 named the governance risk of provisioning at scale: a one-at-a-time admin-console workflow gives you an audit trail for free, one click at a time, but a bulk script that creates dozens of accounts in a loop can just as easily create dozens of accounts with no audit trail at all, if nobody turned recording on first. This chapter's lab deliberately reproduces that exact governance failure mode before fixing it, rather than assuming it away.

The Admin REST API's real shape

Per Keycloak's own Admin REST API reference (fetched live for this chapter; the reference itself is still labeled a preview feature, not personally screenshot-verified beyond what this chapter's own curl calls confirmed), every admin endpoint hangs off one base pattern:

{server-base-url}/admin/realms/{realm}/{resource}

Three concrete things follow directly from that pattern, each confirmed live against a running Keycloak 26.8.2 instance rather than assumed from the reference alone:

  • The realm in the path is the realm being administered, not necessarily the realm the caller authenticated against. This chapter's lab authenticates once against master (the only realm allowed to hold Keycloak's own administrative accounts, per chapter 20's master-realm boundary rule) and then issues calls against /admin/realms/northwind-apps/... — one session, many target realms, as long as the authenticated identity has rights over each one.
  • Every call requires a bearer access token (chapter 8's generic concept, concrete here): no cookie, no session the way a browser login uses one — an Authorization: Bearer <token> header, full stop.
  • Collection endpoints page with first/max query parameters, not a response header. A live call against GET /admin/realms/northwind-apps/users returned no total-count header of any kind in this chapter's test — getting a true total requires a separate call to that resource's own /count endpoint, confirmed live below.

Authenticating: two real patterns, confirmed live

Chapters 13-14 already covered OAuth 2.0's password and client-credentials grants in the abstract, against the Duende demo server. This chapter is where the Admin REST API's own authentication becomes concrete, with two real, distinct patterns depending on who — or what — is calling:

Two real authentication patterns for the Admin REST API, confirmed live against Keycloak 26.8.2
PatternClient / grantFits
Interactive human scriptingBuilt-in admin-cli client (public, no secret), Resource Owner Password Credentials grant, with a real human's own admin username/passwordA specialist's own terminal session running kcadm.sh or ad-hoc curl calls — this chapter's lab uses exactly this.

This chapter's lab used the first pattern, and decoded the real token it got back rather than trusting a description of one. A raw curl call against the token endpoint — the exact same endpoint every OIDC client in this course has used since chapter 15 — returns a normal OAuth token response:

curl -s -X POST "http://localhost:8080/realms/master/protocol/openid-connect/token" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "client_id=admin-cli" -d "grant_type=password" \
  -d "username=admin" -d "password=admin_lab_password"
{
  "access_token": "eyJhbGciOiJSUzI1NiIs...",
  "expires_in": 60,
  "refresh_expires_in": 1800,
  "refresh_token": "eyJhbGciOiJIUzUxMiIs...",
  "token_type": "Bearer",
  "not-before-policy": 0,
  "session_state": "8204veZhoFpavJFjJYmTDhil",
  "scope": "profile kc-admin-api email"
}

Two details here are real findings, not restatements of the grant type: the access token's expires_in is 60 seconds on this image's default master realm — genuinely short, so a long-running script needs the paired refresh token or must re-authenticate, not assume one token lasts the whole job — and the scope string includes kc-admin-api specifically, a scope this image attaches that an ordinary application client's token would not carry. Decoding the access token's payload directly (base64url, not guessed) confirms why that scope matters:

{
  "exp": 1794302063,
  "iat": 1794302003,
  "iss": "http://localhost:8080/realms/master",
  "aud": "http://localhost:8080/admin/realms/master",
  "typ": "Bearer",
  "azp": "admin-cli",
  "scope": "profile kc-admin-api email"
}

The aud (audience) claim targets the Admin REST API itself (/admin/realms/master), not an application's own API the way chapter 15's OIDC claims chapter framed a typical resource-server audience. This is the concrete mechanism behind "this token can administer Keycloak" rather than "this token can call some other app's backend" — the same bearer-token concept from chapter 8, scoped by claim rather than by a different kind of token.

kcadm.sh: a thin wrapper, nothing more

The glossary already defines kcadm.sh as Keycloak's bundled Admin REST API CLI client, shipped at /opt/keycloak/bin/kcadm.sh. This chapter adds the mechanics confirmed live:

  • kcadm.sh config credentials --server ... --realm master --user admin --password ... performs exactly the password-grant token request shown above, then caches the resulting access and refresh tokens in a config file — confirmed in this chapter's lab at /opt/keycloak/.keycloak/kcadm.config inside the container (the Linux default is $HOME/.keycloak/kcadm.config; it resolves to that path because /opt/keycloak is the container's own keycloak user's home directory). Every subsequent kcadm.sh call in the same shell reuses that cached session rather than re-authenticating.
  • Generic resource verbs — get, create, update, delete — map directly onto HTTP GET/POST/PUT/DELETE against the same /admin/realms/{realm}/{resource} paths this chapter already described. -r sets the target realm, -s key=value sets a field on the request body, -q key=value adds a query-string parameter (this is the real pagination flag — see below), and --fields filters which keys of the response get printed.
  • A real pitfall confirmed in this chapter's own lab run: kcadm.sh create normally prints a Created new X with id 'Y' confirmation line, taken from the response's Location header. Some admin endpoints — this chapter ran into it directly on partial-export — return a response body but no Location header, so the create command exits 0 with zero printed output, looking exactly like a silent success and a silent no-op at the same time. Passing -o forces kcadm.sh to print the actual response body instead of relying on that header, which is how this chapter confirmed the call had, in fact, done something.
  • --format csv --noquotes turns a JSON array response into a plain value list — this chapter's bulk-onboarding script below uses exactly this to extract a user's or group's id into a shell variable for a follow-up call, since most Admin REST API resources are identified by an internal UUID the caller usually has to look up first, not by a human-chosen name.

Realm export and import: three real mechanisms, not one

This course's labs since chapter 20 have each started from a fresh realm. This chapter ran all three of Keycloak's real export/import mechanisms directly, rather than describing one and assuming the others behave the same way — they do not:

Three real export/import mechanisms, confirmed live against Keycloak 26.8.2 (per Keycloak's own Importing and Exporting Realms guide plus this chapter's own curl/kcadm/kc.sh runs)
MechanismInvoked viaIncludes users?Server state required
Partial exportREST POST /admin/realms/{realm}/partial-export (or kcadm.sh create partial-export -r <realm> -o)No — confirmed live: the response has no users key at all, not even an empty oneServer stays running; this is an ordinary authenticated REST call
Full exportServer CLI: kc.sh export --dir <dir> --realm <realm>Yes — confirmed live: a separate per-realm users file, including each user's hashed-and-salted credential dataThe Keycloak server process must not be running — this is a separate, one-shot "nonserver" launch mode, not a REST call at all
Partial importREST POST /admin/realms/{realm}/partialImport (or the Admin Console's own partial-import screen, which per the official guide can load a CLI-produced full export, including its users)Whatever the submitted payload contains — can include usersServer stays running; conflicts are resolved per an ifResourceExists policy of SKIP, OVERWRITE, or FAIL, confirmed live below
Pitfall — a full export is a secret, not a backup script's harmless log

This chapter's lab ran kc.sh export against its test realm and read the resulting per-user file directly. One real user's credential entry looked like this:

{
  "username": "acme-admin",
  "credentials": [ {
    "type": "password",
    "secretData": "{\"value\":\"M+2l4k8Qph/Mt4o+SyXAB/N+F5gIpF6qlSgUfLNZ5dM=\",\"salt\":\"BBzUe40hFsIzZhWzo5JbzA==\",...}",
    "credentialData": "{\"hashIterations\":5,\"algorithm\":\"argon2\",...}"
  } ]
}

The password itself is not stored in plaintext — it's an Argon2 hash with its own salt, the same discipline any credential store should use — but this is still real secret material, not metadata: every user's hashed credential, for every user in the realm, in one file. If you see a full realm export committed to a git repo, attached to a support ticket, or dropped on a shared drive "just for reference," the cause is almost always treating it like the much smaller, user-free partial export above. Keycloak's own guide is explicit that only these full, boot-time exports — not the Admin Console's partial export — are "suitable for backups or data transfer between servers," which makes this exact file the one most likely to actually get handled carelessly.

  3. Write the real bulk-onboarding script. Usernames, roles, and groups are read from a small table inside the script — the same shape a CSV-driven real onboarding list would have:

    #!/bin/sh
# bulk-onboard.sh
set -e
KCADM=/opt/keycloak/bin/kcadm.sh
REALM=northwind-apps

USERS="
acme-admin:Dana:Lin:tenant-admin:Engineering
globex-admin:Marcus:Reyes:tenant-admin:Engineering
initech-support:Sam:Okafor:support-agent:Support
umbrella-support:Tia:Novak:support-agent:Support
"

for row in $USERS; do
  username=$(echo "$row" | cut -d: -f1)
  first=$(echo "$row" | cut -d: -f2)
  last=$(echo "$row" | cut -d: -f3)
  role=$(echo "$row" | cut -d: -f4)
  group=$(echo "$row" | cut -d: -f5)

  echo "=== Onboarding $username ==="
  $KCADM create users -r "$REALM" -s username="$username" -s enabled=true \
    -s firstName="$first" -s lastName="$last" -s "email=$username@customer.example" \
    -s emailVerified=true

  $KCADM set-password -r "$REALM" --username "$username" --new-password 'Onboard-Temp-2026!' --temporary
  $KCADM add-roles -r "$REALM" --uusername "$username" --rolename "$role"

  group_id=$($KCADM get groups -r "$REALM" -q "search=$group" --fields id --format csv --noquotes | head -n1)
  user_id=$($KCADM get users -r "$REALM" -q "username=$username" --fields id --format csv --noquotes | head -n1)
  $KCADM update "users/$user_id/groups/$group_id" -r "$REALM"

  echo "--- confirm: role + group mapping for $username ---"
  $KCADM get "users/$user_id/role-mappings/realm" -r "$REALM" --fields name
  $KCADM get "users/$user_id/groups" -r "$REALM" --fields name
done

Common mistakes

  • If you see a kcadm.sh create command exit 0 with no printed confirmation at all, the cause is very often an endpoint — this chapter hit it directly on partial-export — that returns a body but no Location header; add -o to force the real response body to print instead of trusting the absence of output as either success or failure.
  • If you see a restore script written against a realm's partial-export JSON assuming it will contain users, the cause is confusing it with a full export — partial export (REST) never includes users at all, confirmed live in this chapter; only the server-CLI full export does.
  • If you see a full realm export file treated as harmless metadata — attached to a ticket, committed to a repo, left on a shared drive — the cause is forgetting it contains every user's hashed-and-salted password credential, not just configuration.
  • If you see a bulk-automation script that ran cleanly but left no audit trail anyone can find later, the cause is almost always that adminEventsEnabled was off before the script ran — and turning it on afterward does not retroactively log what already happened, exactly as this chapter's own lab reproduced.
  • If you see a CI job on a shared runner unexpectedly reuse another job's Keycloak admin session, the cause is kcadm.sh's own config-caching behavior — it writes the access/refresh token to a config file by default; unattended automation should pass --no-config (or an isolated config path) so nothing is cached between runs.
  • If you see a script build a REST call like /admin/realms/{realm}/{realm}/partial-export and get a 404, the cause is manually prefixing the realm again on top of what kcadm.sh -r or a hand-built base URL already supplies — this chapter made exactly that mistake once while drafting this lab, and the fix was simply dropping the duplicate realm segment.
  • If you see someone try to run kc.sh export against a Keycloak container that's still serving traffic on the same data, the cause is treating full export like an ordinary REST call — it is a separate, one-shot server launch mode that explicitly requires the regular server process not to be running.

Takeaways

  • The Admin Console, kcadm.sh, and any hand-written script are three equally valid clients of exactly one bearer-token-protected Admin REST API at {server}/admin/realms/{realm}/{resource} — confirmed by reproducing a kcadm.sh action with a raw curl call against the identical endpoint.
  • An admin-scoped access token's aud claim targets the Admin REST API itself (/admin/realms/{realm}), and its scope includes kc-admin-api — confirmed by decoding a real token, not assumed from the grant type alone.
  • Two authentication patterns fit two different callers: the built-in admin-cli client with a human's password (interactive scripting) versus a dedicated service-account client with the client-credentials grant (unattended automation, the same pattern chapter 36 covers for applications).
  • kcadm.sh is a thin wrapper: get/create/update/ delete map onto HTTP verbs against the same REST paths, -q sets query parameters (including the real first/max pagination flags), and -o forces the real response body to print for endpoints with no Location header to report instead.
  • There is no total-count response header on Admin REST API list endpoints — getting a true count requires a separate call to that resource's own /count endpoint, confirmed live.
  • Partial export (REST), full export (server CLI), and partial import (REST) are three distinct mechanisms, not three names for one operation: only the full, server-CLI export includes users and their hashed credentials, and only it requires the server process to be stopped first.
  • A bulk-automation script is only as auditable as the realm's adminEventsEnabled setting at the moment it ran — this chapter deliberately reproduced the governance gap chapter 10 warned about (four real accounts created with zero recorded admin events) before fixing it and showing the real, detailed event record a fifth account creation left once logging was on.
  • A full realm export is secret material, not a backup script's harmless log — this chapter read a real exported user's credential entry directly and found a salted Argon2 hash, not a plaintext password, but still real, sensitive data for every user in the realm.
  • partialImport's ifResourceExists parameter (SKIP, OVERWRITE, or FAIL) is the real, explicit conflict policy for merging data into a live realm — confirmed live by adding one new user to a realm that already had others.
