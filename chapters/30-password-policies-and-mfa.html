    30. Password Policies, Brute-Force Protection & MFA Config

    Chapter 21 walked past this realm's Security Defenses tab and explicitly deferred it: "brute-force detection and password policy are chapter 30's subject in full, once a realm actually has users worth protecting." That realm now has users (chapter 22), roles and groups (chapter 23), a client (chapter 24), and a conditional-OTP auth flow (chapter 25) — everything chapter 21 was waiting on. This chapter closes that loop for real: it sets a passwordPolicy string and watches Keycloak reject a bad password with its own real error message, turns on brute-force detection with deliberately small numbers and actually locks an account out by failing a login three times, confirms that lockout against the Admin REST API's own attack-detection endpoint rather than assuming the third attempt "probably" worked, and sets the OTP Policy fields that govern every TOTP code chapter 5 described in the abstract.

    Why this matters

    These three controls are the ones an auditor actually asks to see evidence of, not just a toggle. A PCI-DSS assessor reviewing Meridian Trust's online banking realm, a HIPAA security-rule reviewer looking at Riverside Health's clinician accounts, and Northwind Apps's own enterprise customers filling out a security questionnaire all ask variants of the same three questions: what stops a weak password, what stops someone from just guessing until they get in, and what happens if they guess right anyway. An IAM specialist who can only say "we enabled MFA" hasn't answered any of the three — this chapter is about being able to point at the exact realm fields, the exact values chosen, and the exact test that proved each one actually works, because "I configured it" and "I confirmed it" are different claims and only the second one survives an audit.

    What concept is this?

    Chapter 5 described MFA and risk-based authentication as general ideas: proof from more than one factor category, and asking for more proof only when risk signals warrant it. Chapter 9 named credential stuffing and password reuse as the threat that makes a weak, reused password dangerous at scale, and brute-force guessing as the threat that makes an unlimited number of login attempts dangerous even against a password nobody else has ever seen. Put together, those two chapters argued for exactly three defenses, layered: raise the cost of a successful guess (a strong password policy), cap how many guesses an attacker gets before something stops them (brute-force lockout), and make sure a correctly guessed password still isn't enough on its own (MFA/OTP). This chapter is where all three stop being arguments and become realm fields with real, tested values on northwind-apps.

    Password policies: the real syntax, confirmed live — and a correction

    Keycloak stores a realm's password policy as one string in the passwordPolicy REST field. Before writing anything, this chapter's lab tested the field's actual separator syntax directly against a running Keycloak 26.8.2 realm rather than assuming it — and the result corrects an assumption this chapter's own brief started from. The rules are not semicolon-separated; they are joined with the literal word and:

    docker compose exec keycloak /opt/keycloak/bin/kcadm.sh update realms/northwind-apps \
  -s 'passwordPolicy=length(12) and digits(1) and upperCase(1) and lowerCase(1) and specialChars(1) and notUsername(undefined) and passwordHistory(3)'
    docker compose exec keycloak /opt/keycloak/bin/kcadm.sh get realms/northwind-apps --fields passwordPolicy
    {
  "passwordPolicy" : "length(12) and digits(1) and upperCase(1) and lowerCase(1) and specialChars(1) and notUsername(undefined) and passwordHistory(3)"
}

    Each clause is <policyId>(<param>), and a handful of policy types take no meaningful parameter at all — notUsername above is written as notUsername(undefined) because the Admin Console always serializes it with that literal placeholder value, which this chapter kept rather than guessing at a cleaner-looking alternative.

    Lab, part 1: the rejection, captured for real

    Pitfall — notUsername is not a substring check

    This chapter also tested a password that contains the username as part of a longer string — ppm-test-user1A!, for the user ppm-test-user — with notUsername(undefined) active and no notContainsUsername rule configured. It was accepted (exit code 0, no rejection message at all). notUsername only rejects a password that is exactly equal to the username; it does nothing against a password that merely embeds the username as a recognizable substring with a few characters tacked on, which is exactly the pattern a real attacker who already knows a target's username would try first. If a password policy needs to block that pattern too, the separate notContainsUsername (and notContainsEmail) policy types exist for it — this chapter's realm did not add them, so northwind-apps as configured here is genuinely exposed to that specific pattern, a real gap worth naming rather than glossing over.

    Brute-force detection: the real Security Defenses fields, and a real lockout

    Chapter 21's glossary entry for the Security Defenses tab promised "the specific lockout fields" here. Per Keycloak's official Server Administration Guide's "Mitigating security threats" chapter (fetched live for this chapter) and cross-checked directly against the RealmRepresentation REST schema (version 26.7.2 javadocs, the closest published match to this lab's 26.8.2 build), the realm fields behind that tab are:

    Brute-force detection fields — REST field names confirmed directly against a live 26.8.2 realm's own response
    REST fieldWhat it controlsThis chapter's lab value
    bruteForceProtectedMaster on/off switch for the whole mechanism.true
    failureFactor("Max Login Failures" in the console.) Number of consecutive failures before a wait is imposed.3 — deliberately low, for a lab that needs to actually trigger a lockout quickly.
    waitIncrementSeconds("Wait Increment.") How much wait time is added each time the failure count crosses another multiple of failureFactor (under the default MULTIPLE strategy).10
    maxFailureWaitSeconds("Max Wait.") Ceiling on how long a single temporary lockout can last, however high the failure count climbs.60
    minimumQuickLoginWaitSeconds("Minimum Quick Login Wait.") The wait applied specifically for failures that arrive faster than quickLoginCheckMilliSeconds apart.10
    quickLoginCheckMilliSeconds("Quick Login Check Millis.") Below this gap between failures, Keycloak treats the attempt as an automated "quick" retry rather than a normal one.1000 (default, unchanged)
    maxDeltaTimeSeconds("Failure Reset Time.") How long a failure count is remembered before it resets to zero on its own.43200 (default, unchanged)
    permanentLockoutIf true, a triggered lockout disables the account until an administrator re-enables it, instead of auto-expiring.false — this lab demonstrates the auto-expiring temporary form.
    bruteForceStrategyNewer field (MULTIPLE or LINEAR) controlling how the wait grows as failures accumulate.MULTIPLE (default, unchanged)
    maxTemporaryLockoutsNewer field: lock permanently after this many separate temporary lockouts (0 disables this escalation).0 (default, unchanged)
     
    kcadm.sh update realms/northwind-apps \
  -s bruteForceProtected=true -s failureFactor=3 -s waitIncrementSeconds=10 \
  -s maxFailureWaitSeconds=60 -s minimumQuickLoginWaitSeconds=10 \
  -s quickLoginCheckMilliSeconds=1000 -s maxDeltaTimeSeconds=43200 -s permanentLockout=false
    {
  "bruteForceProtected" : true,
  "permanentLockout" : false,
  "maxFailureWaitSeconds" : 60,
  "minimumQuickLoginWaitSeconds" : 10,
  "waitIncrementSeconds" : 10,
  "quickLoginCheckMilliSeconds" : 1000,
  "failureFactor" : 3
}

    Lab, part 2: triggering and confirming a real lockout

    Chapter 24 used a disposable, clearly-labeled Direct Access Grant (ROPC) client purely as a lab technique to mint tokens without a browser, explicit about chapter 13's framing of that grant as deprecated for real applications. This chapter reuses the same technique for a different reason: ROPC is the only grant where a script can submit a wrong password on purpose and read the server's real, immediate response — a browser-based flow can't be driven headlessly the same way without fabricating what a browser would have shown.

    1. Register the disposable client:

      kcadm.sh create clients -r northwind-apps -s clientId=ppm-lab-dag -s enabled=true \
  -s publicClient=false -s secret=ppm-lab-dag-secret -s directAccessGrantsEnabled=true \
  -s standardFlowEnabled=false

    2. A first direct-grant attempt with the correct password, before touching brute-force settings, surfaced an unrelated real finding worth recording honestly: it failed with "Account is not fully set up", not a token. The cause, confirmed by checking the user record, was Keycloak 26.x's declarative User Profile silently requiring firstName/ lastName by default — a brand-new admin-created user with neither set is incomplete from the profile's point of view even though requiredActions was empty. Setting both fixed it:

      kcadm.sh update users/<id> -r northwind-apps -s firstName=Lab -s lastName=Test
      curl -s -X POST http://localhost:8080/realms/northwind-apps/protocol/openid-connect/token \
  -d "grant_type=password" -d "client_id=ppm-lab-dag" -d "client_secret=ppm-lab-dag-secret" \
  -d "username=ppm-test-user" -d "password=Correct-Horse-9!"
      {"access_token":"eyJ...", "expires_in":300, ... "token_type":"Bearer", ...}

      A real access token, confirming the baseline actually works before testing the failure path.

    3. Check the attack-detection endpoint before any failures — it exists, and starts clean:

      kcadm.sh get attack-detection/brute-force/users/<id> -r northwind-apps
      {
  "failedLoginNotBefore" : 0,
  "numFailures" : 0,
  "numTemporaryLockouts" : 0,
  "disabled" : false,
  "numSecondaryAuthFailures" : 0,
  "lastIPFailure" : "n/a",
  "lastFailure" : 0
}

    4. Submit three wrong passwords in a row (failureFactor=3), a couple of seconds apart so the "quick login" path doesn't change the arithmetic:

      curl -s -X POST .../protocol/openid-connect/token -d "grant_type=password" \
  -d "client_id=ppm-lab-dag" -d "client_secret=ppm-lab-dag-secret" \
  -d "username=ppm-test-user" -d "password=WrongPassword-1!"
# {"error":"invalid_grant","error_description":"Invalid user credentials"}
# ...repeated for WrongPassword-2! and WrongPassword-3!, same response each time

    Continuing the same lab realm and user — steps 5 through 8 confirm the lockout is real, prove it blocks even the correct password, and exercise both recovery paths.

    1. Confirm the lockout really happened — don't infer it from three identical-looking error responses, read the actual state:

      kcadm.sh get attack-detection/brute-force/users/<id> -r northwind-apps
      {
  "failedLoginNotBefore" : 1794302348,
  "numFailures" : 3,
  "numTemporaryLockouts" : 1,
  "disabled" : true,
  "numSecondaryAuthFailures" : 0,
  "lastIPFailure" : "172.28.0.1",
  "lastFailure" : 1794302338292
}

      disabled: true and numTemporaryLockouts: 1 — a real, confirmed lockout.

    2. The sharpest proof it's real: submit the correct password while locked out.

      curl -s -X POST .../protocol/openid-connect/token -d "grant_type=password" \
  -d "client_id=ppm-lab-dag" -d "client_secret=ppm-lab-dag-secret" \
  -d "username=ppm-test-user" -d "password=Correct-Horse-9!"
      {"error":"invalid_grant","error_description":"Invalid user credentials"}

      The right password gets the exact same generic error as a wrong one — deliberate, see the common mistakes section below.

    3. Wait past waitIncrementSeconds (10 seconds in this lab) and confirm the account recovers on its own, with no admin action:

      sleep 12
kcadm.sh get attack-detection/brute-force/users/<id> -r northwind-apps --fields disabled,numFailures
      { "disabled" : false, "numFailures" : 3 }

      Note numFailures itself is not reset by the wait expiring — only disabled flips back. A follow-up correct-password login then succeeded and returned a real token.

    4. The other recovery path — an administrator clearing a lockout directly, without waiting — re-triggered with three more failures and then confirmed:

      kcadm.sh delete attack-detection/brute-force/users/<id> -r northwind-apps
      kcadm.sh get attack-detection/brute-force/users/<id> -r northwind-apps
      {
  "failedLoginNotBefore" : 0, "numFailures" : 0, "numTemporaryLockouts" : 0,
  "disabled" : false, "numSecondaryAuthFailures" : 0, "lastIPFailure" : "n/a", "lastFailure" : 0
}

      Fully reset, and a correct-password login immediately succeeded with no wait at all — the manual unlock an admin would reach for on a real support ticket ("I'm locked out but it's really me").

    OTP Policy tab: the fields behind chapter 5's TOTP math

    Chapter 5 explained TOTP in the abstract: a shared secret, a moving factor (time, rounded to a fixed step), and both sides independently computing the same code without transmitting it again. The realm's OTP Policy tab is where that abstract description becomes concrete numbers. Per Keycloak's official guide (fetched live) and confirmed directly against this lab's own realm representation:

    {

    This chapter did not re-run chapter 22's/25's full OTP enrollment and code-generation round trip (scanning a QR code with an authenticator app isn't something a no-browser session can do), so the claim here is scoped exactly like chapter 26's theme-mechanism claim: the fields are real, the write genuinely persists, and the values are Keycloak's own documented meanings — not a personally re-verified "I scanned a QR code and a changed-algorithm code matched." The look-ahead window specifically exists because device clocks drift from the server's clock; otpPolicyLookAheadWindow=1 means the server also accepts a code from one period before or after the current one, trading a small amount of replay-window width for tolerance of realistic clock skew — a direct answer to the "requires reasonably synchronized clocks" caveat chapter 5's own TOTP glossary entry already flagged.

    Case study: Meridian Trust's three controls as compliance evidence

    Case study — Meridian Trust

    Meridian Trust is a retail bank under PCI-DSS, and chapter 11 already named what PCI-DSS actually demands of IAM: strong, enforced authentication controls and documented account-lockout behavior aren't optional hardening — they are specific, auditable requirements an assessor checks for by name. For Meridian's online-banking realm, the three controls this chapter configured aren't a security team's nice-to-have; they're the literal evidence an auditor asks to see:

    • Password policy as a documented control, not a verbal promise. The exact string this chapter set on northwind-apps — minimum length, mixed character classes, no reuse of the last three passwords — is the kind of value Meridian's own retail-banking realm would set, with one addition Meridian specifically cannot skip: notContainsUsername alongside notUsername, precisely because this chapter's own lab proved notUsername alone lets a password containing the username straight through. A bank cannot afford that gap; a B2B SaaS dashboard realm might reasonably accept more risk there, which is exactly why this is a deliberate per-realm policy choice, not a universal default.
    • Brute-force lockout tuned for fraud exposure, not lab convenience. This chapter used failureFactor=3 and a 10-second wait purely so the lab could trigger and observe a lockout quickly. Meridian's real realm would use numbers closer to Keycloak's own defaults (failureFactor=30, waitIncrementSeconds=60, maxFailureWaitSeconds=900) or tighter — balanced against the brute-force detection's own documented downside this chapter's sources named: an attacker who already knows a target's username can deliberately trigger lockouts as a denial-of-service tactic against legitimate customers, so Meridian's fraud team, not just its security team, has a real stake in where these numbers land.
    • MFA as the control that survives a leaked password. Chapter 3 already used Meridian's own online banking as the AAA worked example — "a password plus a one-time code sent to the customer's phone." The OTP Policy fields this chapter configured are the realm-wide knobs behind that one-time code's actual math: digit count, period, hash algorithm, and the drift-tolerance window, every one of them a real, checkable setting rather than a feature a product page merely claims to have.

    Common mistakes

    • If you see a passwordPolicy string joined with semicolons silently do nothing, the cause is the wrong separator — Keycloak's real syntax joins clauses with the literal word and, not a semicolon; this chapter's own brief started from that same wrong assumption and this lab is the correction.
    • If you see a password containing the username slip past a policy that includes notUsername, the cause is that notUsername only rejects an exact match to the username — catching a password that merely contains the username as a substring requires the separate notContainsUsername policy type, confirmed missing-by-default in this chapter's own lab.
    • If you see "Account is not fully set up" from a direct-grant login for a user that has an empty requiredActions list and a working password credential, the cause is very often Keycloak's declarative User Profile silently requiring attributes like firstName/ lastName that an admin-created test user never got — this chapter hit exactly this and fixed it by setting both.
    • If you see the correct password rejected with the exact same "Invalid user credentials" message a wrong password gets, the cause is not a bug — Keycloak deliberately returns the identical generic error whether the account is locked or the password is simply wrong, so an attacker (or a confused script) can't use the error message itself to distinguish "wrong password" from "this account exists and is currently locked," which would otherwise leak account-enumeration information.
    • If you see a brute-force lockout's disabled flag clear itself but numFailures stay nonzero, the cause is that the wait timer resets disabled/failedLoginNotBefore, not the running failure count itself — only maxDeltaTimeSeconds elapsing, or an explicit admin DELETE on the attack-detection endpoint, actually zeroes numFailures.
    • If you see a reader assume a lower failureFactor is always safer, the cause is missing the documented downside: Keycloak's own guide names brute-force detection's trade-off directly — an attacker who knows real usernames can trigger lockouts deliberately as a denial-of-service tactic against the very users the feature is meant to protect, so the number is a balance, not a one-directional dial.
    • If you see an OTP enrollment stop validating codes right after an admin changes otpPolicyAlgorithm, otpPolicyDigits, or otpPolicyPeriod, the cause is that those fields govern how new codes are generated and checked going forward, not a retroactive re-derivation of already-enrolled secrets — existing enrollments can effectively break and need re-enrollment, the same "doesn't retroactively fix existing records" pattern chapter 26's password-hashing-algorithm note and chapter 22's credential material both already illustrated.

    Takeaways

    • Keycloak's passwordPolicy realm field joins clauses with the literal word and, not a semicolon — confirmed by writing and reading back a real policy string against a running 26.8.2 realm.
    • This chapter's lab triggered real rejections for three distinct password-policy failures (too short, missing a digit, password-history reuse) and captured each one's actual invalidPassword...Message error code rather than narrating a plausible-looking one.
    • notUsername only rejects an exact match to the username; a password that merely contains the username as a substring needs the separate notContainsUsername policy type — confirmed missing by testing a substring-containing password and watching it get accepted.
    • Brute-force detection's real REST fields are bruteForceProtected, failureFactor (Max Login Failures), waitIncrementSeconds (Wait Increment), maxFailureWaitSeconds (Max Wait), minimumQuickLoginWaitSeconds, quickLoginCheckMilliSeconds, maxDeltaTimeSeconds (Failure Reset Time), permanentLockout, bruteForceStrategy, and maxTemporaryLockouts — all confirmed directly against a live realm's own representation, not assumed from memory.
    • A real lockout was triggered by submitting three deliberately wrong passwords via a disposable, clearly lab-only Direct Access Grant client, and confirmed — not assumed — by reading GET /attack-detection/brute-force/users/{id} and seeing disabled: true.
    • Even the genuinely correct password is rejected during a lockout, with the identical generic error a wrong password gets — a deliberate anti-enumeration design choice, confirmed by testing it directly.
    • A temporary lockout recovers automatically once waitIncrementSeconds elapses (disabled flips back to false, but numFailures itself is not reset); an administrator can also clear it immediately via DELETE on the same attack-detection endpoint — both paths were exercised for real in this chapter's lab.
    • The OTP Policy tab's real fields — otpPolicyAlgorithm, otpPolicyDigits, otpPolicyPeriod, otpPolicyLookAheadWindow, otpPolicyCodeReusable, plus otpPolicyInitialCounter for HOTP — are the concrete numbers behind chapter 5's TOTP mechanics, each confirmed against a live realm's default and changed value.
    • The look-ahead window exists specifically to tolerate clock drift between a device and the server, directly answering the synchronization caveat chapter 5's own TOTP glossary entry already flagged.
    • Password policy, brute-force detection, and MFA/OTP policy are not three unrelated settings screens — they are chapter 5's MFA concept and chapter 9's credential-stuffing/brute-force threat material, made concrete as three layered defenses against the same attack, each active at a different stage of it.

    Self-check

    Click a question to reveal a model answer. Try answering it yourself first — the point is to check your own reasoning against it, not to read the answer first.

    1. Explain, without looking it up, why notUsername and notContainsUsername are two different policy types rather than one — what specific password would pass the first check but fail the second?

      Model answernotUsername only rejects a password that is exactly equal to the username, while notContainsUsername rejects a password that merely contains the username anywhere inside a longer string. This chapter's own lab proved the gap directly: for the user ppm-test-user, the password ppm-test-user1A! passed notUsername(undefined) cleanly (it isn't an exact match) but would be rejected by notContainsUsername because it embeds the username as a recognizable substring — exactly the pattern a real attacker who already knows a target's username would try first.

    2. Walk through what actually happens, state by state, between a user's first wrong password and their account recovering, under the exact values this chapter used (failureFactor=3, waitIncrementSeconds=10). What changes at each step, and what stays the same?

      Model answerThe 1st and 2nd wrong passwords each increment numFailures (1, then 2) while the account stays in the "Watching" state (disabled: false). The 3rd wrong password pushes numFailures to 3, matching failureFactor, which flips the account into "Temporarily disabled": disabled becomes true, failedLoginNotBefore is set roughly 10 seconds into the future, and numTemporaryLockouts increments to 1. While in that state, even the correct password is rejected with the same generic error. Once the 10-second waitIncrementSeconds window passes, disabled flips back to false and failedLoginNotBefore resets to 0 automatically — but numFailures stays at 3 the whole time; only an admin DELETE on the attack-detection endpoint, or maxDeltaTimeSeconds elapsing, actually zeroes it.

    3. Why does Keycloak return the identical "Invalid user credentials" error for a locked account as for a merely wrong password, instead of a distinct "account locked" message? What would a distinct message leak to an attacker?

      Model answerA distinct "this account is locked" message would confirm, just from the error text alone, that the username is real and that enough failed attempts have accumulated to trigger a lockout — information an attacker doing credential stuffing or brute-force guessing shouldn't get for free. Returning the exact same generic error whether the password is simply wrong or the account is currently locked prevents that kind of account-enumeration and state-disclosure leak; the attacker (or a confused automated script) can't distinguish "wrong password" from "right username, currently locked out" just by reading the response.

    4. A colleague proposes setting failureFactor=1 on a customer-facing realm "to be as strict as possible." What documented downside should make you push back on that number specifically?

      Model answerKeycloak's own documentation names the trade-off directly: brute-force detection can be weaponized as a denial-of-service tactic by an attacker who already knows (or guesses) real usernames — they don't need the correct password at all, just one deliberate wrong guess per target account to lock out a legitimate customer over and over. With failureFactor=1, a single mistyped password (by the real user themselves, or a single attacker probe) is enough to trigger a lockout every time, turning a security control into an easy tool for harassing or locking out the very users it's meant to protect.

    5. Why does changing otpPolicyAlgorithm on a realm with users who already enrolled OTP under the old algorithm create a real operational problem, rather than being a purely cosmetic change?

      Model answerThe OTP Policy fields govern how codes are generated and validated going forward; they don't retroactively re-derive or re-issue the secrets already enrolled on users' authenticator apps. Once an admin changes otpPolicyAlgorithm (or otpPolicyDigits/otpPolicyPeriod), the server starts expecting codes computed under the new algorithm, but each already-enrolled authenticator app is still generating codes the old way against the same shared secret — so those users' existing codes stop validating and they effectively need to re-enroll MFA, the same "doesn't retroactively fix existing records" pattern seen elsewhere with password-hashing-algorithm changes.

    6. Pick one of Northwind Apps, Riverside Health, or Meridian Trust and argue for a different balance of failureFactor and waitIncrementSeconds than Meridian's own case study above — what about that organization's users or threat model justifies the difference?

      Model answerNorthwind Apps, as a B2B SaaS company with many tenants and a broad, self-service customer base, would reasonably choose a looser balance than Meridian's banking posture — something closer to Keycloak's own default failureFactor=30 with a modest wait increment. Northwind's users are logging into a business dashboard, not moving money, so the fraud exposure per account is far lower than Meridian's, while the cost of locking out a confused, typo-prone enterprise customer (who then opens a support ticket) is comparatively higher relative to the risk being defended against. Meridian's retail-banking realm, by contrast, justifies a tighter number because a successful account takeover there has direct financial and PCI-DSS consequences that Northwind's dashboard access does not.
