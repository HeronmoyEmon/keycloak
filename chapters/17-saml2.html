17. SAML 2.0

Chapter 7 used "assertion" and "metadata" as generic, cross-protocol words, deliberately not committing to a wire format. This chapter commits: SAML (Security Assertion Markup Language) 2.0 is the older of the two federation protocols this course covers, standardized by OASIS in 2005, and it is still very much alive in production enterprise SSO — just not usually in new greenfield builds, which mostly reach for OpenID Connect (chapter 15) instead. You will meet SAML constantly as an IAM specialist: hospital networks, government systems, and large enterprise federations that predate OIDC's rise still run it with vendors who never migrated, and Keycloak has to speak it fluently as both an Identity Provider and a broker. No lab this chapter — see why below.

Why this matters

A real IAM specialist does not get to choose which protocol every integration partner speaks. A hospital's EHR vendor, a bank's old core-banking SSO module, or a government portal will frequently hand you a SAML metadata file and nothing else — and expect you to configure trust against it correctly, debug a signature-validation failure under pressure, and explain to a security auditor exactly what a SAML assertion does and does not prove. Treating SAML as "the old, dead protocol" is itself a mistake that shows up on the job: it is still the default for a large population of long-lived enterprise federations, and it is not going away on any specific timeline. This chapter gives you the structural detail chapter 7 deliberately withheld, and ties every piece back to the OIDC vocabulary chapter 15 just built, so you can translate between the two protocol families fluently.

Recall from chapter 7

Chapter 7 defined the IdP as the system that authenticates the user and asserts identity, and the relying system as either the SP (SAML's name for that role) or the RP (OIDC's name for the same role) — same role, different protocol vocabulary. It also named three ingredients of establishing trust between an IdP and a relying application: metadata, certificates/signing keys, and registered redirect URIs. This chapter is SAML's turn to make all of that concrete: SAML uses the term "SP," not "RP," throughout, and this chapter shows exactly what SAML's metadata and assertions look like on the wire.

The SAML assertion, structurally

Chapter 7's generic definition of an assertion was "the message an IdP sends stating who the user is." In SAML, that message is a literal, signed XML document: a <saml:Assertion> element with a handful of required child elements, each doing a specific job.

  • <saml:Subject> — who this assertion is about. Almost always contains a <saml:NameID> (the user's identifier, in a declared format — email address, a persistent opaque ID, etc.) and a <SubjectConfirmation> that ties the assertion to this specific browser exchange (so a captured assertion can't trivially be replayed elsewhere).
  • <saml:Conditions> — constraints the SP must check before trusting the assertion: a NotBefore/NotOnOrAfter validity window, and an <AudienceRestriction> naming exactly which SP this assertion is meant for (so one SP can't replay an assertion that was actually issued for a different SP).
  • <saml:AuthnStatement> — records that authentication actually happened: when (AuthnInstant) and by what method (AuthnContextClassRef, e.g. password vs. a stronger multi-factor context).
  • <saml:AttributeStatement> — optional, but where most of the useful payload lives in practice: arbitrary name/value attributes about the user (email, department, group memberships) the IdP is willing to hand to this SP.

A realistic (trimmed, not 100%-spec-complete) assertion for a Riverside Health clinician logging into a clinical-systems vendor's portal looks like this:

<saml:Assertion xmlns:saml="urn:oasis:names:tc:SAML:2.0:assertion"
                 ID="_a75adf55-01d7-40cc-929f-dbd8372ebdfc"
                 IssueInstant="2026-11-10T14:02:11Z" Version="2.0">
  <saml:Issuer>https://sso.riversidehealth.example/idp</saml:Issuer>
  <ds:Signature>...</ds:Signature>  <!-- XML digital signature over this assertion -->

  <saml:Subject>
    <saml:NameID Format="urn:oasis:names:tc:SAML:1.1:nameid-format:emailAddress">
      j.alvarez@riversidehealth.example
    </saml:NameID>
    <saml:SubjectConfirmation Method="urn:oasis:names:tc:SAML:2.0:cm:bearer">
      <saml:SubjectConfirmationData NotOnOrAfter="2026-11-10T14:07:11Z"
          Recipient="https://ehr-vendor.example/saml/acs"/>
    </saml:SubjectConfirmation>
  </saml:Subject>

  <saml:Conditions NotBefore="2026-11-10T14:01:41Z" NotOnOrAfter="2026-11-10T14:07:11Z">
    <saml:AudienceRestriction>
      <saml:Audience>https://ehr-vendor.example/saml/metadata</saml:Audience>
    </saml:AudienceRestriction>
  </saml:Conditions>

  <saml:AuthnStatement AuthnInstant="2026-11-10T14:02:10Z">
    <saml:AuthnContext>
      <saml:AuthnContextClassRef>urn:oasis:names:tc:SAML:2.0:ac:classes:PasswordProtectedTransport</saml:AuthnContextClassRef>
    </saml:AuthnContext>
  </saml:AuthnStatement>

  <saml:AttributeStatement>
    <saml:Attribute Name="department">
      <saml:AttributeValue>Cardiology</saml:AttributeValue>
    </saml:Attribute>
    <saml:Attribute Name="clinicianRole">
      <saml:AttributeValue>attending-physician</saml:AttributeValue>
    </saml:Attribute>
  </saml:AttributeStatement>
</saml:Assertion>
Pitfall

The <ds:Signature> wraps the assertion, not the overall HTTP response. An SP that only checks "did this XML come over HTTPS from the right URL" and never actually validates the embedded XML signature against the IdP's trusted certificate is not really verifying anything — it's trusting the transport, not the assertion. XML signature validation (canonicalization, then signature verification) is a well-known source of real vulnerabilities (XML signature wrapping attacks) when implemented carelessly; this is one reason mature SAML libraries, not hand-rolled XML parsing, are the only sane way to consume SAML in production.

SAML metadata, structurally

Chapter 7's generic "metadata" entry said each side needs a machine-readable description of the other's endpoints and capabilities. SAML's version of that is an XML document — <EntityDescriptor> — that an IdP and an SP exchange (often just by fetching each other's metadata URL once, during integration setup) so both sides can configure themselves correctly instead of an administrator typing URLs and certificate fingerprints into forms by hand.

<EntityDescriptor entityID="https://sso.riversidehealth.example/idp">
  <IDPSSODescriptor protocolSupportEnumeration="urn:oasis:names:tc:SAML:2.0:protocol">
    <KeyDescriptor use="signing">
      <ds:KeyInfo><ds:X509Data><ds:X509Certificate>MIIDaz...</ds:X509Certificate></ds:X509Data></ds:KeyInfo>
    </KeyDescriptor>
    <SingleSignOnService Binding="urn:oasis:names:tc:SAML:2.0:bindings:HTTP-Redirect"
        Location="https://sso.riversidehealth.example/idp/sso"/>
    <SingleSignOnService Binding="urn:oasis:names:tc:SAML:2.0:bindings:HTTP-POST"
        Location="https://sso.riversidehealth.example/idp/sso"/>
  </IDPSSODescriptor>
</EntityDescriptor>

Three things every SAML metadata document carries: the entity's unique identifier (entityID — not necessarily a reachable URL, just a stable name), its signing (and sometimes encryption) certificate so the other side can validate signatures, and the concrete endpoint URLs for each supported binding. An SP's metadata mirrors this shape with an <SPSSODescriptor>, listing its AssertionConsumerService (ACS) URL — the endpoint the IdP posts the assertion back to.

In Keycloak

A Keycloak realm configured as a SAML Identity Provider publishes its own IdP metadata at a fixed per-realm URL, and the admin console's Identity Providers screen lets you import an external SAML IdP's metadata (or an SP's metadata, when Keycloak is acting as the SP side via a SAML-speaking client) by URL or file upload instead of typing certificate fingerprints by hand. Full hands-on depth, including signature/encryption key configuration, lands in chapter 31 (identity brokering) — Keycloak supports SAML as a broker/IdP protocol, not just OIDC.

Bindings: how a SAML message actually travels over HTTP

SAML itself is protocol-agnostic about transport — the OASIS bindings specification defines several ways to carry a SAML message, but two dominate real-world browser SSO:

HTTP-Redirect vs. HTTP-POST binding
BindingHow the message travelsTypical use
HTTP-RedirectThe SAML message is deflate-compressed, then base64- and URL-encoded, then appended as a query parameter on a 302 redirect URL. Limited by browsers' practical URL-length ceiling.The initial AuthnRequest from SP to IdP — small enough to fit in a URL.
HTTP-POSTThe SAML message is base64-encoded and placed in a hidden form field; the browser receives an auto-submitting HTML form (a <body onload="document.forms[0].submit()"> page) that POSTs it to the destination. No practical size ceiling.The Response carrying the full signed assertion back to the SP — assertions, especially with several attributes and a signature, are routinely too large for a URL.

That size difference is the whole reason the two are paired the way they are: an AuthnRequest is small (little more than "please authenticate this user, here's who I am"), so Redirect is simple and fine; the signed assertion response is not small, so forcing it through a URL would silently break the moment it got too long for a given browser/proxy's limit. POST has no such ceiling, which is why it is the near-universal choice for the assertion leg even though some IdPs also support POST for the request leg.

Pitfall

If you ever see a "URL too long" or a silently truncated redirect in a SAML integration, the cause is almost always someone trying to carry something assertion-sized over the Redirect binding instead of POST — check which binding each leg is actually configured to use before assuming a network or proxy bug.

SP-initiated vs. IdP-initiated flows

A SAML login can start from either side, and which one happened changes what the SP needs to track.

  • SP-initiated — the user visits the SP first (e.g. types the EHR vendor's URL directly). The SP has no session for this user yet, so it builds an AuthnRequest, redirects the browser to the IdP (HTTP-Redirect), the user authenticates (or the IdP recognizes an existing session), and the IdP POSTs a Response containing the assertion back to the SP's ACS URL. This is the more common shape and the one chapter 7's generic SSO diagram already illustrated at a protocol-agnostic level.
  • IdP-initiated — the user starts at the IdP itself (e.g. a hospital intranet portal/app-launcher page listing every connected clinical system) and clicks a link for a specific SP, with no prior AuthnRequest ever sent. The IdP builds an unsolicited Response and POSTs it straight to the SP's ACS URL.
Pitfall

IdP-initiated SSO is inherently harder to protect against replay, because the SP has no AuthnRequest of its own to correlate the Response against (no InResponseTo value to check). A well-implemented SP still enforces Conditions (validity window, audience restriction) and, ideally, a RelayState-based mechanism to know where to send the user next — but if you ever see "IdP-initiated SSO is just inherently less secure," that's not quite right either: it is less self-defending at the protocol level, which is exactly why careful Conditions validation at the SP matters more here than in the SP-initiated case, not why it should be dismissed outright. Many real deployments (app-launcher portals) rely on it.

SAML vs. OIDC: the same ideas, two different wire formats

Chapter 15 built the OIDC vocabulary; the mapping below is worth returning to any time you feel yourself reaching for the wrong term in the wrong protocol's conversation.

SAML 2.0 concepts mapped to their OIDC equivalents
SAML 2.0OIDC equivalentWhat differs
<saml:Assertion>ID TokenBoth say "this is who the user is, asserted by the IdP." SAML's is signed XML; OIDC's ID token is a signed/optionally encrypted JWT (JSON + JWS/JWE, chapter 16).
SAML metadata (EntityDescriptor XML)Discovery document (/.well-known/openid-configuration)Both describe endpoints/capabilities so the other side can self-configure. SAML metadata is XML, usually exchanged once during setup; OIDC discovery is JSON, fetched live over HTTP by the RP.
Service Provider (SP)Relying Party (RP)Same role (chapter 7); different name per protocol.
<saml:AttributeStatement>Claims in the ID token / UserInfo responseBoth carry user attributes. SAML attributes are XML name/value pairs inside the signed assertion; OIDC claims are JSON keys, split between the ID token and the separate UserInfo endpoint.
HTTP-Redirect / HTTP-POST bindingsBrowser redirects carrying query parameters (authorization code, state)Both move protocol messages via browser redirects/form posts; OIDC/OAuth messages are URL-encoded form/query parameters, not an XML envelope.
XML digital signature (<ds:Signature>)JWS (JSON Web Signature)Both prove the issuer signed the content and it wasn't tampered with. XML signing (canonicalization rules, signature wrapping risk) is notoriously fiddlier to implement correctly than JWS's much simpler, more constrained structure — a real factor in why new builds default to OIDC.
Key idea

SAML is not "the deprecated protocol" and OIDC is not "the protocol that replaced it" in the sense of one making the other obsolete — they are two still-live protocol families serving overlapping but not identical needs. SAML's installed base in long-lived enterprise and government federations, certified regulated integrations, and vendors who built their SSO modules a decade-plus ago is large and genuinely not disappearing on any fixed timeline. OIDC is the default choice for new builds, especially anything mobile/SPA-facing, because JSON + JWS is substantially simpler to implement correctly than XML + XML digital signatures. Expect to work with both for the foreseeable future, not to retire one.

Case study — Riverside Health

Riverside Health's hospital-network SSO deployment predates OIDC's dominance by years. Several of its clinical-systems vendors — the EHR platform, a lab-results system, a radiology PACS viewer — integrated with the hospital's identity provider via SAML back when that was the only mature option for enterprise federation, and none of those vendor relationships have had a reason to migrate since: the integrations work, they're validated, and re-certifying a clinical system's authentication pathway is its own regulatory undertaking under HIPAA (chapter 11), not something undertaken casually. Riverside's Keycloak realm (once it's stood up in Part IV) will need to speak SAML fluently as an Identity Provider to these vendors' SPs — this is the realistic, common shape of "legacy protocol support" in IAM work, not a hypothetical.

Why this chapter has no lab

Every prior Part III chapter with a lab (13-15) worked against a real server with nothing heavier than curl and a browser, because OAuth/OIDC messages are URL-encoded parameters and JSON — trivially inspectable and constructible by hand. SAML does not offer that path. A real SAML exchange involves generating or obtaining an XML signing certificate, correctly canonicalizing XML before signing it, building and parsing full EntityDescriptor/Assertion documents, and validating signatures against a trust anchor — none of which curl does, and none of which is reasonably hand-rolled without a real SAML library (and a library-driven exercise would be testing the library's correctness, not teaching SAML's mechanics). Rather than force a lab that would either hide all the real mechanics behind a library or produce a broken, unverifiable toy, this chapter stays conceptual and structural. The genuinely hands-on SAML work in this course happens in chapter 31 (identity brokering), using Keycloak itself as the SAML IdP/SP implementation — at that point there is a real server doing the XML signing and parsing correctly, and the lab is about configuring trust, not hand-building XML.

Common mistakes

  • If you see someone treat SAML as simply obsolete, the cause is overgeneralizing from "OIDC is the default for new builds" to "nobody uses SAML anymore" — a large population of enterprise/government federations and legacy vendor integrations still run it, with no fixed retirement date.
  • If you see an SP accept an assertion after only checking the response arrived over HTTPS from the right-looking URL, the cause is skipping XML signature validation against the IdP's trusted certificate — transport security and assertion-signature validation are not the same check.
  • If you see a "URL too long" failure or a silently truncated SAML message, the cause is almost always carrying an assertion-sized message over the HTTP-Redirect binding instead of HTTP-POST.
  • If you see someone call the relying application in a SAML flow "the RP," the cause is importing OIDC vocabulary where it doesn't belong — SAML's term for that role is SP (chapter 7).
  • If you see an IdP-initiated SSO failure blamed on "there was no request to match," the cause is expecting an InResponseTo correlation that simply doesn't exist for unsolicited Responses — IdP-initiated flows are validated via Conditions (validity window, audience), not request correlation.
  • If you see a reader confuse a SAML <saml:Attribute> with an OIDC "scope," the cause is conflating "what data comes back" (attributes/claims) with "what the client is asking permission for" (scopes) — SAML has no real equivalent of OAuth scopes at all.

Glossary terms introduced here

Takeaways

  • A SAML assertion is a signed XML document with, at minimum, a Subject, Conditions, an AuthnStatement, and often an AttributeStatement — chapter 7's generic "assertion" made concrete.
  • SAML metadata (<EntityDescriptor>) describes an IdP's or SP's entityID, certificates, and binding-specific endpoint URLs — chapter 7's generic "metadata" made concrete.
  • HTTP-Redirect carries small messages (typically the initial AuthnRequest) as URL parameters; HTTP-POST carries larger messages (typically the signed assertion response) via an auto-submitting form, because assertions routinely exceed practical URL length limits.
  • SP-initiated SSO starts with the SP sending an AuthnRequest; IdP-initiated SSO starts with the user at the IdP (e.g. an app-launcher portal) and produces an unsolicited Response with no preceding request to correlate against.
  • SAML's assertion maps conceptually to OIDC's ID token, and SAML metadata maps conceptually to OIDC's discovery document — same jobs, but XML+XML-signatures vs. JSON+JWS as the wire format.
  • SAML is not obsolete: it remains the backbone of many long-lived enterprise and government federations and of vendor integrations built before OIDC's rise, even though OIDC is now the default choice for new builds.
  • Validating a SAML assertion means validating its embedded XML signature against the IdP's trusted certificate, not merely trusting that the response arrived over HTTPS.
  • SP and RP remain the same role under two different protocol names (chapter 7) — SAML always says SP, never RP.
  • This chapter has no lab by design: SAML's XML-signing/parsing/validation requirements are heavier than curl-friendly, and the course's real hands-on SAML work lands in chapter 31 against an actual Keycloak IdP implementation.
