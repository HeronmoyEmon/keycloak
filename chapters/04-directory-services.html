4. Directory Services & Identity Stores

Before any organization buys an IAM product, it almost always already has a directory — a list of employees, their departments, their phone extensions, and the password that gets them onto the corporate network. This chapter is about that older, more boring-sounding layer: what a directory service actually is, the vendor-agnostic LDAP/X.500 vocabulary for talking about it, and Active Directory, the product that holds this data for most of the world's workforces. None of this is Keycloak-specific — it's the thing Keycloak (and every other IAM product) has to connect to, not replace.

Why this matters

An IAM specialist who only knows "modern" IAM — tokens, OAuth, a shiny admin console — will be stuck the first time a client says "our users are already in AD, we're not re-entering ten thousand employees by hand." That sentence comes up constantly in real engagements, and the honest answer is never "migrate everyone" — it's "connect to what's already there." Understanding directory services is what lets you have that conversation competently, and it's the concept that chapter 7 (federation) and chapter 32 (Keycloak's LDAP/AD user federation) exist to put into practice.

What a directory service is, and why it came first

A directory service is a specialized data store optimized for one job: holding records about people, systems, and resources, and answering lookups against them quickly — "who is jane.doe," "what department is she in," "is this the right password for her." It is read-heavy, hierarchically organized, and built for lookups rather than for transactions — closer to a phone book than to a bank ledger. That shape predates the modern IAM product category by decades: once an organization has more than a handful of employees, it needs *some* authoritative list of who they are, independent of any particular application.

Key idea

Directory services aren't a competitor to IAM — they're usually the thing IAM sits on top of. Most organizations already have a directory (frequently Active Directory) holding their workforce before they ever evaluate an IAM product. The IAM system's job is to authenticate and authorize against that existing population, not to become a second, competing copy of it.

LDAP and X.500: the vendor-agnostic vocabulary

X.500 is an ITU-T standard, from the directory-services world of the 1980s, that defines a comprehensive (and heavyweight) model for directories and the protocols to access them. LDAP (Lightweight Directory Access Protocol) is, as its name says, a lighter-weight protocol for accessing directories that follow that same basic data model, running over ordinary TCP/IP instead of X.500's original heavyweight stack. LDAP is the protocol you'll actually encounter in practice — it's what Keycloak speaks in chapter 32, and what most directory products (including Active Directory) expose for interoperability — so the rest of this chapter uses LDAP's vocabulary, inherited from X.500's data model.

A directory organizes its data as a tree, and every record in that tree follows the same basic shape:

Core LDAP/X.500 vocabulary
TermWhat it is
Directory Information Tree (DIT)The hierarchical structure the whole directory is organized into — a tree of entries, typically shaped around an organization's domain and internal structure.
EntryOne record in the tree — a person, a group, a device. Roughly analogous to a row, except entries live in a tree instead of a flat table.
Distinguished Name (DN)The full, unique path to one entry from the root of the tree — the entry's unique address inside the DIT.
Relative Distinguished Name (RDN)The single component of a DN that distinguishes an entry from its siblings under the same parent — the DN is just a chain of RDNs read from the entry up to the root.
objectClassA declaration, on an entry, of what kind of thing it is and which attributes it's allowed or required to carry — e.g. person, organizationalPerson, inetOrgPerson. An entry can have more than one.
AttributeA named value on an entry — cn (common name), mail, telephoneNumber. This is the same general concept chapter 2 introduced (a fact recorded about an identity that isn't itself proof of anything) — a directory attribute is simply that concept's concrete form inside an LDAP entry.

The bind operation: where directories meet authentication

LDAP defines several operations (search, compare, add, modify, delete), but the one that matters most for IAM is bind. Binding means a client connects to the directory and presents a DN and a credential — typically a password — and the directory checks whether that credential is correct for that DN. A simple bind with a DN and password is, functionally, an authentication attempt: the directory is being asked "is this the right password for this entry?" the same question an IAM system asks internally, just phrased in LDAP's own vocabulary. An anonymous bind connects without presenting any credential at all — useful for unauthenticated read-only lookups, and a real security risk if left open on a directory that was never meant to allow it.

Pitfall

A bind succeeding only proves the password was correct for that DN — it says nothing about what that entry is allowed to do. Treating "bind succeeded" as "access granted" conflates authentication and authorization exactly the way chapter 3 warned against; a real system still has to make a separate authorization decision afterward.

Active Directory: the dominant enterprise directory product

Active Directory (AD) is Microsoft's directory product, and it is the directory most workforces actually run on — if an organization has Windows-joined machines, there's a very good chance AD is the authoritative store for its employee population. AD implements the same general directory-service shape described above (it exposes an LDAP interface among others), with its own vocabulary layered on top:

Active Directory vocabulary mapped to generic LDAP concepts
AD termWhat it meansGeneric LDAP equivalent
DomainA security and administrative boundary — a set of users, computers, and policies managed together, identified by a DNS-style name such as riversidehealth.local.Roughly, the root of a DIT for that organization.
Organizational Unit (OU)A container used to group users, computers, or groups within a domain for the purpose of applying policy and delegating administration — e.g. an OU for Clinicians, a separate OU for IT Staff.Analogous to the generic ou entries in an LDAP DIT.
Domain Controller (DC)A server that holds a copy of the domain's directory data and services authentication requests against it.The directory server itself.

One more fact worth knowing and nothing more: AD's native authentication protocol is Kerberos, not a simple LDAP bind — that's how a domain-joined Windows machine actually authenticates a logged-in user behind the scenes. Kerberos is its own ticket-based protocol with real depth (key distribution centers, ticket-granting tickets, mutual authentication), and it is deliberately out of scope for this course — you only need to know it exists and that it's AD's native mechanism, not LDAP bind, so you aren't left wondering later why "AD authentication" and "LDAP bind" aren't quite the same conversation.

Case study — Riverside Health

Riverside Health's entire clinician workforce — doctors, nurses, administrative staff — lives in an on-prem Active Directory that long predates any IAM modernization project. Shift schedules, department assignments, and badge-linked accounts are already there. When Riverside eventually connects Keycloak (chapter 32), the goal is never to copy ten thousand clinicians into a new user store — it's to have Keycloak authenticate against the AD that's already authoritative, so nurses keep using the same credentials they've always had, and HR keeps managing joiners/leavers in the one place it already does.

Case study — Northwind Apps

Northwind Apps also runs an Active Directory — but only for its own internal staff (engineers, support, sales). Its SaaS customers' end users — the thousands of people at hundreds of customer companies who log into Northwind's product — are not in that AD at all. They live in a completely separate CIAM identity store, because they aren't Northwind employees and have no business being managed alongside Northwind's own workforce directory. This is the workforce-directory vs. CIAM-store split in concrete form: same company, two populations, two stores, two very different sets of governance rules.

Why this matters for federation

Put the pieces together and the motivation for two later chapters becomes obvious: an organization almost never wants to migrate an existing directory's population into a separate IAM product — that's slow, risky, and creates two copies of the truth that will drift apart. Instead, the IAM system connects to the directory that's already authoritative. Chapter 7 names this pattern formally as federation; chapter 32 is where you'll configure Keycloak's actual LDAP/AD user federation feature and watch it happen for real.

In Keycloak

Keycloak's User Federation provider lets a realm authenticate against an existing LDAP directory or Active Directory instead of storing passwords itself — Keycloak performs a bind against the directory on the user's behalf. Chapter 32 sets this up end to end, against a real containerized LDAP server, including attribute mapping and sync settings.

Common mistakes

  • If you see someone treat "LDAP" and "Active Directory" as synonyms, the cause is usually not realizing LDAP is a vendor-agnostic protocol and AD is one (very common) product that happens to speak it alongside its own native mechanisms.
  • If you see a successful bind being treated as proof the user is authorized for something, the cause is conflating authentication and authorization again — a bind only proves the password was correct, nothing about permissions.
  • If you see a directory configured to allow anonymous bind in production with no clear reason, the cause is usually a default nobody revisited, not a deliberate security decision.
  • If you see a project plan that includes "migrate all AD users into the new IAM tool," the cause is usually not having considered federation as the alternative — ask why the existing directory can't just be connected to instead.
  • If you see someone expecting a DN to behave like a stable, memorable username, the cause is forgetting that a DN encodes an entry's position in the tree — move the entry (e.g. a different OU) and its DN can change.

Glossary terms introduced here

Takeaways

  • A directory service is a read-optimized store for people/system/resource records, and most organizations have one before they adopt any IAM product.
  • X.500 is the heavyweight 1980s directory standard; LDAP is the lightweight, TCP/IP-based protocol most real directories (including Active Directory) actually speak.
  • A Directory Information Tree (DIT) organizes entries hierarchically; a Distinguished Name (DN) is an entry's full, unique path from the root.
  • An entry's objectClass values declare what kind of thing it is; its attributes are facts about it — the same general Attribute concept from chapter 2, in concrete LDAP form.
  • The bind operation is literally an authentication attempt: a DN plus a credential, checked by the directory — but a successful bind proves nothing about authorization.
  • Active Directory is the dominant enterprise directory product; domains and organizational units (OUs) are its structure for grouping and policy.
  • Kerberos is AD's native authentication protocol for day-to-day login — worth knowing it exists, deliberately out of this course's depth.
  • Federation (chapter 7) and Keycloak's user federation (chapter 32) exist specifically to connect an IAM system to an existing directory instead of migrating its population.
  • Workforce directories and CIAM identity stores are often two completely separate systems inside the same organization, as Northwind Apps illustrates.
