    25. Authentication Flows & Required Actions

    Chapters 20-24 treated "log in to northwind-apps" as a black box: a username, a password, a token. This chapter opens that box. Every Keycloak login runs through an authentication flow — a configurable tree of steps with real requirement levels attached to each one — and that tree is exactly where chapter 5's MFA theory stops being theory. This chapter clones the realm's browser flow and adds a conditional OTP requirement that only challenges Northwind's tenant-admins, using the real Admin REST API, with every command below either actually run and captured or clearly labeled as drawn from Keycloak's current documentation instead.

    Why this matters

    "Just turn on MFA" is not a real configuration task — someone has to decide who gets challenged, when, with which factor, and what happens to everyone else. An IAM specialist who can only toggle a single realm-wide "require OTP" switch will eventually be asked for something more specific — step-up on a sensitive action, a second factor only for administrators, a different rule for brokered logins than for direct ones — and Keycloak's answer to all of that is the same mechanism: authentication flows, their executions, and the four requirement levels those executions can take. This is also the chapter where chapter 23's roles stop being an isolated RBAC exercise and start gating something a real user actually experiences at login time.

    Recall — chapter 5 and chapter 23

    Chapter 5 built OTP from the ground up: a possession factor, a shared secret established once at enrollment, a moving factor (time for TOTP), and — critically — the idea of step-up authentication: an extra factor demanded mid-session or at login, triggered by risk or context rather than applied to every single login on a fixed schedule. It described that decision in the abstract ("a system evaluates signals… and raises or lowers how much proof it demands"). This chapter is where that decision gets a concrete home: a Keycloak conditional subflow, with a real condition attached to it. Chapter 23 created the realm role tenant-admin inside northwind-apps; that role is this chapter's trigger condition, not a hypothetical one — "require OTP for tenant-admins" is the running example built below, start to finish.

    The five built-in flows, one line each

    A new Keycloak realm doesn't start with one flow — it starts with several, each bound to a different purpose, each independently configurable. This chapter's own test realm (a freshly created northwind-apps, confirmed via kcadm.sh get authentication/flows, output below) came with seven top-level flows; five of them map to IAM concepts this course already introduced, plus two Keycloak-specific ones (clients, for client-to-client authentication, and docker auth, for the Docker registry protocol — neither gets further treatment in this course):

    The five built-in flows this chapter cares about (alias as returned by the Admin REST API)
    FlowBound byWhat it governs
    Browser (browser)browserFlow Standard interactive web login — the redirect-to-a-login-page path chapter 13 called the authorization code flow. This chapter's entire lab lives here.
    Direct Grant (direct grant)directGrantFlow API-style, non-interactive login — credentials arrive directly in a token request (chapter 13's resource-owner-password-credentials shape), with no redirect and no login page at all.
    Registration (registration)registrationFlow Self-service account creation via the login page's "Register" link — a different process from logging in, with its own steps (e.g. terms-and-conditions, profile capture).
    Reset Credentials (reset credentials)resetCredentialsFlow The forgot-password / account-recovery path.
    First Broker Login (first broker login)firstBrokerLoginFlow Runs exactly once per user, the very first time they authenticate through a brokered external IdP (chapter 31's subject) — before Keycloak has decided whether to link, create, or reject a local account for them.

    Executions, requirement levels, and conditional subflows

    Each flow is a tree. Every node in that tree — whether a single authenticator (e.g. "Username Password Form") or a nested subflow containing more nodes — is an execution, and every execution carries a requirement level:

    The four requirement levels (not every execution type can take all four — see requirementChoices below)
    LevelMeaning
    REQUIREDMust succeed for the flow to proceed. If several REQUIRED executions sit side by side at the same level, every one of them must pass.
    ALTERNATIVEOne of several acceptable paths at that level — succeeding at any one ALTERNATIVE execution is enough; Keycloak does not demand all of them.
    CONDITIONALOnly for subflows. The subflow (and everything nested inside it) is evaluated at all only if every REQUIRED condition-type execution directly inside it evaluates true first. If any required condition fails, the whole subflow — and its children — is skipped outright, not merely treated as optional.
    DISABLEDNever evaluated, as if the execution weren't configured at all.
    Pitfall — a real one, hit while building this chapter's lab

    A CONDITIONAL subflow's own condition executions are implicitly ANDed when more than one is set to REQUIRED. Leaving Keycloak's default "Condition - user configured" REQUIRED alongside a newly added "Condition - user role" REQUIRED doesn't give you "OTP for tenant-admins" — it gives you "OTP only for tenant-admins who also already have a credential configured," which silently excludes every tenant-admin who hasn't enrolled OTP yet. This chapter's lab disables the old condition explicitly (see the before/after diagram below) rather than leaving both in place.

    Key idea

    The default flow already does something close to "conditional OTP" — it only asks a user for a second factor if they already have one configured. That's a sensible default (it doesn't force brand-new users into OTP mid-login), but it's keyed on enrollment status, not on who the user is. "Challenge every tenant-admin, whether or not they've enrolled yet" needs a different condition entirely — which is exactly what this chapter adds.

    Cloning the browser flow and adding conditional OTP for tenant-admin

    Keycloak will not let you edit a built-in flow's steps directly — every control in the Admin Console is read-only on browser itself, by design, so a known-good default always exists to fall back to. The fix, in the Console or via the API, is the same: duplicate the flow first, then edit the copy. Every step below is a real kcadm.sh call against the Admin REST API, run and captured in this chapter's own test realm.

    1. Copy the browser flow — the Admin REST API's POST /{realm}/authentication/flows/{flowAlias}/copy endpoint, which kcadm.sh create ... /copy wraps:

      docker compose exec keycloak /opt/keycloak/bin/kcadm.sh create authentication/flows/browser/copy \
  -r northwind-apps -s newName="browser - northwind step-up"

    Required actions, revisited at the realm level

    Chapter 22 assigned a required action to one specific user — a one-time task Keycloak forces immediately after an otherwise-successful login, before a session is issued (distinct from a flow execution, which runs during the credential check itself, not after it). This chapter's question is the realm-wide version: which required actions exist, and which ones does every new user get automatically, without an administrator assigning them one by one?

    1. List the realm's required actions (13 exist by default; condensed to the ones this chapter touches):

      docker compose exec keycloak /opt/keycloak/bin/kcadm.sh get authentication/required-actions \
  -r northwind-apps
      { "alias" : "CONFIGURE_TOTP", "name" : "Configure OTP", "enabled" : true,
  "defaultAction" : false, "priority" : 54 }
{ "alias" : "UPDATE_PASSWORD", "name" : "Update Password", "enabled" : true,
  "defaultAction" : false, "priority" : 57 }
{ "alias" : "VERIFY_EMAIL", "name" : "Verify Email", "enabled" : true,
  "defaultAction" : false, "priority" : 50 }

      enabled means the action exists as an option at all in this realm; defaultAction is the separate, realm-wide switch this chapter actually changes.

    2. Flip CONFIGURE_TOTP's defaultAction to true — every newly created northwind-apps user now gets "Configure OTP" added to their own required-actions list automatically, with no per-user step:

      docker compose exec keycloak /opt/keycloak/bin/kcadm.sh update authentication/required-actions/CONFIGURE_TOTP \
  -r northwind-apps -s alias=CONFIGURE_TOTP -s name="Configure OTP" -s providerId=CONFIGURE_TOTP \
  -s enabled=true -s defaultAction=true -s priority=54
      docker compose exec keycloak /opt/keycloak/bin/kcadm.sh get authentication/required-actions/CONFIGURE_TOTP \
  -r northwind-apps
      { "alias" : "CONFIGURE_TOTP", "name" : "Configure OTP", "enabled" : true,
  "defaultAction" : true, "priority" : 54 }

    This pairs naturally with the conditional OTP flow above: the flow change makes OTP mandatory at login for anyone holding tenant-admin; the required-action change makes sure a brand-new user, tenant-admin or not, is actually walked through enrolling OTP the first time they'd otherwise need it, rather than hitting a locked door with no way through.

    Case study: Meridian Trust's step-up, in the vocabulary this chapter just built

    Case study — Meridian Trust

    Meridian Trust is not the realm this chapter actually configured — Northwind Apps is — but its chapter 5 scenario is the clearest motivating reason a bank would ever need a custom flow instead of a flat realm-wide rule. Recall the shape: a routine login and a routine balance check pass with the normal factor set; the moment the same customer initiates a large, first-time, or unusually-sized wire transfer, Meridian's system interrupts the flow and demands an additional factor before the funds move. In the vocabulary this chapter just built, that is a CONDITIONAL subflow gating a second-factor execution — exactly the shape of northwind-apps's new "Browser - Conditional 2FA" subflow, except Meridian's triggering condition would evaluate transaction context (amount, payee history, device) at the moment of a specific action rather than role membership at login time. Keycloak's authenticator SPI (chapter 39-40's territory) is exactly where a bank like Meridian would implement a custom condition provider for that transaction-aware trigger, since conditional-user-role only answers "who is this user," not "what are they about to do." The mechanism — a condition gating an otherwise-ALTERNATIVE factor into REQUIRED — is the same one this chapter actually built for Northwind; only the condition's own logic would differ.

    Common mistakes

    • If you see an admin try to edit browser's steps directly and find every control greyed out, the cause is Keycloak's deliberate read-only protection on built-in flows — duplicate it first, then edit the copy.
    • If you see a cloned, fully customized flow apparently having zero effect on real logins, the cause is almost always forgetting the last step: the realm's browserFlow (or whichever binding applies) still points at the original alias until it's explicitly repointed.
    • If you see a conditional 2FA subflow that "should" require OTP for a specific role but doesn't, the cause is often a leftover REQUIRED condition from the original flow still ANDed in — e.g. an old "Condition - user configured" sitting beside a new "Condition - user role," silently adding "and already enrolled" to the rule.
    • If you see condUserRole set to a role name that looks correct but the condition never fires, the cause may simply be that the role doesn't exist (or isn't assigned to the user being tested) yet — Keycloak stores the string without validating the role exists at config-save time, so a typo or a not-yet-created role fails silently rather than with an error.
    • If you see someone conflate a required action with a flow execution because "they both relate to MFA," the cause is missing the timing difference — a flow execution runs during the credential check itself (and can block a session from ever being issued); a required action runs only after authentication has already otherwise succeeded, as a one-time gate before the session is handed over.

    Takeaways

    • Keycloak ships five built-in flows this course has a reason to care about — Browser, Direct Grant, Registration, Reset Credentials, First Broker Login — each bound to the realm by its own settings field (browserFlow, directGrantFlow, etc.).
    • Every node in a flow is an execution, and every execution carries one of four requirement levels: REQUIRED, ALTERNATIVE, CONDITIONAL (subflows only), or DISABLED.
    • A CONDITIONAL subflow only runs at all if every REQUIRED condition execution directly inside it evaluates true first — and multiple REQUIRED conditions in the same subflow are implicitly ANDed, a real pitfall this chapter's own lab hit and had to fix.
    • northwind-apps's real, default browser flow already ships with a conditional 2FA subflow gated on "has this user already enrolled a credential" — this chapter's lab captured that exact tree live via the Admin REST API before changing anything.
    • Built-in flows cannot be edited in place; the Admin REST API's flow-copy endpoint (and the Console's "Duplicate" action) is the only way to get an editable version, and this chapter actually exercised that endpoint, not just described it.
    • This chapter's conditional-OTP lab added a Condition - user role execution (provider conditional-user-role, configured with condUserRole=tenant-admin) and set OTP Form to REQUIRED beneath it — a real, concrete instance of chapter 5's possession-factor and step-up-authentication concepts, keyed to chapter 23's role.
    • Cloning a flow changes nothing about real logins until the realm's corresponding flow-binding field is explicitly repointed at the clone's alias — a separate, easy-to-forget step.
    • Required actions (chapter 22's per-user assignment) also have a realm-wide defaultAction switch — flipping it for CONFIGURE_TOTP means every newly created user gets OTP enrollment queued automatically, with no per-user step.
    • This chapter is explicit about its verification boundary: every Admin REST API call and its output is real and independently re-read back; the Admin Console's actual screens are described from Keycloak's current documentation, and an actual end-to-end login round trip against the customized flow was not attempted this session.

    Self-check

    Click a question to reveal a model answer. Try answering it yourself first — the point is to check your own reasoning against it, not to read the answer first.

    1. Explain, without looking back at the chapter, why leaving the default "Condition - user configured" REQUIRED alongside a new "Condition - user role" REQUIRED in the same subflow does not produce "OTP for every tenant-admin."

      Model answerMultiple REQUIRED condition executions inside the same CONDITIONAL subflow are implicitly ANDed together, not evaluated independently. "Condition - user configured" only evaluates true for a user who already has a credential (like OTP) enrolled, so leaving it REQUIRED alongside the new role condition actually produces "OTP for tenant-admins who have also already enrolled a credential" — which silently excludes any tenant-admin who hasn't enrolled OTP yet, the opposite of "challenge every tenant-admin." That's exactly why this chapter's lab explicitly set the old condition to DISABLED rather than leaving it in place.

    2. Walk through what would happen, step by step, if you cloned the browser flow, fully reconfigured the copy, but forgot to update the realm's browserFlow setting.

      Model answerThe clone would exist in the realm's authentication flows list, fully configured with the new tenant-admin OTP condition, but it would never actually run against a real login. The realm's browserFlow field would still point at the original, untouched browser alias, so every interactive login would keep executing the old tree — tenant-admins would log in exactly as before, with no new OTP challenge, and nothing in the Console would look obviously broken, which is exactly what makes this mistake easy to miss. Only the explicit "update realms/northwind-apps -s browserFlow=..." rebind step actually switches real logins over to the clone.

    3. Chapter 5 described step-up authentication as a decision triggered by risk/context rather than a fixed schedule. In your own words, map that description onto the specific mechanism (requirement levels + conditions) this chapter actually used to implement it for tenant-admins.

      Model answerChapter 5's "a system evaluates signals and raises or lowers how much proof it demands" becomes, concretely, a CONDITIONAL subflow whose condition execution (here, conditional-user-role checking for tenant-admin) is the signal evaluation, and the OTP Form's requirement level is the "how much proof" dial: for a user who fails the condition, OTP Form is effectively skipped (the subflow never runs), while for a user who passes it, OTP Form is REQUIRED rather than merely ALTERNATIVE. The "risk/context" in this instance is role membership rather than, say, device or transaction risk, but the mechanism — a condition gating a factor from optional to mandatory — is identical to the general pattern chapter 5 described in the abstract.

    4. Why can't Keycloak's built-in conditional-user-role condition implement Meridian Trust's wire-transfer step-up scenario on its own, and what would have to be built instead?

      Model answerconditional-user-role can only answer "does this user hold a given role" — a static fact about identity, evaluated at login time. Meridian's scenario needs a decision based on transaction context at the moment of a specific action (the amount being transferred, whether the payee is new, whether the device is recognized), none of which is a role and none of which is known at login time at all, since the wire transfer happens after the session already exists. Implementing that requires a custom condition provider written against Keycloak's authenticator SPI (chapters 39-40) that evaluates those transaction signals and only then escalates a factor from ALTERNATIVE to effectively REQUIRED for that specific action.

    5. What, specifically, separates a required action from a flow execution — and why does that difference matter for when in the login process each one can act?

      Model answerA flow execution runs during the credential check itself, as part of deciding whether authentication succeeds at all — it can block a session from ever being issued (that's exactly what this chapter's REQUIRED OTP Form does for tenant-admins). A required action runs only after authentication has already otherwise succeeded, as a one-time gate before the session is handed over to the application (e.g. Configure OTP, Update Password). The difference matters because a required action can never prevent a credential check from succeeding — it can only add a mandatory step between "credentials verified" and "session issued" — whereas a flow execution is part of the verification itself.

    6. This chapter admits it did not script an actual login round trip against the customized flow. What was verified instead, and what exactly is still an open gap between that and a real end-user observation?

      Model answerWhat was verified: every Admin REST API create/update call used to build the clone and reconfigure its executions was independently re-read back with a separate GET afterward, confirming Keycloak actually stored each requirement level and config value exactly as intended (Figure 25.3's "after" panel is built entirely from those re-reads, not from the create calls' own success messages). The open gap is that no one actually drove a browser (or scripted an equivalent form submission) through a real login as a tenant-admin test user to directly observe the OTP challenge appear, and as an ordinary user to observe it stay absent — the configuration is confirmed correct in the realm's stored state, but not confirmed correct from a live end-user's observed experience.
