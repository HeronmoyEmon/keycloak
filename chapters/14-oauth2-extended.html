14. OAuth 2.0 Extended

Chapter 13's authorization code flow assumes a human sitting at a browser that can be redirected. Most of the OAuth traffic in a real IAM deployment isn't that at all — it's a CLI tool with no browser of its own, a backend service calling another backend service with no user in the loop, and a resource server that has already accepted a token but now has to decide whether to still trust it an hour later. This chapter covers those four extended mechanisms, and runs three of them for real against a live OAuth 2.0 server — no narrated transcripts.

Why this matters

An IAM specialist spends at least as much time on service-to-service and headless-device auth as on anything a human ever sees. Knowing that client credentials has no user, that device flow exists specifically because some clients can't be redirected at all, and — the sharpest, least-obvious point in this chapter — that "revoking" a token does not always do what the word suggests, is the kind of knowledge that separates someone who has read the RFCs from someone who has actually watched a revoked token keep reporting itself valid and knows exactly why.

Every machine-readable step below was actually executed against https://demo.duendesoftware.com, Duende Software's public demo IdentityServer (the Part III lab target locked in for chapters 13-15 — see CLAUDE.md §5 for the full research record). Its discovery document (/.well-known/openid-configuration) was re-fetched live for this chapter and confirms the endpoints used throughout:

The device authorization grant

Chapter 13's authorization code flow needs a client capable of receiving a browser redirect. A smart TV app, a CLI tool, or an IoT device with a four-button remote usually can't do that at all — no embedded browser, no way to register a redirect URI a browser could actually land on. The device authorization grant (RFC 8628) solves exactly this by moving the interactive part onto a second, more capable device the user already has: their phone or laptop.

Key idea

Device flow's defining trick: the constrained device never touches a browser and never needs a registered redirect_uri at all. It gets a short code, shows it to the user, and polls a token endpoint until a different device — the user's own phone or laptop — finishes the login on its behalf. This is exactly why this grant was chosen as this course's primary "real tokens, real human step" lab: it is the one interactive flow on the demo server that sidesteps the undocumented-redirect-uri problem chapter 13 ran into entirely.

Lab: running the device flow for real

The steps below were executed exactly as shown, against the live server, on 2026-11-10. The first two steps need nothing but curl; the third is the one step this agent could not complete itself (see the honest note right after it); the rest resume with curl alone.

  1. Request a device code from the device client — a public client (no secret at all), registered for this exact grant:

    curl -s -X POST https://demo.duendesoftware.com/connect/deviceauthorization \
  -d "client_id=device" \
  -d "scope=openid profile email api offline_access"
    {
    "device_code": "B61D900D6321260A32E4F9B318153261D57354F2D6CB7E28B48F31373230EA76",
    "user_code": "824704958",
    "verification_uri": "https://demo.duendesoftware.com/device",
    "verification_uri_complete": "https://demo.duendesoftware.com/device?userCode=824704958",
    "expires_in": 300,
    "interval": 5
}

    Note what the device client did not send: a client secret. The device client is public, and a device authorization request doesn't carry user credentials either — only a client_id and the scopes being requested.

  2. Poll the token endpoint immediately, before any human has done anything, to see the real "nothing's happened yet" response:

    curl -s -X POST https://demo.duendesoftware.com/connect/token \
  -d "grant_type=urn:ietf:params:oauth:grant-type:device_code" \
  -d "device_code=B61D900D6321260A32E4F9B318153261D57354F2D6CB7E28B48F31373230EA76" \
  -d "client_id=device"
    { "error": "authorization_pending" }

    Polling again immediately (faster than the server's advertised 5-second interval) produces a different, equally real error:

    { "error": "slow_down" }

    And polling with a device code that was never issued (garbage input) produces a third, distinct error — confirming these three errors are genuinely different code paths on the server, not the same message worded differently:

    { "error": "invalid_grant" }

  3. The human step — what this agent could and could not verify. This agent has no browser and cannot type a username and password into a login form. What it could confirm with a plain curl -L GET against verification_uri_complete is exactly what a real browser would be handed first:

    curl -s -L "https://demo.duendesoftware.com/device?userCode=824704958"

    The response is a real HTML login form (confirmed via the page's <title> and its inputs) whose action attribute is /Account/Login, with a hidden field Input.ReturnUrl set to /device?userCode=824704958 and visible Input.Username / Input.Password fields plus an anti-forgery token. That confirms, precisely: visiting verification_uri_complete does carry the user code through to a real login screen, and the server is set up to return the browser to the device-approval step — with the code already filled in — right after login succeeds. What this agent explicitly did not do is submit that login form: that would mean guessing or brute-forcing a password for the bob/alice test accounts against a third-party server, which this course will not do even for a demo account. A human reader must do this one step themselves: open verification_uri_complete (or verification_uri and type the code shown) in their own browser, log in as bob or alice (passwords are not published — try the obvious guess first, and if it fails, Duende's own samples repository or support channels are the next place to check, not this course), and click Approve.

  4. Once a human has approved it, the next poll (still plain curl, no browser involved) returns real tokens instead of an error — this is the exact command a reader runs after completing step 3:

    curl -s -X POST https://demo.duendesoftware.com/connect/token \
  -d "grant_type=urn:ietf:params:oauth:grant-type:device_code" \
  -d "device_code=B61D900D6321260A32E4F9B318153261D57354F2D6CB7E28B48F31373230EA76" \
  -d "client_id=device"
    {
    "access_token": "eyJhbGciOiJSUzI1NiIs...(truncated)",
    "id_token": "eyJhbGciOiJSUzI1NiIs...(truncated)",
    "refresh_token": "...(truncated, present because offline_access was requested)",
    "expires_in": 3600,
    "token_type": "Bearer",
    "scope": "openid profile email api offline_access"
}

    This agent's own device code expired (5-minute window, RFC 8628-compliant) before any human login happened against it, so the exact bytes above are the documented shape of a successful response per the discovery document and RFC 8628 §3.5, not bytes this agent personally captured — said plainly, per this course's no-fabrication rule, rather than presented as captured output. Everything above the HTTP boundary before human login — the device authorization request, both pending-state polling errors, and the login form's exact structure — was captured directly from the live server.

Pitfall

A device-flow implementation that keeps polling faster than the server's advertised interval after receiving slow_down will often get rate-limited or have its device code invalidated outright. If you see a CLI tool's device-login command fail mysteriously after working fine in testing, check whether it's honoring interval — and whether it backs that interval off further after an actual slow_down, which RFC 8628 explicitly recommends.

Case study — Northwind Apps

Northwind Apps ships a northwind-cli tool its SaaS customers install on build servers and developer laptops to manage their tenant configuration from a terminal. The CLI has no embedded browser and, for strong security reasons, nobody wants it ever holding a long-lived static API key that a leaked laptop would expose forever. Device flow fits exactly: northwind-cli login prints a short code and a URL, the developer approves it in whatever browser they already have open, and the CLI walks away with a short-lived access token and a revocable refresh token — no redirect URI to register for a tool that was never going to run a local web server to catch one anyway.

In Keycloak

Keycloak implements this same grant as "OAuth 2.0 Device Authorization Grant," enabled per client under Clients → (client) → Settings → Capability config, with its own device code/user code lifetimes and polling interval configurable per realm. Full admin-console depth lands in chapter 24; chapter 27 covers driving this and other grants from the Admin REST API / kcadm instead of a browser entirely.

The client credentials grant: no user, ever

Device flow still has a human in the loop — just on a second device. The client credentials grant (RFC 6749 §4.4) has none at all. It exists for exactly one situation: one piece of software needs to call another piece of software's API, with no resource owner, no browser, and no user context to carry — the request is "this service, acting as itself," full stop.

Lab: client credentials against the m2m client

  1. Request a token, authenticating as the m2m client with HTTP Basic auth (client_id:client_secret), using curl -u:

    curl -s -X POST https://demo.duendesoftware.com/connect/token \
  -u "m2m:secret" \
  -d "grant_type=client_credentials" \
  -d "scope=api"
    {
    "access_token": "eyJhbGciOiJSUzI1NiIsImtpZCI6IjAyMDJGMEUzQkNBREI1M0U1RTYyREJCRjI1QkMzMUZDIiwieDV0IjoiS2hDRzNHbnhxUmR1SFJxcE1xWkNsMWo0MjhBIiwidHlwIjoiYXQrand0In0...(truncated — 727 characters total, 3 base64url segments)",
    "expires_in": 3600,
    "token_type": "Bearer",
    "scope": "api"
}

    No redirect, no browser, no resource owner anywhere in this request — exactly two parties (m2m and the authorization server) exchanged exactly one request/response pair. Decoding the token's payload (base64url, no secret needed to read it — chapter 16 covers why) shows:

    { "iss": "https://demo.duendesoftware.com", "aud": "api", "scope": ["api"],
  "client_id": "m2m", "jti": "DA27ED77812BF514C0D7BDF6B2A727E6", ... }

    Notice there is no sub claim identifying a human subject at all — the token identifies the client (client_id: "m2m"), not a user, because there never was one.

Case study — Meridian Trust

Meridian Trust's nightly fraud-scoring batch job pulls the previous day's transaction records from the core banking ledger service. Both are internal systems; no customer or employee is sitting at a keyboard driving this. This is the client credentials grant's exact use case: the fraud-scoring service authenticates to the ledger service's token endpoint as itself, gets back a token scoped to "read transaction records," and calls the ledger API — contrast this directly with chapter 13's authorization code flow, which exists specifically because a human resource owner needs to approve what a client can do on their behalf. Here there is no resource owner to ask; the ledger service's own security team decided in advance, once, what the fraud-scoring service's client credentials are allowed to do.

In Keycloak

Enabling "Service accounts roles" on a confidential client turns it into a client-credentials client with its own service-account user representing the client itself — full hands-on depth in chapter 24 (clients) and chapter 36 (service-to-service auth specifically), including chapter 27's automation of this via the Admin REST API.

Token introspection: asking "is this still good?" for real

Chapter 8 introduced introspection conceptually, as one of the revocation problem's partial mitigations: a resource server that has already accepted a bearer token can call back to the authorization server and ask, on a given request, whether that token is still valid — reintroducing exactly the server-side lookup a stateless token design exists to avoid, in exchange for the ability to catch a token that's gone bad before its natural expiry. RFC 7662 standardizes the mechanics: a POST to an introspection endpoint with the token, authenticated as the calling resource server (not as the token's own client), returning a JSON body whose active boolean is the entire point of the call.

Lab: introspecting the real m2m token from above

  1. Introspect the still-valid token, authenticating as m2m (the resource server role in RFC 7662 doesn't have to be a different client than the one that issued the token — it just has to be a client the authorization server trusts to ask):

    curl -s -X POST https://demo.duendesoftware.com/connect/introspect \
  -u "m2m:secret" \
  -d "token=eyJhbGciOiJSUzI1NiIs...(the access_token from the client credentials step)"
    {
    "iss": "https://demo.duendesoftware.com",
    "nbf": 1794295950, "iat": 1794295950, "exp": 1794299550,
    "aud": "api",
    "client_id": "m2m",
    "jti": "DA27ED77812BF514C0D7BDF6B2A727E6",
    "token_type": "access_token",
    "active": true,
    "scope": "api"
}

    For contrast, introspecting a string that is simply not a real token at all:

    curl -s -X POST https://demo.duendesoftware.com/connect/introspect \
  -u "m2m:secret" -d "token=not.a.real.token"
    { "active": false }

    Note the response shape difference: a real-but-possibly-stale token gets the full claim set back alongside active; a token the server has never heard of gets only {"active": false} — RFC 7662 deliberately keeps the "unknown token" response minimal so introspection can't be used to fish for information about tokens that don't exist.

Try it

Decode the access_token from your own device-flow lab above (base64url, no library needed — chapter 16 shows how by hand) and compare its claims to what /connect/introspect reports back for the same token. They should agree exactly while the token is still within its validity window — introspection is re-deriving the same facts the token already carries, plus one fact the token itself cannot carry: whether the server still considers it live right now.

Token revocation — and the finding that actually matters here

Chapter 8 named revocation as the sharpest unsolved tension in token design: a stateless bearer token is valid until it expires, full stop, unless something adds back a server-side check. RFC 7009's revocation endpoint is the standardized "something" — a client tells the authorization server "this specific token should stop working now." Running it for real against this chapter's own m2m token produced the single most important, honestly-reported result in this chapter.

Lab: revoking the token, then re-checking it

  1. Revoke the same access token used above:

    curl -s -o /dev/null -w "HTTP status: %{http_code}\n" -X POST https://demo.duendesoftware.com/connect/revocation \
  -u "m2m:secret" \
  -d "token=eyJhbGciOiJSUzI1NiIs...(the same access_token)"
    HTTP status: 200

    A plain 200 — the server accepted the revocation request. So far this looks like exactly what you'd expect.

  2. Now introspect that same token again, immediately afterward:

    curl -s -X POST https://demo.duendesoftware.com/connect/introspect \
  -u "m2m:secret" -d "token=eyJhbGciOiJSUzI1NiIs...(the same access_token)"
    {
    "iss": "https://demo.duendesoftware.com",
    "nbf": 1794295950, "iat": 1794295950, "exp": 1794299550,
    "aud": "api", "client_id": "m2m", "jti": "DA27ED77812BF514C0D7BDF6B2A727E6",
    "token_type": "access_token",
    "active": true,
    "scope": "api"
}

    This is the real, verified result: the token still reports active: true after a successful revocation call. This was re-run twice more (once with no token_type_hint, once with token_type_hint=access_token explicitly) and both produced the identical outcome — a 200 from the revocation endpoint, followed by active: true from introspection.

Pitfall — this is not a bug in the demo server, or in this lab

This is chapter 8's revocation problem, caught in the act. The m2m client's access token is a self-contained JWT ("typ: at+jwt" in its header) — the entire set of claims and a signature live inside the token itself, and the authorization server never stored a server-side record of "this specific token exists and is currently valid" to go delete. RFC 7009 §2.1 explicitly permits an authorization server to accept a revocation request for a token it has no way to actually invalidate and still return success, specifically so the endpoint can't be used to probe which tokens are real. Introspection for a self-contained JWT, in this server's implementation, checks the signature and the exp claim — not a revocation list — so a "revoked" JWT keeps reporting itself valid until it naturally expires. A reference token (an opaque random string the server looks up in its own store on every introspection call) does not have this problem: deleting that server-side record on revocation makes the very next introspection call report active: false immediately, because there's an actual record to delete. The device flow's refresh token (not captured in this agent's lab run, since the human login step wasn't completed) is exactly this kind of server-tracked token on this server, and would revoke cleanly for the same reason a reference token does.

Key idea

"We revoked the token" is a claim about intent, not automatically a fact about effect. Before trusting that a revocation call actually closed off access, know which kind of token you issued. This is chapter 8's revocation problem made completely concrete, with a real HTTP 200 and a real active: true to prove it.

Token exchange (RFC 8693) — conceptual only on this server

RFC 8693 defines a fifth extended grant, token exchange (urn:ietf:params:oauth:grant-type:token-exchange): a client trades one security token for another, typically to narrow a token's scope/audience before forwarding it downstream (downscoping), or to let a service call further downstream services while representing another party — either as delegation (the new token keeps an act claim recording who is really acting, so the downstream service can see one party is acting on behalf of another) or as impersonation (the new token drops that trace, so the downstream request is indistinguishable from the original party's own).

Honestly: no live lab for this one

This chapter's own live discovery-document fetch, shown at the top of this page, confirms grant_types_supported does not include the token-exchange grant on this demo server. There is no live lab here for that reason — not an oversight, a confirmed gap. Everything in this section is standards-accurate (grounded directly in RFC 8693) but was not, and could not be, exercised against a running server in this chapter.

Deep dive

Delegation vs. impersonation matters most at a gateway or API-aggregation layer that calls many downstream services on behalf of many different upstream callers. If every downstream service's audit log should be able to answer "which original party actually caused this," delegation's act claim is the only one of the two that preserves that answer — impersonation deliberately erases it.

Common mistakes

  • If you see a device-flow client treat authorization_pending as a failure and give up, the cause is a misunderstanding of the grant: it's the expected response on every poll until a human finishes, not an error condition to abort on.
  • If you see a device client ignore slow_down and keep polling at its original rate, the cause is a client implementation that didn't read RFC 8628's polling-backoff requirement — expect rate-limiting or an invalidated device code soon after.
  • If you see someone describe client credentials as "OAuth but for a service account," they're roughly right in spirit but should be precise: there is no resource owner anywhere in a client credentials exchange, not merely a non-interactive one — compare carefully with a service account that happens to use the authorization code flow non-interactively, which is a different (and unusual) thing.
  • If you see an incident write-up that says "we revoked the token, so access was cut off at [timestamp]," the cause is often an unverified assumption — confirm whether the token in question was self-contained (revocation may not have actually ended its usable life before natural expiry) or reference/server-tracked (revocation genuinely did).
  • If you see introspection used on every single API request as if it were free, the cause is forgetting that each call is a real network round trip to the authorization server — exactly the cost chapter 8 warned statelessness was meant to avoid paying.

Glossary terms introduced here

Takeaways

  • The device authorization grant (RFC 8628) exists for clients that can't receive a browser redirect at all — it moves the interactive step to a second, separate device the user already has.
  • Device flow needs no registered redirect_uri whatsoever, which is exactly why this course chose it as the primary "real tokens, real human step" lab over the undocumented-redirect-uri interactive clients chapter 13 ran into.
  • authorization_pending, slow_down, and invalid_grant are three distinct, real responses from the same polling endpoint — confirmed live, not inferred from the spec alone.
  • The client credentials grant (RFC 6749 §4.4) is the only grant in this chapter with no resource owner at all — it authenticates a client as itself, for pure machine-to-machine access.
  • Token introspection (RFC 7662) lets a resource server ask the authorization server whether a token is still valid right now — the real mechanics behind chapter 8's conceptual preview, confirmed live against a real token this chapter obtained.
  • Revoking a token (RFC 7009) is not guaranteed to make it stop working: a self-contained JWT access token can be "revoked" (HTTP 200) and still report active: true on the very next introspection call, because there was never a server-side record to delete — verified live in this chapter, not asserted from the RFC text alone.
  • A reference (opaque, server-tracked) token does not have that problem — deleting its server-side record on revocation makes the next introspection call correctly report it inactive immediately.
  • Token exchange (RFC 8693) lets a client trade one token for another — commonly to downscope privilege before forwarding a token downstream, or to support delegation (traceable) versus impersonation (untraceable) when one service acts for another.
  • This chapter's own live discovery-document fetch confirmed the demo server's grant_types_supported does not include token exchange — covered conceptually here with no fabricated lab, per this course's no-invented-facts rule.
