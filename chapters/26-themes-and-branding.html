26. Themes, Branding & Localization

This is the last chapter in the northwind-apps realm build arc that began in chapter 20. Settings, users, roles/groups, clients, and auth flows are all in place; the one thing left is what the realm's screens actually look like, and in which languages. This chapter does that honestly: it confirms, for real against a running Keycloak, exactly which built-in themes this image ships and how a realm's theme assignment is stored and read back — and it is explicit about the one thing a text-only session genuinely cannot do, which is look at a rendered page.

Why this matters

A login screen is the first and most frequently seen surface of an entire IAM program, and for a CIAM product like Northwind's, it is also a conversion surface — chapter 12 already flagged "login-page branding/conversion impact" as one of the things that distinguishes CIAM buying decisions from workforce IAM ones. An IAM specialist is routinely asked to make a login page look like the product, support the languages a customer base actually uses, and do both without forking vendor code or breaking on the next upgrade. Keycloak's theme system is the mechanism for that. Getting it wrong usually looks like either a half-styled login page after a botched override, or a theme name typed into a realm setting that quietly does nothing because nothing by that name actually exists on disk — both are cheap mistakes to make and cheap to avoid once you know how the mechanism is actually checked (or isn't).

What concept is this?

Chapter 12 named branding/conversion and localization reach as real, buyer-relevant differentiators between CIAM and workforce IAM products — this chapter is where that stops being a market-landscape bullet point and becomes a realm setting you can read back with kcadm.sh. The underlying IAM concept is extensibility (chapter 1 defined it generically as customizing a vendor system "via a defined plugin interface rather than forking the product's source code") applied to the presentation layer specifically: a theme is a plugin that swaps what the IdP's screens look like and which languages they speak, without touching Keycloak's own code. Chapter 8's and chapter 2's identity lifecycle also resurfaces here in miniature — a theme and a locale are both just attributes of a realm, read at request time, exactly like a user attribute is read at authentication time.

Theme types: which screens each one covers

Keycloak's own current Server Administration Guide (fetched live for this chapter) names four theme categories a realm configures independently, each on its own tab under Realm settings → Themes:

The four realm-level theme settings, per Keycloak's own documentation
SettingREST fieldCovers
Login themeloginTheme"Username password entry, OTP entry, new user registration, and other similar screens related to login" — the pages this course's labs have been hitting since chapter 20.
Account themeaccountTheme"The console used by the user to manage his or her account" — self-service password/MFA/session management, chapter 1's "self-service" concept made concrete.
Admin console themeadminThemeThe skin of the Keycloak Admin Console itself — the tool every lab in this course has been described as using.
Email themeemailThemeTemplates for every email Keycloak sends (verification, password reset, OTP codes).

A fifth type, the welcome theme, exists too, but it is configured differently: it is an instance-wide default page (what you see hitting http://localhost:8080/ with no realm in the URL at all), set via a server startup option (--spi-theme--welcome-theme=<name>), not a per-realm REST field — this chapter's labs only touch the four realm-level fields above.

Assigning a theme at the realm level, confirmed live

Before setting anything, this chapter's lab asked what themes actually exist on this Keycloak 26.8.2 image, rather than assuming names from memory or from an older Keycloak version's docs. Keycloak 26.x does not ship themes as a plain directory tree you can ls directly — the built-in themes are bundled inside JARs, and /opt/keycloak/themes/ only contains a README.md pointing you at them:

  1. Listing /opt/keycloak/themes/ inside the running container confirms this directly:

    docker compose exec keycloak ls /opt/keycloak/themes/
    README.md

    The README itself says exactly why: "Built-in templates ... can be found within the theme directory of ../lib/lib/main/org.keycloak.keycloak-themes-26.8.2.jar, which can be opened using any standard ZIP archive tool," and explicitly warns "Built-in themes should not be modified directly, instead a custom theme should be created."

  2. The container has no unzip binary, so this chapter copied the jar out to the host with docker compose cp and inspected it with Python's standard-library zipfile module instead of guessing. The real, confirmed top-level theme names in this exact image are:

    Top-level theme names: ['base', 'keycloak', 'keycloak.v2']
base        -> ['account', 'admin', 'email', 'login']
keycloak    -> ['common', 'email', 'login', 'welcome']
keycloak.v2 -> ['login']

    Three real names, not an invented fourth: base (the shared foundation every other theme extends — its own login/theme.properties sets abstract=true, meaning Keycloak's realm Themes dropdown hides it from direct selection, a courtesy the REST API does not enforce, as the pitfall below shows), keycloak (the older PatternFly v3/v4 "classic" theme — still fully present, with login, email, and welcome types), and keycloak.v2 (the newer PatternFly v5 theme, with darkMode=true in its properties, but only a login type — see the pitfall on Account/Admin Console theming below for why).

  3. With a real theme name confirmed to exist, set it on northwind-apps:

    docker compose exec keycloak /opt/keycloak/bin/kcadm.sh update realms/northwind-apps -s loginTheme=keycloak

    Then confirm it actually persisted, independently of the update command's own silence (no output on success is itself something worth confirming, not assuming):

    docker compose exec keycloak /opt/keycloak/bin/kcadm.sh get realms/northwind-apps --fields loginTheme
    {
  "loginTheme" : "keycloak"
}

    Before this command ran, the same get call against loginTheme returned nothing for that field at all — kcadm.sh's --fields output simply omits a field that is unset, which is itself a useful thing to know when reading these responses: an absent key means null, not an empty string.

Pitfall — the REST API does not validate that a theme name is sane

This chapter also set accountTheme=base and adminTheme=base on northwind-apps via kcadm.sh, specifically to test a question the docs don't answer directly: does the Admin REST API check that the name you give it is a real, renderable theme for that type? It does not. Both writes succeeded and both read back exactly as set:

{
  "loginTheme" : "keycloak",
  "accountTheme" : "base",
  "adminTheme" : "base",
  "emailTheme" : "keycloak"
}

base is marked abstract=true specifically so the Admin Console's own Themes-tab dropdown won't offer it as a selectable option — but that is a UI-level courtesy, not a server-side constraint, and kcadm.sh/the REST API go around it entirely. If you see a realm with a theme field set to a name that doesn't resolve to anything sensible at render time, the cause is very often exactly this: someone (or some automation) wrote the field directly through the REST API or kcadm.sh rather than through the Console's dropdown, and nothing on the write path caught the mistake. This also means a typo in an Infrastructure-as-Code theme name (Terraform, Ansible, a CI script) will silently "succeed" and only surface the next time someone actually looks at the rendered page.

How a real custom theme is actually built

Nothing above created a new theme — it assigned one of the three that already ship with this image. Building Northwind's own branded theme is a different, larger task this chapter did not attempt to fabricate: it requires creating a real themes/<name>/<type>/ directory structure with override files, and this course has no way to render the result without a browser to confirm it actually looks right. What follows is the real mechanism, confirmed by inspecting the shipped themes' own files directly (not guessed), plus Keycloak's official UI Customization Guide — Working with themes (fetched live for this chapter) for the complete how-to.

Reading keycloak/login/theme.properties and keycloak.v2/login/theme.properties directly out of the jar shows the real inheritance mechanism in practice, not paraphrased:

Real theme.properties contents read directly from this image's built-in themes jar
ThemeKey lines
base/loginlocales=ar,az,ca,...,zh-TW (the full supported-locale list)
abstract=true
keycloak/loginparent=base
import=common/keycloak
styles=css/login.css (PatternFly v3/v4)
keycloak.v2/loginparent=base
import=common/keycloak
darkMode=true (PatternFly v5)

A custom theme follows the identical pattern: a new directory (say, themes/northwind/login/) with its own theme.properties declaring parent=keycloak or parent=base to inherit everything it doesn't explicitly override, a resources/ folder (css/, js/, img/) for Northwind's logo and stylesheet, a messages/ folder of messages_<locale>.properties files for translated text, and, only where the default markup itself needs to change (not just its styling), an FTL template override such as login/login.ftl placed at that exact path to shadow the parent theme's own template of the same name. The official guide's own development workflow is to start Keycloak with theme/template caching explicitly disabled (--spi-theme--cache-themes=false --spi-theme--cache-templates=false, or rely on start-dev's equivalent built-in behavior) so edits show up on refresh, then re-enable caching for production since disabling it "will significantly impact performance" per the guide's own words.

Key idea — what this chapter can and cannot claim

This chapter can honestly claim: the three bundled theme names are real (confirmed by inspecting the actual jar, not recalled from memory); setting loginTheme/accountTheme/ adminTheme/emailTheme on northwind-apps genuinely persists (confirmed by an independent read-back, the same discipline chapter 20 used for realm creation); the parent=/import=/abstract= mechanism is real (confirmed by reading the shipped themes' own property files). It cannot claim: that northwind-apps's login page now visually looks like Keycloak's classic theme, or any particular rendered appearance at all — no browser tool exists in this environment, and claiming a visual result without one would break this course's own "no invented facts" rule as surely as inventing an RFC number would.

Internationalization, confirmed live

Separately from which theme a realm uses, a realm also controls which languages its theme renders in. Per the Server Administration Guide: Realm Settings → Localization is where an administrator enables internationalization and picks supported languages, and — already true before this chapter touched anything — "every UI screen is internationalized in Keycloak," with English as the default.

  1. Before any change, internationalizationEnabled on a fresh realm defaults to false (confirmed, not assumed):

    docker compose exec keycloak /opt/keycloak/bin/kcadm.sh get realms/northwind-apps \
  --fields loginTheme,accountTheme,adminTheme,emailTheme,internationalizationEnabled,supportedLocales,defaultLocale
    {
  "internationalizationEnabled" : false
}

    Every other field in that call is simply absent from the response, confirming none of them are set yet either.

  2. Enable it and declare supported locales and a default, all in one kcadm.sh call:

    docker compose exec keycloak /opt/keycloak/bin/kcadm.sh update realms/northwind-apps \
  -s internationalizationEnabled=true \
  -s 'supportedLocales=["en","de","fr","es"]' \
  -s defaultLocale=en

    Confirmed with an independent read:

    docker compose exec keycloak /opt/keycloak/bin/kcadm.sh get realms/northwind-apps \
  --fields internationalizationEnabled,supportedLocales,defaultLocale
    {
  "internationalizationEnabled" : true,
  "supportedLocales" : [ "de", "en", "fr", "es" ],
  "defaultLocale" : "en"
}

    Note the order in the response (de, en, fr, es) does not match the order submitted (en, de, fr, es) — supportedLocales is stored as an unordered set server-side, not a sequence, so nothing about ordering is load-bearing for which locales are actually supported.

Each supported locale still needs an actual translation to render correctly — the base theme's own theme.properties lists dozens of locale codes it ships message bundles for out of the box (ar,az,ca,cs,da,de,el,en,es,...,zh-TW, confirmed by reading that exact file, rather than assumed from a features list), so de, fr, and es above all have real built-in translations already. A genuinely new language not already in that list would need its own messages_<locale>.properties file added to a custom theme — declaring a locale as "supported" on the realm and actually having strings for it are two different things, and only the REST API enforces neither against the other, same as the theme-name pitfall above.

Case study: Northwind Apps' branding decision

Case study — Northwind Apps

Northwind Apps sells to other businesses, but its actual end users — the people typing a password into northwind-apps's login screen — are often each customer company's own employees, not Northwind's. Chapter 12 named exactly this tension as a CIAM-adjacent concern even inside a B2B product: login-page branding affects trust and conversion, and a customer's IT security reviewer is unlikely to be reassured by a login page that visibly still says "keycloak" at the bottom. A real Northwind theming project would create its own themes/northwind-login/login/ override (parent keycloak.v2, Northwind's logo and color palette in resources/, no FTL changes needed unless the form layout itself must change) and set loginTheme=northwind-login — the exact mechanism this chapter verified using the stock keycloak name instead, because building and visually checking that real asset is outside what a no-browser session can honestly claim to have done. The internationalization piece is not hypothetical, though: Northwind's own customer base plausibly spans English, German, French, and Spanish-speaking companies, which is exactly the locale set this chapter actually enabled on the realm.

Common mistakes

  • If you see someone try to ls a Keycloak 26.x container's /opt/keycloak/themes/ expecting to browse the built-in themes directly, the cause is assuming an older Keycloak layout — in this version only a README.md lives there, and the real built-in theme files are inside a JAR that has to be opened with a zip tool, not ls.
  • If you see a realm's theme field set to a name that doesn't actually render anything sensible, the cause is very often a direct REST/kcadm.sh write that skipped the Admin Console's dropdown — the REST API does not validate that the name resolves to a real theme directory for that type.
  • If you see someone set adminTheme or accountTheme to base expecting a visible result, the cause is forgetting base is marked abstract=true specifically because it is meant only to be inherited from, not used directly — the write succeeds but is not a sane configuration.
  • If you see a reader declare a locale in supportedLocales and assume it's now fully translated, the cause is conflating "listed as supported" with "has a messages_<locale>.properties file" — the realm setting and the actual translation coverage are two independent things, and nothing on the write path checks one against the other.
  • If you see a custom theme's CSS silently stop applying after it's set as a realm's loginTheme in production, a common cause is theme/template caching (disabled under start-dev, enabled by default under production start) serving a stale cached copy — the fix per the official guide is either a server restart, disabling caching during active development with the documented SPI options, or clearing data/tmp/kc-gzip-cache.
  • If you see someone look for a welcomeTheme field on the realm's REST representation next to loginTheme/accountTheme/adminTheme/emailTheme, the cause is assuming all five theme types are configured the same way — the welcome theme is an instance-wide server startup option, not a per-realm field at all.

Glossary terms introduced here

Takeaways

  • Keycloak 26.x ships its built-in themes inside a JAR (org.keycloak.keycloak-themes-26.8.2.jar), not as a browsable directory tree — /opt/keycloak/themes/ only contains a README.md explaining this.
  • The three real bundled theme names confirmed by inspecting that jar directly are base (abstract, inherited-from only), keycloak (the classic PatternFly v3/v4 theme, with login, email, and welcome types), and keycloak.v2 (the modern PatternFly v5 theme with darkMode=true, login type only in this image).
  • A realm's four theme fields — loginTheme, accountTheme, adminTheme, emailTheme — were each set on northwind-apps via kcadm.sh update and confirmed with an independent kcadm.sh get call, the same two-command discipline chapter 20 used for realm creation.
  • The Admin REST API does not validate that a theme name resolves to anything real or sane for its type — setting adminTheme=base (an abstract, inherit-only theme) succeeded and persisted exactly like setting it to a genuinely usable name would.
  • A real custom theme is built as themes/<name>/<type>/ with its own theme.properties (declaring parent= and optionally import=), a resources/ folder, a messages/ folder of locale-specific .properties files, and FTL template overrides only where markup, not just styling, needs to change — confirmed by reading the real theme.properties files of the shipped themes, not paraphrased from memory.
  • This chapter did not build or visually verify a custom "Northwind" theme — no browser tool exists in this environment, so the lab instead verified the real, checkable part of the mechanism (listing real bundled names, assigning one, confirming persistence) using a genuine built-in theme name.
  • internationalizationEnabled defaults to false on a fresh realm; enabling it plus setting supportedLocales and defaultLocale was confirmed live, the same way the theme fields were.
  • Keycloak's documented locale resolution order checks, in sequence: user-selected, user-profile locale, a client-requested locale (e.g. OIDC's ui_locales), a cookie, the browser's Accept-Language header, the realm's defaultLocale, and finally English — a custom LocaleSelectorProvider SPI can replace this order entirely.
  • Declaring a locale as supported on a realm and that locale actually having translated message bundles are two independent facts; nothing on the write path checks one against the other, exactly like the theme-name validation gap above.
  • This chapter closes the northwind-apps realm build arc begun in chapter 20: settings, users, roles/groups, clients with a custom claim mapper, a conditional-OTP auth flow, and now theming and localization, every one of them created and independently re-confirmed against a real running Keycloak rather than narrated.
