    8. Tokens & Sessions, Conceptually

    Once a principal authenticates, the system needs some way to remember "this request belongs to that already-proven identity" on every subsequent request, without asking for a password again each time. There are really only two shapes that memory can take — a token or a session — and almost every argument you will ever have about authentication architecture is secretly an argument about which of those two shapes to use, and what that choice costs you later.

    Why this matters

    An IAM specialist is routinely asked to explain why "we can't just revoke that token right now" or why a mobile app stays logged in for weeks while a banking app logs out in minutes. Both answers trace back to the same handful of ideas in this chapter: what a bearer token actually is, what a claim is, and the genuine, unsolved-in-general tension between scaling an authentication system and being able to instantly take access away. Get this chapter's vocabulary straight and the rest of Part III's protocol depth (OAuth, OIDC, JWTs) has somewhere solid to attach.

    Tokens vs. sessions: two ways to remember "already authenticated"

    After a principal authenticates and becomes a subject (chapter 2), a system needs a way to carry that proof forward across many later requests. There are two fundamentally different strategies for doing that:

    Token-based vs. session-based memory of "already authenticated"
    StrategyWhat the client holdsWhat the server does on each request
    TokenA self-contained piece of data describing the subject (who, issued by whom, expires when).Verifies the token's signature and reads its contents directly — no database lookup required.
    SessionA short, opaque identifier (e.g. a cookie value) that means nothing by itself.Looks the identifier up in a server-side store to find out who it belongs to and whether it's still valid.

    Both strategies solve the same problem — "remember this request is from an already-authenticated subject" — but they make opposite bets about where the proof lives: inside the thing the client holds (token), or inside a server-side record that the client's identifier merely points at (session). The rest of this chapter is mostly about following that one design decision to its consequences.

    Bearer tokens: whoever holds it, can use it

    Most tokens used in modern IAM systems are bearer tokens. The name describes the defining property exactly: whoever bears — holds and presents — the token is treated as authorized to use it. The token itself carries no built-in proof that the party presenting it is the same party it was originally issued to.

    Key idea

    A bearer token is like a claim ticket at a coat check: the attendant doesn't check your ID against the ticket, they just hand over whatever the ticket is for. Possession is the proof. That design is simple and fast to verify, and it has one direct, serious consequence: if a bearer token is stolen, the thief can use it exactly as the real owner could — no further proof of identity required — until the token expires.

    This is not a flaw unique to one bad implementation; it is what "bearer" means by definition. Some advanced schemes bind a token to proof of possessing an additional secret (so a stolen token alone isn't enough), but the plain bearer-token model that dominates OAuth 2.0 and OIDC deployments today does not do this, and this course treats that plain model as the default to reason about.

    Pitfall

    Teams sometimes talk about a bearer token as if it were "the user" — as in, "we know it's really her, the token says so." A bearer token proves that someone who had the token made the request. It is silent on whether that someone was the principal it was issued to. Treat token possession and principal identity as two different facts whenever you're reasoning about an incident.

    Claims: what a token actually says

    A token is useful because it carries claims — key-value assertions about the subject the token represents. A claim is simply a statement the issuer is vouching for: "this token is for user X," "it was issued by Y," "it expires at time Z," "this subject holds the manager role." At this conceptual level, don't worry yet about exactly how claims are packaged into bytes on the wire (that's JWT structure — JWS/JWE/JWK — and it's chapter 16's job in full). For now, think of a token as an envelope and claims as the statements written inside it.

    Common claim categories, conceptually
    CategoryAnswersTypical example
    SubjectWho is this token for?"user: jane.doe@northwindapps.com"
    IssuerWho vouches for this token?"issued by: Northwind's identity system"
    Validity windowFrom when, until when, is this token good?"issued at 09:00, expires at 09:15"
    Authorization dataWhat is this subject allowed to do?"roles: [support-agent]"
    AudienceWhich service is this token meant for?"audience: billing-api"
    Case study — Riverside Health

    Picture a token Riverside Health's identity system issues to Dr. Alvarez, a clinician, after she logs in on her hospital workstation. It names her as the subject, names Riverside Health's identity system as the issuer, carries a short validity window, lists clinician and patient-record-read as authorization data, and names the hospital's EHR API as the audience. Every one of those claims is a separate, individually checkable statement — the EHR API specifically checks the audience claim to make sure a token minted for, say, the billing system can't be replayed against patient records instead.

    Stateless vs. stateful authentication architecture

    The token/session split from earlier in this chapter has a formal name once you're talking about whole-system architecture: stateless authentication (self-contained, verifiable tokens, no database lookup needed) versus stateful authentication (a session identifier that requires a server-side lookup on every request). Each makes a real trade-off, not a free win:

    Stateless vs. stateful — the real trade-off
    Stateless (token)Stateful (session)
    Scaling across many serversExcellent — any server can verify the token on its own, no shared session store needed.Requires a shared, replicated session store every server can reach; that store becomes its own piece of infrastructure to run and scale.
    Early revocationHard — the token is self-contained and valid anywhere it's accepted; see the revocation problem, next.Trivial — delete the session record server-side and the identifier instantly stops working everywhere.
    Per-request costOne signature check, no network round trip to a store.One lookup against the session store, which itself costs time and adds a dependency.
    Case study — Northwind Apps

    Northwind Apps runs its SaaS product across many independently scaling API servers behind a load balancer, with no guarantee two requests from the same customer land on the same server. A stateless access token is a natural fit here: any server can verify it alone, with no shared session infrastructure to keep in sync across regions. The cost of that choice shows up later, in the revocation problem below.

    The revocation problem

    Here is the honest, unsolved-in-general tension at the center of this chapter: once a stateless bearer token is issued, it is valid until it expires. There is no clean way to invalidate it early without undermining the entire reason it's stateless in the first place — the moment you add "but check a central revocation list on every request," you've reintroduced the server-side lookup that stateless design exists to avoid, and you're back to paying a stateful system's cost.

    Key idea

    This isn't a bug waiting to be patched — it's the direct, structural consequence of choosing statelessness. You cannot have "verifiable by anyone with zero lookups" and "instantly revocable by a central authority" at the same time, for the same token, in the general case. Real systems don't solve this; they manage it with partial mitigations that trade some of the stateless benefit back for some control.

    The mitigations this course will build on later are genuinely partial, not full solutions:

    • Short token lifetimes. If a stolen token is only valid for two minutes, the window of damage is small even though the token itself still can't be revoked early. This trades convenience (more frequent re-authentication or silent refresh) for a smaller blast radius.
    • Refresh-token rotation. Keep the access token very short-lived, and use a longer-lived refresh token (itself revocable, because refreshing typically does involve a server-side check) to mint new access tokens as needed. This moves the "can we still trust this" check to a less frequent point rather than eliminating it.
    • Token introspection. A resource server can call back to the issuer on each request to ask "is this token still good?" — which works, but reintroduces exactly the server-side lookup that statelessness was meant to avoid. Full mechanics in chapter 14.
    • Signing-key rotation. Rotating the key used to sign tokens can invalidate every token signed with the old key at once — a blunt instrument (it revokes everything, not one specific token) but sometimes exactly the tool needed, e.g. after a suspected key compromise. Full mechanics in chapter 16.
    Pitfall

    "We'll just revoke the token" is one of the most common incorrect assumptions made about stateless bearer tokens by engineers who haven't internalized this trade-off. If the system was designed to be purely stateless with no introspection step, there may be no mechanism to revoke a specific already-issued token at all — the honest answer is often "wait for it to expire," which is exactly why token lifetime becomes a security control, not just a convenience setting.

    Case study — Meridian Trust

    Meridian Trust deliberately issues very short-lived access tokens for its banking API — often measured in minutes. This is a direct, intentional response to the revocation problem: Meridian cannot cleanly revoke a stolen stateless token early, so it shrinks the amount of time a stolen token stays useful instead. The convenience cost (frequent silent token refresh in the background) is judged worth it given PCI-DSS exposure and fraud risk on a banking API.

    Case study — Northwind Apps

    Northwind Apps' SaaS product faces the opposite pressure: customers want to stay logged in for weeks without re-entering credentials, which argues for a long-lived refresh token. But the longer a refresh token lives, the longer a thief who steals one has a usable path to new access tokens. Northwind's product team has to explicitly choose a refresh-token lifetime that balances user convenience against exactly that exposure — there's no setting that gives them both for free.

    In Keycloak

    Realm Settings → Tokens (chapter 21) is where access-token and refresh-token lifetimes are configured per realm, and Keycloak's session management (chapter 29) is what makes refresh-token revocation actually work in practice — full depth lands in both of those chapters.

    Common mistakes

    • If you see a design doc that says "we'll just revoke the access token if something goes wrong," the cause is usually a team that hasn't confirmed whether their token scheme supports revocation at all — plain stateless bearer tokens often don't.
    • If you see an incident response plan with no answer for "how long could a stolen token still be used," the cause is usually that nobody treated token lifetime as a security control, only as a session-length convenience setting.
    • If you see a system add a server-side revocation check "to fix" stateless tokens and then wonder why it isn't scaling the way stateless was supposed to, the cause is that the fix reintroduced the exact server-side lookup statelessness was chosen to avoid.
    • If you see someone treat "the token says user X" as proof that user X made the request, the cause is conflating bearer-token possession with principal identity — a stolen token says exactly the same thing a legitimate one does.

    Takeaways

    • A token and a session are two different strategies for remembering "already authenticated" across requests — self-contained data versus a server-side lookup.
    • A bearer token's defining property is that whoever holds it can use it; the token carries no proof it's being presented by the party it was issued to.
    • If a bearer token is stolen, the thief can use it exactly as the real owner could, until it expires — this is the direct security implication of "bearer."
    • Claims are key-value assertions carried inside a token (subject, issuer, validity window, authorization data, audience) — the exact JWT packaging comes in chapter 16.
    • Stateless authentication scales better across many servers with no shared session store; stateful authentication is trivially revocable but needs that shared store.
    • The revocation problem is genuine and unsolved in general: a stateless bearer token can't be cleanly invalidated early without reintroducing the server-side lookup statelessness exists to avoid.
    • Short token lifetimes, refresh-token rotation, introspection, and signing-key rotation are honest partial mitigations for the revocation problem, not full solutions.
    • Meridian Trust's very short access-token lifetimes and Northwind Apps' refresh-token lifetime trade-off are the same underlying tension showing up as two different business decisions.
    • Token introspection (chapter 14) and signing-key rotation (chapter 16) both trade back some of the stateless benefit in exchange for more control.

    Self-check

    Click a question to reveal a model answer. Try answering it yourself first — the point is to check your own reasoning against it, not to read the answer first.

    1. Explain, without naming a specific product, why a stolen bearer token is as dangerous as a stolen password for the lifetime of that token.

      Model answerBecause bearer tokens carry no proof of who is presenting them — possession alone is treated as authorization, exactly like a password. A thief holding a stolen bearer token can do anything the legitimate owner could do until the token expires, the same way a thief holding a stolen password can log in as that person; the only difference is the fixed expiry window, which is why token lifetime doubles as a security control.

    2. A colleague says "let's just make every token stateless and skip the session store entirely." What question should you ask them before agreeing?

      Model answerAsk how they plan to revoke a token early if it's stolen or a user needs to be locked out immediately — a purely stateless design has no clean answer short of waiting for expiry, reintroducing a lookup (which defeats the point), or rotating the signing key (a blunt instrument that invalidates everything, not just the one token). If the system can't tolerate a window of continued access after a compromise is discovered, pure statelessness is the wrong trade-off.

    3. Walk through why adding a central revocation check to a stateless token system quietly turns it into a stateful system in practice.

      Model answerThe entire benefit of statelessness is that any server can verify a token on its own, with no shared infrastructure and no network round trip. The moment you add "but check a central revocation list on every request," every server now has to call out to that shared list before trusting the token — exactly the server-side lookup a session-based (stateful) design requires. The token still looks stateless (self-contained claims, a signature), but the system's actual operational behavior and cost profile has become stateful in every way that matters.

    4. Why does Meridian Trust choose short-lived access tokens specifically, rather than simply avoiding bearer tokens altogether?

      Model answerBearer tokens are what the OAuth 2.0/OIDC ecosystem Meridian's banking APIs run on, and avoiding them entirely would mean giving up the standardized, interoperable tooling the rest of the industry relies on — not a realistic option. Since Meridian can't cleanly revoke a stolen stateless token early, it instead shrinks the window in which a stolen token is dangerous by keeping access-token lifetimes very short (minutes), accepting more frequent background refresh as the cost of reducing the fraud exposure a PCI-DSS environment makes especially expensive.

    5. If you were advising Northwind Apps on its refresh-token lifetime, what questions would you ask before recommending a specific number of days or weeks?

      Model answerHow sensitive is the data Northwind's SaaS product exposes, and what's the real cost to the business if a stolen refresh token stays usable for that long? Does Northwind have a working revocation or introspection path for refresh tokens, so a detected theft can actually be cut short rather than just noted? And how much login friction will Northwind's customers tolerate, since a shorter refresh-token lifetime directly trades away the "stay logged in for weeks" convenience they're asking for.

    6. Describe one scenario where a claim inside a token could be true and verifiable, yet still not answer "is this really the right person using it."

      Model answerA token's subject claim correctly says "jane.doe" and its signature verifies cleanly — both true and verifiable — but if the token was stolen from Jane's laptop by malware, the party actually presenting it to the API is the attacker, not Jane. The claim describes who the token was issued to, not who is currently holding it; a plain bearer token has no mechanism binding the claim to the real-time identity of whoever presents it.
